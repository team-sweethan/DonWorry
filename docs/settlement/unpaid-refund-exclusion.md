# 4단계 지급 전 환불 제외·배치 경합 보호 (#488)

현재 후속 변경: [5단계 #493](refund-recovery.md)에서 지급 후 환불을 APPLIED/RECOVERY로 등록하고 후속 지급에서 회수한다. 아래 PENDING 유지 설명은 4단계 도입 기록이며 현재 회수 정책은 후속 문서를 따른다.

## 범위와 결과

기존 전액 환불 성공 이벤트와 원 수수료·순정산액 스냅샷을 유지한다. P6가 환불 결과를 처리할 때 아직 지급되지 않은 정산이면 다음을 같은 트랜잭션에서 확정한다.

| 대상 | 변경 |
| --- | --- |
| captures | COMPLETED·원 금액·완료 시각 보존 |
| settlements | SCHEDULED → CANCELED, 수정 시각 갱신. 원 금액·수수료·D+3 일정 보존 |
| settlement_refund_adjustments | PENDING → APPLIED / UNPAID_EXCLUSION, remaining_amount=0 |
| merchant_payouts / items | 환불 건을 지급 대상에서 제외. 기존 완료 지급 원장은 변경하지 않음 |

고객 환불액 10,000원·수수료 300원·순정산액 9,700원이면 해당 9,700원 정산을 지급 후보에서 제외한다. 이미 제외한 9,700원을 지급 원장의 refund_deduction_total에 다시 더하지 않는다. 현재 차감 컬럼은 0을 유지하며 지급 후 회수 차감은 5단계다. 전부 환불된 가맹점에는 빈 지급 원장을 만들지 않는다.

## 잠금과 순서

지급일별 원장 잠금만으로는 다른 날짜의 배치와 환불을 조율할 수 없다. P6 소유 `merchant_settlement_locks`에 가맹점별 한 행을 두어 두 경로의 최상위 잠금으로 사용한다. P1의 merchants 행은 변경하거나 잠그지 않는다.

- 잠금 준비: 짧은 독립 READ_COMMITTED 트랜잭션으로 공통 행 UPSERT를 커밋한다. 이 과정에는 금융 금액·상태 변경이 없다.
- 환불 수신 금융 트랜잭션: 준비된 가맹점 공통 행 쓰기 잠금 → 원 정산 잠금 → 동일 취소 내용 검증 → 수신 원장 저장·미지급 제외 → 커밋.
- 지급 배치 금융 트랜잭션: 준비된 가맹점 공통 행 쓰기 잠금 → 이전 PENDING 미지급 조정 적용 → 당일 지급 행 → 지급 대상 정산 → 상세·합계·완료 → 커밋.
- 진입 서비스는 NOT_SUPPORTED로 시작하고 공통 잠금 서비스가 TransactionTemplate의 REQUIRES_NEW/READ_COMMITTED를 두 번 순차 실행한다. 준비 커밋 후 연결을 반환하고 금융 트랜잭션에서 잠금과 작업을 함께 소유한다. 이벤트 수신·배치의 비트랜잭션 진입에서 풀 1개로도 연결을 이중 점유하지 않는다.
- 최초 UPSERT를 금융 트랜잭션에 넣으면 유니크 인덱스의 supremum 대기로 다른 가맹점의 잠금 행 삽입도 지연될 수 있어 준비를 분리한다. 준비한 잠금 행은 이후 금융 실패에도 유지하되 수신 원장·정산·지급 변경은 함께 롤백한다.
- 지급 대상 ID는 잠금 없이 조회하고 해당 PK만 단건으로 잠근다. 범위 FOR UPDATE가 옵티마이저의 PK 스캔을 선택해 다른 가맹점 행에서 대기하는 것을 피한다. 같은 가맹점 공통 잠금이 ID 선정과 단건 잠금 사이의 환불 변경을 막는다.
- 같은 가맹점의 쓰기는 한 서버·여러 서버·여러 날짜 실행에서 직렬화한다. 다른 가맹점의 지급은 독립적으로 진행한다.
- 이전 PENDING을 지급 전에 처리하는 내부 메서드는 지급 서비스가 공통 잠금을 확보한 뒤 같은 트랜잭션에서만 호출한다. 조회 페이지는 adjustment_id 기준 200개 키셋으로 진행한다.

### 경합의 두 결과

1. 환불 수신이 먼저 잠금을 확보·커밋: CANCELED 정산은 지급 후보·상세에서 빠진다.
2. 지급이 먼저 잠금을 확보·커밋: 지급 기록을 유지하고 환불 조정은 PENDING으로 보존한다. 이후 5단계에서 회수·차감·잔액 이월한다.
3. 먼저 처리하던 지급/환불이 실패: 동일 트랜잭션의 상태·원장 변경을 롤백하고 잠금을 반환한다. 기다리던 경로는 커밋된 상태를 다시 읽는다.

P5가 고객 환불을 실행하는 시점 자체를 잠그는 계약은 아니다. 환불 성공 이벤트가 늦게 도착해 그 사이 지급됐다면 PENDING 회수 대상으로 남긴다. canceledAt이 과거라는 이유로 이미 완료한 지급을 취소하거나 수정하지 않는다.

## 중복·정합성·실패

- 같은 취소의 재전달은 원 수신 기록을 반환한다. APPLIED의 잔여액·반환 수수료·적용 시각을 다시 설정하지 않는다.
- 이전 3단계에서 저장한 PENDING은 재전달 또는 지급 대상 선정 전 보정 경로에서 미지급 제외한다.
- 제외 시 원 식별자·금액·저장 수수료·순정산액을 다시 대조한다. 지급 상세가 있는데 상태만 SCHEDULED라면 오류로 거절한다.
- 실제 DB 업데이트 실패 시 수신 INSERT·정산 CANCELED·조정 APPLIED를 함께 롤백한다. Modulith에는 예외를 전달해 기존 실패 발행 기록을 재전달할 수 있다.
- 배치 안의 이전 PENDING 적용과 지급 확정도 같은 가맹점 트랜잭션이다. 해당 지급이 실패하면 그 실행에서 수행한 이전 PENDING 적용도 롤백된다.
- 운영자 강제 변경·자동 재시도 정책·DB 수동 보정은 추가하지 않는다.

## 신규 ERD: merchant_settlement_locks

실제 SQL은 [신규 migration](../../backend/src/main/resources/db/migration/V20261103_164349__create_merchant_settlement_locks.sql)이 정본이다. 기존 migration과 금융 금액 컬럼은 변경하지 않는다.

| 컬럼 | 타입 | NULL | 설명 |
| --- | --- | --- | --- |
| lock_id | BIGINT | N | PK AUTO_INCREMENT |
| merchant_id | BIGINT | N | 양수, UNIQUE, P1 논리 참조 |
| created_at | DATETIME(6) | N | 최초 생성 시각, UTC |

최초 쓰기 직전 짧은 트랜잭션에서 UPSERT로 생성하므로 기존 데이터 backfill이 필요 없다. 준비 행 생성은 먼저 커밋되고 금융 금액·상태 변경은 이후 단일 금융 트랜잭션에 포함된다. 잠금 보유 여부를 boolean으로 저장하지 않고 DB 트랜잭션 행 잠금으로 보장한다. created_at은 잠금 만료 시각이 아니다. 별도 상태·잔액·모듈 간 FK·연쇄 삭제가 없다.

## 활성화와 배포 조건

`settlement.refund-receiving.enabled`와 자동 배치는 기본 비활성을 유지한다. 지급 후 PENDING 회수·이월이 아직 없으므로 **이번 단계만으로 운영 환불을 활성화하지 않는다.** P5 발행 어댑터·고객 환불 실행·인증·HTTP 계약은 변경하지 않는다.

신규 SQL 적용 전 구버전 지급/환불 쓰기를 중지하고 새 코드로 전환한다. 공통 잠금을 사용하지 않는 구버전 인스턴스와 혼합 실행하면 경합 보호가 보장되지 않는다. 원장 조회·현금흐름·화면의 지급 후 차감 반영은 6~7단계다.

## 검증 계획

일반 검사·모듈 검사, 실제 MariaDB의 신규 SQL/JPA, 같은 취소 중복·이전 PENDING·201개 페이지 경계·DB 업데이트 실패 롤백·순정산액 0을 검증한다. 실제 두 연결로 환불 우선/지급 우선/지급 롤백 후 환불/다른 가맹점 독립성을 확인한다. 기존 일정산·전체 P6 회귀와 CI 결과는 PR에 커밋별로 기록한다. 개인 DB 초기화·운영 적용·실제 환불 활성화는 별도다.
