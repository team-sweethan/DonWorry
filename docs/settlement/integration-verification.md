# P6 실연동 검증과 활성화 준비 (#233)

## PR에서 검증할 경계

`PaymentSettlementRefundMariaDbTests`는 P5 환불 접수와 실제 매입 조회를 거쳐 P6 수신·정산 원장·지급 처리까지 확인한다. 격리 MariaDB에서 발행 어댑터만 테스트 설정으로 등록하고 기존 모의 환불기를 사용한다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 지급 전 전액 환불 | 환불 10,000원 성공 후 순정산액 9,700원을 지급 대상에서 제외하고 정산을 CANCELED로 남긴다. |
| 지급 후 전액 환불 | 원 매입·정산·지급을 보존하고 다음 지급의 순정산액 19,400원에서 9,700원을 차감한다. |
| P6 저장 실패 | P5 성공은 조회할 수 있고 미완료 발행을 선별 재전달하면 P6 반영을 복구한다. 환불기는 한 번만 호출한다. |
| 같은 환불 이벤트 재수신 | 조정 원장과 지급 배분이 중복되지 않고 미회수액을 초기화하지 않는다. |

로컬 또는 CI에서 전체 `./gradlew mariaDbTest`를 실행한다. Docker가 준비된 환경에서 이 클래스만 확인하려면 `./gradlew mariaDbTest --tests '*PaymentSettlementRefundMariaDbTests' -x settlementSeoulMariaDbTest`를 사용한다. 부족액 이월·동시 실행은 [환불 회수 검사](refund-recovery.md)와 [미지급 제외 검사](unpaid-refund-exclusion.md)도 함께 확인한다.

## 배포 환경에서 확인할 항목

1. 격리 환경의 배포 SHA와 플래그 상태를 기록한다. P5 #383과 P6 #233에서 운영용 `PaymentRefundCompletion` 등록 조건과 수신·발행 활성화 순서를 확인한다. 리스너가 없는 동안의 환불 성공은 해당 리스너용 발행 기록이 없으므로 별도 대조·복구 방법을 합의한다.
2. 가맹점 두 곳으로 로그인해 정산 기간 합계·월 누적·지급 명세·잔액을 원장과 대조한다. 다른 가맹점 데이터가 섞이지 않는지 확인한다.
3. CakeShop에서 [실제 HMAC 요청](pickup-api.md)을 보내 상품·픽업 기록을 저장한 뒤 동일 가맹점·주문의 P5 매입과 연결되는지 확인한다. 발신 코드·키 배포·프록시 확인은 담당자와 진행한다.
4. 환불 전후 지급, 일부 회수 후 이월, 중복·저장 실패 후 재전달, 지급과 환불 수신 경합을 확인한다. 거래별로 결제·취소·매입·정산·지급 ID와 금액을 대조한다. 수신 실패 복구에는 원래 발행을 재전달한다.
5. 수신·배치 활성화와 배치 시각은 팀 합의 후 배포 변경으로 제출한다. CI 결과와 실연동 결과를 별도로 기록한다.

관련 계약은 [지급 조회·예측](payout-forecast.md), [환불 수신·발행 기록](refund-receiving.md)을 참고한다.
