# 0078. 시스템 수행자 감사 기록과 사장님 계정 정지

- 상태: 제안 — #517 사용자 설계·구현 승인, #515 전체 경계 합의와 구분
- 날짜: 2026-11-04
- 관련: #517, #515, [구현·검증 명세](../identity/517-operator-suspension.md)

## 결정

기존 `fds → identity :: api` 방향에 `OperatorAccountSuspender.suspend(userId)`를 둔다. identity 내부에서 OPERATOR만 정지하며 직원은 거절한다. 이미 정지된 OPERATOR는 변경하지 않는다.
호출자 트랜잭션을 중단하고 기존 계정 잠금 안에서 새 트랜잭션으로 상태·감사를 커밋한 뒤 세션을 만료한다. 호출자 롤백으로 정지를 취소하지 않는다.
감사 수행자는 STAFF/SYSTEM으로 구분한다. SYSTEM은 수행자 ID가 없으며, 기존 FK를 유지한 nullable ID와 CHECK로 조합을 강제한다. 기존 감사 경로는 STAFF를 명시한다.
정지 사유는 P2가 소유하고, identity는 `USER_SUSPENDED_BY_FDS`와 상태 전후만 기록한다. 가맹점·키·결제는 정지하지 않는다.

## 버린 대안

- 관리자 `setStatus` 직접 호출: 로그인한 관리자·세션을 전제로 하므로 시스템 수행자를 위조하게 된다.
- 가상 시스템 사용자 생성: 실제 직원 FK와 시스템 개념을 섞고 불필요한 로그인 계정을 만든다.
- 호출자 트랜잭션 참여: 잠금 해제 뒤 커밋되거나 커밋 전에 세션이 만료될 수 있어 기존 로그인·관리자 직렬화와 맞지 않는다.
- 정지 이벤트: 허용된 방향의 즉시 Java 호출로 충분하다. 이벤트 전달·중복 관리 범위를 늘리지 않는다.
- 가맹점 정지: 계정 로그인 차단이라는 #515 정책과 달라 HMAC 결제를 막는다.

## 영향

P1 감사 테이블·Entity·서비스와 공개 Java API·예외만 확장한다. 새 모듈 의존·HTTP API는 없다. 화면은 기존 가드의 실제 동작을 검증한다.
동시성·롤백·세션·로그인·HMAC·기존 감사·데이터 업그레이드를 테스트한다. 실행 근거는 명세에 기록한다.
단일 JVM 잠금·메모리 세션을 유지한다. P2 룰·403 이벤트·해제 후 재정지 방지 계약은 #515 후속이다.
