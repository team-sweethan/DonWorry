# 0057. HELD 고객 모의 승인 취소와 P3 성공 전달

- **상태:** 제안 — P5 실행·오류 처리 추천안, P3 이벤트/저장/Case 정책 확인 전. 구현·실행 검증 없음
- **날짜:** 2026-10-31
- **관련:** #382, #381, #380, [ADR-0056](0056-cancellation-request-contract.md), [ADR-0027](0027-payment-actions.md)
- **영향 받는 담당:** P5, P3, CakeShop(P1). P6 환불·정산 전달은 별도 범위

## 배경

#381 공통 API·저장·조회가 병합됐지만 정상 HELD 취소는 실행부 미연결로 NOT_READY다. 직원 VOID에는 재사용 가능한 모의 실행기가 있으나 직원 공개 요청/결과는 decisionId와 인계 기록을 전제로 한다. 고객 취소를 직원 결과로 전달하면 기존 P3 계약과 충돌한다.

직원 신규 조치는 현재 고객 취소 작업을 확인하지 않는다. P3 Case 종료 계산도 모든 결제에 직원 판정/금융 인계가 있는 경우를 전제로 하므로 고객 취소 성공을 별도로 표현해야 한다.

## 결정 제안

1. 외부 부작용 없는 모의 취소를 P5의 동일 결제 잠금·하나의 트랜잭션에서 실행한다. 성공은 VOIDED/SUCCEEDED와 성공 발행을 함께 커밋한다. 명시적 거절은 HELD/FAILED로 기록한다. 기술 실패는 전체 롤백하며 외부 실행 결과 불명과 구분한다.
2. 양쪽 신규 금융 조치가 상대 작업을 같은 결제 잠금 아래 대조한다. 고객 FAILED 이후 직원 신규 조치도 운영 확인 전 차단하는 안을 제안한다. 저장된 기존 요청의 결과 재조회는 유지한다.
3. 고객 성공만 `payment.api.PaymentCustomerVoidSucceeded`로 P3에 알리는 안을 제안한다. 필드는 cancellationId·paymentId·merchantId·amount·completedAt이다. 직원 PaymentActionResult는 유지한다.
4. P3는 고객 취소 사실을 직원 판정과 분리하여 영속 보존하고, 중복·HELD와의 순서 역전·기존 판정과의 경합을 처리하는 안을 제안한다. P3 소유 저장 방식과 Case 종료 정책은 미확정이다.
5. 필수 운영 수신 계약/구현·통합 검증 전에는 HELD NOT_READY를 유지한다. 단순 설정 또는 테스트용 리스너가 실제 준비를 대신하지 않는다.

정확한 오류·HTTP·신규 직원 거절 코드와 수신/활성화 조건은 [#382 계약 7~10절](../payment/382-held-cancellation.md#7-모의-실행오류-처리-제안)을 따른다. 이번 제안은 담당 합의·구현 승인을 대신하지 않는다.

## 고려한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 고객 취소를 직원 REJECT로 호출/발행 | 가짜 decisionId/인계가 필요하며 감사 의미가 다름 |
| 모의 취소도 먼저 PROCESSING을 커밋하고 비동기 실행 | 외부 부작용 없는 실행에 중단 복구·워커·추가 전달이 필요해짐 |
| 기술 예외를 모두 FAILED 또는 UNKNOWN으로 저장 | 명시적 거절·코드 오류·외부 결과 불명이 섞임 |
| 고객 FAILED 뒤 직원 조치를 즉시 허용 | 기존 실패 VOID 조회의 HELD 조건·운영 복구 정책과 충돌. 허용하려면 관련 계약을 함께 개정해야 함 |
| 새 직원 거절에 기존 충돌 코드를 재사용 | P3가 정상 고객 취소를 버그로 기록하거나 잘못된 안내를 할 수 있음 |
| P5가 P3 Case 테이블을 직접 수정 | 소유 경계·의존 방향 위반 |
| Case 미존재의 취소 성공 이벤트를 처리 완료 후 버림 | 늦은 HELD 수신이 이미 취소된 결제를 판정 대상으로 만들 수 있음 |
| 고객 취소 성공이면 Case 전체를 즉시 종료 | 같은 Case의 다른 결제와 보안 조사 정책을 무시함 |

## 영향

- API: 고객 HTTP는 #381 계약 유지. P3용 고객 VOID 성공 이벤트와 직원 신규 접수 거절 코드 추가 제안. P3의 응답 전용 코드 매핑·수신 계약 확인 필요.
- DB: P5 기존 요청/작업 테이블 재사용안. P3 취소 사실 영속 보관은 담당 설계·ERD 확인 후 별도 migration 필요 여부 결정. 이번 DB 변경 없음.
- 화면: CakeShop의 취소 성공/거절/조회는 기존 계약 사용. P3에 고객 취소 표시·판정 제외·기존 인계와 구분 필요. 실제 화면 구현 없음.
- 테스트: 성공/거절/기술 실패·원자성, 반복·동시 요청, 직원 조치 양방향 경합, P3 수신 실패 재전달·중복·순서 역전·다중 결제 Case 검증 필요.
- 문서: #382 조사에 상세 실행/전달 제안을 추가하고 목록에서 연결한다. 기존 채택 ADR의 의존 방향은 바꾸지 않는다.

## 검증

`dev 2bd7f87` 코드와 #381 저장 계약을 읽어 대조했다. 문서 링크·공백 검사만 수행했다. 실행 코드·새 이벤트·P3 저장/Case 정책·금융 실행은 미구현/미검증이다. P3에게 메시지를 보내거나 담당 합의를 받은 단계가 아니다.
