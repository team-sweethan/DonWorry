# 0055. 진행 중 결제 취소의 일시 거절과 조회 후 재요청

- **상태:** 사용자 정책 확인 — 상세 외부 계약·담당 확인·구현은 후속
- **날짜:** 2026-10-31
- **관련:** #153, #380, #381, [ADR-0054](0054-full-cancellation-policy.md)
- **영향 받는 담당:** P5, P1/CakeShop, P3, P6

## 배경

현재 PENDING은 승인 전과 승인 후 자동 매입 대기를 모두 포함하고, HELD도 직원 CAPTURE 요청 후 완료 대기일 수 있다. 결제 상태만으로 매입 전 취소를 실행하면 이미 진행 중인 매입과 충돌할 수 있다. #189의 조회는 요청 철회나 원자적 실행 판단을 보장하지 않는다.

## 결정

2026-10-31 사용자는 진행 중 취소 요청을 예약하지 않고 **잠시 거절 후 조회·재요청**하는 방식을 선택했다. 승인 전 PENDING·자동 매입 대기·직원 매입 대기는 즉시 금융 실행하지 않는다. FDS 오류로 멈춘 건은 복구 필요로 구분하고 기존 복구 절차 후 재요청한다.

상태·승인 참조·요청 단계·직원 조치·P6 사실을 구분하는 [단계별 정책](../payment/380-cancellation-stage-policy.md)을 후속 설계 기준으로 사용한다. 결과 반영 후 HELD는 승인 취소, CAPTURED는 전액 환불로 판단한다. 정산 완료 후 취소 허용과 성공 결과 전달·후속 차감 정책은 ADR-0054를 유지한다.

## 고려한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 진행 중 취소를 예약하고 완료 뒤 자동 실행 | 예약 영속화·재시작 복구·취소 의사와 금융 실행의 추가 계약이 필요하므로 최초 범위에서 제외 |
| 요청을 열린 채로 유지하며 매입 완료까지 대기 | 완료 지연·유실 시 응답 시간을 제한하기 어렵고 결국 별도 결과 조회가 필요 |
| PENDING을 모두 승인 전으로 보고 즉시 취소 | 승인된 자동 매입 대기도 PENDING이므로 현재 코드와 맞지 않음 |
| P6 조회가 비어 있으면 즉시 승인 취소 | 아직 전달·커밋되지 않은 매입 요청을 배제할 수 없음 |

## 영향

- API: 진행 중 일시 거절·오류 복구 필요·기존 완료 결과를 구분한다. HTTP 코드·요청 키 재사용·조회 계약은 #381에서 확정한다. 현재 API 변경은 없다.
- DB: 이번 변경 없음. 취소 예약을 실행 대상으로 저장하지 않는다. 요청 이력·멱등 저장 여부와 구조는 #381에서 담당·ERD 확인 후 결정한다.
- 화면: 거절을 취소 성공으로 표시하지 않는다. CakeShop의 안내·재요청 UX는 담당 확인이 필요하다.
- 테스트: #380 후속 구현에서 잠금 선후·늦은 매입 완료·응답 유실·오류 복구·중복 요청을 검증한다.
- 모듈: 의존 방향 유지. P5 잠금으로 P6 실행을 중단할 수 있다고 가정하지 않는다.
