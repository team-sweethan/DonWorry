# 0025. CSRF 토큰 교환 준비와 검사 설정 분리

- **상태:** 제안 — #126 사용자 구현 승인, PR 리뷰 대상
- **날짜:** 2026-10-25
- **관련:** #126, #68 5단계, #125, #128, #129, #131, [ADR-0014](0014-session-authentication.md)
- **영향 받는 담당:** P1, P2~P6(검사 활성화 시), P4·CakeShop(서버 간 예외·인증 후속)

## 배경

브라우저 세션 쿠키는 요청에 자동으로 붙으므로 CSRF 대비가 필요하다. 그러나 현재 다른 담당의 API·curl 호출은 토큰 없이 동작한다. #126은 토큰 교환을 먼저 준비하고 실제 차단은 #68 5단계에서 공지한 뒤 켜도록 범위를 정했다.

## 결정

- `security.csrf.enabled`의 기본값은 false다. `DONWORRY_CSRF_ENABLED`로 덮어쓸 수 있으나 실제 공용 환경 활성화는 이번 범위에 없다. Spring CSRF 필터·SPA 처리는 유지하고 검사 matcher만 설정값과 안전하지 않은 메서드 조건으로 제어한다. GET·HEAD·OPTIONS·TRACE는 검사하지 않는다.
- `CookieCsrfTokenRepository`의 `XSRF-TOKEN` 쿠키를 사용하고 프론트가 `X-XSRF-TOKEN` 헤더로 돌려보낸다. SPA의 일반 쿠키 토큰과 XOR 요청 속성을 Spring 표준 `spa()`가 구분한다. 쿠키는 Path=/, SameSite=Lax, JavaScript에서 읽기 가능이다. Secure는 요청의 HTTPS 여부를 따르며 운영 프록시·HTTPS 설정은 #131에서 검증한다. 인증용 JSESSIONID의 HttpOnly·세션 정책은 유지한다.
- `GET /api/auth/csrf`는 익명·비밀번호 강제 변경 계정 모두 이용 가능하다. 204와 `Cache-Control: no-store`로 응답한다. 토큰이 없으면 쿠키를 발급하고 있으면 유지하며, 로그인 세션을 만들지 않는다. Spring SPA 처리에서 다른 응답에도 쿠키가 발급될 수 있다.
- 수동 로그인은 기존 `UserSessionService.establishAuthentication`의 합성 전략에 `CsrfAuthenticationStrategy`를 한 번 추가한다. 동시 로그인 검사 → 세션 ID 교체 → 세션 등록 → 기존 CSRF 토큰 폐기를 수행한다. 필터 체인 설정만으로 수동 로그인에 연결됐다고 간주하지 않는다.
- 일반 로그아웃은 Spring CSRF configurer가 등록하는 `CsrfLogoutHandler`, 전체 로그아웃은 기존 공통 로그아웃 handler에 추가한 `CsrfLogoutHandler`로 토큰을 폐기한다. 이후 안전한 요청 또는 다음 변경 요청 전 `/csrf` 호출에서 새 토큰을 받는다. 갱신 요청 실패를 이미 성공한 로그인·로그아웃의 실패로 표시하지 않는다.
- 본인 비밀번호 변경(#128)은 현재 세션과 CSRF 쿠키를 유지한다. #129의 AUTH_008·일반 권한 부족 AUTH_002와 CSRF 누락·불일치 403 `CSRF_001`을 구분한다. CSRF 실패는 업무 처리 전에 필터에서 반환하며 토큰·비밀번호를 응답·로그에 넣지 않는다.
- `frontend/src/api/client.ts`는 변경 요청에 현재 쿠키 값을 붙이며, 토큰이 없으면 먼저 발급받는다. 동시에 시작한 발급은 공유한다. 발급 뒤에도 쿠키를 읽지 못하면(다른 도메인 배포·쿠키 차단) 헤더 없이 보내고 검사 여부는 서버 설정에 맡긴다. 검사 끔 기본값에서 프론트가 요청을 막지 않기 위해서다. 정확히 HTTP 403 + CSRF_001인 경우에만 거절된 쿠키를 지우고 새로 발급받은 뒤 원래 요청을 한 번 재전송한다. `/csrf`는 쿠키가 남아 있으면 같은 토큰을 유지하므로 지우지 않으면 같은 값을 다시 보낸다. 네트워크·5xx·일반 403은 자동 재시도하지 않는다. 한 번만 읽을 수 있는 Stream 본문은 재전송하지 않는다.
- 토큰 발급 대기·재시도 중 세션 세대가 바뀌거나 요청이 취소되면 업무 요청을 보내지 않는다. 선행 토큰 발급의 401도 원래 업무·비밀번호 변경 요청의 기존 만료 통지 규칙을 따른다. 재시도에도 기존 헤더·본문·credentials를 유지한다.
- `/internal/**`는 CSRF 검사 예외다. CakeShop 웹훅의 정확한 경로는 미합의이므로 추측한 예외나 넓은 `/api/**` 예외를 추가하지 않는다. 서버 간 인증과 실제 검사 활성화는 #68 5단계에 남긴다.

쿠키 저장 방식의 토큰은 서버 세션에 귀속된 폐기 목록이 아니다. 로그인 후 테스트는 **현재 새 쿠키 + 이전 헤더**가 거부되는지 검사한다. 예전 쿠키·헤더 쌍 자체를 서버에서 영구 폐기하는 기능을 보장하지 않는다. 이 보장이 필요하면 저장 방식을 별도 합의해야 한다.

## 버린 대안

- 기본값으로 검사 활성화: 토큰 없는 다른 담당의 POST를 막아 #126 범위를 넘는다.
- false일 때 `csrf.disable()`: 발급·SPA 처리·표준 로그아웃 정리가 함께 제거돼 준비 상태를 검증하기 어렵다.
- 모든 403·네트워크 오류 재시도: 권한 오류를 숨기거나 이미 처리된 계정 생성·임시 비밀번호 발급을 반복할 수 있다.
- 로그인·로그아웃 이후 프론트 메모리에 토큰 유지: 폐기된 값을 다시 보내기 쉽다. 각 전송 시 쿠키를 읽는다.
- 세션 저장 토큰·DB·Redis 도입: #68의 쿠키 저장 합의를 바꾸고 이번 준비 작업 범위를 넓힌다.

## 영향과 검증

- API: GET /api/auth/csrf, CSRF_001 ProblemDetail 추가. 로그인·로그아웃 성공 응답 형식과 기존 401·403 코드는 유지한다.
- DB·모듈 경계: 변경 없음. 다른 담당의 코드·공개 Java 계약 변경 없음.
- 화면: 화면별 수정 없이 공통 API 클라이언트에서 토큰을 전송한다.
- 테스트: 기본 설정의 기존 인증·업무 요청 회귀 검사, 활성화 설정의 실제 필터와 쿠키 누락·불일치·정상 요청, 수동 로그인·두 로그아웃·강제 변경 접근, 실제 HTTP 쿠키 저장소, 프론트 동시 발급·오류 구분·한 번 재시도·세션 세대·취소·실패 복구를 검사한다.
- 실행 결과는 PR의 테스트 결과·미검증에 기록하며 위 계획만으로 검증 완료로 보지 않는다.
