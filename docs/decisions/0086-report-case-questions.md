# 0086. 보고서 뒤 사건 질문 · 답변 — 저장된 보고서 사실로 답하고, 필요할 때만 넓혀 본다

- **상태:** 제안 — 사용자 설계 결정(11/09, #624). 접근 기록 종류 추가는 P1 확인 필요
- **날짜:** 2026-11-09
- **관련:** Issue #624, [ADR-0009](0009-ai-investigation-call-structure.md) (결정 8 · 9 · 13), [ADR-0082](0082-insider-access-security.md) (4절 기록 방식), [ADR-0083](0083-ai-kill-switch.md) (긴급정지)
- **영향 받는 담당:** P4 (ai-server · `investigation/report` · 화면), P1 (`StaffAccessType` 값 하나 추가)

## 배경

- AI 보고서는 사건마다 같은 흐름으로 만든다. 기본 조회 7개는 코드가 하고, AI는 90일 이력을 더 볼지만 고르고 요약을 쓴다 (ADR-0009 결정 9). 같은 근거면 같은 보고서가 나와야 감사할 수 있어서 이 고정은 유지한다
- 보고서는 사건에 대해 Spring이 가진 자료를 거의 다 담는다. 결제 표 · FDS 근거 · 비슷한 사건 · 고객 이력 · 같은 카드/기기/IP(앞뒤 1시간 포함) · 주문 정보 · ML 참고 · 확인할 것이 카드로 나뉘어 있다
- 그래서 직원이 막히는 지점은 "자료가 없음"보다 "어느 카드에 있는지, 카드끼리 어떻게 이어지는지"다 (#620 실제 동작 확인 V1, 11/07)
- 11/09 확인: 질문을 받아 새로 조회할 만한 자료는 이력 90일과 연관 결제의 더 긴 시간대(6 · 24시간)뿐이다. 비슷한 사건 상세는 나란히 보기 화면(`CaseComparePage`)에, ML 참고는 결제 표에 이미 있다

## 결정

직원이 보고서를 본 뒤 그 사건에 대해 자유롭게 묻고 바로 답을 받는다. **AI는 저장된 보고서 사실로 답하고, 보고서에 없는 것은 허용된 넓혀 보기 도구 2개 중에서 골라 조회한다.** 판정은 하지 않는다.

### 1. 질문 방식 — 자유 입력 + 예시 칩

- 입력창 하나. 자주 묻는 질문은 칩으로 한 번에 넣는다 (예: "신규 기기로 한 결제는?", "같은 IP 결제는 언제였나요?", "이 고객 평소 결제는?")
- 질문은 300자까지. 표현은 자유이고, 답할 수 없는 종류는 4절의 답 종류로 갈린다
- **이어서 묻기 (11/09 사용자 결정):** 같은 보고서에서 같은 직원이 한 **직전 질문 · 답 3개까지** 함께 넘긴다. "그럼 2번 결제는요?"처럼 앞 답을 받아 묻게 하려는 것이다
  - 넘기는 것은 검사를 통과한 답(`ANSWER` · `NOT_IN_REPORT` · 거절)뿐이다. 실패한 답은 넘기지 않는다
  - 앞 답의 근거 번호는 그대로 쓸 수 있고, 앞 답에서 새로 조회한 값(`추가-N`)은 그 조회 시각과 함께 사실로 다시 넣는다. 앞 답 문장 자체는 근거로 인용할 수 없다 (문장 속 숫자는 여전히 사실에서만)
- **질문 횟수 상한 (11/09 사용자 결정):** 직원 한 명이 보고서 하나에 **최근 24시간 30개**까지. 넘으면 AI를 부르지 않고 "오늘 질문 한도를 넘었습니다"로 답하며 질문 행을 만들지 않는다. 실수 · 반복 클릭으로 OpenAI 요금이 나가는 것을 막는 출발값이다

### 2. 대상과 권한

- 결제 사건의 **성공한 AI 보고서 하나**에 묻는다. 고정 보고서(AI 정지 중 생성) · 내부자 사건 보고서는 대상이 아니다
- 권한은 보고서 인쇄와 같다. 열린 사건은 담당자만, 종료된 사건은 보안 직원 누구나 (`CaseAccessGuard`)
- AI 긴급정지(ADR-0083)가 켜져 있으면 질문을 받지 않는다
- 새 HTTP API는 같은 PR에서 `SecurityConfig`에 정확한 경로로 등록한다 (AGENTS.md 4절)

### 3. 답의 근거 — 저장된 사실 우선, 넓혀 보기 2개

- AI에게 주는 것: 그 보고서에 저장된 사실 목록(`report_body.facts`, 번호 포함)과 질문
- AI가 고를 수 있는 도구 (읽기 전용, 사건 번호는 코드가 묶는다)

  | 도구 | AI가 정하는 값 | 허용 범위 | 자료 |
  | --- | --- | --- | --- |
  | 고객 이력 넓혀 보기 | 기간 | 90일만 (30일은 보고서에 있음) | 기존 Tool API, P5 공개 창구 |
  | 같은 카드 · 기기 · IP 시간대 넓혀 보기 | 사건 결제 앞뒤 시간 | 6 · 24시간 (1시간은 보고서에 있음) | 기존 Tool API에 시간 인자 추가, P2 공개 창구는 그대로 |

- 범위 밖 값 · 목록 밖 도구는 코드가 거절한다. 질문 하나에 도구는 최대 2번
- 보고서를 만든 뒤 사건 증거 버전이 바뀌었으면 도구를 쓰지 않고 저장된 사실로만 답하며, 화면에 알린다 (지금 조회값과 보고서 값이 섞이지 않게)
- 도구 결과는 코드가 사실 문장 · 번호(예: `추가-1`)로 바꿔 AI에 준다. 보고서 사실 번호와 겹치지 않는다
- **계산값은 코드가 만든다 (11/09 사용자 결정).** AI를 부르기 전에 저장된 보고서(결제 표 · 시각)로 코드가 계산한 사실을 번호(`계산-N`)와 함께 넣는다. 출발 목록: 사건 결제 합계 · 건수, 첫 결제~마지막 결제 간격, 결제 사이 간격. AI는 더하거나 빼지 않고 인용만 한다
  - 이유: 검사기는 "답 속 숫자가 근거 사실에 있는가"만 본다. AI가 계산한 숫자는 맞아도 근거에 없어 걸리고, 틀려도 그럴듯해 보인다. 코드가 계산하면 맞는 답은 통과하고 틀린 숫자는 생길 수 없다
  - 예전 보고서에도 결제 표가 있어 그대로 계산된다 (보고서 형식 변경 없음). 목록에 없는 계산을 물으면 `NOT_IN_REPORT`로 답하고, 자주 나오면 목록에 더한다

### 4. 답의 모양과 검사

- 답 종류는 넷: `ANSWER`(사실로 답함) · `NOT_IN_REPORT`(보고서와 허용 도구로 알 수 없음) · `DECLINED_DECISION`(판정 · 권고 질문) · `DECLINED_SCOPE`(사건 밖 · 개인정보 질문)
- `ANSWER`는 문장마다 근거 사실 번호를 단다. 보고서 문장과 같은 검사를 쓴다: 받은 번호만, 문장의 숫자는 근거 사실에 있는 숫자만, 판단 표현 금지 (`narrative.py` 재사용). 걸리면 한 번 다시 쓰고, 또 걸리면 "답을 만들지 못했습니다 — 보고서를 직접 확인하세요"
- 거절 문장은 AI가 쓰지 않고 코드의 고정 문장을 쓴다. `DECLINED_DECISION`은 "판정은 직원이 합니다"와 그 보고서의 확인할 것 전체(결제별 징후의 확인할 것 + AI 추가 제안)를 함께 보인다
  - 전체를 보이는 이유 (11/09 사용자 결정, #750): 화면의 확인할 것 체크는 브라우저에만 있고 서버에 저장되지 않아 "아직 안 한 것"을 서버가 알 수 없다. 체크를 저장하는 일은 저장 칸 · API · 화면이 바뀌는 별도 작업이라 하지 않는다. 거절 답의 목적은 직접 확인할 항목을 안내하는 것이라 이미 한 항목이 함께 보여도 해가 없다
- 연락처 · 다른 고객 개별 결제 · 카드 토큰 · IP 원문은 사실 목록과 도구 결과에 처음부터 없다. AI가 거절을 놓쳐도 내보낼 원문이 없다
- 직원 질문은 자료로만 다룬다. 시스템 지시를 바꾸는 문장은 따르지 않도록 프롬프트에 적고, 위 검사가 결과를 막는다

### 5. 저장과 접근 기록

- P4 새 테이블 `ai_report_questions`에 질문 하나당 한 줄을 쌓는다. 덮어쓰지 않고 지우지 않는다
  - 칸(안): `question_id` · `report_id`(P4 `ai_reports` 물리 FK — 같은 담당) · `case_id`(P3 논리 참조) · `staff_id`(P1 논리 참조) · `question` · `status`(`RUNNING` · `ANSWERED` · `DECLINED` · `FAILED`) · `answer_body`(JSON: 답 종류 · 문장 · 근거 번호 · 부른 도구와 값 · 도구 조회 시각 · 모델 · 토큰) · `report_evidence_version` · `asked_at` · `answered_at`
  - 정확한 컬럼 · 타입은 구현 PR의 migration이 정본이다. 같은 PR에서 `docs/erd/` P4 표에 추가한다
- 질문 접수 때 `StaffAccessRecorder.recordAllowed`로 접근 기록을 남긴다. 새 값 `REPORT_QUESTION` (P1 `StaffAccessType`, VARCHAR라 migration 없음). 거부는 `CaseAccessGuard`가 기록한다
- 기록이 남는 이유: 판정 전에 직원이 무엇을 묻고 무엇을 들었는지 나중에 확인할 수 있고, 사건과 상관없는 질문 반복을 내부자 감시에서 볼 수 있다. 내부자 규칙을 새로 만들지는 이 ADR에서 정하지 않는다

### 6. 호출 방식 — 동기

- 화면 → Spring `POST /api/security-cases/{caseId}/reports/{reportId}/questions` → ai-server `POST /questions` → (필요하면) ai-server가 기존 Tool API 호출 → 답
- 순서: ① 트랜잭션 1에서 권한 확인 · 횟수 상한 확인 · 질문 행(`RUNNING`) 저장 · 접근 기록 → 커밋. 직전 질문 · 답 3개는 이 테이블에서 읽어 ai-server 요청에 싣는다 ② 트랜잭션 밖에서 ai-server 호출 (시간 제한 30초) ③ 트랜잭션 2에서 결과 저장. AI 호출 동안 DB 연결을 잡지 않는다
- 시간 초과 · ai-server 장애는 `FAILED`로 저장하고 화면에 "답을 만들지 못했습니다"를 보인다. 자동 재시도는 하지 않는다 (직원이 다시 묻는다)
- mock 제공자는 고정 답(사실 번호를 모두 단 문장)을 돌려준다. CI는 진짜 AI를 부르지 않는다

### 7. 화면

- 보고서 아래 "이 사건에 대해 묻기" 칸. 답과 보고서를 시각적으로 나누고 "보고서가 아니며 판정 근거가 아닙니다"를 늘 보인다
- 답의 근거 번호를 누르면 보고서의 해당 카드로 이동한다 (기존 `goToCard.ts`)
- 같은 보고서에 한 질문 · 답은 화면을 다시 열어도 목록으로 보인다 (5절 저장분)

### 하지 않는 것

- 대화로 판정 · 상태 변경 (ACCEPT / REJECT 연결 없음)
- 여러 사건을 넘나드는 질문, 사건 밖 데이터 조회
- 직전 3개보다 긴 대화 기록, 다른 직원 · 다른 보고서의 질문 이어 받기
- 새 자료원 도구(차단 목록 이력 · 규칙 최근 적중 추이 · 구매자 로그인 #661). 자료를 가진 담당의 공개 창구가 생기면 이 ADR을 개정해 3절 표에 추가한다

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 정해진 질문 버튼만 | 답이 정해져 있으면 AI 없이 화면 기능으로 충분하다. 직원이 실제로 묻고 싶은 "카드끼리 연결" 질문을 다 버튼으로 만들 수 없다 |
| 저장된 사실만 (도구 없음) | 가장 싸고 안전하지만 "평소 결제는?"처럼 30일로 알 수 없는 질문에 답하지 못한다. 넓혀 보기 2개는 기존 창구라 추가 비용이 작다 |
| 인자 받는 새 도구 (비슷한 사건 열기 · ML 참고 · FDS 근거 결제 지정 등) | 11/09 확인 결과 모두 보고서나 나란히 보기 화면에 이미 있다. 같은 자료를 한 번 더 조회할 뿐이다. 비슷한 사건의 판정 사유는 직원이 쓴 자유 글이라 다른 고객 개인정보 · 지시문이 섞일 위험도 있다 |
| 새 자료원 도구를 먼저 만든 뒤 질문 · 답변 (B안) | 차단 목록 이력 · 규칙 추이 · 로그인 기록은 P2 · 가맹점 합의와 새 공개 창구가 필요해 오래 걸린다. 질문 · 답변 틀을 먼저 두면 도구만 나중에 붙인다 |
| 질문 · 답변 없이 보고서 화면에서 찾기 개선만 (C안) | 비용은 가장 적지만 질문마다 근거를 골라 엮어 주는 기능이 없다. 사용자 결정(11/09)으로 A안 |
| 보고서 생성처럼 비동기 (접수 → 진행 조회 → 결과) | 질문 하나에 OpenAI 기준 몇 초라 접수 · 진행 · 결과 3단계가 과하다. 화면 · Spring · ai-server 모두 상태 관리가 늘어난다 |
| 질문 · 답을 저장하지 않음 / 접근 기록만 | 판정 전에 무엇을 들었는지 추적할 수 없고, 내부자 감시에서 질문 내용을 볼 수 없다 |
| AI가 기본 조회 도구 전체를 다시 고르게 함 | 보고서에 이미 있는 결과를 다시 조회한다. #578에서 같은 이유로 버렸다 (ADR-0009 결정 9) |
| 질문마다 따로 (이전 질문 안 넘김) | 처음 안이었으나 "그럼 2번 결제는요?" 같은 이어 묻기가 안 돼 자유 질문의 쓸모가 크게 준다. 넘기는 앞 답은 검사를 통과한 것이라 오류가 이어질 위험이 작다 (11/09) |
| 대화 기록 전체를 넘김 | 질문할수록 넘기는 글과 비용이 커지고, 오래된 앞 답이 새 답을 끌고 간다. 직전 3개로 자른다 |
| 질문 횟수 상한 없음 | 반복 클릭 · 실수로 요금이 나가도 막을 장치가 없다 |
| AI가 계산하게 두고 숫자 검사를 뺌 | gpt-4.1-mini는 단순 합계를 대개 맞히지만 틀린 경우를 검사가 가려낼 수 없다. 저장된 답이 판정 직전에 읽힌다 |
| AI가 계산하고 코드가 다시 계산해 대조 | 사실이 문장 형태라 AI가 어떤 값을 어떻게 계산했는지 코드가 알려면 계산 형식을 따로 정해야 한다. 자주 묻는 계산은 미리 만드는 편이 단순하다 |
| AI의 해석 · 추정("도용 가능성이 높다")을 허용 | ADR-0009 결정 8 · 13과 어긋난다. 실제로 AI가 기준표와 반대로 분류한 기록이 있다(연속 결제를 "평소 결제"로 씀, #548). 그럴듯한 틀린 해석은 직원 판정을 끌고 간다 |
| 거절 문장도 AI가 씀 | 판정 질문 거절 문구가 실행마다 달라지고 "취소하는 편이 낫다" 같은 판단이 섞일 수 있다 |
