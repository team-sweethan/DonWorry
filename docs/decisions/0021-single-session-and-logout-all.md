# 0021. 계정당 단일 세션과 모든 기기 로그아웃

- **상태:** 제안 — #125 구현 반영, PR 리뷰 대상
- **날짜:** 2026-10-24
- **관련:** Issue #68, #125, #126, #128, #129, #130, ADR-0014
- **영향 받는 담당:** P1 주환. 다른 모듈의 Java 계약·DB·접근 정책은 변경하지 않는다.

## 배경

#68은 계정당 유효 로그인 1개, 새 로그인 우선, 서버 메모리 세션 유지를 정했다. 현재 로그인은 Controller가 호출하는 AuthService에서 처리하므로 Security 설정만으로 세션 등록·동시 로그인 제한이 실행되지 않는다. SessionUser record의 기본 동등성은 권한·표시 이름까지 포함하므로 계정 식별 기준으로 사용할 수 없다.

#128은 현재 세션을 유지한 종료, #129·#130은 대상 계정의 전체 종료가 필요하다. 이번에는 재사용할 기능을 제공하고 계정·비밀번호·가맹점 변경 연결은 각 후속 이슈에 남긴다.

## 결정

서블릿 컨테이너의 메모리 세션을 유지하며 Spring Security의 SessionRegistry와 동시 로그인 전략·필터를 사용한다. UserIdSessionRegistry는 등록·조회 principal을 userId(Long)로 정규화한다. 실제 인증 principal과 /login·/me 응답은 기존 SessionUser를 유지한다.

### 로그인과 세션 수명

- AuthService는 인증·권한 조회 후 UserSessionService.establishAuthentication을 직접 호출한다.
- CompositeSessionAuthenticationStrategy는 동시 로그인 검사(최대 1개, 새 로그인 허용) → changeSessionId → 세션 등록 순서로 실행한다. 이후 SecurityContext를 명시적으로 저장한다.
- UserSessionService의 인증 확립·세션 만료·전체 로그아웃은 같은 인스턴스 모니터로 직렬화한다. 검사와 등록 사이에 다른 로그인이 끼어들지 못한다. 비밀번호 검증·DB 조회는 모니터 밖에서 끝낸다. 단일 서버 MVP의 짧은 메모리 작업이며, 다중 서버 지원은 이번 범위가 아니다.
- 필터 체인의 동시 세션 설정과 수동 로그인 전략은 동일한 SessionRegistry를 사용한다. HttpSessionEventPublisher는 실제 로그아웃·타임아웃·ID 변경을 목록에 반영한다.
- 이전 세션은 즉시 expireNow로 표시하고 다음 요청의 ConcurrentSessionFilter에서 무효화한 뒤 401 AUTH_001 ProblemDetail로 응답한다. 만료 표시 직후 목록에서 제거하지 않는다. 이미 처리 중인 요청 취소나 브라우저 푸시는 제공하지 않는다.
- 일반 로그아웃의 POST /api/auth/logout, 비로그인·반복 요청 204 동작은 유지한다.

### 전체 로그아웃 HTTP 계약

| 항목 | 결정 |
| --- | --- |
| 메서드·경로 | POST /api/auth/logout-all |
| 호출자 | 로그인한 모든 역할 |
| 요청 | 본문 없음. 사용자 ID는 요청 값 대신 인증 principal에서 가져온다 |
| 성공 | 현재 세션을 포함한 전체 세션 만료, 현재 요청의 세션·인증·JSESSIONID 쿠키 정리, 204 No Content |
| 비로그인·만료 | 401 AUTH_001 ProblemDetail |
| GET | 실행하지 않는다 |

끊긴 세션 쿠키로 보낸 첫 요청은 경로와 무관하게 ConcurrentSessionFilter가 세션을 무효화하고 401 AUTH_001로 끝낸다. permitAll 경로와 POST /api/auth/login도 마찬가지다. 다음 요청부터는 세션이 없는 요청으로 처리되어 다시 로그인할 수 있다. POST /api/auth/logout은 LogoutFilter가 먼저 처리하므로 204를 유지한다.

이 경로와 /api/auth/me는 인증을 요구한다. 다른 API의 permitAll 및 CSRF 비활성화는 #68 5단계까지 유지한다. 따라서 세션을 끊었다는 사실이 아직 전체 업무 API의 비로그인 접근까지 차단한다는 뜻은 아니다.

### 내부 재사용과 후속 연결

- UserSessionService.expireAll(userId): 활성 세션 전체 만료. 대상 세션이 없거나 반복 호출해도 정상이다.
- expireAllExcept(userId, retainedSessionId): 지정 세션을 제외한 활성 세션 만료. 이미 만료된 세션은 되살리지 않는다.
- identity 내부 기능이므로 api/ 공개 계약이나 모듈 의존은 추가하지 않는다.
- #128에서 현재 세션 ID를 보존하고, #129에서 변경 대상 userId를 종료한다. #130에서는 가맹점 소속 사용자 ID를 조회해 종료한다. 가맹점 조회 책임을 세션 서비스에 넣지 않는다.
- DB 변경에 연결할 때는 커밋 성공 후 종료하며, 로그인과 DB 변경의 경쟁 조건은 해당 후속 이슈에서 검증한다. 이번 모니터만으로 인증 전 DB 조회와 계정 변경 사이의 경쟁까지 해결했다고 보지 않는다.
- #126의 CsrfAuthenticationStrategy는 기존 수동 로그인 경로에 통합해야 한다. 전체 로그아웃에도 CSRF 토큰 정리 정책을 함께 적용해야 하며, 이번에는 서버 검사를 활성화하지 않는다.

### 화면

이번에는 모든 기기 로그아웃 버튼을 화면에 두지 않는다. 계정당 유효 세션이 1개이므로 현재 기기에서 누를 때 다른 기기 세션은 이미 만료되어 있고, 결과가 일반 로그아웃과 같다. 다른 사람이 같은 계정으로 로그인한 경우에도 내 세션이 먼저 끊겨 버튼을 누를 수 없고, 다시 로그인하면 상대 세션이 끊긴다. 두 버튼을 나란히 두면 사용자가 차이를 알 수 없다.

HTTP API와 세션 종료 서비스는 유지한다. 실제 쓰임은 #128·#129·#130의 서버 측 강제 종료다. 화면 버튼은 동시 세션 수를 늘리거나 설정 화면을 만들 때 다시 검토한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| maximumSessions 설정만 추가 | Controller 수동 로그인에서 세션 검사·등록이 실행되지 않는다 |
| SessionUser record 자체를 목록의 키로 사용 | 권한·이름이 바뀌면 같은 계정을 다른 principal로 인식한다 |
| SessionUser의 equals/hashCode를 userId 기준으로 변경 | 세션 목록의 식별 요구를 데이터 객체 전체의 동등성으로 확장하지 않는다 |
| 자체 HttpSession 참조 목록과 직접 원격 invalidate | 컨테이너 객체의 수명과 동시성 관리가 중복된다. 표준 만료 표시·필터·이벤트를 사용한다 |
| DB·Redis 세션 저장 | #68·#125의 메모리 세션 유지 범위와 다르다 |
| 기존 로그아웃을 전체 종료로 변경 | 현재 기기만 로그아웃하는 기존 계약을 보존하고 명시적인 별도 동작을 제공한다 |
| 공통 헤더에 모든 기기 로그아웃 버튼 추가 | 단일 세션에서는 일반 로그아웃과 결과가 같아 사용자에게 차이 없는 버튼이 두 개 생긴다 |

## 영향

- API: POST /api/auth/logout-all 추가. 만료된 이전 세션은 다음 요청에서 401 AUTH_001을 받는다. 기존 로그인 응답·에러 코드는 유지한다.
- DB: 스키마·마이그레이션·Entity 변경 없음. 서버 재시작 시 세션과 목록은 사라진다.
- 화면: 변경 없음. 끊긴 세션의 401은 기존 세션 만료 안내를 그대로 사용한다.
- 테스트: 두 기기·동시 로그인·사용자 ID 식별·전체 및 선택 종료·다른 사용자 보호·세션 이벤트·실제 쿠키 폐기·끊긴 쿠키의 첫 로그인 요청 거절 후 재로그인을 검사한다.
- 문서: identity README와 ADR 목록을 갱신한다. 채택된 ADR-0014 본문은 보존한다.
