# 0083. AI 조사 긴급정지 — 스위치 저장 · 역할 · 진행 중 보고서 처리

- **상태:** 제안 — 역할 규칙(`SecurityConfig`)은 P1 주환 확인 필요
- **날짜:** 2026-11-07
- **관련:** #626, [ADR-0009](0009-ai-investigation-call-structure.md) (AI 조사 호출 구조), [ADR-0059](0059-security-default-deny.md) (기본 거절), 「금융분야 인공지능 가이드라인」(금융위원회, 2026.6, 2026-06-22 시행 — [보도자료](https://www.fsc.go.kr/no010101/87142) 별첨2-2)
- **영향 받는 담당:** P4 현규(구현), P1 주환(`SecurityConfig` 역할 규칙 · 메뉴), P3 수민(영향 없음 — 판정 · Case 상태를 바꾸지 않음을 확인)

## 배경

AI 조사를 쓸지는 설정 파일 값 `ai.server.enabled`(`AI_SERVER_ENABLED`, 기본 false) 하나로 정한다.

- 끄려면 설정을 바꾸고 서버를 다시 띄워야 한다. 운영 중 AI가 이상한 보고서를 내도 바로 멈출 수 없다
- 누가 · 언제 · 왜 껐는지 기록이 없다
- 설정 값을 보는 곳은 `AiReportService`의 새 요청(`run`)과 재시작 재개(`resumeUnfinished`) 두 곳뿐이다. 이미 ai-server에 맡긴 보고서의 재시도(`AiInvestigationRunner.submitNext`)와 결과 반영(`AiReportResultService.apply`)은 설정을 보지 않는다

AI를 끈 상태에서 쓰는 고정 보고서(`FixedReportGenerator`)는 이미 있다. 판정 기준표(ADR-0009 결정 11)도 Spring에 있어 AI 없이 권고가 나온다.
고정 보고서는 AI 보고서와 같은 기본 조회를 코드로 돌리고 같은 기준표로 계산한다. 빠지는 것은 AI가 쓰는 설명뿐이다:

| 보고서 내용 | AI 보고서 | 고정 보고서 |
| --- | --- | --- |
| 결제별 금액 · 시각 · FDS 점수 · 걸린 규칙과 기준값, 카드 · 기기 · 접속 국가 신호 | ✅ | ✅ 같음 |
| 판정 기준표 (징후 표: 고위험 · 주의 · 정상 사유 · 판정 전에 확인할 것, 세 칸 권고) | ✅ | ✅ 같음 (Spring 같은 계산) |
| 비슷한 과거 사건 · 고객 최근 결제 · 같은 카드/기기/IP 결제 표, 사건 경위 · 근거 목록 | ✅ | ✅ 같음 (고객 이력은 30일) |
| 개요 한 줄 | ✅ | 이 ADR에서 추가 (결정 6) |
| 조사 요약 (사실을 엮은 설명) | ✅ AI | ❌ 고정 문장 |
| 추가 조사 (예: 90일로 넓히기) · AI 추가 제안 | ✅ AI | ❌ |

AI는 판단하지 않는 전달자다 — 권고는 코드가, 판정은 직원이 한다(ADR-0009 결정 7 · 11). 그래서 꺼도 판정 흐름은 그대로이고, 끄는 피해가 작다.

「금융분야 인공지능 가이드라인」(2026.6)은 사람이 즉시 개입할 수 있는 수단을 요구한다. 원문(별첨2-2):

- 3.2 인적 개입 원칙 적용·운영 (p.33): "인적 개입의 수단을 구축할 경우에는 감독자의 역할 및 권한과 인적(감독자) 개입방법(오버라이드·중단·재개승인 등)을 문서화하고 임계치·경보·대시보드·긴급정지 기능(Kill switch) 등의 수단을 조합해 상시 모니터링과 즉시 개입이 가능하도록 설계한다."
- 같은 절 (p.33): "필요시 시스템 동작을 일시 중지하거나 수정할 수 있는 권한과 도구를 갖출 수 있으며 기존 모형 및 통계 기반 모형을 백업모형으로 활용할 수 있다."
- 같은 절 표 (p.34) 긴급정지 기능 — 고위험 인공지능 "필수 적용": "이상 또는 긴급 상황 발생 시 해당 인공지능시스템을 즉시 중단하고 문제 요소 격리" / "긴급정지, 안전모드 전환 등의 기능을 인공지능 운영 시스템에 반영하고 (직관적 UI 제공) 관련 기록 보존"
- 같은 절 (p.34): "인적 개입의 결과는 설명 가능한 근거와 함께 사후 추적 가능한 로그로 보존하여 책임성과 재현성을 확보한다."
- 3절 점검 항목 ⑦ "긴급정지(Kill switch), 재정의(Override), 안전모드 전환 등 구체적인 인적 개입 방법이 시스템에 마련되어 있고 관련 절차가 문서화되어 있는가?", ⑧ "인적 개입 수단의 이행 결과는 책임 추적성을 위해 설명 가능한 사유와 함께 기록·보존되는가?"
- 5.2 안전장치 마련 (p.57): "기존 모형 및 통계 기반 모형을 백업모형으로 활용하거나, 사후 개입 장치인 긴급정지 기능 및 회생 계획 설계 등 관리 방안을 마련한다."

원문은 **누가 끄고 누가 다시 켜는지**와 **다시 켜기 승인 방법**을 정하지 않는다. 회사가 정해 문서화하라고 한다. 이 ADR이 그 문서다 (점검 항목 ⑦).

이 가이드라인은 법적 강제력이 없는 자율규제이고, AI 조사 보고서의 위험 등급은 회사의 위험평가로 정한다. 이 프로젝트는 위험 등급을 매기지 않았다. 등급과 관계없이 위 수단을 갖추기로 한다.

## 결정

관리자 화면에서 켜고 끄는 **AI 조사 스위치**를 둔다. 꺼지면 같은 자리에서 고정 보고서(백업모형)를 만들고, 판정은 지금처럼 직원이 한다.

끄는 방법 — 설정 파일 수정 · 재배포 · 재시작이 없다:

1. 보안 직원이나 ADMIN이 화면 [AI 조사 긴급정지]에서 사유를 쓰고 [끄기]
2. `POST /api/ai-switch/stop` → `ai_switch_histories`에 `STOPPED` 한 줄
3. Spring이 보고서를 다룰 때마다(결정 4의 네 경로) 마지막 기록을 읽고, 꺼져 있으면 ai-server를 부르지 않고 고정 보고서를 만든다 — 사건 정보가 ai-server · LLM으로 나가지 않는다
4. 누른 순간 진행 중이던 보고서는 바로 고정 보고서로 마무리한다 (결정 5)

다시 켜기는 ADMIN이 같은 화면에서 [다시 켜기] — 다음 처리부터 AI를 쓴다. ai-server는 그동안 떠 있고 Spring이 부르지 않을 뿐이다.

### 1. 상태 저장 — 변경 기록 표 하나, 추가만

새 표 `ai_switch_histories` (P4 소유):

| 칸 | 타입 | 뜻 |
| --- | --- | --- |
| `switch_history_id` | `BIGINT AUTO_INCREMENT` PK | |
| `action` | `VARCHAR(20) NOT NULL` | `STOPPED` · `RESUMED` (`EnumType.STRING`) |
| `reason` | `VARCHAR(500) NOT NULL` | 사유 — 필수 |
| `changed_by_user_id` | `BIGINT NOT NULL` | 바꾼 직원 — `platform_users` 논리 참조 (담당이 달라 FK 없음, AGENTS.md 4절) |
| `changed_by_name` | `VARCHAR(100) NOT NULL` | 그때의 이름 (계정 이름이 바뀌어도 기록은 그대로) |
| `changed_at` | `DATETIME(6) NOT NULL` | UTC |

- 인덱스 `idx_ai_switch_histories_changed (changed_at)`
- 지금 상태는 **마지막 행**(가장 큰 `switch_history_id`)이다. 행이 없으면 **켜짐** — 배포 직후 기존 동작이 바뀌지 않는다
- 행을 고치거나 지우지 않는다. 상태와 기록이 한 곳에 있어 서로 어긋나지 않는다
- 모양은 P2 `fds_rule_policy_change_histories`(켜고 끄기 + 바꾼 사람 ID · 이름 · 시각)를 따른다

### 2. 설정 파일과 스위치 — 둘 다 켜져야 AI

| `ai.server.enabled` | 스위치 | AI 조사 |
| --- | --- | --- |
| true | 켜짐 (기록 없음 포함) | 씀 |
| true | 꺼짐 | 안 씀 — 고정 보고서 |
| false | 무엇이든 | 안 씀 — 고정 보고서 |

- 설정은 "이 서버에 ai-server가 연결돼 있나"(설치 사실), 스위치는 "운영자가 쓰도록 허락했나"(운영 판단)다
- 설정이 꺼진 서버에서도 스위치를 조작하고 기록할 수 있다. 화면은 "설정에서 꺼짐 — 스위치를 켜도 고정 보고서"를 보여 준다
- 결과 마감 확인(`AiReportTimeoutChecker`, `@ConditionalOnProperty`)은 지금처럼 설정을 따른다

### 3. 역할 — 끄기는 쉽게, 다시 켜기는 엄격하게

| | SECURITY_STAFF | ADMIN | OPERATOR |
| --- | --- | --- | --- |
| 조회 `GET /api/ai-switch` (상태 · 최근 기록 20건) | ✅ | ✅ | ❌ |
| 끄기 `POST /api/ai-switch/stop` (사유 필수) | ✅ | ✅ | ❌ |
| 다시 켜기 `POST /api/ai-switch/resume` (사유 필수) | ❌ | ✅ | ❌ |

- 괜히 끈 피해는 그동안 보고서가 고정 보고서로 나오는 것뿐이다(판정 · 돈에 영향 없음). 늦게 끈 피해는 문제 있는 AI 보고서가 판정 근거로 쌓이는 것이다. 그래서 끄는 문턱을 낮춘다
- AI 보고서를 매일 읽어 이상을 가장 먼저 보는 사람은 보안 직원이다. 관리자를 기다리면 "즉시 개입"이 늦다
- 다시 켜기는 가이드라인의 "재개승인"에 해당한다 — 원인을 확인했다는 판단이므로 끈 사람이 아닌 책임자(ADMIN)가 한다
- 남용은 사유 필수와 기록으로 막는다. 관리자는 기록을 보고 다시 켤지 정한다
- `SecurityConfig`에 정확한 메서드 · 경로로 규칙을 두고(ADR-0059), 서비스도 역할을 한 번 더 확인한다
- 사유는 앞뒤 공백을 뺀 1~500자. 없으면 400, 이미 같은 상태면 409 — 동시에 눌러 같은 상태 기록이 두 줄 생기지 않게

### 4. 스위치를 확인하는 곳 — AI로 이어지는 네 경로 모두

| 경로 | 지금 | 꺼져 있으면 |
| --- | --- | --- |
| 새 요청 `AiReportService.run` | 설정만 봄 | 고정 보고서 |
| 재시작 재개 `AiReportService.resumeUnfinished` | 설정만 봄 | 고정 보고서 |
| 재시도 `AiInvestigationRunner.submitNext` | 안 봄 | ai-server에 다시 맡기지 않고 고정 보고서 |
| 결과 반영 `AiReportResultService.apply` | 안 봄 | AI 본문을 저장하지 않고 고정 보고서 |

- 고정 보고서 생성(지금 `AiReportService.runFixed`)을 별도 컴포넌트로 옮겨 `AiReportService`와 `AiInvestigationRunner`가 함께 쓴다 (순환 방지)
- AI 경로에서 고정 보고서로 마무리할 때도 AI 경로와 같은 `AiReportFinished`를 발행해 Case 상태를 다시 계산하게 한다
- 진행 표시 조회(`AiReportProgressService`)는 바꾸지 않는다 — 끄는 순간 진행 중 보고서가 끝나므로(5) 진행 표시도 사라진다

### 5. 끄는 순간 진행 중인 보고서 — 즉시 고정 보고서로 마무리

가이드라인 "즉시 중단하고 문제 요소 격리"에 따라, 끄는 기록이 커밋된 뒤(트랜잭션 밖) 끝나지 않은 보고서(`PENDING` · `RUNNING`)를 처리한다.

1. 보고서 잠금(`AiAttemptTracker.lockFor`)을 잡고 진행 중 시도를 지운다 — 늦게 온 콜백은 "진행 중 시도 없음"으로 무시된다
2. **같은 `report_version`**에서 고정 보고서로 끝낸다 — 새 버전을 만들지 않는다 (ADR-0009 결정 3)
3. 이미 끝난 보고서는 바꾸지 않는다 (`AiReportWriter.succeed` · `fail`이 끝난 보고서면 false)

끄기와 콜백이 겹쳐 1번 전에 결과가 들어와도, 결과 반영(4의 `apply`)이 스위치를 다시 보므로 AI 본문은 저장되지 않는다.

한계: ai-server에는 취소 API가 없다. 이미 나간 LLM 호출은 끝까지 돌고 결과만 버려진다. 시도 상태는 서버 메모리에 있어 서버 1대를 전제로 한다(ADR-0009와 같은 전제).

### 6. 고정 보고서 — 왜 고정인지 남긴다

- `investigationTrace`에 선택 칸 `fixedReason`: `CONFIG_OFF`(설정 꺼짐) · `ADMIN_STOPPED`(긴급정지). 예전 보고서에는 없다
- 한계 문장(`recommendation.limitations`)도 사유별로 쓴다. 지금의 "고정 문장 보고서입니다(AI 연결 전)"는 긴급정지와 구분되지 않는다
- 보고서 버전마다 저장되므로, 다시 켠 뒤에도 그 버전이 왜 고정인지 남는다. 다시 켠 뒤 재요청하면 새 버전이 AI로 생기고 고정 버전은 그대로 쌓인다 (ADR-0009 결정 3)
- 화면은 고정 보고서면 **보고서 맨 위(결론 위)에 안내 한 줄**을 둔다 — 조사 과정 탭 · 맨 아래 한계 문장만으로는 첫 화면에서 보이지 않아, 직원이 요약이 짧은 이유를 모른 채 읽는다
  - `ADMIN_STOPPED`: "AI 조사 긴급정지 중에 만든 고정 보고서입니다. 조회 결과와 판정 기준표는 AI 보고서와 같고, AI 요약과 추가 조사는 없습니다."
  - `CONFIG_OFF`: 같은 모양으로 "AI 서버가 꺼진 상태에서 만든…"
  - 조사 과정 탭 안내 · 사용 모델 문구도 둘을 구분한다
- 정지 사유 · 끈 사람은 보고서에 넣지 않는다 — 스위치 기록(결정 1)에 있고, 보고서는 "왜 고정인지"만 알면 된다
- 개요 한 줄(`caseOverview`)을 고정 보고서에도 넣는다 — 긴급정지 중에는 고정 보고서가 실제로 쓰이는 대체 보고서라 AI 보고서와 모양을 맞춘다. 문장은 ai-server `assemble.py`의 `case_overview`와 같다 (ADR-0009 결정 10 버린 대안 "긴급 정지 작업과 같이 한다"를 여기서 처리)

| 대안 | 버린 이유 |
| --- | --- |
| 설정 파일 값만 쓰기 (지금) | 바꾸려면 재시작해야 하고, 누가 · 왜 바꿨는지 기록이 없다. 가이드라인 "즉시 개입" · 기록 보존을 못 맞춘다 |
| ai-server의 LLM 제공자(`AI_SERVER_LLM_PROVIDER`)를 mock으로 바꾸기 | ai-server를 다시 띄워야 하고, mock이 만든 가짜 문장이 AI 보고서처럼 저장된다 — 멈추는 것이 아니라 가짜 결과를 계속 낸다. 사건 정보도 계속 ai-server로 나간다 |
| 스위치만 보고 설정 파일 값은 무시 | 설정을 끈 로컬 · 테스트 · ai-server 없는 서버에서 기록이 없으면 켜짐이라, 없는 ai-server를 불러 보고서가 모두 FAILED가 된다 |
| 끄기 · 켜기 모두 ADMIN만 | 이상을 먼저 보는 보안 직원이 관리자를 기다려야 해 개입이 늦다 |
| 끄기 · 켜기 모두 보안 직원 · ADMIN | 끈 사람이 원인 확인 없이 스스로 다시 켤 수 있다. 가이드라인이 "중단"과 "재개승인"을 나눈 취지와 맞지 않는다 |
| 다시 켜기를 두 사람 승인(요청 → 승인) | 원문이 방법을 정하지 않았고, 다시 켜도 판정은 직원이 하므로 이번 범위에는 과하다. 후속 |
| 진행 중 보고서는 AI 결과대로 끝내고 새 요청 · 재시도만 막기 | 끈 뒤에도 결과 마감(5분)과 재시도 동안 AI 본문이 저장될 수 있다. "즉시 중단 · 격리"에 맞지 않는다 |
| 끄는 순간 진행 중 보고서를 FAILED로 끝내기 | 직원이 수동 판정으로 가야 한다. 고정 보고서로 끝낼 수 있는데 근거를 버린다 |
| 상태 한 행을 두고 UPDATE + 별도 기록 표 | 상태와 기록이 어긋날 수 있다. 조회량이 적어 마지막 행을 읽어도 충분하다 |
| P1 `admin_change_histories` 재사용 | 대상이 사용자 · 가맹점 하나여야 한다는 CHECK 제약이 있다. P1 표의 뜻을 바꾸게 된다 |
| ML 그림자 채점(`ai.ml-shadow.enabled`)도 같은 스위치로 | 결제 판정에 쓰지 않는 그림자 기록이고 LLM이 아닌 RF 모델이다. 이번 범위(AI 조사) 밖, 후속 |

## 영향

- API: `GET /api/ai-switch` · `POST /api/ai-switch/stop` · `POST /api/ai-switch/resume` (P4 `investigation/report`). `SecurityConfig` 역할 규칙 추가 (P1 파일)
- DB: 새 표 `ai_switch_histories` (P4 마이그레이션 · 엔티티). `ai_reports`는 바꾸지 않는다 — 고정 사유는 `report_body` 안 (AGENTS.md 6절)
- 보고서 본문: `investigationTrace.fixedReason`, 고정 보고서 `caseOverview` — 둘 다 선택 칸이라 예전 보고서 · ai-server 보고서는 그대로
- ai-server: 변경 없음
- 화면: 관리자 메뉴 "관리" · 보안 직원 메뉴 "조사"에 [AI 조사 긴급정지] (보안 직원은 다시 켜기 버튼 없음). 고정 보고서 맨 위 안내 한 줄(`ReportFull`), 조사 과정 · 사용 모델 문구에 긴급정지 구분
- P3: 판정 · Case 상태를 바꾸지 않는다. 고정 보고서로 끝나도 지금처럼 `AiReportFinished` → Case 상태 재계산. 자동 ACCEPT / REJECT 없음 (AGENTS.md 6절)
- 테스트: 꺼진 상태의 네 경로(새 요청 · 재개 · 재시도 · 결과 반영), 끄는 순간 진행 중 보고서, 설정 · 스위치 조합, 기록 · 사유, 역할별 403
- 문서: `docs/erd/README.md` 2절 P4 행, ADR-0009에 이 ADR 링크
