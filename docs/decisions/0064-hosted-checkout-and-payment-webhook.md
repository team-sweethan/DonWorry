# 0064. 돈워리 호스팅 결제창과 결제 상태 웹훅

- **상태:** 채택 — 저장소 구현 완료(결제창 PR #425, 서명기 #449, 웹훅 발송 #451, 재전송 한도 #455). P1 확인 완료(2026-11-02, PR #403). 4절·4-1 개정은 P1·P4·P6 합의(2026-11-04, #492). CakeShop 쪽 4절 반영은 CakeShop 저장소 PR. 2-1절(모의 카드 한 장 · 카드 추가)은 P5 업무를 대신 맡은 P3 수민 결정(2026-11-10, #766)
- **날짜:** 2026-11-01 (2026-11-02 개정: P1 확인 반영, 사후 거절을 이행 전·후로 나눔, 웹훅 역할 분담. 2026-11-03 개정: 웹훅 재전송 한도 #455. 2026-11-04 개정: `HELD`를 가맹점에 "결제 확인 중"으로 알리고 진행은 가맹점이 선택, 사후 거절 손실은 가맹점 부담 #492. 2026-11-10 개정: 모의 카드를 한 장으로 줄이고 결제창에서 카드 추가(모의 등록) #766)
- **관련:** #402, #455, #492, #149, #154, #242, #255, [ADR-0037](0037-merchant-hmac-authentication.md), [ADR-0059](0059-security-default-deny.md), [ADR-0058](0058-captured-refund-contract.md), [ADR-0068](0068-p6-capture-business-day-settlement.md)
- **영향 받는 담당:** P5(결제 — 구현, CakeShop 연동 포함), P1(`identity/api/MerchantWebhookSigner` 리뷰 — 구현은 P5로 변경 2026-11-02, `SecurityConfig` 리뷰), P6(정산 변경 없음 확인 — 4-1, #492), CakeShop 저장소(`team-sweethan/cakeshop_refactoring`, 4절 해석·주문 상태는 P3 수민이 맡음 2026-11-04). P2·P3는 기존 결제 흐름을 그대로 쓰므로 계약 변경 없음

## 배경

- #149로 CakeShop 서버가 서명(ADR-0037)한 `POST /api/payments`로 결제를 요청하고 조회할 수 있다. 이 방식은 카드·기기·IP 같은 위험 신호를 **CakeShop 서버가 모아 보내야** 한다. 구매자 브라우저의 기기·IP를 가맹점이 정확히 대신 보내기 어렵고, 카드 정보를 가맹점 서버가 다루게 된다.
- 실제 PG(Toss·이니시스 등)는 PG가 결제창을 띄우고 가맹점은 결제를 준비·확인만 한다. 돈워리도 같은 구조여야 FDS가 구매자 브라우저의 신호를 직접 받는다.
- HELD 결제는 보안 직원 판정까지 몇 시간이 걸릴 수 있다. 판정 결과(VOIDED 등)를 CakeShop이 알 방법이 조회뿐이라 #154에서 별도 통지 도입 여부를 검토 중이었다.
- CakeShop 실제 연동은 #242에서 담당·범위 재협의 전까지 보류 상태다(2026-10-28 P1 결정). 이 ADR은 P5 인수자가 연동 방식을 제안하고 재개를 요청하는 근거다.
- 로컬 샌드박스(원본과 분리된 복사본, 원격 없음)에서 아래 결정대로 돈워리·CakeShop을 구현했고, 결제 완료·HELD → 직원 거절 → CakeShop 주문 취소·웹훅 실패 후 재전송을 화면과 두 DB로 확인했다.

## 결정

**돈워리가 결제창을 호스팅하고, 결제 상태가 바뀌면 가맹점에 서명한 웹훅을 보낸다. 가맹점은 웹훅 본문을 믿지 않고 기존 서명 조회로 다시 확인해 반영하며, 웹훅을 놓쳐도 조회 배치로 맞춘다.**

### 1. 결제 준비 — `POST /api/payment-sessions` (가맹점 서버 → 돈워리)

- 인증: ADR-0037 가맹점 HMAC 서명 + `Idempotency-Key`(UUID). 같은 키·같은 내용이면 같은 세션, 다른 내용이면 409 `IDEMPOTENCY_KEY_CONFLICT`
- 요청: `orderRef`, `customerRef`(숫자 문자열), `amount`, `orderCreatedAt`, `orderName`, `buyerEmail`(선택), `successUrl`, `failUrl`, `notifyUrl`(선택). 금액·주문번호·고객 참조·주문 시각 규칙은 `POST /api/payments`(#149)와 같다. **카드·기기·IP는 받지 않는다**
- `successUrl`과 `failUrl`은 같은 출처(scheme·host·port)여야 한다. 이 출처가 결제창이 결과를 알리는 유일한 대상이다
- 응답: `sessionKey`(`pss_` + 128비트 난수), `checkoutUrl`(`{공개 주소}/checkout/{sessionKey}`), `expiresAt`(= `orderCreatedAt` + 10분, #149 결제 접수 기한과 같음). 기한이 지난 주문은 409 `ORDER_EXPIRED`
- 세션은 결제 시도 키(`attemptKey`)를 하나 갖는다. 결제창에서 여러 번 눌러도 같은 시도라 결제가 두 번 생기지 않는다

### 2. 결제창 — 공개 API와 화면 (구매자 브라우저 → 돈워리)

| 경로 | 하는 일 |
| --- | --- |
| `GET /api/checkout/{sessionKey}` | 가맹점 이름·주문명·금액·만료 여부·모의 카드 목록(기본 카드)·이 결제창에서 추가할 수 있는 카드(`addableCard`, 2-1)·결과(있으면)·취소 주소·가맹점 출처 |
| `POST /api/checkout/{sessionKey}/payments` | 모의 카드(기본 카드 또는 추가한 카드) 선택 + 기기 ID로 결제. 기존 결제 접수·FDS 평가·모의 승인 흐름(`PaymentRequestFlowService`)을 그대로 탄다. IP는 돈워리가 요청에서 직접 읽되, 프록시 뒤에서도 구매자 IP가 되도록 identity의 신뢰 프록시 규칙(`identity/api/ClientIpResolver`, 로그인 이력과 같은 설정)으로 읽는다. 결제 시작 직전 가맹점이 `ACTIVE`인지 다시 확인한다(정지면 409 `MERCHANT_INACTIVE`). 처음 누른 카드·기기·IP를 세션에 고정해, 접수 뒤 평가·승인 중 실패해도 재시도는 같은 값으로 같은 시도를 이어 간다. 세션 만료(409 `SESSION_EXPIRED`)와 가맹점 정지 검사는 **새 접수만** 막는다. 같은 시도 키로 이미 접수된 결제는 만료 뒤에도 이어서 처리하고, 결제창 열기·결과 조회도 그 결제를 찾는다 |
| `GET /api/checkout/{sessionKey}/result` | 처리 중이면 결제창이 다시 조회 |

- **로그인·쿠키를 쓰지 않는다.** 권한은 추측할 수 없는 세션 키뿐이다. 응답에 가맹점 내부 값(`customerRef`·`notifyUrl`)을 넣지 않고 `Cache-Control: no-store`를 붙인다
  - 결제창 화면도 직원 화면용 요청 함수(CSRF 준비 · 쿠키 전송 · 세션 활동 기록)를 쓰지 않고 `api/checkout.ts`의 전용 호출로 쿠키 없이(`credentials: omit`) 부른다(PR #425 P1 리뷰)
- **CSRF 검사에서 제외한다.** CSRF는 쿠키로 인증하는 요청을 지키는 장치인데 이 경로는 쿠키 인증이 없다. 또 결제창은 다른 사이트(CakeShop) 안의 iframe으로 열리므로 돈워리의 `SameSite=Lax` 쿠키(`XSRF-TOKEN`)가 전송되지 않는다. 검사를 켜 두면 결제 버튼이 403이 된다. CSRF 검사는 #416(ADR-0063)에서 기본으로 켜졌으므로 결제창 구현 PR에서 이 세 경로를 반드시 제외한다
- ADR-0059 기본 거절 아래에서 위 세 경로만 정확한 메서드·경로로 연다. ADR-0063이 직원 체인(`SecurityConfig`)에 새 CSRF 예외를 금지하므로, CakeShop 서명·AI 서버처럼 **결제창 전용 체인 `identity/security/CheckoutSecurityConfiguration`**(세션·쿠키 없음, CSRF 끔, 다른 메서드는 403)에 둔다(2026-11-02 구현 PR, P1 리뷰)
- 결과: 카드 승인(`authorized`)이고 상태가 `PENDING`·`HELD`·`CAPTURED`면 `successUrl?paymentKey=&orderId=&amount=`, 그 밖에는 `failUrl?code=`, 구매자가 닫으면 `failUrl?code=USER_CANCELED`. 구매자 이메일(`buyerEmail`)은 세션 생성 때 FDS 입력과 같은 규칙으로 검사해 잘못된 값은 400으로 거절한다. 결과 · 취소 · 만료 뒤 이동 신호를 가맹점 화면이 받지 못하면(복귀 주소와 다른 출처로 열린 경우 등) 4초 뒤 "쇼핑몰 화면으로 이동" 링크를 보인다(셋 다 같은 경로)
- 화면 `/checkout/:sessionKey`(돈워리 프론트, 로그인 없음): iframe 안에서 열렸으면 높이 변화(`donworry-checkout-resize`)와 결과 이동(`donworry-checkout`)을 `postMessage`로 **가맹점 출처에만** 보낸다. 가맹점은 `event.origin`을 확인하고 같은 출처 주소로만 이동한다

### 2-1. 모의 카드와 카드 추가 (2026-11-10 개정, #766)

- 카드사는 실제로 연동하지 않고 가상으로 있다고 가정한다. 결제창이 처음 보여 주는 카드는 **한빛카드 `**** 4821` 한 장**이다. 누리카드 `**** 1173`(코드 `B`, #582)은 뺀다
- 결제창의 **[카드 추가]**를 누르면 모의 등록 안내가 나오고, [등록]을 누르면 누리카드 `**** NNNN`(코드 `N`)이 목록에 생기고 선택된다. 카드번호 · 유효기간 · 인증 같은 입력은 받지 않는다. 구매자가 카드사에서 카드를 새로 등록했다고 가정하는 단계다
- 추가한 카드는 **그 결제창(세션)에서만** 쓴다. 저장하지 않으므로 다음 주문의 결제창에는 다시 한빛카드만 보인다. 결제창 하나에 한 장이다
- 카드 토큰 · 표시값은 돈워리가 만든다 (`payment/service/CheckoutMockCard`)
  - 기본 카드 토큰: 가맹점 고객 + 카드 코드의 해시. #582 때와 같은 값이라 이미 한빛카드를 쓴 고객에게는 계속 쓰던 카드다
  - 추가 카드 토큰: 가맹점 고객 + 카드 코드 + 세션의 시도 키(`attemptKey`) 해시. 같은 시도를 다시 하면 같은 값이라 2절의 같은 시도 이어 가기와 충돌하지 않고, 다른 결제창에서는 매번 그 고객이 처음 쓰는 카드가 된다
  - 추가 카드 끝 4자리: 같은 해시에서 뽑고 `4821` · `1173`과 겹치지 않게 한다. 결제창이 보여 준 값과 FDS에 저장되는 표시값(`누리카드 **** NNNN`, 50자 이하)은 같다
- 세션에는 카드 코드 `N`으로 고정한다. 기존 `submitted_card`(1자리)를 그대로 쓰므로 저장 구조는 바뀌지 않는다
- FDS 규칙은 바꾸지 않는다. 추가한 카드는 R03(신규 카드)의 "기존에 없던 cardToken"이 된다
  - R03은 그 고객의 승인 이력이 있을 때만 걸린다. 처음 결제하는 고객이 추가 카드를 쓰면 점수가 붙지 않는다
  - 중위험(50점) 시연은 한빛카드로 한 번 승인받은 고객이 새 기기에서 추가 카드로 결제한다(R02 + R03)
- 추가한 카드는 다시 쓰이지 않아, 그 카드를 차단 목록(R07)에 올려도 차단 효과를 보일 수 없다. 카드 차단 시연은 한빛카드로 한다
- 지금 없는 카드(누리카드 `1173`, 예전 C · D)로 고정 · 접수된 시도는 PR #587 규칙대로 이어 간다. 접수 전이면 다시 고른 카드로 바꾸고, 접수됐으면 저장된 위험 신호를 그대로 쓴다

### 3. 결제 상태 웹훅 (돈워리 → 가맹점 `notifyUrl`)

- 언제: 결제창에서 결제가 접수된 뒤, 그리고 그 결제의 (상태, 승인 여부)가 마지막으로 보낸 값과 달라질 때마다. 예) `HELD` → 직원 거절 → `VOIDED`
- 본문(JSON): `eventId`(`evt_{paymentId}_{상태}_{A|N}` — 같은 상태 변화는 같은 ID), `type`(`payment.status_changed`), `paymentId`, `orderRef`, `paymentStatus`, `authorized`, `amount`, `occurredAt`
- 헤더: `X-Merchant-Code`, `X-Timestamp`, `X-Event-Id`, `X-Signature`
- 서명: 가맹점 API 서명(ADR-0037)과 **같은 가맹점 키**, 다른 접두어 `DONWORRY-WEBHOOK-V1`. 서명 원문은 `DONWORRY-WEBHOOK-V1\n{가맹점 코드}\n{timestamp}\n{eventId}\n{sha256(body) hex}`. 접두어가 달라 웹훅 서명을 API 요청 서명으로 재사용할 수 없다. 가맹점은 시각을 ±300초로 검사한다
- 서명기는 키를 가진 identity가 `identity/api/MerchantWebhookSigner`로 공개한다. payment는 키를 직접 읽지 않는다
  - 계약: `sign(merchantId, eventId, body)` → `SignedWebhook(merchantCode, timestamp, eventId, signature)`(헤더 4개에 그대로). 쓸 수 있는 키가 없으면(연동 전 · 키 미발급 · 사용 불가) empty — 호출자는 보내지 않고 다시 시도한다. 없는 가맹점 · 형식이 틀린 eventId(`[A-Za-z0-9_.:-]{1,100}`) · null 본문은 `IllegalArgumentException`. 정지 가맹점도 서명한다(이미 받은 결제의 상태 변화는 알린다). 구현 `identity/service/MerchantWebhookSignerService`
- 역할(2026-11-02 P1 합의, 같은 날 변경): 처음에는 identity 서명 기능을 P1이 구현하기로 했으나, P1 일정 때문에 **서명기도 P5가 구현하고 P1이 리뷰**한다. 돈워리 웹훅 발송과 CakeShop 수신·검증은 P5가 구현한다
- 웹훅을 이번 범위에 넣는 이유: 4절처럼 `HELD`를 "결제 확인 중"으로 알리고 판정(`CAPTURED`·`VOIDED`)이 나면 바로 풀거나 취소하려면 CakeShop이 판정을 빨리 알아야 한다. 조회 배치(60초)만으로는 그만큼 가맹점이 더 기다리고, 그사이 가맹점이 진행을 고를 수 있다
- 전송: 업무 트랜잭션 밖의 스케줄러(기본 5초)가 보낸다. 2xx면 보낸 상태를 기록하고 끝, 아니면 5초부터 두 배씩 최대 5분 간격으로 다시 보낸다. 타임아웃 3초, 리다이렉트를 따르지 않는다
- 재전송 한도(2026-11-03, #455): 같은 상태를 첫 시도부터 약 24시간(293번째 시도, `PaymentSession.NOTIFY_MAX_ATTEMPTS`) 동안 못 보내면 그 상태의 알림을 그만두고 가맹점 조회 배치에 맡긴다. 한도는 상태마다 따로 센다. 재시도 중인 웹훅의 eventId를 `notify_event_id`에 두고, 재시도 중 결제 상태가 바뀌어 보낼 eventId가 달라지면 실패 횟수와 간격을 처음부터 다시 센다(PR #457 Codex 리뷰 — 이어 세면 `HELD`를 오래 재시도한 뒤의 `VOIDED`가 첫 실패만으로 중단된다). 그만둘 때 그 상태를 `notified_status`·`notified_authorized`에 처리한 것으로 기록해 다음 주기에 다시 예약되지 않게 하고, 상태가 또 바뀌면(예: `HELD` → `VOIDED`) 횟수를 새로 세어 다시 알린다. `notify_attempts`는 남기고 `next_notify_at`을 비우므로 운영에서는 `notify_attempts > 0 AND next_notify_at IS NULL`로 중단된 세션을 찾는다. 중단 때 WARN 로그(`결제 웹훅 재전송 중단`, 세션 ID · 결제 ID · 상태 · 횟수)를 남긴다
- 가맹점 쪽 규칙: 서명·시각 확인 → **본문은 믿지 않고 `paymentId`로 서명 조회(#149)해서 반영** → 같은 결과면 아무것도 바꾸지 않는다(중복·순서 역전 안전) → 2xx 응답. 웹훅을 놓쳐도 조회 배치(최근 결제를 주기 조회)로 맞춘다

### 3-1. 서명 조회 응답에 `authorized` 추가 (#149 조회 계약 확장)

- `GET /api/payments/{paymentId}`·`GET /api/payment-orders`(주문번호 조회) 응답(`MerchantPaymentResponse`)에 `authorized`(boolean, 카드 승인이 끝났는지)를 **추가**한다. 값은 승인 참조(`authorizationRef`)가 있는지로만 정하고, 승인 참조 원문은 계속 내보내지 않는다
- 이유: `PENDING`은 "승인 전 평가 중·오류로 멈춤"과 "승인 후 매입 대기"를 함께 담는다(#149 설계). 웹훅 본문을 믿지 않고 조회로 반영하려면, 조회만으로 승인 여부를 알 수 있어야 4절 규칙(승인된 결제를 결제 완료와 결제 확인 중으로 나눔)을 지킬 수 있다. 결제창을 닫았거나 웹훅을 놓쳐 조회 배치로 복구할 때도 같다
- 필드 추가만 하므로 이 값을 모르는 기존 호출자(`scripts/demo/cakeshop_pay.py` 등)는 그대로 동작한다. 새 `PaymentStatus`는 만들지 않는다
- 결제창 결과(2절)와 웹훅 본문의 `authorized`도 같은 기준으로 계산한다

### 4. CakeShop이 결과를 해석하는 규칙 (2026-11-04 개정, #492)

조회 응답(3-1)의 결제 상태와 `authorized`로 정한다. 돈워리는 결제 상태만 알리고 주문 진행 상태(제작·픽업)와 이행 여부는 받지 않는다.

| 조회 결과 | 구매자 | 가맹점 오너 |
| --- | --- | --- |
| `authorized=true`, `PENDING`(ALLOW 승인 후 매입 대기) 또는 `CAPTURED` | 결제 완료 | 결제 완료 |
| `authorized=true`, `HELD`(REVIEW, 직원 판정 전) | 결제 완료. 주문 상태는 "주문 확인 중" | **결제 확인 중** + 알림 |
| `VOIDED`(직원 거절, 승인 취소 · 청구 없음) | 주문 취소. 이유 없이 "결제 승인이 취소되어 주문이 취소되었습니다. 카드 청구는 되지 않습니다" | 결제 취소 → 진행 전 주문은 자동 취소 |
| `authorized=false`인 `PENDING` | 처리 중 | 처리 중 |

- `HELD`도 승인은 끝났으므로 구매자를 결제창에서 기다리게 하지 않는다(2절 결과 주소는 그대로 `successUrl`)
- **구매자에게는 결제 검토 상태(결제 확인 중 · 보안 검토 · FDS)를 보여 주지 않는다.** 사기범에게는 걸렸다는 신호가 되고 정상 구매자는 불안해한다. 대신 가맹점 주문 상태로 "주문 확인 중"을 보인다
- **오너는 진행 여부를 고른다.** 버튼을 막지 않는다
  - ① 판정 기다리기 ② 고객에게 전화 등으로 확인한 뒤 진행 ③ 주문 취소(`HELD` 고객 취소는 승인 취소, #382)
  - 확인 중에 이행 동작(CakeShop: 제작 시작 · 픽업 완료 · 일반 상품을 픽업 준비로 넘기기)을 하면 확인 창("돈워리가 확인 중인 결제입니다. 진행 후 거절되면 손실은 가맹점이 부담합니다")을 거치고, 누가 언제 진행했는지 가맹점이 기록한다. 확인은 가맹점 서버에서 검사한다
  - 가맹점 가입 때 이 규칙과 손실 부담(4-1)을 안내한다
- `CAPTURED`(직원 승인) 웹훅 · 조회가 오면 결제 완료로 바꾼다. 매입 · 정산 자체는 돈워리 안의 일이다. 정산일은 판정(매입)한 날 기준 영업일 D+3이라(ADR-0068) 판정이 늦으면 정산도 늦어진다. 가맹점 안내에 함께 적는다
- 가맹점에는 결제 상태와 승인 여부만 간다. FDS 점수 · 위험 사유 · 조사 보고서는 보내지 않는다
- 판정 목표 시간: Case 접수 후 1시간 이내, 그 안에서도 최대한 빨리(2026-11-04 합의). 직원 화면 알림은 별도 이슈
- CakeShop 쪽 화면 · 주문 상태(기존 `UNDER_REVIEW` 재사용, 일반 상품 `HELD`면 `UNDER_REVIEW`로) · 문구는 CakeShop 저장소 PR에서 구현한다

#### 4-1. 사후 거절(HELD → 직원 거절 → VOIDED) 손실은 가맹점 부담 (2026-11-04 개정, #492)

직원 거절은 카드 승인 취소(VOID)라 고객 돈은 빠져나가지 않고, 매입이 없어 P6 정산 행도 생기지 않는다.

| VOIDED를 받았을 때 가맹점 주문 | 가맹점이 하는 일 | 손실 |
| --- | --- | --- |
| 오너가 아직 진행하지 않음(판정을 기다림) | 자동 취소(재고 · 쿠폰 복구, 고객 알림) | 없음. 범죄자도 얻는 것이 없다 |
| 오너가 확인 창을 거쳐 진행함 | 오너가 처리한다 | **가맹점 부담.** 돈워리는 보상하지 않는다 |

- 이유: 11/03 회의에서 직원 판정에 픽업 완료 여부를 쓰지 않기로 했고, P6 정산도 매입일 D+3으로 픽업과 분리됐다(ADR-0068). 돈워리는 이행 여부를 알 수 없으므로 "이행됐으면 돈워리 부담"을 지킬 수 없다. 대신 오너가 확인 중임을 알고 진행과 그 책임을 확인 창에서 직접 고른다
- 오너가 기다리면 손실이 없다. 기다림은 판정 목표 시간(4절)으로 줄인다
- 2026-11-02 결정(이행 전 취소 · 이행 뒤 돈워리 부담, PR #403 P1·P4 논의)은 아래 고려한 대안에 남긴다
- 결제 시점 추가 인증(2차 인증)이 즉시 이행 가맹점의 근본 해결이지만 이번 범위에서는 구현하지 않는다(2026-11-03 회의, 발표에서 확장 방향으로 설명)

### 5. 저장

- P5 소유 새 테이블 `payment_sessions`: 세션 키, 가맹점, 멱등 키, 시도 키, 주문 값, 세 주소, 상태(`OPEN`·`SUBMITTED`), 연결 결제 ID, 만료 시각, 마지막으로 알린 상태·승인 여부, 알림 시도 횟수·다음 시각, 재시도 중인 eventId(`notify_event_id`, #455에서 컬럼 추가)
- `payment_id`는 같은 담당(P5) `payments`로 물리 FK, `merchant_id`는 P1 `merchants` 논리 참조(AGENTS.md 4절)
- `submitted_card`·`submitted_device_id`·`submitted_ip`·`submitted_at`: 처음 결제를 누른 값. 재시도는 이 값으로 같은 결제 시도를 이어 간다(2026-11-02 PR #425 리뷰)
- 별도 이벤트 저장(outbox) 테이블은 두지 않는다. 세션 하나는 결제 하나만 알리므로 "마지막으로 알린 값"과 현재 결제 상태의 차이로 다시 보낼지 정한다

### 6. 주소와 실행 환경

코드에 주소를 넣지 않는다. `localhost`는 설정 기본값과 테스트에만 쓴다.

| 설정 | 어디 | 뜻 |
| --- | --- | --- |
| `payment.http.enabled=true` | 돈워리 | 가맹점 결제 API·결제창 API·웹훅 발송을 켠다(기존 결제 API와 같은 스위치) |
| `DONWORRY_PUBLIC_BASE_URL` | 돈워리 | 결제창 주소의 앞부분. 이용 신청 메일이 쓰는 기존 값과 같다(돈워리 화면 공개 주소) |
| `DONWORRY_PAYMENT_ENABLED=true` | CakeShop | 돈워리 결제 선택을 켠다 |
| `DONWORRY_PAYMENT_BASE_URL` | CakeShop | 돈워리 API 주소 |
| `DONWORRY_PAYMENT_SHOP_BASE_URL` | CakeShop | 결제창이 돌려보낼 주소·웹훅 받을 주소의 앞부분(CakeShop 공개 주소) |
| `DONWORRY_MERCHANT_HMAC_CAKESHOP` | 양쪽 OS 환경 변수 | 같은 가맹점 키(ADR-0037, `docs/identity/246-cakeshop-provisioning.md`) |

- 결제창 이동·결과 전달은 **구매자 브라우저**가 하므로 브라우저가 두 주소에 닿기만 하면 된다
- 웹훅은 **돈워리 서버가 CakeShop 서버로** 보낸다. 돈워리 서버에서 `DONWORRY_PAYMENT_SHOP_BASE_URL`에 닿지 못하면(예: 돈워리는 서버, CakeShop은 개인 PC) 웹훅은 실패·재시도만 하고, CakeShop 조회 배치(기본 60초)가 대신 맞춘다. 반영이 늦을 뿐 결과는 같다
- CakeShop이 https면 돈워리도 https여야 한다. 아니면 브라우저가 iframe을 혼합 콘텐츠로 막는다
- 로컬에서 둘 다 `localhost`로 열면 호스트가 같아 세션 쿠키(`JSESSIONID`)가 겹친다(돈워리 직원 로그인 시 CakeShop 로그아웃). 로컬 안내는 CakeShop을 `http://127.0.0.1:8080`으로 연다. 이러면 운영처럼 "다른 사이트 iframe" 조건도 로컬에서 재현된다

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| #149처럼 CakeShop이 카드·기기·IP를 모아 `POST /api/payments`로 보내기 | 구매자 브라우저의 기기·IP를 가맹점이 대신 보내 FDS 근거를 신뢰하기 어렵고, 가맹점 서버가 카드 정보를 다룬다. 서버 간 결제 API는 시연 스크립트용으로 유지한다 |
| 결제창을 새 창(팝업)·전체 이동으로만 열기 | 팝업 차단과 화면 이탈이 생긴다. iframe 레이어를 기본으로 하고, 결과는 `redirectUrl`이라 전체 이동에도 그대로 쓸 수 있다 |
| 웹훅 없이 CakeShop 조회만 | HELD 판정은 몇 시간 뒤라 짧은 주기 조회는 부하가 크고, 긴 주기는 VOIDED 반영이 늦다. 조회는 유실 복구용 배치로만 둔다. 4-1의 "제작 전이면 취소"는 거절을 빨리 알아야 효과가 있다(2026-11-02 P1이 조회만으로 갈지 물어 다시 검토함) |
| 웹훅 본문을 그대로 믿고 반영 | 위조·재전송·순서 역전을 모두 가맹점이 따로 막아야 한다. 서명 확인 뒤에도 조회로 확인하면 본문은 "다시 볼 때"라는 신호로만 쓰인다 |
| 웹훅 전용 키를 따로 발급 | 키 발급·교체·폐기 절차가 두 벌이 된다. 같은 키에 접두어로 용도를 나누면 서로 재사용할 수 없다 |
| 웹훅 서명을 payment가 직접 계산 | 가맹점 키는 identity 내부(`MerchantSecretService`)에 있다. payment가 키를 읽으면 모듈 경계(AGENTS.md 4절)를 깬다 |
| (#455) 재전송 한도 없이 계속 보내기 | 수신부가 없어지거나 주소가 틀린 세션을 5분마다 영원히 다시 보낸다. 웹훅을 놓쳐도 조회 배치가 맞추므로 계속 보낼 이유가 없다 |
| (#455) 첫 실패 시각 컬럼을 추가해 시간으로 한도 계산 | 재전송 간격이 고정이라 횟수로 환산해도 약 24시간으로 같다. 앱이 멈춰 있던 시간만큼 늦게 그만두지만, 그동안은 어차피 보내지 못했다 |
| (#455) 중단 표시 컬럼(예: `notify_gave_up_at`) 추가 | `notified_*`의 뜻(마지막으로 알린 값)을 그대로 지킬 수 있지만, 중단된 세션은 `notify_attempts`와 `next_notify_at`으로 이미 구분된다 |
| (#455) 컬럼 없이 실패 횟수를 상태와 관계없이 이어 세기 | 처음 구현(PR #457 첫 커밋)이 이랬다. 재시도 중 상태가 바뀌면 새 상태가 앞 상태의 실패를 이어받아 `VOIDED`처럼 빨리 알려야 하는 알림이 거의 재시도 없이 중단된다. 어느 상태를 재시도 중인지 DB에 없어 구분할 수 없으므로 `notify_event_id` 컬럼 하나를 더한다 |
| outbox 테이블로 이벤트마다 행 저장 | 세션당 결제가 하나라 "마지막으로 알린 값"만으로 충분하다. 행이 쌓이는 저장·정리 비용만 생긴다 |
| 결제창 API를 CSRF 검사 안에 두기 | 다른 사이트 iframe에서는 `SameSite=Lax` 쿠키가 오지 않아 CSRF를 켜면 결제가 막힌다. 쿠키 인증이 없는 경로라 CSRF가 지킬 대상도 없다 |
| 승인돼도 매입(CAPTURED)까지 CakeShop 결제 완료를 미루기 | HELD는 직원 판정까지 오래 걸려 구매자가 결제창에서 기다릴 수 없다. 승인은 끝났으므로 구매자에게는 완료로 보이고, 가맹점 오너에게만 "결제 확인 중"으로 알린다(4절, #492). 거절되면 웹훅으로 취소한다 |
| 승인 여부를 조회에 넣지 않고 웹훅 본문의 `authorized`만 쓰기 | 웹훅은 놓칠 수 있고 본문은 믿지 않기로 했다. 조회 배치로 복구할 때 승인된 `PENDING`과 평가 중 `PENDING`을 구분할 수 없다 |
| 승인 후 매입 대기를 나타내는 새 `PaymentStatus` 추가 | P2·P3·P6가 읽는 상태 계약이 모두 바뀐다. 가맹점 조회에 필드 하나를 더하는 것으로 충분하다 |

## 영향

- API: 새 가맹점 API `POST /api/payment-sessions`, 공개 API `/api/checkout/{sessionKey}` 3개, 가맹점에 보내는 웹훅. 모두 `payment.http.enabled=true`일 때만 켜진다. 기존 서명 조회 응답에 `authorized` 필드를 추가한다(3-1, 필드 추가만이라 기존 호출자 영향 없음). `POST /api/payments` 요청 계약은 바뀌지 않는다
- 모듈: identity가 `identity/api/MerchantWebhookSigner`를 새로 공개한다(P5 구현 · P1 리뷰, payment → identity 의존은 기존 허용 범위). `SecurityConfig`·`MerchantSecurityConfiguration` 경로 등록은 P5가 구현 PR에 넣고 P1이 리뷰한다(AGENTS.md 4절). 구매자 IP 조회를 위해 `identity/api/ClientIpResolver`를 새로 공개한다(기존 `LoginHistoryRequestMetadata`가 구현, P1 리뷰)
- 정산: 변경 없음. `VOIDED`는 매입이 없어 정산 행이 없고, 사후 거절 손실은 가맹점 부담이라 돈워리 부담분 지급은 하지 않는다(4-1, #492). 정산일은 매입일 기준 영업일 D+3(ADR-0068)
- DB: P5 migration 1개(`payment_sessions`)
- 화면: 돈워리 프론트 공개 화면 `/checkout/:sessionKey`. CakeShop 결제 화면의 모달·웹훅 수신·조회 배치, 4절 "결제 확인 중" 표시 · 확인 창 · 주문 상태는 CakeShop 저장소
- 테스트: 세션 생성·멱등·만료·같은 출처 검사, 조회 응답 `authorized`(승인 전·후 `PENDING`, HELD, DECLINED), 결제창 결제 중복 방지, 결과 주소, 웹훅 서명 고정 벡터(돈워리·CakeShop 같은 값), 재전송 간격 · 한도(#455), `HELD` → `VOIDED` · `HELD` → `CAPTURED` 웹훅(#492), CSRF를 켠 상태의 결제창 결제
- 문서: `docs/payment/`에 연동 안내, #154는 이 ADR로 결정 기록
- (2-1, #766) API: `GET /api/checkout/{sessionKey}` 응답에 `addableCard` 필드 추가, `cards`는 한 장. `POST`가 받는 카드 코드는 `A` · `N`(`B`는 새 접수에서 400). 가맹점 · FDS 계약은 바뀌지 않는다. DB 변경 없음. 화면은 결제창 [카드 추가]와 모의 등록 안내. CakeShop은 카드 코드 · 표시값을 쓰지 않아 바뀌지 않는다
