# 0035. 장기 보류 결제의 확인 기한과 금융 종료 분리

- **상태:** 제안 — #152 P1/CakeShop·P3·P5·P6 합의 전. 구현 착수·기간 수치 미확정
- **날짜:** 2026-10-26
- **관련:** [Issue #152](https://github.com/team-sweethan/DonWorry/issues/152), [ADR-0030](0030-cakeshop-payment-attempts.md), [ADR-0027](0027-payment-actions.md), [ADR-0012](0012-payment-settlement-dependency.md)
- **영향 받는 담당:** P1/CakeShop · P3 수민 · P5 시은 · P6 민정. 평가 오류 복구는 P2 정후 협의

## 배경

`dev 35585fe`에서 주문 생성 후 10분은 새 결제 시도 접수 기한이며 기존 시도 종료를 뜻하지 않는다. PENDING에는 평가 중단과 승인 후 매입 대기가 섞이고 HELD에도 직원 CAPTURE 대기가 포함된다. P6 완료가 P5보다 먼저 커밋될 수 있어 조회 상태나 경과 시간만으로 취소를 결정할 수 없다.

현재 직원 VOID는 HELD의 모의 취소이며 미승인 PENDING 종료·고객 취소·환불은 구현돼 있지 않다. P3 완료 기반 인계 방침과 실제 목업 연결도 구분해야 한다. 상세 근거는 [정책 초안 §2](../payment/152-long-held-payment-policy.md#2-현재-구현-근거)에 기록한다.

## 결정 제안

돈워리 내부 대응의 결정 후보·소유 범위는 [내부 대응 기준](../payment/152-internal-response.md)에 정리한다. P5는 내부 분류·최초 확인·자기 대응 목표·조회 요구·복구 확인 기준을 선택할 수 있다. P3의 판정/인계 대응과 P6의 실제 결과 확인·원래 전달 복구·확정 실패는 해당 담당 수락이 필요하다. 이 구분은 정책 채택이나 운영 기능 구현을 뜻하지 않는다. CakeShop 관련 합의는 별도 범위로 유지한다.

**시간 기준은 경고·담당자 확인과 인계에 사용하고, 실제 금융 결과를 근거로 종료한다.** 결제 상태·처리 단계·승인·직원 조치·P6 결과와 원래 전달 기록을 확인한 뒤 복구 또는 허용된 취소를 선택하는 방향을 제안한다. 담당자 수락 전 채택된 정책으로 사용하지 않는다.

- 결과 미확인·타임아웃·전달 지연으로 실패·취소·예약 해제를 확정하지 않는다. 새 키로 우회 결제하지 않는다.
- 매입 완료가 확인되면 완료 반영을 복구한다. 주문 이행 불가·고객 취소는 #153 취소·환불 계약과 연결한다. 환불 허용 조건·정산 완료 후 처리는 이 ADR에서 확정하지 않으며 ADR-0012의 기존 제약을 변경하지 않는다.
- 현재 직원 경로는 결제당 영속 조치로 반대 조치를 막는다. 미래 자동/고객 취소와 매입 발행 경합은 같은 통제 근거와 P6 계약을 함께 설계한다. 조회만 먼저 하고 취소하는 방식으로 해결됐다고 보지 않는다.
- 미승인 종료와 VOID 실패 해소, 예약 유지 불가 대응은 기능·절차 합의가 필요하다. 주문 만료에 EXPIRED를 사용하거나 직원 REJECT를 고객 취소로 재사용하지 않는다.
- 최대 보류·예약 유지 시간과 경고·대응·재시도 수치는 미정이다. 10분 접수 기한·24시간 P3 CAPTURE 경고·화면 5초 조회 제안을 자동 취소 기한으로 전용하지 않는다.
- 활성화 전에 발견·담당·인계·복구 수단과 예외 주문 대응을 확인하는 안을 제안한다. #149 인증·요청·조회 검증은 그대로 선행 작업이다.

시간 시작 기준·원인별 담당·경합 예시·활성화 조건은 [정책 초안](../payment/152-long-held-payment-policy.md), 수락 질문과 회신 관리는 [확인 문안](../payment/152-policy-confirmation.md)을 따른다. 기존 채택 ADR을 대체하거나 의존 방향을 바꾸지 않는다.

## 고려한 대안

| 대안 | 제외하는 이유 |
| --- | --- |
| 10분 또는 고정 시간 초과 즉시 자동 실패·취소 | 접수 기한과 금융 종료가 다르고 P6 실제 완료를 놓칠 수 있다 |
| 오래된 결제를 일괄 EXPIRED 처리 | 승인 만료 의미를 바꾸며 실제 만료 근거·전이 구현도 없다 |
| 주문 만료를 직원 REJECT/VOID로 재사용 | 고객 취소와 부정거래 판정 의미가 다르며 현재 PENDING·매입 중·CAPTURED에 적용할 수 없다 |
| 예약 한도 도달 즉시 해제하고 늦은 결과 무시 | 이미 매입된 주문의 이행·환불 문제를 숨기며 실제 금융 사실을 잃는다 |
| 무기한 대기와 조회만 유지 | 오류·전달 지연은 조회만으로 해결되지 않고 예약 유지 가능 범위도 확인되지 않았다 |
| 취소 직전 P6 조회만 추가 | 조회 이후 매입·정산 확정과 경합할 수 있다. 실행을 함께 통제하는 계약이 필요하다 |

## 영향

- API: 현재 계약 변경 없음. 향후 원인별 운영 조회·미승인 종료·고객 취소·환불·P6 결과 확인 계약은 소유 담당 합의 후 별도 구현한다. 타 모듈 내부 참조 없이 api/ 경계를 사용한다.
- DB: 이번 스키마 변경 없음. 시간 추적·취소 경합·복구의 영속 근거가 필요하면 소유 담당·ERD 합의와 Flyway 변경을 후속 이슈에서 다룬다. 컬럼·테이블을 미리 확정하지 않는다.
- 화면: 합의 후 판정 대기·금융 대기·결과 미확인·확정 실패와 담당자 확인을 구분한다. CakeShop 예약/이행과 P3 Case는 각 담당 소유이며 이번 구현 없음.
- 테스트: 응답 유실·시간 경계·CAPTURE/VOID 경합·늦은 완료·재전달·부분 실패 검증이 필요하다. [검증 계획](../payment/152-long-held-payment-policy.md#8-합의-후-검증-계획) 참조.
- 문서: P5 README·#149 설계에서 초안을 연결한다. 담당 회신과 필요한 구현 이슈를 연결한 뒤 채택 여부를 판단한다. #153·#154는 별도 계약 범위를 유지한다.

## 검증

현재 코드와 문서를 대조한 제안이다. 이번 변경은 Markdown 문서뿐이며 backend·MariaDB 실행 검사는 해당 없음이다. 문서 검사 명령·결과는 변경 보고에 기록한다. 정책 동작·P3 운영 연결·CakeShop E2E·Notion 최신 내용은 미검증이다. 문서 작성으로 #152 합의·구현·통합 검증 완료를 표시하지 않는다.
