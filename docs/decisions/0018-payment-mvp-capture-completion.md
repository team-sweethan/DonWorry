# 0018. 1차 CAPTURE 완료 통지로 영속 접수 확인

- **상태:** 대체됨 (→ [ADR-0027](0027-payment-actions.md)) — #158 P3 검토 의견 반영
- **날짜:** 2026-10-23
- **관련:** Issue #104, [ADR-0012](0012-payment-settlement-dependency.md), [ADR-0010](0010-payment-operation-storage.md)
- **영향 받는 담당:** P3·P5·P6, CakeShop 결과 연계 담당

2026-10-26 #158에 따라 ADR-0027로 대체한다. 아래 본문은 당시 제안과 미검증 범위를 보존한 기록이다. 현재 직원 조치 계약은 ADR-0027을 따르며, acceptedAt은 P3 결과 반영 시각이고 completedAt은 별도 이력으로 남긴다. CAPTURE 확정 실패는 P5·P6 후속 협의 대상으로, 도입 시점은 미정이다. 이 상태 변경이 ADR-0027의 팀 채택이나 전체 연동 검증 완료를 뜻하지 않는다.

## 배경

P6 담당 ERD는 PROCESSING 선행 커밋 없이 요청 수신 후 즉시 매입·정산 예정금을 저장하는 1차 구조다. 담당자는 두 저장을 한 트랜잭션으로 구현했으며 이벤트 연동은 구현 전이라고 전달했다. 해당 작업 코드는 이 문서 작업에서 검증하지 않았다.
기존 P5 문서는 미합의 보조 테이블 3개와 별도 접수·실행 결과·시도 번호를 함께 요구하는 형태라 1차 필수 계약으로 오해하기 쉽다.
FDS 정본과 ADR-0012는 영속 접수 결과와 실제 실행 결과를 구분한다. 이번 안은 단순 필드 정리가 아니라 CAPTURE 인계 확인 시점을 변경하는 제안이다.

## 결정 제안

1. P6의 매입 COMPLETED·정산 SCHEDULED 저장과 완료 이벤트 발행 기록을 한 트랜잭션으로 남기고 커밋 후 전달한다. 별도 접수 커밋·접수 이벤트는 1차 CAPTURE 경로에서 생략한다.
2. 완료 업무 필드는 `paymentId`, `captureId`, `capturedAt`을 사용한다. 별도 작업 ID·외부 결과값·시도별 UNKNOWN 프로토콜은 요구하지 않는다. 전달 메타데이터는 공통 계약으로 정한다.
3. P5는 적법한 요청과 완료 결과를 대조해 CAPTURED와 후속 통지 발행 기록을 함께 저장한다. 직원 ACCEPT 건은 커밋 후 P3에 인계 완료를 통지한다.
4. P3의 `target_operation_id = captureId`, `accepted_at = capturedAt` 매핑을 제안한다. 완료 시각을 접수 증거의 시각으로 사용하는 것이며 커밋 시각·수신 시각과 구분한다.
5. 실패·중복·재전달·반대 조치 차단은 유지한다. 실패 기록과 P3 REQUESTED/FAILED 기준·재시도 주체는 합의 후 구현한다.

접수와 실행은 여전히 다른 업무 의미다. 이번 안은 성공 기록 하나로 두 사실을 확인하는 방식이며, 완료가 확인되기 전에는 CAPTURE 인계가 ACCEPTED가 되지 않는다.

## 고려한 대안

| 대안 | 이번 제안에서 선택하지 않은 이유 |
| --- | --- |
| 별도 접수 저장·이벤트 유지 | 실행 전 Case 종료에 유리하지만 P6의 선행 커밋 없는 1차 흐름에 접수·실행 분리와 실패 복구를 추가해야 함 |
| 같은 커밋에서 접수·완료 이벤트 각각 발행 | 성공 시 두 이벤트가 같은 저장을 근거로 하면서 중복·순서 처리만 늘어남. 실패 시 접수 근거 문제는 별도로 남음 |
| paymentId만 완료 통지 | P5 상태 변경에는 사용할 수 있으나 P3 대상 작업 ID·시각과 매입 기록 추적을 위해 기존 captureId·capturedAt을 함께 제안 |
| P5 발행만으로 P3 인계 완료 | P6가 저장하지 못한 경우도 인계 완료가 되어 영속 접수 확인을 충족하지 못함 |

## 영향과 한계

- API: `payment → settlement`, 이벤트 타입 `settlement.api`는 유지. P5→P3는 `payment.api`. 요청 입력·수수료·판정 상관관계·완료 메타데이터는 별도 합의 필요.
- DB: 이 PR은 스키마를 바꾸지 않는다. 기존 P6 PK·시각과 P3 인계 컬럼을 활용하는 안이다. P5 요청 상관관계·실패 이력·동시성 근거가 현 ERD로 충분한지는 구현 전에 확인한다.
- 화면·업무: CAPTURE 완료 확인 전 Case가 열린 상태로 남는다. 기존 실행 전 종료 정책과 달라진다. ALLOW는 P3 인계 대상이 아니다. VOID 접수 시점은 변경하지 않는다.
- 테스트: 동시 저장 원자성, 커밋 후 통지·재전달, P5 반영과 후속 통지 원자성, P3 매핑·종료 조건, 충돌·권한을 [검증 계획](../payment/verification.md)대로 확인한다. 전부 현재 미검증이다.
- 문서: [설계](../payment/design.md)와 [문서 대조 현황](../README.md)에 기존 정책과의 차이를 명시한다. 채택된 ADR-0012 본문·상태는 이 제안만으로 변경하지 않는다.

최신 dev `d9e4251`에 병합된 P3 목 연동은 즉시 접수 응답을 사용하고 HandoffService는 현재 시각으로 accepted_at을 기록한다. capturedAt을 전달·반영하려면 P3 계약·테스트 변경이 필요하다. 이 PR은 해당 코드를 바꾸지 않는다.

## 채택 전 확인

- P3·P6가 완료 기반 접수 확인과 Case 종료 지연을 수용하는가?
- captureId·capturedAt 매핑과 P5→P3 판정/인계 상관관계는 무엇인가?
- 저장 실패·영구 거절·응답 유실의 구분, REQUESTED/FAILED 정책과 재시도 책임은 무엇인가?
- VOID 접수 증거·작업 ID, 요청 수수료 입력, 이벤트 재발행·멱등성은 어떤 계약으로 구현하는가?

합의되면 이 ADR의 채택 범위와 ADR-0012의 접수 프로토콜 대체 관계를 명시하고 관련 Notion을 동기화한다. 그 전에는 문서 초안 병합만으로 기존 계약이 변경됐다고 간주하지 않는다.
