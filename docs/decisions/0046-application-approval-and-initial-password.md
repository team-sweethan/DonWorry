# 0046. 이용 신청 승인 원자성과 첫 비밀번호 설정

- **상태:** 제안 — P1 사용자 설계·구현 승인, PR 리뷰 대상
- **날짜:** 2026-10-29
- **관련:** #315 PR 3, ADR-0024·0028·0043~0045
- **영향 받는 담당:** P1. 다른 담당 API·금융 테이블·모듈 의존 변경 없음.

## 결정

신청 승인과 가맹점·계정·권한·관리 이력·72시간 첫 설정 토큰·발송 시도 저장을 한 트랜잭션으로 수행한다. 기존 생성 검증·이력은 MANDATORY 내부 서비스로 추출해 수동 생성과 공유한다. 신청 행 잠금으로 승인·반려의 중복 처리를 차단한다.
2026-10-29 P1 사용자의 후속 승인으로 로그인 아이디를 관리자 입력에서 신청자 선택으로 변경한다. 신청 시 선택한 아이디를 저장·예약하고 승인에는 그 값만 사용한다. 수동 계정 생성도 예약을 확인하며, 기존 NULL 신청은 임의 발급 없이 반려·재신청으로 안내한다. 비밀번호는 승인 후 본인이 설정한다.
SMTP는 커밋 후 잠금 밖에서 수행하고 실패해도 승인·발급을 유지한다. 첫 설정은 정확한 공개 POST와 CSRF로 처리하며 fragment 토큰을 페이지에서 제거한다.
첫 비밀번호 설정과 관리자 초기화는 기존 계정 잠금을 공유한다. 초기화의 해시 변경과 첫 설정 토큰 폐기를 같은 커밋에 넣는다.
상세 HTTP·잠금 순서·화면·오류·검증 계약은 [설계](../identity/315-approval-design.md)를 따른다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 관리자가 로그인 아이디까지 지정 | 신청자가 사용할 계정 정보를 직접 정할 수 없다는 사용자 피드백에 따라 변경한다 |
| 신청 단계에서 비밀번호도 수집 | 승인 후 본인 설정 흐름을 유지해 미승인 신청에 비밀번호 해시를 보관하지 않는다 |
| 예약 없이 희망 아이디만 저장 | 신청 후 수동 생성/다른 승인에 의해 선점되어 재선택용 별도 절차가 필요해진다 |
| 기존 아이디 없는 신청에 자동 아이디 부여 | 신청자가 직접 선택한다는 새 계약을 어긴다 |
| 기존 두 생성 API 연속 호출 | 각각 독립 커밋해 가맹점만 남는 부분 발급이 가능하다 |
| 승인 후 계정 발급을 비동기 처리 | 별도 중간 상태·복구 프로토콜이 필요하며 이번 원자적 발급 요구를 늘린다 |
| 메일 실패 시 승인 롤백 | 이미 발송한 메일은 회수할 수 없고 SMTP 결과와 계정 저장 결과를 혼동한다 |
| 임시 비밀번호를 승인 메일로 전달 | 비밀번호 원문 메일 발송을 금지한 #315와 충돌한다 |
| GET 링크 방문 시 비밀번호 설정 확정 | 메일 미리보기·보안 스캐너가 일회용 토큰을 소비할 수 있다 |
| 초기화 커밋 뒤 별도로 토큰 폐기 | 중간 실패/경쟁에서 옛 링크로 초기화 비밀번호를 덮어쓸 수 있다 |
| 사업자번호 중복 승인 자동 차단 | 기존 가맹점 중복은 관리자 판단이라는 #315 합의를 바꾼다 |

## 영향과 검증

- DB: P1 merchant_applications의 requested_login_id·진행 중 예약 생성 컬럼·UNIQUE를 새 migration으로 추가한다. 기존 migration은 보존한다.
- API·화면: ADMIN 목록·상세·승인·반려, 공개 첫 설정 POST·화면, 관리자 홈/메뉴 진입.
- 기존 기능: 관리자 수동 생성과 초기화 회귀 검사. 기존 일반 비밀번호 변경·인가 정책 유지.
- 테스트: 실제 MariaDB 동시성·원자성·토큰·인가, Mailpit SMTP, 프론트 계약과 브라우저 검증.
- Gmail 실제 수신과 운영 배포는 별도 검증이며 이 문서 자체는 통과 근거가 아니다.
