# 0058. CAPTURED 전액 환불과 P6 성공 전달

- **상태:** 제안 — 사용자 전달로 P6 성공 전달 방향 확인, P5 모의 실행 기반 구현. 2026-11-06 운영 발행 어댑터·환불 성공 재전달 추가(플래그 기본 꺼짐, 재전달 방식은 P6 확인 대기). 실제 연동 검증 후속
- **날짜:** 2026-10-31
- **관련:** #383, #233, #153, [ADR-0054](0054-full-cancellation-policy.md), [ADR-0056](0056-cancellation-request-contract.md)
- **영향 담당:** P5, P6, P1/CakeShop. 상태 소비 화면·조사 조회 영향 확인 필요

## 배경

공통 취소 저장은 REFUND와 매입 ID를 지원하지만 환불 실행과 P6 성공 수신은 없다. 정산 완료 후 환불도 허용하므로 성공 당시 관측한 정산 상태만으로 처리 경로를 결정할 수 없다. 고객 전액과 정산 차감액도 구별해야 한다.

## 결정 제안

1. 고객 환불 원본은 P5 기존 취소 작업에 저장한다. CAPTURED는 매입 사실로 보존하고 REFUND/SUCCEEDED로 환불 성공을 표현하는 안을 추천한다. 새 결제 상태 도입은 아직 결정하지 않는다.
2. `settlement.api.PaymentRefundSucceeded`에 cancellationId/paymentId/captureId/merchantId/cancellationAmount/canceledAt을 전달한다. 성공 저장과 발행 기록을 원자적으로 확정하고 P6는 커밋 후 수신한다. 시작·실패·미확정은 성공 통지로 보내지 않는다.
3. P6는 자기 매입/정산 원본과 대조하고 cancellationId의 영속 중복 방지와 정산 변경을 같은 트랜잭션으로 처리한다. 전액 1회 범위의 상충 결과도 검출한다.
4. 정산 전 지급 제외 또는 완료 후 차감 중 하나만 적용되도록 P6 배치와 잠금 규칙을 맞춘다. 수수료와 정산 차감 계산식·이월 저장은 P6 확인 사항이다.
5. P6 전달 실패를 P5 환불 실패로 바꾸지 않는다. 동일한 성공 결과를 재전달하며 금융 실행을 반복하지 않는다. 실제 수신/재전달 검증 전에는 NOT_READY를 유지한다.

필드·실패 처리·상태 소비자 영향과 확인문은 [#383 7~9절](../payment/383-captured-refund.md#7-p5--p6-성공-전달-계약-제안-2단계)을 따른다. 이 제안은 사용자/P6 합의를 대신하지 않는다.

## 고려한 대안

| 대안 | 우선안으로 채택하지 않은 이유 |
| --- | --- |
| 환불 후 결제를 VOIDED로 변경 | 매입 전 승인 취소와 매입 후 환불의 의미가 다름 |
| 즉시 REFUNDED 상태 추가 | 표현은 명확하나 모든 상태 소비자·기존 직원 결과/조회 계약을 함께 변경해야 함 |
| P5에서 P6 정산 상태를 보고 차감 경로 지정 | 읽은 뒤 배치가 완료될 수 있어 실제 반영 시점과 다름 |
| P6 동기 반영이 실패하면 환불도 실패로 반환 | 이미 확정된 금융 성공과 정산 전달 실패가 섞임 |
| P6 전달 재시도 때 환불 재실행 | 중복 금융 실행 위험 |
| 이벤트 타입을 payment.api에 배치 | settlement → payment 의존이 추가되어 기존 방향과 순환 |
| P5에서 차감액 계산/정산 테이블 수정 | P6 소유 수수료·정산 정책과 저장 경계를 침범 |

## 영향

- API: 신규 성공 이벤트 제안. 고객 HTTP는 기존 취소 결과 계약을 재사용하되 결제 CAPTURED만으로 환불을 판단하지 않도록 소비자를 확인한다.
- DB: P5 기존 REFUND 작업 재사용. 새 P5 migration 필요성을 아직 확인하지 않았으며 P6 멱등 수신·차감 저장 설계는 담당 소유다. 이번 DB 변경 없음.
- 화면: CakeShop 주문 취소와 운영 조회가 환불 작업을 구별해야 한다. 실제 화면 변경은 이번에 수행하지 않는다.
- 테스트: 성공/거절/오류·원자성·중복 요청·전달 재시도·정산 배치 경합·차감 이월을 검증해야 한다. 대역과 실제 P6 연결을 구별한다.
- 의존: 기존 payment → settlement 유지, allowedDependencies 변경 없음.

## 검증

`dev 2053542` 코드와 관련 이슈를 대조한 문서 제안이다. 문서 링크·공백 검사만 수행하며 실행/DB/실제 P6 수신은 미구현·미검증이다. 담당자에게 전달하거나 합의를 받은 단계가 아니다.

## 담당 확인과 구현 진행

사용자가 민정님의 긍정 회신을 전달했다. 6개 성공 필드·중복 반영 방지·성공 결과 재전달 방향을 확인한 것으로 기록하며, 상세 수수료/차감 계산식이나 운영 복구 담당 확정으로 확대하지 않는다. 후속 작업 요청으로 CAPTURED 보존·기존 REFUND 결과 표현을 사용한 모의 실행 기반과 성공 이벤트를 구현한다. 실제 P6 수신/운영 발행 어댑터는 추가하지 않는다. [#383 11절](../payment/383-captured-refund.md#11-p5-모의-전액-환불-기반-구현)에 구현과 검증 범위를 기록한다.

## 운영 발행과 환불 성공 재전달 (2026-11-06)

P6 회신(수신·지급 전 제외·지급 후 회수 반영 완료, P5 운영 어댑터만 남음)에 따라 P5 운영 발행을 추가한다. 상세는 [#383 13절](../payment/383-captured-refund.md#13-운영-발행-어댑터와-환불-성공-재전달).

- `payment.refund-completion.enabled=true`일 때만 `PaymentRefundCompletion` 운영 Bean을 등록한다. 기본은 꺼짐이라 기존 NOT_READY가 유지된다.
- P6 수신이 실패해 `FAILED`로 남은 `PaymentRefundSucceeded` 발행만 P5가 주기적으로 다시 보낸다(기본 5분, 시도 10회 상한). 환불 실행기는 다시 부르지 않는다(결정 5번).
- 켜는 순서: P6 `settlement.refund-receiving.enabled`를 먼저 또는 같은 배포에서 켠다. 리스너가 꺼진 동안 발행하면 P6용 발행 기록이 남지 않는다.

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 재전달 없이 발행만 등록 | P6 저장이 한 번 실패하면 누군가 다시 보내기 전까지 환불이 정산에 반영되지 않는다. 운영자 재전달 수단도 아직 없다 |
| 앱 시작 시 미완료 발행 전체 재발행(`republish-outstanding-events-on-restart`) | 모든 모듈 이벤트에 영향을 주는 공통 설정이며 아직 정하지 않은 정책이다(modulith 04). 재시작 전까지 복구되지 않는다 |
| 모든 이벤트를 주기적으로 재전달 | 다른 담당 리스너의 멱등·순서 전제를 확인하지 않았다 |
| `PROCESSING`까지 재전달 | 처리 중인 전달과 겹쳐 실행될 수 있다. 멈춘 것인지 판단할 기준이 없다 |
| 시도 횟수 상한 없이 반복 | P6가 영구적으로 거부하는 결과(대조 불일치 등)를 끝없이 반복하며 로그만 쌓인다 |
| P6가 재전달 담당 | 발행 기록은 P5 트랜잭션이 만든 것이고, P6 문서도 자동 재시도는 범위 밖으로 두었다 |

영향: API·DB·화면 변경 없음. 새 설정 3개(P5 플래그·간격·상한)와 배포 시 P6 플래그 2개를 함께 켜야 한다. 의존 방향(payment → settlement.api)은 그대로다.
