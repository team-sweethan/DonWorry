# 0036. P2 FDS 오류 분석·재탐지 계약

- **상태:** 전체 계약 제안 — 내부 ERROR 정책 및 명시적 실행 주체·권한·진입점 합의 완료, P5 저장·API 및 잠금·전달 복구·CSRF 설계 사용자 승인·문서화, 구현·통합 검증 전
- **날짜:** 2026-10-27
- **정책 합의 기록일:** 2026-10-28
- **관련:** #152, #190, #218, [ADR-0012](0012-payment-settlement-dependency.md), [ADR-0035](0035-long-held-payment-policy.md)
- **영향 받는 담당:** P1 주환 (직원 권한·CSRF) · P2 정후 · P5 시은

## 배경

P5가 FDS 평가를 동기 호출한 뒤 P2 내부 시스템 오류의 `ERROR`를 받아 결제를 대기시키는 경우가 있다. P2가 P5의 결제 요청 내부를 직접 읽지 않고, 저장된 ERROR 평가와 오류 조사에 필요한 스냅샷을 공개 계약으로 받아야 한다.

기존 `FdsEvaluator.evaluate`는 같은 `evaluationRequestId`의 평가 결과를 반환하는 최초 탐지 계약이다. 이 계약을 바꾸면 기존 P5 호출자에 영향을 주며, 같은 UUID 재호출은 새 평가가 아니다.

## 정책 합의 근거와 범위

사용자가 P2 제공 문서를 전달한 뒤 아래 6개 항목의 제안을 P2에게 확인했고, 이 대화에서 "P2가 이 기준으로 진행해도 좋다고 답변이 왔어"라고 알렸다. 이 사용자 전달을 P2 동의 근거로 기록한다. P2의 원문 회신이나 별도 메신저를 직접 확인한 것으로 표현하지 않는다.

이후 사용자가 단순화한 명시적 실행 방식을 선택하고 "P1과 P2도 동의했어"라고 전달했다. 아래 실행 주체·권한·진입점 추가 합의도 이 사용자 전달을 근거로 기록하며, P1·P2의 원문 회신을 직접 확인한 것으로 표현하지 않는다.

이번 합의는 실제 내부 시스템 `ERROR` 응답 이후의 정책과 명시적 실행 방식에 한정한다. #190의 응답 유실·기존 UUID 결과 복원 설계 전체나 신규 저장 구조를 확정한 것은 아니다. 정책 합의와 코드 구현·실행 검증은 별도로 기록한다.

| 번호 | 합의 항목 | 내용 |
| --- | --- | --- |
| 1 | 적용 범위 | P2가 실제 `ERROR`를 반환한 내부 시스템 오류만 처리한다. 타임아웃·통신 오류는 이번 계약·구현 범위에서 제외한다. |
| 2 | 시각·횟수 | P5가 FDS 호출 시각 `requestedAt`과 응답 수신 시각 `respondedAt`을 기록한다. `evaluationAttemptNo`는 최초 평가 1, 새 UUID 재탐지 2로 센다. 같은 요청의 재전송은 횟수를 올리지 않는다. |
| 3 | 재탐지 가능의 의미 | `REEVALUATION_AVAILABLE`은 "재탐지를 시도해도 됨"이며 장애 복구 완료를 보장하지 않는다. 현재 P2의 `TRANSIENT_` 오류 코드 판별과 실제 복구 확인을 혼동하지 않는다. |
| 4 | 실행 방식 | 자동 실행 없이, 보안 직원의 명시적 실행 요청으로 최초 ERROR당 새 평가 1회만 허용한다. P5가 현재 결제 상태를 확인한 뒤 실행한다. 이벤트 수신 자체는 실행 승인이 아니다. |
| 5 | 재탐지도 ERROR | 추가 재탐지 없이 `NEEDS_REVIEW`를 유지하고 수동검토로 넘긴다. `NEEDS_REVIEW`는 요청 처리 단계이며, 오류만으로 결제를 승인·거절·취소하지 않는다. |
| 6 | 중복 방지 | 같은 작업을 재전송할 때는 `failureReportId`, 새 평가 UUID, `retryId`와 원래 평가 입력값을 유지한다. 재전송마다 새 작업 ID를 발급하지 않는다. |

시각은 호출·수신 관측값이며 결제 생성 시각이나 P2 평가 완료 시각으로 대체하지 않는다. 현재 P5가 수집·보존하지 않은 값은 있다고 가정하지 않으며, 미수집된 과거 건의 처리 방법은 후속 설계에서 정한다. 결제 시도 `attemptNo`와 평가 횟수 `evaluationAttemptNo`도 구분한다.

## 명시적 실행 방식 추가 합의 (2026-10-28)

| 항목 | 합의 내용 |
| --- | --- |
| 실행 주체·권한 | 직원 로그인 세션의 `SECURITY_STAFF`만 실행한다. `ADMIN`의 기존 운영 조회 권한은 실행 권한으로 확대하지 않는다. `OPERATOR`·CakeShop·AI 서버에는 실행 권한을 부여하지 않는다. |
| 진입점 | P5의 `POST /api/payment-operations/{paymentId}/fds-reevaluations`로 접수한다. 경로의 결제 ID만 업무 입력으로 받고, 별도 요청 본문·분석 ID·실행 사유·클라이언트 멱등키는 요구하지 않는다. 세션 인증과 CSRF 토큰은 별도로 필요하다. |
| 서버 확인 | P5가 현재 결제의 ERROR와 해당 평가에 연결된 `REEVALUATION_AVAILABLE` 분석 결과를 확인한다. 원래 평가 입력과 실행자 식별자는 서버에서 확보하며 요청자가 덮어쓰지 않는다. |
| 실행·중복 처리 | 최초 ERROR당 재탐지 작업을 하나만 만든다. 중복 요청은 기존 작업을 반환하며 새 평가를 추가로 실행하지 않는다. P5가 새 평가 UUID·`retryId`를 생성·보존하고 같은 작업 재전송에 재사용한다. |
| 반복 ERROR | 재탐지도 ERROR이면 `NEEDS_REVIEW`를 유지하고 추가 실행을 차단한다. 수동검토 상세 절차는 후속이다. |
| 화면 | 첫 구현에는 별도 화면을 만들지 않는다. 직원 로그인 세션으로 같은 API를 호출해 검증하고, 화면은 후속으로 연결한다. P2 개발용 Mock API를 직원 실행 진입점으로 사용하지 않는다. |
| 필수 보호·기록 | 서버 권한·CSRF 검사와 실행자·작업 기록, 중복 실행 방지를 포함한다. 화면이나 클라이언트 멱등키가 없다는 이유로 생략하지 않는다. |

담당 경계는 P1의 직원 권한·CSRF 연결, P2의 기존 분석·재탐지 계약 확인, P5의 실행 접수·상태 검사·작업 저장·P2 호출·결과 반영이다. P5는 `identity.api.CurrentStaff` 등 공개 경계를 사용하고 다른 모듈 내부 클래스를 참조하지 않는다.

현재 운영 조회 보호는 GET·HEAD 경로에 적용되며 POST는 아직 없다. 새 POST 구현 시 같은 변경에서 해당 경로의 서버 권한과 CSRF 보호를 연결하고 검증해야 한다. 현재 `security.csrf.enabled` 기본값은 false이므로 기존 설정만으로 새 POST가 보호된다고 가정하지 않는다. 아래 추가 설계에 따라 두 직원 POST만 항상 CSRF를 검사하고 다른 경로의 기존 설정은 유지한다. P1과 matcher·필터 동작을 구현 검토하며 전체 API 설정을 이번 문서로 변경하지 않는다.

## P5 저장·응답 계약 문서화 (2026-10-28)

사용자가 단일 복구 테이블을 사용하는 설계안을 선택하고 코드·DB 변경 없이 문서화하도록 요청했다. 상세는 [#190 P5 FDS 복구 저장·API 계약](../payment/190-fds-recovery-contract.md)을 따른다. 기존 실행 정책의 P1·P2 동의가 이번 상세 스키마 전체에 대한 담당 확인을 의미하지는 않는다.

- P5 신규 `payment_fds_recoveries` 한 행에 원본 ERROR·보고·분석·명시적 실행 작업을 보존한다. 기존 `payments`는 결제 정본, `payment_requests`는 현재 적용 평가·단계로 유지한다.
- 기존 `recordEvaluation`의 보호를 풀지 않고, 복구 작업과 일치하는 새 결과만 적용하는 별도 전이를 설계한다. 정상 결과 적용·모의 승인·작업 종료의 원자성과 동일 키 재개를 검증한다.
- 상태는 WAITING_ANALYSIS / READY / REQUESTED / COMPLETED / MANUAL_REVIEW다. 중복 POST는 기존 작업을 확인하며 새 키를 발급하지 않는다. 완료는 금융 성공과 구분한다.
- 응답은 복구 상태·재탐지 결과·현재 결제 상태를 구분한다. 오류는 ProblemDetail + code, 중복 요청은 행 잠금 대기 후 기존 결과 반환/동일 작업 재개, 정상 결과 기록은 200, 실행 불가 409, 기술 장애 503/500으로 구분한다.
- 대안: 보고·분석·작업별 여러 테이블 대신 한 행을 사용한다. 원본 ERROR 없이 현재 평가만 덮어쓰거나, 기존 요청을 영구 ERROR로 두고 모든 조회·승인에 예외를 만드는 방식은 피한다.
- 현재 같은 DB의 P2와 P5 모의 승인을 하나의 실행 트랜잭션에 포함하는 설계다. 실제 외부 승인으로 바뀌면 외부 효과와 DB 롤백을 함께 취소할 수 없으므로 재설계한다.

이 단계에서는 SQL·Entity·Controller·보안 설정을 변경하지 않는다. 잠금·전달 복구·CSRF 방향은 아래 추가 설계로 구체화하며, 담당 ERD 확인·상세 구현 검토·수동검토 절차는 후속이다.

## 잠금·전달 복구·CSRF 추가 설계 (2026-10-28)

사용자가 202 제외·전달 복구 POST 추가·CSRF 적용안을 선택하고 최신 dev에서 문서화하도록 요청했다. 이는 이번 상세 변경에 대한 사용자 승인이다. 기존 P1·P2 동의 기록을 이 추가 API와 세부 구현까지 별도 확인받은 것으로 확대하지 않는다. 상세 상태·오류·복구 절차는 [P5 계약](../payment/190-fds-recovery-contract.md)에 기록한다.

- 기존 PESSIMISTIC_WRITE로 payments → payment_requests → 복구 행 순서로 잠그고, 뒤 요청은 유한 대기 후 상태를 다시 확인한다. 완료 작업은 기존 결과 반환, 롤백된 작업은 동일 키로 재개한다. 대기 초과·데드락은 롤백 후 503이다. 202와 별도 실행 중 판별 상태를 제외한다.
- `POST /api/payment-operations/{paymentId}/fds-recovery-deliveries`를 추가한다. 보안 직원이 같은 failureReportId로 오류 보고를 재전달하고, 해당 보고·이벤트 타입·P5 리스너의 실패/중단된 기존 분석 이벤트 전달만 복구한다. 새 평가·승인·새 작업 키를 만들지 않는다.
- P2의 동일 보고 재호출은 이벤트를 재발행하지 않으므로 보고 재전달과 분석 이벤트 재전달을 구분한다. 현재 처리 중·완료·무관한 기록은 제외하며, 분석과 P5 기록이 불일치해 복구할 기록이 없으면 수동 확인 대상으로 남긴다. 범용 이벤트 복구 #191로 확대하지 않는다.
- 전달 복구는 현재 요약을 200으로 반환하며 WAITING_ANALYSIS이면 전달 완료를 뜻하지 않는다. GET으로 확인하고 READY 이후 재탐지 POST를 별도로 실행한다. 자동 배치·큐를 추가하지 않는다.
- 기존 SecurityConfig·쿠키 토큰 저장소를 사용해 재탐지/전달 복구 두 POST만 전역 CSRF 설정과 무관하게 항상 검사한다. 다른 요청은 기존 CSRF 설정을 따른다. 두 POST는 SECURITY_STAFF 세션 권한을 적용하며 ADMIN 조회 권한을 확대하지 않는다.
- 로그인 후 기존 `/api/auth/csrf`로 토큰을 확보한다. CSRF 실패는 기존 CSRF_001, 역할 불허는 AUTH_002를 사용한다. 복수 보안 실패는 필터 순서에 따라 CSRF 403이 먼저 발생할 수 있다.

유한 잠금 대기의 설정·값, 이벤트 리스너/상태의 안전한 선별과 중단 판별, P1의 matcher·필터 적용은 구현 시 확인·검증한다. 해당 경계가 확인되지 않은 상태에서 무조건 이벤트를 재전달하거나 운영 복구 완료로 표시하지 않는다.

## 결정

- 기존 `fds.api.FdsEvaluator.evaluate(FdsEvaluationRequest)`는 변경하지 않는다.
- P5는 P2 내부 시스템 오류의 `ERROR`를 `FdsFailureReporter.report(FdsEvaluationFailureReport)`로 P2에 보고한다. 보고에는 `failureReportId`, 원본/현재 평가 UUID, 저장된 평가 ID·오류 코드, 원래 평가 입력, P5 관측 시각·상태 스냅샷을 포함한다.
- P2는 `fds_failure_analyses`에 보고와 분석 결과를 저장한다. P5 소유 ID는 논리 참조이며 FK를 만들지 않는다.
- 분석 저장 후 P2는 `fds.api.FdsEvaluationFailureAnalyzed` 이벤트를 발행한다. 이벤트 타입은 P5가 import 가능한 `fds.api`에 둔다.
- P2가 실제 `ERROR` 평가와 재탐지 허용 근거를 확인해 `REEVALUATION_AVAILABLE`를 발행한 경우에만 재탐지 후보가 된다. P5는 위 정책에 따른 명시적 실행 요청과 현재 결제 상태를 확인한 뒤 `FdsReevaluationRequester.reevaluate(FdsReevaluationRequest)`를 호출한다. 이 분석 결과는 장애 복구 완료나 자동 실행 승인을 뜻하지 않는다.
- 재탐지 요청은 원본 UUID와 새 UUID, `retryId`를 함께 전달한다. P2는 새 평가를 `fds_evaluations`에 저장하고 원본 UUID·재탐지 키를 연결한다.
- P2는 오류 보고의 평가 ID·원본 UUID 계보를 저장된 평가와 대조한다. 재탐지는 원본 ERROR 평가 행을 잠가 같은 원본 평가의 동시 요청을 직렬화하고, 이미 사용된 새 평가 UUID는 거절한다.
- 같은 `retryId` 재전송은 원본 UUID·새 UUID뿐 아니라 평가 입력 스냅샷도 같을 때만 기존 결과를 반환한다.
- P2는 P5 결제 상태를 변경하지 않으며, 분석 이벤트도 재탐지를 강제하지 않는다.

| 최초 탐지 API에 오류 분석 필드를 추가 | 정상 최초 탐지와 사후 오류 분석의 책임이 섞이고 기존 호출자 계약이 바뀐다. |
| 같은 평가 UUID로 최초 탐지 API를 재호출 | 기존 저장 결과를 반환하는 멱등 호출이므로 새 평가가 실행되지 않는다. |
| P2가 P5 테이블을 직접 조회 | 모듈 경계를 위반한다. |
| P2가 오류만으로 결제를 자동 취소·거절 | 평가 오류는 금융·결제 종료 근거가 아니다. |
| 분석 이벤트 수신 즉시 자동 재탐지 | 보안 직원이 현재 상태를 확인해 명시적으로 실행하도록 합의했으므로 이벤트만으로 실행하지 않는다. |
| 재탐지도 ERROR이면 계속 재탐지 | 최초 연동의 실행 범위를 최초 ERROR당 1회로 제한하고, 반복 오류는 수동검토로 처리한다. |
| 재전송마다 새 평가 UUID·`retryId` 발급 | 같은 작업이 여러 평가로 실행될 수 있어 작업 식별자를 보존한다. |
| 전용 화면·실행 사유·클라이언트 멱등키를 먼저 도입 | 첫 구현은 결제 ID와 서버의 원본 ERROR 기준 중복 방지로 단순화한다. 권한·CSRF·실행자와 작업 기록은 유지한다. |
| ADMIN 조회 권한으로 재탐지도 허용 | 조회와 실행 권한을 분리하고 명시적 실행은 보안 직원으로 제한한다. |
| 잠금 경합을 별도로 판별해 202 반환 | 기존 잠금 대기 후 재조회·기존 결과 반환으로 단순화하고 대기 초과·데드락은 503으로 구분한다. |
| 재탐지 POST나 조회 GET에서 전달 복구도 수행 | 전달 복구와 평가 실행을 구분하기 위해 직원 전달 복구 POST를 별도로 둔다. |
| 전체 API의 CSRF를 동시에 활성화 | 기존 단계적 적용 범위를 유지하고 두 POST에만 항상 검사를 적용한다. |

## 영향

- API: P2 공개 오류 보고·재탐지 인터페이스와 분석 완료 이벤트가 추가된다.
- DB: P2 `fds_failure_analyses`와 `fds_evaluations` 재탐지 연결 컬럼을 추가한다.
- P5: 호출·응답 시각과 평가 횟수 수집·보존, 오류 보고·이벤트 수신·재탐지 작업 이력, 원본 ERROR 보존 및 새 결과 반영은 후속 작업이다. 현재 `PaymentRequest.recordEvaluation`은 다른 UUID와 저장 결과 교체를 거절하므로 별도 적용 설계가 필요하다. 신규 테이블의 논리 설계는 위 사용자 승인 문서에 기록하며, 물리 스키마 반영은 담당 ERD 확인과 후속 migration 작업에서 진행한다.
- API·화면: 보안 직원 전용 P5 재탐지·전달 복구 POST 두 경로를 추가할 계획이며 첫 구현에는 화면을 추가하지 않는다. 응답 DTO·HTTP 상태·오류 코드 및 진행 중/완료 작업 표현은 위 상세 문서에 기록했으며 미구현이다.
- 인증·인가: P1과 두 POST의 직원 권한·선택적 CSRF 강제 검사를 연결한다. 실행자 식별자는 세션에서 확보하며 기존 ADMIN 운영 조회 권한을 실행으로 확대하지 않는다.
- 정책: 최초 연동에서는 자동 재탐지를 활성화하지 않는다. 향후 자동화의 횟수·간격은 별도 합의 대상이다.
- 테스트: 익명·ADMIN·OPERATOR 실행 거절, 보안 직원 허용, CSRF 누락·변조 거절, 업무 입력이 결제 ID뿐인 호출과 중복 요청의 기존 작업 반환을 검증한다. 실제 ERROR 보고부터 명시적 재탐지·결제 결과 반영까지 검증한다. 보고·이벤트·재탐지 중복, 서로 다른 작업 키의 동시 실행, 중단·재시작, 늦은 결과, 재탐지 ERROR와 이미 진행된 결제의 재실행 차단을 포함한다.

## 남은 결정과 후속 작업

- 실행 주체·권한·진입점은 위 추가 합의로 확정했다. API 응답·오류 계약은 위 상세 문서에 기록했다. 두 POST의 CSRF 강제 적용 방향은 위 추가 설계로 정했다. 필터·matcher 구현 검토와 수동검토 절차는 후속이다. 오류 연락 담당·대체 담당 지정은 #190의 기존 제외 범위를 유지한다.
- P5 상태·원본/현재 평가 연결·작업 키 보존·접수/실행 구분은 위 상세 문서를 구현 기준으로 검토한다. 기존 행 잠금과 전달 복구 POST를 사용한다. 유한 대기 설정·이벤트 기록 선별·중단 판별 및 #191 경계는 구현 전에 확인한다.
- P5 신규 저장 구조가 필요하면 소유 담당 확인과 ERD·migration 절차를 따른다. 이 합의 자체를 미합의 테이블·컬럼의 구현 승인으로 해석하지 않는다.
- P2의 기존 분석·재탐지 구현과 P5의 최초 ERROR당 1회 제한을 통합 검증한다. P2 API가 존재한다는 사실만으로 P5의 1회 실행·중복 승인 방지가 구현됐다고 판단하지 않는다.
- #190의 응답 유실·기존 UUID 결과 복원은 이번 내부 ERROR 합의와 분리해 남긴다. #190 전체를 완료 처리하지 않는다.

## 구현·검증 상태

- 기준 코드: `72cc5c8`. P2 오류 분석·재탐지 공개 API 구현은 존재하며, P5 보고·수신·재탐지 결과 적용은 미연결이다.
- 재탐지·전달 복구 POST, 두 경로의 권한·CSRF 검사, 실행자·재탐지 작업 기록과 이벤트 선택 재전달은 아직 구현·검증하지 않았다.
- 이번 변경은 정책 합의와 후속 범위의 문서 반영이다. 코드·DB 변경이나 자동 실행 활성화는 없다.
- backend·MariaDB 실행 및 P2·P5 통합 동작은 이번 문서 작업에서 미검증이다. 문서 검사 명령과 실제 결과는 PR에 기록한다.

## #273 분석 사유 보존 구체화 — 2026-10-28

사용자가 담당 ERD 반영과 P2 분석 사유 보존 방식을 승인했다. payment_fds_recoveries.reason_code는 수신한 P2 분석 사유를 보존한다. 재탐지 ERROR 코드로 덮어쓰는 대안은 지연된 분석 이벤트의 동일 내용 비교 근거를 잃으므로 사용하지 않는다. API reasonCode는 정상 완료 시 null, 재탐지 ERROR 시 현재 평가 errorCode, 분석상 불가 시 저장된 분석 사유를 반환한다.

DB는 기존 19개 필드를 유지하고 별도 종료 사유 컬럼은 추가하지 않는다. 별도 수동 종료 사유 영속화는 #274에서 검토한다. 화면 추가는 없고, API 표현과 DB 저장 의미를 구분한다. 테스트에는 재탐지 후 지연 분석 이벤트의 멱등 비교와 응답 사유 매핑을 포함한다. [#273 저장 필드·제약](../payment/273-fds-recovery-storage.md)을 참조하며 작업 브랜치에 저장·보고·분석 수신·상세 GET 구현을 반영했다. 최신 검사 결과는 해당 문서의 최종 점검 기록을 따른다. 운영 DB 적용 및 #274·#275 실행 API는 후속이다.
