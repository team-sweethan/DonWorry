# 0014. MVP 세션 인증과 단계별 보안 적용

- **상태:** 제안 — 구현 반영, 팀 리뷰 필요
- **날짜:** 2026-10-22
- **관련:** Issue #68, #69, #72, #76
- **영향 받는 담당:** P1 주환, P2~P6(API 접근 정책), P4 현규(서버 간 인증 후속)

## 배경

ADMIN 로그인 MVP는 브라우저 새로고침 후에도 로그인 상태를 유지해야 한다. 다른 담당의 API 개발은 로그인 연동보다 먼저 진행 중이다. #69 0절과 #72는 `/api/auth/me`만 인증을 요구하고 나머지 요청은 허용하며, CSRF 활성화와 서버 API 차단은 #68 5단계에서 함께 적용하도록 범위를 정했다.

## 결정

브라우저 인증은 JSESSIONID 기반 서버 세션을 사용한다. TASK 02(#72)에서는 세션 저장소와 보안 응답을 구성하고, 실제 로그인·내 정보·로그아웃은 TASK 03(#76)에서 구현한다. CSRF는 MVP에서 비활성화하고 #68 5단계에서 서버 API 접근 제한과 함께 활성화한다.

### 세션과 인증 경계

- `HttpSessionSecurityContextRepository`를 Bean으로 등록하고 필터 체인과 #76 로그인 처리에서 같은 저장소를 사용한다. 인증 저장은 명시적 `saveContext()` 호출을 전제로 한다.
- 세션 생성 정책은 `IF_REQUIRED`, 고정 방지 정책은 `changeSessionId`로 둔다. 수동 로그인은 필터 체인 설정만으로 세션 ID가 바뀌지 않으므로 #76에서 인증 성공 후 `SessionAuthenticationStrategy`를 실행하거나 기존 세션 유무를 처리해 직접 변경해야 한다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Lax`로 설정한다. 비활동 만료 시간은 30분을 제안값으로 적용하고 PR 리뷰에서 확정한다.
- 로컬은 HTTP이므로 `Secure`를 켜지 않는다. HTTPS 배포 시 쿠키의 `Secure` 설정을 적용한다.
- 폼 로그인·HTTP Basic·요청 캐시·기본 로그아웃은 비활성화한다. #76에서 `/api/auth/logout`을 Security 로그아웃 필터로 구성하고 세션 무효화 후 204를 반환한다. #72의 API 로그아웃 설명은 #76의 구체적인 필터 방식으로 인계한다.

### 접근 정책과 응답

- `/api/auth/me`는 인증을 요구한다. 그 외 경로는 `permitAll`로 유지하며 역할별 접근 제한을 추가하지 않는다.
- 비로그인은 401 `AUTH_001`, 권한 부족은 403 `AUTH_002`를 `application/problem+json`으로 반환한다. 현재 권한 부족 경로는 없으므로 403은 핸들러를 직접 호출해 검증한다.
- 응답은 Spring `ProblemDetail`을 사용한다. 에러 코드는 identity 내부 enum에 두며 공통 에러 계층이나 전역 Advice를 만들지 않는다.
- 프론트의 Vite `/api` 프록시를 유지하므로 CORS 설정은 추가하지 않는다.

### 후속 범위

- #76: 실제 인증, 세션 ID 변경, 인증 저장, `/me`, API 로그아웃. 로그인 응답에서 쿠키 속성과 세션 유지·무효화를 검증한다.
- #68 5단계: 서버 API 차단, CSRF 토큰 제공·프론트 전송·로그인 시 토큰 교체, `/internal/**`·CakeShop 웹훅 제외 정책, 서버 간 인증. ADR-0009의 서비스 키 인증은 이 단계에서 구현하며 현재 구현되었다고 보지 않는다.
- `SameSite=Lax`는 CSRF 보호를 대체하지 않는다. 이번 비활성화는 개발 MVP의 단계별 적용 결정이다.
- 운영 배포 전: HTTPS 쿠키 설정과 #69의 개발용 ADMIN 시드 운영 제한 후속을 처리한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| JWT 인증 | 현재 브라우저 MVP에는 서버 세션으로 충분하다. 토큰 저장·갱신·폐기 계약을 추가하지 않는다. 향후 변경 시 별도 ADR로 검토한다. |
| 처음부터 CSRF 활성화 | 토큰 API와 프론트 처리, 서버 간 호출 예외를 함께 정해야 한다. #69의 단계별 개발 범위에 맞춰 #68 5단계로 미룬다. |
| 모든 API를 즉시 인증 필수로 전환 | P2~P6 개발 요청이 막힌다. 현재 단계는 `/me` 하나만 보호한다. |
| 무상태 정책 또는 인증 정보 자동 저장에 의존 | JSESSIONID 유지 요구와 맞지 않거나, 수동 로그인에서 저장을 누락할 수 있다. 저장소를 공유하고 명시적으로 저장한다. |

## 영향

- API: 비로그인 `/api/auth/me`는 컨트롤러 구현 전에도 401이다. 다른 요청은 기존 접근 정책을 유지한다. 401·403은 JSON 응답 계약을 갖는다.
- DB: 테이블·마이그레이션·Entity 변경 없음. 인증 세션은 현재 서블릿 컨테이너가 관리한다.
- 화면: 이번 PR의 프론트 변경 없음. #76·#78에서 세션 로그인과 401 처리를 연결한다.
- 테스트: DB 없는 MVC 슬라이스에서 접근 정책·세션 인증 복원·에러 응답을 검사한다. MariaDB 회귀 검사는 별도 실행한다.
- 문서: 이 ADR과 ADR 목록에 결정 이유·미검증·인계 사항을 기록한다.

## 검증

2026-10-22, `98bfa61`에서 분기한 `feature/72-session-security`의 미커밋 구현 상태에서 실행했다.

- `cd backend && ./gradlew spotlessApply check mariaDbTest`: 통과. 일반 테스트 64개(보안 MVC 테스트 7개 포함), MariaDB 테스트 13개, 실패·오류·건너뜀 0개. 모듈 경계·계층 검사와 Flyway 전체 적용·JPA validate를 포함한다.
- Boot 4의 MVC 보안 슬라이스 자동 설정을 위해 기존 `spring-security-test` 직접 의존을 `spring-boot-starter-security-test`로 바꾸고 `spring-boot-starter-webmvc-test`를 추가했다. 최초 검증에서 드러난 `HttpSecurity` Bean 누락을 보완한 뒤 위 전체 검사를 통과했다.
- `cd backend && ./gradlew bootRun --args=--server.port=18081`: 로컬 MariaDB 연결 및 서버 기동 확인. 검증 후 서버 종료.
- `curl --silent --show-error --include http://localhost:18081/api/auth/me`: 401, `application/problem+json;charset=UTF-8`, `AUTH_001`과 한글 메시지 확인. 리다이렉트·세션 쿠키 발급 없음.
- `curl --silent --show-error --include --request POST http://localhost:18081/api/security-test-missing`: CSRF 토큰 없이 404 확인.
- 같은 없는 경로에 GET 요청도 404 확인. 서버 기동 검증에서 일반 요청이 401·403으로 차단되지 않았다.

실제 로그인·세션 ID 교체·로그아웃·쿠키 발급은 #76 구현 전이므로 미검증이다. ADR 채택과 만료 시간 30분 확정은 팀 리뷰가 필요하다.

## 팀 공유 문안

> #72에서는 `/api/auth/me`만 로그인이 필요하며 나머지 경로는 기존처럼 허용됩니다. CSRF는 계속 비활성화되어 요청 방식은 같습니다. `/internal/**` 인증·CSRF 처리는 #68 5단계에서 진행합니다. P4 현규 담당의 서버 간 인증도 해당 단계에서 연동합니다.

공유용 문안이며, 실제 팀 메시지는 별도로 전송하지 않았다.
