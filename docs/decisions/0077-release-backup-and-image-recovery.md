# 0077. 배포 전 DB 백업과 승인된 이전 이미지 복구

- **상태:** 제안 — #483 구현·리뷰 대상, 운영 설치·실검증 전
- **날짜:** 2026-11-04
- **관련:** #448 D (#483), [ADR-0074](0074-approved-release-update.md), [ADR-0075](0075-deployment-serialization-and-interruption.md)
- **영향 받는 담당:** P1·VM/Jenkins 운영 담당, migration 작성 담당

## 배경

기존 최초 배포는 SHA 태그만 기록한다. 새 배포 경로는 digest 묶음을 저장하지만 이전
운영 배포의 묶음·백업이 없으면 안전한 복귀 대상을 고를 수 없다. 앱 기동 중 Flyway가
실행되므로 이미지 복귀와 DB 복원은 다른 작업이다.

## 결정

### 최초 복구 후보와 백업

`register-current`는 운영자가 지정한 현재 SHA와 실제 컨테이너 이미지 ID·로컬 RepoDigests·
원격 플랫폼 manifest/revision을 대조한다. main 또는 prod marker로 이전 대상을 고르지 않는다.
서비스별 해당 저장소 RepoDigest가 하나가 아니거나 index 검증이 불가능하면 거절한다.
현재 Compose/환경/bind/명령의 해시와 digest Compose, DB/Flyway 상태, 운영자·근거를 저장한다.
기존 컨테이너의 실행 ref는 SHA 태그여도 이미지 ID가 맞아야 한다. 등록은 서비스를 바꾸지 않는다.
root는 이때 DB/업무 정상 상태를 근거 기록에서 확인한다. 이 등록을 과거 배포 성공이나
복원 검증으로 해석하지 않는다. 구현 변경 등으로 구성이 달라졌을 때도 명시적 재등록을 허용한다.
미해결 실패가 있으면 재등록할 수 없으며, 동일한 구성의 중복 등록은 거절한다.

#480 이전 빌드(현재 운영 `sha-1514b3d` 포함)는 서비스 이미지에 revision label이 없어 최초 등록이
불가능하고, 그러면 새 경로로 첫 업데이트를 시작할 수 없다. 기존 `deploy-donworry`도 최초 배포만
실행한다. 그래서 `register-current --without-revision`을 둔다. label이 **없을 때만** 허용하고 다른 SHA의
label은 거절하며, 이미지 ID·RepoDigest·원격 digest·플랫폼 대조는 유지한다. 묶음과 복구 승인에
`revision_verified: false`를 기록한다. 새 배포 대상(prepare)에는 적용하지 않는다.

배포는 이전 성공/등록 묶음 전체의 실제 이미지·기동 상태와 현재 구성 일치를 확인해야 한다.
이전 묶음이 없으면 서비스 변경 전에 차단한다.
기능 검사 정책·구현과 등록된 현재 묶음은 `prepare`와 `apply` 실행 기록을 만들기 전에 확인한다.
서비스를 바꾸지 않은 사전 조건 누락이 `failed`·`PAUSE_CD`로 남으면 `reconcile`·`register-current`로도
풀 수 없기 때문이다. 공통 잠금 아래 다운로드 뒤, Compose 적용 전
`dw_migrate`로 단일 DB를 `mariadb-dump --single-transaction --quick --triggers --hex-blob` 백업한다.
비밀번호는 컨테이너 내부 환경에서만 읽는다. SQL을 메모리/Jenkins 로그로 반환하지 않고
`releases/<배포 묶음>/database.sql`에 0600으로 직접 쓴다. 성공 종료·비어 있지 않음·fsync·
해시/크기·시작/완료 시각·기존 묶음 ID를 result의 backup에 기록한다.
미완료 덤프는 삭제하거나 성공으로 승격하지 않으며 root 전용 기록으로 보존한다.
DB 백업은 900초, 재시도 없음이다. 백업 용량/보관 기간/별도 매체 보관은 운영자가 정한다.

InnoDB 테이블만 허용한다. 뷰·루틴·이벤트는 현재 백업 정책 대상이 아니므로 발견하면 차단한다.
Flyway 성공 이력과 컬럼·인덱스·참조/체크 제약·테이블 설정·트리거·서버 버전을 지문화한다.
백업 전후 및 최종 적용 전 지문이 달라지면 배포를 멈춘다. 지문에는 업무 행을 넣지 않는다.
백업 중 DDL은 금지한다. 공통 잠금 밖의 root 수동 SQL까지 통제하는 보안 경계는 아니다.

백업 성공은 복원 성공을 뜻하지 않는다. `restore_verified=false`를 유지한다. 격리된 로컬
fixture DB의 덤프/복원 테스트는 운영 DB 백업의 복원 가능성·권한·용량·실행 시간을 증명하지 않는다.
실제 백업을 별도 DB에 복원해 확인하는 작업과 그 증거는 운영 적용 전 별도로 수행한다.

### 핵심 기능 검사

health 다음, 기록 게시 전에 root 소유 `functional_check.py`를 Python으로 한 번 실행한다.
60초 제한이며 실패·timeout이면 failed/PAUSE_CD다. 자동 재시도·임의 결제는 하지 않는다.
파일과 `functional-check.json`은 승인 구성 해시에 포함한다. 정책에는 `environment=approved-test`,
`test_data`, `evidence`를 요구한다. 승인된 테스트 환경·데이터·검사 구현이 없으면 적용 전에 차단한다.
현재 저장소는 특정 로그인/결제 시나리오를 임의로 승인하거나 실행 가능한 예제 검사로 제공하지 않는다.
검사 시나리오와 데이터의 합의·실검증은 미완료이며 이 조건을 운영 준비 완료로 표시하지 않는다.
root 파일 소유/쓰기 권한과 hook이 사용하는 추가 자원의 통제는 #484 설치 전제다.

### 이미지 복구와 중단

배포 실패는 자동 복구 대신 지속 기록·PAUSE_CD와 `approve-recovery` → `recover` 절차로 연결한다.
운영자는 이전 작업/daemon 종료, DB와 업무 데이터 호환성, 복귀 영향 확인 근거를 남기고
복구를 별도로 승인한다. 승인에는 실패 결과 해시·이전 성공 묶음·운영자·근거·시각을 묶는다.
대상은 **해당 배포의 성공한 백업 기록에 연결된 직전 성공/등록 묶음**뿐이다.
이미지·구성은 저장 snapshot을 사용하고 태그/main/prod에서 다시 고르지 않는다.

DB health가 비정상이거나 Flyway 실패/이력 없음, 백업 때와 다른 스키마/Flyway 지문,
현재 환경/Compose/bind/명령 불일치면 거절한다. `.env`의 IMAGE_TAG 차이만 복귀를 허용한다.
스키마 지문 일치는 업무 데이터 호환성의 증명이 아니다. 명시적 승인 근거에서 확인해야 한다.
호환 migration도 지문이 달라지면 이 구현은 자동 판단하지 않고 거절한다.
복구 도중 pull 뒤 및 기동/기능 검사 뒤 DB 지문을 다시 대조한다.

복구도 같은 `exclusive`·`operation(kind='recovery')`를 사용한다. 별도 묶음/result에 기록하고
앱 3개만 `--no-deps --no-build --pull never`로 적용한다. DB 서비스·볼륨·SQL은 복원하지 않는다.
기동/기능 검사 뒤 SHA 태그·두 배포 기록을 게시한다. 원래 실패 result는 보존하고 별도 resolution,
current 저장 후에만 PAUSE_CD를 해제한다. 복구 실패/부분 적용은 재시도하지 않고 운영자로 넘긴다.
복구 승인당 서비스 적용은 한 번이다. 성공 결과 뒤 게시만 끊겼다면 같은 recover로 전체 상태를
재검사해 게시를 끝낼 수 있다. 이 재실행은 Compose up을 다시 호출하지 않는다.

### DB 복원 제한

DB restore·초기화·Flyway repair/clean·자동 down/볼륨 삭제 명령은 제공하지 않는다.
migration 실패/일부 적용/비호환 변경이면 서비스 쓰기 차단 여부를 운영자가 먼저 판단한다.
DB 복원은 백업 시점 이후 거래·판정·정산 등의 데이터 손실을 일으킬 수 있으므로 별도 승인한다.
승인에는 복원 파일 해시/시점, 손실 시간 구간과 영향, 업무 담당 확인, 쓰기 중지·별도 DB 복원
검증·전환/검사 계획을 기록해야 한다. 이미지 복구 승인은 DB 복원 승인을 포함하지 않는다.

## 버린 대안

| 대안 | 버린 이유 |
| --- | --- |
| 실패 시 이전 SHA 태그 자동 실행 | mutable 태그와 DB 변경 때문에 복귀 대상을 보장하지 못함 |
| 백업 파일이 있으면 자동 DB 복원 | 복원 가능성 미검증·배포 이후 데이터 손실 |
| Flyway 이력만 대조 | 실패 migration의 일부 DDL이 이력에 남기 전에 적용될 수 있음 |
| 스키마 같으면 무승인 이미지 rollback | 데이터 의미·진행 중 작업의 호환성은 지문으로 증명할 수 없음 |
| 백업/복구를 잠금 밖에서 별도 shell로 실행 | 배포·수동 실행과 경합하고 중단 기록이 분리됨 |
| health를 핵심 기능 성공으로 간주 | 인증/업무 기능·승인된 테스트 데이터의 동작을 증명하지 못함 |
| label 없는 옛 이미지는 첫 업데이트를 도구 밖 수동 절차로 한 뒤 등록 | 백업·DB 지문·기록 갱신 검사를 사람이 대신해야 하고 잠금·실행 기록 밖의 배포가 생김 |
| revision label 검사를 모든 등록에서 생략 | 다른 SHA label을 가진 이미지까지 받아들여 등록 SHA를 검증할 수 없음 |

## 영향과 검증

업무 API·DB 스키마·화면 변경은 없다. VM CLI, 실행 기록/백업 보관, Jenkins 시간 예산,
승인한 기능 검사 계약이 바뀐다. 새 구현 해시로 기존 배포를 명시적으로 다시 점검/등록해야 한다.
Jenkins 업데이트 적용 예산은 150분으로 늘린다. SSH 종료는 VM 종료로 해석하지 않는다.

대역 검사는 등록·백업 실패·DB 변경 차단·승인된 복구·복구 경합/실패·게시 재개를 검사한다.
옵트인 로컬 MariaDB 검사는 fixture dump를 별도 DB에 실제 복원하고 스키마 변경 탐지를 확인한다.
실제 운영 백업/복원·Jenkins/SSH/VM 중단·핵심 기능·담당자 계약 확인은 별도이며 미검증이다.
실행 명령과 결과는 PR, 절차는 [VM 안내](../../ops/vm/README.md)에 기록한다.

근거: [MariaDB mariadb-dump](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump).
