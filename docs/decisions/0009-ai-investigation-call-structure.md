## 배경

설계 3.6 · 3.7은 다음 구조를 정했다.

- P4 Spring이 FastAPI에 조사를 **비동기**로 요청한다 (`202 Accepted`)
- FastAPI의 AI Agent가 **Spring Tool API**를 호출해 증거를 읽는다 (Tool 6종)
- 결과는 콜백 또는 작업 결과 조회로 받고, Spring이 검증 · 저장한다
- FastAPI는 DB에 직접 접근하지 않고, 금융 상태를 바꾸지 못한다

설계 3.9⑤는 `ai_reports`를 8개 컬럼(`report_id` · `case_id` · `report_version` · `evidence_version` · `status` · `report_body` · `created_at` · `completed_at`)으로 확정했다. 작업 ID · 시도 횟수 · 실패 사유 컬럼은 없고, "시도 횟수 저장 방식은 P4 내부 설계에서 결정"으로 남겼다. 공통 페이지 §5.3(P3 ↔ P4) · §5.4(AI Tool)는 개발 전 결정 항목이 비어 있다.

이 ADR은 (1) FastAPI ↔ Spring 호출의 위치 · 인증, (2) 8개 컬럼 안에서 상태 · 재시도 · 실패를 다루는 방법을 정한다. §5.3 · §5.4는 합의 전이라 미정으로 남긴다.

## 결정 1 — 호출 구조

**Tool API와 결과 수신 엔드포인트를 모두 `investigation/report`에 두고, 내부 전용 경로로 분리한다. 작업 ID는 `report_id`를 그대로 쓴다.**

```mermaid
sequenceDiagram
    participant P3 as investigation (P3)
    participant R as investigation/report (P4)
    participant A as ai-server (FastAPI)
    participant O as payment · fds · identity api

    P3->>R: 조사 요청 (caseId · 증거 버전, 방식 미정 §5.3)
    R->>R: ai_reports PENDING 저장 (report_version + 1)
    R->>A: POST /investigations (reportId, attemptId, caseId, evidenceVersion)
    A-->>R: 202 Accepted
    R->>R: RUNNING (PENDING일 때만 — 조건부 UPDATE)
    loop Agent가 필요한 증거만
        A->>R: GET /internal/ai/tools/{tool}?caseId=…
        R->>R: Case 소속 결제 · 가맹점 범위 검증
        R->>O: 소유 모듈 공개 api 조회
        R-->>A: 필요한 최소 정보
    end
    A->>R: POST /internal/ai/reports/{reportId}/result (attemptId)
    R->>R: 구조 검증 → SUCCEEDED 저장 (PENDING · RUNNING일 때만)
    R->>P3: 완료 통지 (방식 미정 §5.3) · 증거 버전이 바뀌었으면 다음 버전 PENDING
```

| 권한 | Tool은 GET만. 결제 · 판정 · Case 상태를 바꾸는 Tool은 만들지 않는다 |

| 진행 기록 (#322) | FastAPI `GET /investigations/{reportId}`는 `RUNNING`일 때 `progress`(지금까지 끝난 단계, `investigationTrace.steps`와 같은 모양)를 싣는다. 끝나면(`SUCCEEDED` · `FAILED`) 비우고 콜백에도 싣지 않는다. 메모리에만 두며, 새 시도가 오면 이전 시도의 늦은 진행 기록은 버린다. **화면 진행 표시에만 쓰고 결과 반영 · 재시도 판단에는 쓰지 않는다** |

**`find_similar_cases` (#296)** — 구현: `SimilarCaseFinder`. AI Tool과 AI를 끈 고정 보고서가 같은 규칙을 쓴다
- 후보는 종료(`CLOSED`) 사건만, 지금 사건 제외
- "같은 고객"(`SAME_CUSTOMER`): 같은 `merchant_id` + `customer_ref` (`customer_ref`는 가맹점마다 따로 매기는 값이라 가맹점도 같아야 한다)
- "같은 규칙 조합"(`SHARED_RULES`): 최근 종료 100건 중 적중 규칙 코드가 2개 이상 겹치는 사건
- 같은 고객을 먼저, 그다음 같은 규칙 조합. 각각 최근 종료 순, 최대 5건. 전체 건수는 `totalMatched`
- 결과는 결제별 직원 판정 건수(`acceptCount` · `rejectCount`) 그대로. "사기 확정" 같은 해석은 하지 않는다
- 기본 조회로 다룬다: 코드가 조사마다 한 번 조회한다 (결정 9, #578 전에는 "AI가 안 부르면 다시 요청 → 시스템 보충"). 조회가 실패하면 `similarCases: null`로 두고 보고서는 만든다 (참고 자료라 판정에 필요한 보고서를 막지 않는다)
- 조회는 별도 읽기 트랜잭션(`REQUIRES_NEW`)에서 한다 — 고정 보고서가 이 조회의 실패를 잡아도 보고서 트랜잭션이 되돌림 전용이 되지 않게

**`get_payment_history` (#338)** — 구현: `PaymentHistoryFinder` + P5 `PaymentReader.findRecentByCustomer`. AI Tool과 AI를 끈 고정 보고서가 같은 규칙을 쓴다
- "같은 고객": Case의 `merchant_id` + `customer_ref` (`find_similar_cases`와 같은 기준). 다른 가맹점 결제는 읽지 않는다
- 이 사건에 묶인 결제는 뺀다 — "평소 결제"와 비교하는 것이 목적이라, 사건 결제가 섞이면 사건 자체가 정상 근거처럼 보인다. P5 조회에서 건수를 세기 전에 빼서, 사건 결제가 아무리 많아도 사건 밖 결제를 놓치지 않는다 (#338 리뷰)
- 기간 · 건수: 조회 시각 기준 최근 30일, 최근 순 최대 20건. 기간 안에 더 있으면 `truncated: true`
  - **#581부터 기간은 30 · 90 두 값만 받는다** (`lookbackDays`, 안 보내면 30). 30일은 코드가 조사마다 늘 본다(기본 조회). AI는 그 결과를 보고 추가 조사에서 "90일로 넓힐지"만 고른다 — 도구에 인자가 없고 90은 코드가 정한다(추가 도구 연결은 같은 이슈 다음 커밋). 그 밖의 값은 사건 · 결제를 읽기 전에 400
  - 예전에 AI 기간 고르기를 뺀 이유(7B가 매번 다른 기간을 골라 같은 사건의 보고서가 달라짐, 긴 기간의 조회량 — 아래 고려한 대안)는 선택지를 둘로 묶고 30일을 늘 먼저 보는 것으로 막는다. AI를 끈 고정 보고서는 늘 30일
- 상태별 건수(`statusCounts`)는 반환한 결제(최대 20건) 안에서 코드가 센다. 응답: `lookbackDays` · `payments[]`(`paymentId` · `amount` · `paymentStatus` · `requestedAt`) · `statusCounts[]`(`paymentStatus` · `count`) · `truncated`
- 필수 근거 · 실패 처리 · 별도 읽기 트랜잭션은 `find_similar_cases`와 같다 (기본 조회, 실패하면 `paymentHistory: null`로 두고 보고서는 만든다. AI 보고서는 한계 줄에 "고객 최근 결제를 조회하지 못했습니다"를 더한다)
- AI에게는 건수 · 상태별 건수 · 최근 5건의 금액 · 상태 · 시각만 참고로 보여 준다(결제 ID 없음). 이 숫자들은 판단 문장 숫자 검사(`fact_numbers`)에서 근거에 있는 숫자로 인정한다. "이력이 없다는 것만으로 의심하지 않고, 매입 완료 이력만으로 정상이라고 단정하지 않는다"를 지시한다

**`find_linked_payments` (#352)** — 구현: `LinkedPaymentFinder` + P2 `FdsLinkedPaymentReader.findLinked` ([ADR-0034](0034-fds-evidence-read-contract.md)). AI Tool과 AI를 끈 고정 보고서가 같은 규칙을 쓴다
- 비교할 값은 이 사건 결제의 FDS 평가에 남은 카드 토큰 · 기기 ID · IP 주소다 (이메일은 비교하지 않는다). 일치 비교는 P2 안에서 원문으로 하고, P2 밖으로는 숫자 · 판정 코드만 나온다. 카드 토큰 · IP 주소 · 기기 ID · 다른 고객 번호 · 다른 결제 ID는 P4 · AI · 보고서에 들어가지 않는다
- 범위는 Case의 `merchant_id`, 조회 시각 기준 최근 30일. 같은 고객(`customer_ref`) 결제와 이 사건 결제는 세지 않는다 — "다른 고객이 같은 카드를 썼나"가 목적이다
- 결제마다 하나로 센다. 재평가로 평가가 여러 개면 최신 비오류 평가의 판정을 쓴다(`FdsEvidenceReader`와 같은 규칙). 카드사 거절은 P5가 P2 평가에 기록한 승인 결과(`authorization_result = DECLINED`)로 센다 — P5를 따로 부르지 않는다
- 응답: `lookbackDays` · `card` · `device` · `ip` 각각 `provided`(이 사건 결제가 그 값을 보냈는지) · `otherCustomerCount` · `paymentCount` · `resultCounts[]`(`result` · `count`, 허용 · 검토 · 차단 · 평가 오류 순, 0건 제외) · `declinedCount`. `provided: false`는 "같은 값 없음"이 아니라 "비교하지 못함"이다
- **IP 출처 (#637에서 확인):** CakeShop은 결제 준비 요청(`POST /api/payment-sessions`)에 IP를 보내지 않는다. 대신 손님 브라우저가 돈워리 결제창([ADR-0064](0064-hosted-checkout-and-payment-webhook.md))에 직접 접속하고, 돈워리가 그 접속 IP를 기록한다 — `PaymentCheckoutController` → `ClientIpResolver.clientIp(request)` → `PaymentSessionService.pay(sessionKey, body, ipAddress)` → `fixAttempt(…, ipAddress, …)` → 결제 위험 신호 → FDS 평가 `ip_address`. 그래서 결제창 흐름의 IP는 가맹점 서버가 아닌 손님 IP다. 서버 간 결제 API로 들어온 결제는 가맹점이 보낸 `ipAddress`를 쓰고, 보내지 않았으면 "정보 없음"이다 (CakeShop 저장소 5f30d3d · 11/06 기준)
- **결제별 칸 (#533, 추가만 한다):** `payments[]` — 사건 결제마다 `paymentId` · `card` · `device` · `ip`(위와 같은 모양). 위 `card` · `device` · `ip`는 사건 전체 합계라 화면 카드 · 고정 보고서가 그대로 쓴다
  - 판정 기준표는 그 결제의 칸으로만 "같은 카드 · 기기 · IP를 다른 고객이 사용" 징후를 붙인다. 결제 1의 카드만 겹쳤는데 결제 2까지 고위험이 되던 문제 (PR #529 Codex 리뷰)
  - AI 입력에도 결제마다 "같은 카드 · 기기 · IP(이 결제)"를 넣는다. "다른 근거가 없다" 검사도 그 결제의 칸으로 본다
  - 결제별 칸이 없는 예전 응답이면 사건 단위로 붙이되 징후 이름을 "이 사건 결제 중 …"으로 쓴다
- **사건 앞뒤 1시간 칸 (#637, 추가만 한다):** 응답에 `nearbyWindowMinutes`(지금 60), 각 `card` · `device` · `ip`(사건 전체 · 결제별 모두)에 `nearby`(`otherCustomerCount` · `paymentCount` · `resultCounts[]` · `declinedCount`, 뜻은 30일 칸과 같다)
  - 이유: 같은 IP를 다른 고객이 썼을 때 공격은 짧은 시간에 몰리고, 회사 · 카페 같은 공용 와이파이는 한 달에 흩어진다. 30일 합계만으로는 둘이 같은 숫자("다른 고객 5명")로 보인다. 1시간 숫자를 나란히 두면 직원과 AI가 둘을 가를 수 있다
  - 30일 안의 결제를 사건 결제 요청 시각 앞뒤로 다시 센다(경계 포함, 결제 요청 시각 기준). 사건 전체 칸은 같은 값을 쓴 사건 결제 중 하나라도 앞뒤 1시간 안이면 센다. 결제별 칸은 그 결제의 시각 기준이다. 30일 조회 시작보다 앞선 구간은 보지 않는다(사건 결제가 30일 넘게 지난 경우만 해당)
  - 1시간은 출발값이다. P4 `LinkedPaymentFinder.NEARBY_WINDOW` 하나로 P2에 넘기고, 판정 기준표 개선 때 측정해 조정한다
  - 판정 기준표 · 권고는 이 칸을 쓰지 않는다 (기준표 개선 조각에서 정상 사유 · 징후 무게와 함께 정한다)
  - AI 입력(조사 사실 "연결")은 30일 줄 뒤에 "그중 이 결제 앞뒤 1시간 안: 다른 고객 n명 · 결제 n건 …" 또는 "없음"을 붙인다. 예전 응답(칸 없음)은 붙이지 않는다. 보고서 `linkedPayments` · AI를 끈 고정 보고서도 같은 키로 옮긴다
  - 화면 카드 "다른 손님과 겹치는 것": 보안 직원이 네트워크 · 개발 지식 없이 읽도록 줄마다 문장으로 쓴다("이 손님이 결제한 인터넷(와이파이 등)에서 다른 손님 9명이 27번 결제했습니다. 그중 1명(3번)은 이 결제 전후 1시간 안에 결제했습니다."). "이 내용은 어떻게 보나요?"를 누르면 읽는 법이 펼쳐진다 — 설명은 경우마다(카드 겹침 · 기기 겹침 · 인터넷 몰림 · 인터넷 띄엄띄엄 · 카드사 거절 · 정보 없음 · FDS 결과 · 개인정보) 고정 문장으로 적어 두고, 숫자로 이 보고서에 해당하는 것만 코드가 고른다(`frontend/src/utils/linkedPaymentsView.ts`). LLM은 이 카드에 관여하지 않고, 이 사건이 수상한지는 말하지 않는다. 판정 색 태그는 펼침 안으로 옮겼다. 칸이 없는 예전 보고서는 30일 문장만
- 필수 근거 · 실패 처리 · 별도 읽기 트랜잭션은 `find_similar_cases`와 같다 (실패하면 `linkedPayments: null`, AI 보고서 한계 줄에 "같은 카드 · 기기 · IP를 쓴 다른 결제를 조회하지 못했습니다"). 필수 도구가 5종이 되어 Agent 도구 호출 한도를 6 → 7로 올렸다 (여유 2번 유지). #578부터 5종 모두 코드가 하는 기본 조회라 이 한도는 없어지고, AI가 고르는 추가 조회만 3번까지다 (결정 9)
- AI에게는 숫자 없이 "다른 고객 결제 있음 / 없음 / 정보 없음", 다른 고객 "한 명 / 여러 명", 그 결제들의 판정 이름, 카드사 거절 있음 / 없음만 보여 준다. 건수는 보고서 카드에 코드가 채운다. 도구 응답 자체가 숫자 · 판정뿐이라 `llm_content`에서 뺄 것이 없다. "그것만으로 도용을 단정하지 않는다(가족이 기기 · IP를 같이 쓰는 경우), 없음만으로 정상이라고 단정하지 않는다, 정보 없음은 위험 근거가 아니다"를 지시한다

입력에 `caseId`가 있다고 다른 모듈 데이터를 마음대로 읽는 것은 아니다. 각 Tool 구현이 Case 소속 결제 · 가맹점 범위를 검증하고, 소유 모듈의 공개 api로 필요한 정보만 모은다 (설계 3.6 주의).

## 결정 2 — `ai_reports` 8개 컬럼으로 상태 · 재시도 · 실패 다루기

| 상태 | 언제 | 채우는 컬럼 |
| --- | --- | --- |
| `PENDING` | P4가 조사 요청을 받아 행 생성 | `report_version` = 해당 Case 최대값 + 1, `evidence_version` = 요청 시점 Case 증거 버전, `created_at` |
| `RUNNING` | FastAPI가 `202`로 접수. **`PENDING`일 때만** 바꾼다 | — |
| `SUCCEEDED` | 결과 콜백이 구조 검증 통과. **`PENDING` · `RUNNING`일 때만** 바꾼다 | `report_body`(보고서 JSON), `completed_at` |
| `FAILED` | 총 3회 시도 모두 실패 | `report_body`에 `error` 객체(실패 코드 · 사유 · 시도 횟수 · 마지막 시도 시각), `completed_at` = 실패 확정 시각 |

- **상태 변경은 모두 조건부 UPDATE로 한다.** `WHERE report_id = ? AND status IN (…)`처럼 바꿔도 되는 이전 상태를 조건에 넣고, 변경 건수가 0이면 "이미 처리됨"으로 본다. 끝난 상태(`SUCCEEDED` · `FAILED`)는 어떤 경로로도 덮어쓰지 않는다
  - 예) 202 응답 직후 FastAPI가 바로 끝나 성공 콜백이 먼저 `SUCCEEDED`를 저장하면, 뒤이은 `RUNNING` UPDATE는 조건(`status = 'PENDING'`)이 맞지 않아 0건 변경으로 끝난다. 그래서 콜백은 `PENDING`에서도 받는다
- **시도마다 새 토큰 `attemptId`(UUID)를 붙인다.** Spring은 보고서별 "현재 시도 토큰" 하나만 기억하고, 콜백 · 조회 결과의 토큰이 **현재 토큰과 같을 때만** 반영한다
  - 다른 토큰의 콜백은 성공 · 실패 모두 무시한다. 이전 시도는 이미 타임아웃으로 실패 1회로 셌다 (같은 실패를 두 번 세지 않음)
  - 서버가 재시작되면 새 시도는 새 토큰을 받는다. 재시작 전 시도의 늦은 콜백도 같은 규칙으로 무시된다 (번호 1 · 2 · 3처럼 다시 겹치지 않음)
  - 행이 끝난 상태면 토큰이 같아도 무시한다 (조건부 UPDATE). `FAILED` 뒤에 늦게 온 성공도 뒤집지 않는다
  - 이전 시도를 취소하지 않는다. FastAPI가 버려질 작업을 끝까지 돌릴 수 있지만 결과는 반영되지 않는다 (MVP에서 감수)
- **재시도는 같은 행에서 한다.** 같은 증거를 다시 분석하는 것이므로 `report_version`을 올리지 않는다. `UNIQUE(case_id, report_version)`과 충돌하지 않는다
- **한 번의 시도 실패**로 세는 것: FastAPI가 202를 주지 않음(연결 실패 · 5xx · 타임아웃), FastAPI가 실패 결과를 보냄, 결과가 시간 안에 오지 않고 조회로도 완료가 아님, 결과가 구조 검증에 실패함
- **시도 횟수는 실행 중에는 Spring 프로세스 안에서 센다.** 최종 실패 때만 `report_body.error.attempts`에 남긴다. 컬럼을 늘리지 않기 위한 선택이며, 아래 "한계"를 받아들인다
- **실패 사유 위치:** 기획 2.5의 "실패 사유 기록"은 `report_body.error`로 충족한다 (별도 컬럼 없음)
- **`error`는 화면에 보내지 않는다.** 실패 이유는 개발자 조사용이다. 조회 응답은 `FAILED`면 `reportBody: null`로 보내고, 화면은 고정 문구("총 3회 시도")를 보여준다
- **AI 실패는 자동 판정으로 이어지지 않는다.** `FAILED`를 P3에 알리고, 직원이 직접 조사해 `report_id = NULL`로 판정한다 (설계 3.7)

**한계:** 실행 중 서버가 재시작되면 메모리의 시도 횟수 · 현재 시도 토큰이 사라진다. 늦은 콜백 구분은 새 토큰으로 유지되지만, 시도 횟수는 다시 센다. 재시작 시 오래된 `PENDING` · `RUNNING` 행은 조회로 상태를 확인하고, 확인되지 않으면 처음부터 다시 3회를 시도한다. 횟수를 엄밀히 지켜야 한다고 팀이 정하면 `attempt_count` 컬럼 추가를 설계 3.9에 먼저 제안한다.

## 결정 3 — 같은 Case의 중복 실행 방지와 버전

- **새 행을 만들지 않는 경우** (설계 3.5 중복 실행 방지)
  - 같은 Case에 `PENDING` · `RUNNING` 행이 있음 — 요청을 따로 저장하지 않는다. 아래 "완료 후 비교"가 최신 증거를 잡는다
  - 요청한 증거 버전 **이상**을 분석한 행이 이미 있음(상태 무관) — 중복 · 재전달 요청이다. `FAILED`여도 다시 만들지 않는다 (3회 제한 유지). 직원의 수동 재실행은 MVP 범위 밖
- **완료 후 비교는 두 단계로 한다.** ① 종료 상태(`SUCCEEDED` · `FAILED`)를 먼저 커밋하고, ② 별도 트랜잭션에서 현재 Case 증거 버전을 읽어 그 행의 `evidence_version`과 비교한다. 다르면 다음 `report_version`을 `PENDING`으로 만든다
  - 예) 완료 처리 중에 결제가 병합되면: 요청이 ① 전에 왔으면 "진행 중"을 보고 넘어가지만 ②가 그 뒤에 새 증거를 읽어 다음 버전을 만든다. ① 뒤에 왔으면 요청이 직접 만든다. 둘 다 만들려 하면 아래 UNIQUE 합류 규칙으로 하나만 남는다
  - 전제: P3는 증거 버전을 **커밋한 뒤** 조사 요청을 보낸다 (§5.3 합의 항목)
- **동시 요청으로 버전 번호가 겹치면 다시 읽어 합류한다.** 같은 Case에 요청 두 개가 동시에 와서 둘 다 "진행 중 없음 · 최대 버전 1"을 보면 둘 다 v2를 저장하려 한다. 늦은 쪽은 `UNIQUE(case_id, report_version)` 위반을 받는데, 이를 오류로 끝내지 않고 진행 중인 행을 다시 읽어 그 작업에 합류한 것으로 처리한다
  - 늦은 쪽이 더 새 증거 버전을 가져왔어도 빠지지 않는다. 바로 아래 "끝나면 비교" 규칙이 다음 버전을 예약한다
- 늦게 도착한 결과는 자기 행에만 쓴다. 다른 버전 행을 덮어쓰지 않는다. 끝난 행에 오는 결과는 무시한다(멱등, 결정 2 조건부 UPDATE)
- "최신 보고서" = Case 최대 `report_version`이면서 `evidence_version`이 현재 Case 증거 버전과 같은 `SUCCEEDED` 행

## 결정 4 — 화면 계약 (보고서 응답 · ID · 권고 값)

보안 직원 화면(`ReportCard`)이 먼저 만들어졌으므로 응답 형식은 화면 타입 `frontend/src/types/case.ts`(`AiReport` · `ReportBody`)를 따른다. #292부터 화면은 Case 상세의 요약 카드(`ReportCard`)와 보고서 전문 페이지(`CaseReportPage`, `/security/cases/:id/report`)로 나뉜다. **화면 타입과 이 절은 같이 바뀐다. 한쪽만 고치지 않는다.**

- **ID:** DB는 `BIGINT`를 유지하고, P4 응답 JSON에서만 문자열로 보낸다 (`5` → `"5"`). 접두어(`CASE-` 등)는 붙이지 않는다. 요청으로 받은 ID는 문자열 → 숫자로 바꾼다. migration · P3 · 화면은 바꾸지 않는다
- **`report_body` 구조:** 키 순서는 기획 2.7 순서와 같다. 화면 위치는 #591 "결론 먼저" 보고서 전문 페이지 기준이다 — ① 결론 → ② 사건 경위 → ③ 연결 → ④ 판정 근거 상세 → ⑤ 조사 범위 · 한계 (결정 10)

| 키 | 화면 위치 |
| --- | --- |
| `overview` | 상세 정보 펼치기 — 사건 개요 |
| `summary` | ③ 연결의 조사 요약 (AI 해석, 점 목록 · 3문장 뒤 더 보기, #591) |

| `scope` | ⑤ 조사 범위 3칸 — 조회한 것 · 일부러 보지 않은 것 · 확인할 방법이 없는 것 (#591) |

- **#288에서 더한 키 — 추가만 한다.** 그 전에 저장된 보고서에는 없으므로 화면 타입에서는 선택 항목(`?`)이고, ai-server 스키마와 Spring 저장 전 검사에서는 새 보고서에 필수다
  - `verdict.headline`: 결론 한 줄. #532부터 코드가 기준표 판정으로 쓴다 (그 전 보고서는 AI 문장 — 60자 이내 한 문장 검사)
  - `verdict.overallRecommendation`: 코드가 결제별 권고로 계산한다. 하나라도 `REJECT_REVIEW`면 `REJECT_REVIEW`, 모두 `ACCEPT_REVIEW`면 `ACCEPT_REVIEW`, 그 외 `NEEDS_CHECK`

## 결정 5 — LLM 제공자: 배포 VM은 OpenAI (#453)

- **상황:** 보고서는 Ollama(Qwen 7B, 약 4.7GB) 기반 내부망으로 만들었다. 그러나 배포 VM은 사양 한계로 Ollama를 따로 설치할 수 없다. CPU만으로 돌리면 보고서 하나에 수 분이 걸린다. mock은 정해진 문장이라 실제 AI 보고서를 보여 줄 수 없다. 그래서 배포 VM에서는 외부 LLM(OpenAI)을 쓸 수밖에 없다
- **결정:** 기존 LLM 호출 경계(`LlmClient`, AGENTS.md 6절)에 `OpenAiLlmClient`를 추가한다. `AI_SERVER_LLM_PROVIDER=openai`로 켠다. 기본값은 그대로 `mock`이고 `ollama`도 그대로 둔다
- **OpenAI가 맡는 것:** 도구 고르기(#578부터 추가 조사만, 결정 9)와 판단 문장 쓰기만 맡는다. 조사 흐름 · 허용 Tool 목록 · 문장 검사 · 다시 쓰기 · 보고서 조립은 그대로다. 판정은 직원이 하고, AI 실패 시 자동 ACCEPT/REJECT는 없다 (결정 1 그대로)
- **외부로 나가는 것:** AI 입력, 곧 사건의 결제 · FDS 근거 요약이 OpenAI API로 나간다. 범위는 Ollama 때와 같다 (카드 표시값 · IP 원문 없음, #346). 시연 데이터는 합성이다. 실제 고객 데이터에 쓰려면 다시 결정한다
- **키:** `AI_SERVER_LLM_API_KEY`(이미 있던 설정, 팀 공용 키)를 쓴다. 환경 변수로만 넣고 저장소에는 넣지 않는다. `openai`인데 키가 비어 있으면 ai-server가 시작 단계에서 멈춘다
- **모델:** `AI_SERVER_OPENAI_MODEL`, 기본 `gpt-4.1-mini`. 같은 근거에 같은 답을 내도록 `temperature 0`을 쓰므로, temperature를 바꿀 수 없는 추론 모델(GPT-5 계열 등)은 쓰지 않는다
- **출력 형식:** 판단 문장은 JSON Schema 구조화 출력(strict)으로 받는다. strict는 모든 객체에 `additionalProperties: false`가 있어야 하므로, OpenAI 클라이언트 안에서만 스키마 복사본에 붙인다 (Ollama 스키마는 그대로)
- **조사 과정 기록:** `provider: OPENAI`, `model`은 설정한 모델 이름이다. 화면은 OLLAMA처럼 실제 LLM 색(보라)으로 보여 준다

## 결정 6 — 권고 기준: 추가 확인 위주에서 판정 지원 위주로 (#479)

> **#501 결정 7로 대체됨.** 권고를 AI가 고르는 방식은 결정 7에서 판정 기준표(코드)로 옮겼다. 아래는 그 전까지의 기록이다.

- **상황:** 보고서는 보안 직원이 매입 진행(ACCEPT) 또는 승인 취소(REJECT)로 판정하도록 돕는 것이 목적이다. 그런데 판단 문장 프롬프트(`WRITE_SYSTEM`)가 추가 확인 필요(`NEEDS_CHECK`) 쪽으로 기울어 있었다. 직원 입장에서는 "그래서 어느 쪽?"이 남았다
  - 권고 기준에 "대부분의 사건은 이 값이다"(`NEEDS_CHECK`)가 있었다
  - 출력 예시 2개가 `NEEDS_CHECK` · `ACCEPT_REVIEW`뿐이었다. 모델은 규칙보다 예시를 더 잘 따른다(#355)
  - "구매자 본인의 결제 의사"는 모든 결제에서 늘 모르는 사실인데(코드가 `unknowns`에 항상 붙임), 기준이 이것을 판정을 가를 사실의 예로 들어 언제든 `NEEDS_CHECK`를 고를 수 있었다
- **결정:**
  - 위험 · 정상 정황을 모두 따져 어느 쪽이 무거운지를 권고로 고르게 한다. 서로 다른 위험 정황 여럿이 같은 방향을 가리키고 그것을 설명할 정상 정황이 없으면 `REJECT_REVIEW`, 정상 정황이 위험 신호를 설명하면 `ACCEPT_REVIEW`
  - `NEEDS_CHECK`는 정황이 비슷하게 맞서고 판정을 가를 사실을 몰라 어느 쪽으로도 기울지 않을 때만 고른다. 확신이 없다는 이유만으로 고르지 않는다. "구매자 본인의 결제 의사"만으로는 고르지 않는다
  - 출력 예시에 `REJECT_REVIEW` 예시를 더해 권고 세 가지를 하나씩 둔다 (측정 · 시연 시나리오와 다른 가상 사건: 처음 보는 기기 · 카드 · 해외 접속 + 같은 기기를 쓴 다른 고객)
  - **코드 검사:** `NEEDS_CHECK`인 결제의 `unknowns`가 비어 있으면 다시 쓰게 한다(`needs_check_errors`). 예시의 모르는 사실을 그대로 써서 코드가 뺀 뒤 비어도 같다(`emptied_errors`). 직원은 추가 확인 필요를 받으면 무엇을 확인할지 알아야 한다
  - **정상 정황은 같은 종류의 위험 신호만 설명한다:** 평소 비슷한 금액 이력은 고액 신호를 설명하지만 처음 쓰는 기기 · 카드 · 해외 접속은 설명하지 못한다. 설명되지 않은 위험 신호가 남고 그 이유를 모르면 `NEEDS_CHECK`. 1차 실측에서 `measure_mixed`(해외 접속 + 새 기기 vs 평소 금액 이력)가 금액 이력만으로 `ACCEPT_REVIEW`가 나와 넣었다
  - **승인 취소 검토는 정상 고객에게 드문 정황이 하나 이상 있을 때만 (#490):** 드문 정황은 카드사 거절 직후 재시도 · 카드 테스팅 · 같은 카드나 기기를 다른 고객이 씀 · 같은 카드나 기기로 차단된 결제 이력. 해외 접속 · 처음 쓰는 기기 · 처음 쓰는 카드 · 고액 결제는 흔한 신호라 이것들만 겹치면 `NEEDS_CHECK`. 흔한 신호 2개만으로도 "위험 정황 여럿 + 설명할 정상 정황 없음"이 맞아 `REJECT_REVIEW`와 `NEEDS_CHECK` 기준을 동시에 채웠고, 모델이 실행마다 다른 쪽을 골랐다
- **측정:** `run_report --sample tests/fixtures/measure_*.json`(OpenAI gpt-4.1-mini). 고치기 전에는 세 샘플 모두 `NEEDS_CHECK`, 1차 수정 후 `measure_reject` → `REJECT_REVIEW`, `measure_accept` → `ACCEPT_REVIEW`, `measure_mixed` → `ACCEPT_REVIEW`(기대 `NEEDS_CHECK`). 2차 수정(같은 종류만 설명) 후 2회: reject · accept는 기대대로, `measure_mixed`는 `REJECT_REVIEW` · `NEEDS_CHECK`로 갈림. 드문 정황 보강(#490) 후 2회: `measure_reject` → `REJECT_REVIEW` · `measure_accept` → `ACCEPT_REVIEW` · `measure_mixed` → `NEEDS_CHECK`로 2회 모두 기대대로
- **그대로인 것:** 권고는 참고용이고 최종 판정은 직원이 한다. 보고서 형식 · 종합 권고 계산(결정 4) · Spring · 화면은 바꾸지 않는다
- **영향:** AI가 결론을 더 분명히 내면, 직원이 AI와 반대로 판정할 때 사유를 더 써야 하는 경우가 늘어난다(화면의 권고 반대 판정 규칙, `caseDetailView.isOpposing`). 2차의 관리자 승인(권고 반대 매입 허용)과도 이어진다

## 결정 7 — 권고를 판정 기준표(코드)로 (#501)

> #644(결정 13)에서 판정 기준표 4칸 · 권고를 뺀다. 징후 등급 · 정상 사유 · 같은 행동 묶기 규칙은 그대로 쓴다.

  - 1건(시험지 1011)을 단독 실행해 보니 단서는 AI 입력에 들어 있었다. 그런데 AI가 ① 평소 결제 이력(매입 완료 9건)을 정상 정황으로 들어 새 카드 · 새 기기 · 해외 접속까지 맞섰다고 보고 ② 단서를 위험 근거가 아니라 `unknowns`(모르는 사실)로 미뤘다
  - 결정 6의 문장("같은 종류만 설명한다" · "드문 정황")이 있었지만 다른 문장("가족이 같이 쓸 수도")이 이겼다. 사건마다 문장을 덧붙이는 방식(#355 · #479 · #490)으로는 문장끼리 충돌하는 일이 반복된다
- **결정:** 결제별 권고는 코드의 판정 기준표가 정한다. AI는 권고를 고르지 않고, 근거를 모아 이어서 설명한다. 최종 판정은 지금처럼 직원이 한다 (#501 때 `app/agent/evidence.py`, #618부터 Spring `DecisionBasisCalculator` — 결정 11)
  - **징후 나누기:** 고위험 징후(정상 고객에게 거의 없음) — 카드 테스팅(R06) · 차단 목록(R07) · 카드사 거절 직후 재시도(R08) · 같은 카드를 다른 고객이 씀 · 같은 기기를 다른 고객이 씀. 주의 징후(정상 고객에게도 있음) — 고액(R01) · 처음 쓰는 기기(R02) · 처음 쓰는 카드(R03) · 짧은 시간 반복(R04) · 고위험 국가(R05) · 해외 접속(R05가 없을 때) · 같은 IP를 다른 고객이 씀(공유기 · 회사 망에서도 흔해서). 모르는 규칙 코드는 주의 징후로 본다. 예전 영문 코드(`HIGH_AMOUNT` 등)도 같은 규칙으로 읽는다
  - **정상 거래 근거는 정해진 징후만 설명한다(정상 사유):** 사건 전에 비슷한 금액(0.5~1.5배)으로 매입 완료된 결제 2건 이상 → 고액. 사건 결제 앞뒤 10분 안의 결제와 첫 사건 결제 뒤 결제(사건 도중 · 뒤)는 평소 결제로 치지 않는다 (`split_history`의 "그 전 결제"와 같은 기준). 사건은 30분 안의 보류 결제를 합쳐 길어지므로 마지막 사건 결제가 아니라 첫 사건 결제를 기준으로 한다 (#532). 고위험 징후에는 자료만으로 정상 사유를 붙이지 않는다 — 직원 확인으로만 풀린다
  - **"전에 승인된 본인 카드"는 정상 근거로 쓰지 않는다 (Codex 리뷰):** R03이 안 걸린 것은 관리자가 R03을 꺼 둔 경우와 구분할 수 없고, 고객 최근 결제는 카드별 이력이 아니다. P2는 평가 기록(`fds_evaluations.card_token` · 승인 여부)으로 이 값을 계산할 수 있지만 `FdsPaymentEvidence`로 넘기지 않는다. 필요해지면 P2 계약 변경으로 따로 제안한다
  - **같은 행동을 두 번 세지 않는다:** 거절 후 재시도(R08) · 카드 테스팅(R06)이 있으면 짧은 시간 반복(R04)은 그 징후에 포함된 것으로 보고(`countedIn`) 판정에 따로 세지 않는다. 10분 안에 거절된 뒤 다시 결제했다면 이미 짧은 시간에 여러 번 결제한 것이다
  - **판정 기준표:** 정상 사유가 없는 징후로 정한다. 고위험 + 다른 징후 → `REJECT_REVIEW` · 고위험 하나만 → `NEEDS_CHECK` · 주의 징후만 → `NEEDS_CHECK` · 모두 정상 사유 있음 → `ACCEPT_REVIEW`. 종합 권고 계산은 결정 4 그대로다
  - **AI가 하는 일:** 판단 문장 입력에 결제별 "판정 근거"(징후 · 정상 사유 · 기준표 판정, 숫자 · 영문 코드 없이)를 넣는다. AI 출력 형식에서 `recommendation`을 뺐다. AI는 결론 한 줄 · 요약 · 결제별 이유(그 기준표 판정이 나온 이유) · 위험 근거 · 정상 정황 · 모르는 것 · 확인할 일을 쓴다
  - **코드 검사:** 기준표 판정이 `NEEDS_CHECK`인데 `unknowns`가 비면 다시 쓰게 한다 (결정 6의 검사를 기준표 값으로 옮김)
  - **판단 문장도 코드가 쓴다 (#532):** 기준표 판정은 코드가 정해도 결론 한 줄 · 권고 요약 · 결제별 이유를 AI가 써서, 판정과 반대되는 문장(결과는 매입 진행 검토인데 결론은 "승인 취소를 권고")이 그대로 저장될 수 있었다 (PR #529 Codex 리뷰)
    - 이 세 칸은 코드(`app/agent/verdict_text.py`)가 기준표 판정으로 쓰고, AI 출력 형식 · 지시문 · 예시에서 뺐다. 보고서 JSON 모양은 그대로다
    - AI는 요약 · 종합 분석 · 위험 근거 · 정상 정황 · 모르는 것 · 확인할 일(사실)만 쓴다
    - AI 문장에 판단 문구(승인 취소 · 매입 진행을 권고 · 검토)가 섞이면 다시 쓰게 하지 않고 코드가 뺀다 — 같은 문장을 반복하다 조사가 실패한 기록이 있다 (#355). 지난 결제 상태("승인 취소된 결제")는 사실이라 남긴다
  - **FDS 점수 없음 (#532):** 점수가 없으면(평가 오류 · 평가 없음) "FDS 평가 결과 미확인" 주의 징후를 붙여 "징후 없음 → 매입 진행 검토"가 되지 않게 한다. 판정을 올리지도 내리지도 않는다 — 고위험과 겹치는 "다른 징후"로 세지 않는다. 지금은 보고서 생성 전 검사가 점수 없는 결제를 먼저 막아 방어용이다
- **확인:** 단위 테스트(`tests/test_decision_basis.py`)에 시험지 사건 모양을 옮겼다. 1011(같은 카드 다른 고객 + 새 카드 · 기기 · 해외) → `REJECT_REVIEW`, 1066 · 1015(거절 후 재시도 + 짧은 시간 반복, 한 행동으로 셈) · 1014(해외 여행, 주의 징후만) → `NEEDS_CHECK`, 평소 금액의 고액 → `ACCEPT_REVIEW`. 1066(카드 테스팅 모양 사기)은 지금 자료로 한도를 모르고 다시 누른 정상 고객(1015)과 가를 수 없어 추가 확인으로 둔다 (매입 진행이 아니므로 위험한 놓침은 아니다)
- **그대로인 것:** 권고는 참고용이고 최종 판정은 직원이 한다. 권고 값 3종 · 종합 권고 계산 · Spring 저장 전 검사 · 반대 판정 사유 규칙(`caseDetailView.isOpposing`)
- **영향:**
  - 화면: "AI 권고"를 "기준표 판정"으로 바꾸고 판정 근거를 보여 준다. 판정 패널(P3) · 사장님 화면은 문구만 바뀐다 (#501 화면 PR)
  - 같은 근거면 언제나 같은 권고가 나온다. 권고 성적표는 이제 AI가 아니라 기준표를 재는 셈이므로, AI 품질은 문장(이유 · 모르는 것 · 확인할 일)으로 본다
  - 기준표의 짝과 등급은 합성 시험지 기준이다. 실제 결제(Shadow 기록)가 쌓이면 다시 본다. ML 참고 위험도를 넣을 때도 이 기준표에 주의 징후로 더한다 (ML 혼자서 승인 취소 검토가 되지 않게)

## 결정 8 — AI는 판단하지 않고 조사한 사실을 주제별로 전달 (#548)

- **상황:** #532 뒤에도 AI 출력 칸이 판단 모양이었다 — 결제별 위험 근거 · 정상 근거 · 종합 분석. 어떤 사실을 "정상 쪽"에 넣는 것 자체가 판단이라, AI가 기준표와 반대로 분류했다 (예: 사건 결제 앞뒤 10분 안의 같은 연속 결제를 "모두 매입 완료라 평소 결제"로 정상 쪽에 씀)
  - 코드는 이를 단어 목록으로 뒤늦게 지워 왔다 (#542 · #545). 자연어는 단어로 다 가를 수 없어 구멍을 막을 때마다 맞는 문장("평소 결제가 아닙니다")이 잘못 지워졌고, Codex 리뷰가 3차까지 이어졌다
- **결정:** AI의 역할은 전달자다. 사람이 일일이 조회하기 어려운 사실을 모아 주제별로 보여 준다. 위험 · 정상 분류는 기준표(결정 7), 최종 판정은 직원
  - **주제 = 조회 도구 하나:** 결제 이력(`get_payment_history`, 번호 `이력-N`) · 같은 카드 · 기기 · IP(`find_linked_payments`, `연결-N`) · 카드 · 기기 · 접속 정보(`get_fds_evidence`의 접속 정보, `접속-N`) · 비슷한 과거 사건(`find_similar_cases`, `과거-N`). 사건 결제 자체는 결제 카드 · 기준표에 있어 주제로 두지 않는다. 등록표(`app/agent/facts.py`의 `FACT_TOPICS`)에 한 줄 + 사실 뽑는 함수만 더하면 도구가 늘어도 번호 · 출력 형식 · 검사 · 저장이 따라온다
  - **사실 번호:** 코드가 Tool 기록을 사실 한 줄씩으로 만들고 번호를 붙인다. AI에게 줄 때와 보고서에 저장할 때 같은 함수(`fact_catalog`)로 만들어 번호가 어긋나지 않는다. 조회 기록이 없는 주제(조회 실패 · 안 부름)는 빼서 "없다"는 사실로 보이지 않게 한다 (조회 못 한 것은 지금처럼 코드가 한계 줄에 쓴다)
  - **AI 출력:** `summary`(문장 + 근거 번호 2~3개) · `topics`(주제별 문장 + 근거 번호) · `additionalChecks`(확인할 일, 번호 없음). 출력 형식(JSON Schema)이 주제 키와 번호 목록(`enum`)을 고정한다. 모르는 사실(`unknowns`)은 코드가 쓴다
  - **검사:** 단어로 뜻을 추측하지 않는다. ① 근거 번호가 있고 준 번호인지, 주제 칸에는 그 주제 번호인지 ② 문장 속 숫자가 인용한 사실 안에 있는지(작은 수도 본다) ③ 겉모양 — 영어 코드값 · 한자 · 영어 단어 · "확률" 같은 단정 · "~해야" 같은 판단 문구 · 예시 베끼기(요약만, #581) · 반복. 걸리면 코드가 지우지 않고 다시 쓰게 한다 (횟수를 넘으면 `NARRATIVE_INVALID`, 자동 판정 없음)
  - **#581 — 확인할 것(`additionalChecks`)은 예시 베끼기 검사에서 뺀다.** 확인할 것은 사실이 아니라 할 일이라, 사건에 맞으면 예시와 같아도 된다. 요약은 사실 문장이라 예시 사건의 사실을 베끼면 거짓이 될 수 있어 검사를 둔다
    - 측정(`scripts/measure_summary.py`, 샘플 5개): OpenAI(gpt-4.1-mini)는 "카드사에 거절 사유 문의"를 카드사 거절이 있는 사건에서만 썼는데, 검사가 4번 모두 돌려보내 다시 쓰기의 주원인이 됐다(1차 통과 1/5). 거절이 없는 사건에서는 쓰지 않았다
    - Qwen 7B는 거절이 없는 사건에도 확인할 것 예시를 썼다(Case 8과 같은 문제) — Qwen 경로는 PC 개발용이라 보고서 품질을 보장하지 않는다(같은 측정 성공 2/5). 배포 · 시연은 OpenAI(#453). 근본 해결은 확인할 것을 코드 사전이 채우는 일(PLAN T6a)
  - **저장:** `summary`는 문장 목록 그대로 둔다 — 사장님 화면(`MerchantCaseQueryService`, P3)이 읽는다. `factTopics`(주제별 문장 + 번호) · `facts`(번호별 사실 + `evidenceId`)를 더하고 `overallAnalysis` · 결제별 `riskEvidence` · `normalEvidence`를 뺐다. Spring 저장 전 검사는 `overallAnalysis` 대신 `factTopics` · `facts`를 필수로 본다. 고정 보고서(`FixedReportGenerator`)는 둘 다 빈 목록
  - **예전 보고서:** 데이터는 지우지 않는다(물리 삭제 금지). 화면은 예전 AI 문장(위험 쪽 · 정상 쪽 · 종합 분석)을 보여 주지 않고 "예전 형식 보고서라 AI 조사 사실이 없어요"만 보여 준다. 코드가 만든 칸은 그대로다
- **버린 대안:**
  - 단어 필터를 계속 보강 — 자연어 문장 모양이 끝없이 달라 맞는 문장을 지우는 일이 반복된다 (#542 · #545 리뷰 3차)
  - 위험 · 정상 칸은 두고 AI에게 "판단하지 말라"고만 지시 — 칸 이름 자체가 분류를 요구한다
  - 평가어("정상" · "의심") 금지 목록 추가 — 또 하나의 단어 필터라 같은 문제가 생긴다. 프롬프트로만 지시한다
  - 걸린 문장을 지금처럼 코드가 빼기 — 빠진 문장 때문에 칸이 비면 결국 다시 쓰기가 필요했고, 무엇이 왜 빠졌는지 남지 않는다. 지금 기본 제공자(OpenAI)는 지적하면 고쳐 쓴다
- **영향:**
  - ai-server: `facts.py` 추가, 출력 형식 · 검사 · 프롬프트 · 조립 변경. 단어 필터(`sanitize_narrative` · `drop_rule_only` · 연속 결제 필터 · "다른 근거 없음" 검사)와 그 테스트 삭제
  - backend(P4): 저장 전 검사 섹션, 고정 보고서 모양
  - 화면: "AI 참고 설명(위험 쪽 · 정상 쪽)" · "종합 분석" → "AI가 조사한 사실(주제별)", 번호를 누르면 사실 원문과 조회 기록
  - 다시 쓰기가 조금 늘 수 있다 (예전 Qwen 7B는 같은 문장을 반복해 실패한 기록이 있다). 로컬 시연으로 실패 빈도를 본다

- **보충 — 주제별 문장 카드를 빼고 요약이 사실을 잇는다 (#559):**
  - 상황: 실제 화면에서 주제별 문장("AI가 조사한 사실" 카드)이 바로 아래 표 카드(고객 최근 결제 · 같은 카드 · 기기 · IP · 비슷한 과거 사건)를 문장으로 다시 읽을 뿐이었다. 주제별로 나눠 쓰니 같은 결제(최근 30일 결제 2건 = 사건 앞뒤 10분 안 결제 2건)를 따로 적어 "평소 결제가 2건 있다"로 읽힐 수 있었고, 번호 칩("이력-1")도 사람에게 헷갈렸다
  - 결정: AI 출력의 주제별 문장(`topics`)과 보고서 `factTopics`를 뺐다. 요약(`summary`)을 1~3문장으로 하고, 주제를 넘나들며 같은 결제를 이어 쓰게 지시한다. 사실 하나하나는 표 카드가 맡는다
  - **#581 보충 — 3문장에 못 담으면 이어 쓰기:** 요약은 여전히 1~3문장을 지시하되 "다 못 담으면 이어 써도 된다"를 둔다. 문장 수는 실패 사유로 쓰지 않는다 — 최대 문장 수는 그 사건의 사실 수(문장마다 사실이 하나 이상이라 사실마다 한 문장씩 써도 막히지 않는다). 3문장이 꽉 찬 채 눈여겨볼 사실이 빠지면 다시 쓰기 안내에 "다음 문장으로 이어 써라"를 붙인다
    - 이유: 고객 이력 90일(#581)로 이력 사실이 하나 늘자, AI(gpt-4.1-mini)가 이력 사실마다 한 문장씩 써 3문장을 채우고 같은 IP 겹침(눈여겨볼 사실)을 다시 써도 매번 빠뜨렸다(측정 3번 · 9답 모두). 상한이 "사실 다시 읽기"는 못 막고 "눈여겨볼 사실은 꼭" 검사와 부딪혀 보고서를 실패시켰다
    - 길이는 읽기 편의이고 거짓을 막는 장치는 따로 있다(사실 번호 · 인용 사실 안의 숫자 · 예시 요약 베끼기 · 판단 문구 · 눈여겨볼 사실 포함). "없음" 사실을 따로 한 문장으로 써 요약이 4~5문장이 될 수 있다 — 거짓이 아니면 받는다 (11/06 사용자 결정)
    - 버린 대안: 상한 5 고정(결제가 많거나 도구가 늘면 다시 막힌다) · "넷째 문장부터는 새 눈여겨볼 사실만" 검사(측정에서 AI가 넷째 · 다섯째 문장에 "없음" 사실을 써 손님 2명이 새로 실패) · 이력 사실을 코드가 한 줄로 합침(사실 번호 → 표 카드 링크까지 닿는 큰 변경). 다시 써도 빠지면 코드가 빠진 사실을 덧붙이는 안전망은 #591에서 채택했다 (결정 10)
  - 저장: `summary`(문장 목록, 사장님 화면)는 그대로, `summaryFacts`(문장 + 근거 번호)를 더했다. Spring 저장 전 검사는 `factTopics` 대신 `summaryFacts`를 요구한다. 접속 정보 사실에는 `paymentId`를 둔다
  - 화면: 번호는 보이지 않는다. 요약 문장 끝에 근거 사실의 표 카드 제목으로 작은 링크("› 고객 최근 결제")를 붙이고, 누르면 그 카드로 이동해 잠깐 강조한다. 접속 정보는 결제 카드로 간다. 조사 요약 박스의 징후 색 밑줄과 뜻이 겹치지 않게 밑줄 대신 글자 링크로 했다
  - 버린 대안: 주제별 카드를 표로 바꾸기(코드가 그리는 표와 같은 표가 두 번 나온다) · 표 카드마다 AI 한 줄(배치 작업이 크다) · 코드 점검표(표 카드와 겹친다) · 번호 칩 유지(헷갈린다) · 밑줄 링크(징후 색 밑줄과 겹친다). 시간축 · 관계 그림은 다음 작업으로 미뤘다
  - #548로 만든 보고서(`factTopics`만 있음)는 링크 없이 요약 문장만 보인다

## 결정 9 — 기본 조회는 코드가, AI는 추가 조사만 고른다 (#578)

- **상황:** 기본 근거 5종(결제 목록 · FDS 근거 · 비슷한 사건 · 고객 최근 결제 · 같은 카드 · 기기 · IP)을 다 봐야 조사가 끝났다. AI가 빠뜨리면 다시 요청하고, 그래도 안 보면 코드가 보충했다
  - 그래서 AI가 무엇을 고르든 보고서 내용은 같았다. 고르기에 걸린 시간만 남았다: Case 5 기준 13.4초 중 9.2초(조사 시간의 69~79%)
- **결정:** 기본 조회 5종은 코드가 조사마다 한 번씩 한다 (`graph.py`의 `base`). FDS 근거는 사건 결제 번호를 코드가 넣어 한 번에 받는다
  - 실패 규칙은 그대로다: 결제 목록 · FDS 근거를 못 보면 조사 실패(직원은 수동 판정), 참고 3종은 그 칸만 비우고 보고서를 만든다
  - AI는 기본 조회 결과를 보고 더 볼 것이 있을 때만 추가 조회 도구를 고른다. 추가 도구 목록(`EXTRA_TOOLS`)이 비어 있으면 AI를 부르지 않는다
  - **첫 추가 도구 `get_payment_history_90d` (#581):** 같은 고객의 최근 90일 결제. 도구 설명에 "30일 결제로 평소 결제를 볼 수 있으면 부르지 않는다"를 둔다. 인자가 없고 90은 코드가 넣는다(AI가 지어낸 인자는 버림). Spring에는 `lookbackDays=90`으로 묻고, 기본 조회는 기간을 보내지 않는다(30일)
  - AI가 90일을 조회하면 보고서 "고객 최근 결제" 표와 AI에게 주는 사실이 둘 다 90일 결과로 바뀐다 — 마지막 조회를 쓴다. 최근 순 20건이라 30일 결제는 90일 결과에 들어간다(11/06 사용자 결정). 90일 조회가 실패하면 30일 결과를 그대로 쓴다
  - **판정 기준표(정상 근거 · 권고)는 기본 조회 30일로만 계산한다.** AI가 90일을 불렀는지에 따라 같은 사건의 권고가 달라지면 판정 패널의 "권고와 반대면 사유" 규칙 · 판정 기록의 반대 여부 · 사장님 화면 권고가 흔들린다(P3). 기본 조회가 실패하면 90일 결과로 대신하지 않고 이력 없이 계산한다 (Codex 리뷰: 90일 결과가 "최근 30일 비슷한 금액의 결제 2건 매입 완료"로 표시됐다)
  - 추가 도구가 생겨 기본 조회 뒤에 "추가로 볼 조회 고르기"(`DECIDE`)가 늘 한 번 돈다. 화면의 생성 중 문구도 기본 조회 뒤 "추가로 볼 조회를 고르는 중"으로 바꿨다
  - 고르기 틀은 그대로 옮겼다: 허용 목록(기본 조회 도구도 거절) · 도구 설명에 없는 인자 버리기 · 최대 3번(`AI_SERVER_AGENT_MAX_EXTRA_CALLS`, 거절한 호출도 센다)
  - 추가 조회가 실패하면 AI에게는 정해진 문장만 준다. 오류 원문(내부 주소 등)은 외부 AI로 보내지 않고 ai-server 로그에만 남긴다
  - 조사 과정 기록: 기본 조회는 `TOOL`/`SYSTEM`, 추가 조사는 `DECIDE`/`AI` · `TOOL`/`AI`. 단계 이름은 그대로라 예전 보고서도 같은 화면으로 보인다
  - 기본 조회도 지금처럼 ai-server가 Tool API(`/internal/ai/tools/*`)로 조회한다. 권한 검증 · 데이터 범위는 결정 1 그대로다
- **영향:**
  - ai-server: 조사 흐름(`graph.py`), 도구 목록(`tools.py`의 `ExtraTool` · `EXTRA_TOOLS`), 조사 지시문, 설정(`agent_max_tool_calls` · `agent_max_nudges` → `agent_max_extra_calls`). 증거 출처의 "(자동 보충)" 꼬리는 뺐다(기본 조회가 정상 경로). Spring에 보내는 `toolCalls[].filledBySystem`은 기본 조회면 `true`
  - 화면: 생성 중 첫 문구 "사건 근거를 보고 첫 조회를 고르는 중" → "기본 조회 실행 중". 보고서 · 조사 과정 탭 모양은 그대로
  - Spring: 변경 없음

## 결정 10 — 결론 먼저 보고서: 개요 · 판정 전에 확인할 것은 코드가, 안전망은 표시해서 (#591)

- **상황:** 보안 직원이 보고서를 열면 조사 요약 · 표 카드 · 판정 근거가 나란히 있어 "무슨 사건이고 판정 전에 무엇을 확인해야 하나"를 직접 찾아야 했다. 확인할 것은 AI가 2~3개 써서 사건마다 들쭉날쭉했고(결정 8의 예시 베끼기 문제), AI가 눈여겨볼 사실을 끝까지 빠뜨리면 보고서 전체가 `NARRATIVE_INVALID`로 실패해 표 · 근거도 볼 수 없었다
- **결정:**
  - **화면 순서:** ① 결론(개요 한 줄 · 기준표 판정 세 칸 · 징후 표와 판정 전에 확인할 것 체크) → ② 사건 경위 → ③ 연결(조사 요약 + 표 카드) → ④ 판정 근거 상세(결제별) → ⑤ 조사 범위 · 한계, 화면 아래 고정 판정 줄. ①에는 코드가 쓴 칸만 두고 AI 문장은 ③에만 둔다 (#543)
  - **개요 한 줄은 코드가 쓴다:** 고객 · 결제 건수(금액 · 시각) · 걸린 FDS 규칙 이름 · 지금 상태. 모두 Tool 기록 값이고 판단 문구는 없다 (판정은 바로 아래 판정 칸이 보여 준다)
  - **판정 전에 확인할 것은 징후마다 코드 사전(`CHECK_BEFORE`, #618부터 Spring `DecisionBasisCalculator`):** 무엇을 확인할지는 징후가 정하므로 AI가 고르지 않는다. 새 징후를 추가하면 사전에도 한 줄 넣는다(테스트가 검사). AI의 확인할 것(`additionalChecks`)은 그대로 받아 "AI 추가 제안"으로 작게 보여 준다 — 지시문은 이번에 바꾸지 않았다(전후 측정이 섞이지 않게)
  - **체크 상태는 화면에서만:** 판정 기록이 아니라 읽는 도구다. 새로고침 · 버전 전환이면 비워진다. 저장하려면 새 표 · API가 필요하고 P3 판정 영역과 겹친다
  - **안전망 (결정 8 "몰래 고치지 않는다"를 개정):** 다시 쓰기를 다 쓴 뒤 남은 오류가 "눈여겨볼 사실 빠짐"뿐이면 실패 대신 AI 요약을 받고, 빠진 사실 번호를 `summaryAppended`에 넣는다. 사실 문장은 처음부터 코드가 쓴 것이라 거짓이 아니다. 화면은 "요약에 빠진 사실 (시스템이 덧붙임)", 조사 과정은 "시스템이 덧붙임"으로 남긴다 — 몰래 고치는 것이 아니라 덧붙였다고 표시한다. 숫자 · 형식 오류가 하나라도 남으면 지금처럼 실패한다
  - **조사 범위 3칸(`scope`):** 조회 기록으로 코드가 나눈다. 기존 한계 문장 목록(`limitations`)은 다른 화면 · 고정 보고서가 읽어 그대로 둔다
  - **90일 표의 30일 경계선(`inBasis`):** 날짜로 다시 세지 않고, 기준표가 본 30일 기본 조회 결과에 그 결제가 있는지로 정한다 (결정 9 — 기준표는 30일만 본다)
  - **측정:** `scripts/measure_summary.py`가 사건마다 안전망이 덧붙인 사실 수를 기록한다. 안전망이 생기면 "성공"이 쉽게 늘어 AI 요약 품질과 섞이므로 둘을 나눠 읽는다
- **버린 대안:**
  - 안전망 대신 다시 쓰기 횟수 늘리기 — #581 측정에서 같은 답을 3번 냈다. 비용 · 시간만 는다
  - 빠진 사실이 들어가게 코드가 AI 요약 문장 순서를 바꾸거나 고쳐 쓰기 — AI 글의 흐름이 깨지고 결정 8과 정면으로 부딪힌다
  - 확인할 것을 AI 지시문에서 빼기 — 측정 결과가 구조 변경 때문인지 지시문 때문인지 섞인다. 필요하면 다음 작업에서 따로 잰다
  - 체크 상태 서버 저장 — 위 "체크 상태는 화면에서만"
  - 고정 보고서(AI 끔)에도 개요 한 줄 — backend 변경이 생기고 긴급 정지 작업과 같은 파일 근처라 그때 같이 한다
- **영향:**
  - ai-server: `schemas/report.py`(선택 칸 6개) · `evidence.py`(사전) · `facts.py`(`notable`) · `assemble.py`(개요 · 조사 범위 · `inBasis`) · `narrative.py` · `graph.py`(안전망) · `scripts/measure_summary.py`
  - 화면: `ReportFull` 재배치 · `ReportConclusion` 추가 · 조사 요약 점 목록(3문장 뒤 더 보기, 숨은 문장에만 있는 눈여겨볼 사실 수 표시) · 고객 최근 결제 90일 표시 · `CaseReportPage` 판정하러 가기 연결
  - Spring: 본문 코드 변경 없음 (저장 전 검사가 새 선택 칸을 통과시키는지 테스트만 추가)

## 결정 11 — 판정 기준표 계산을 Spring으로 (#618)

> #644(결정 13)에서 칸 · 권고 · 종합 권고 계산과 칸 ↔ 권고 저장 전 검사를 뺀다. 징후 · 정상 근거 · 확인할 것 계산과 Tool `get_decision_basis`는 Spring에 그대로 둔다.

- **상황:** #501(결정 7)에서 권고를 AI 문장 대신 코드의 기준표로 옮길 때, 보고서를 만들던 ai-server(Python `evidence.py`)에 기준표를 두었다. 그 결과
  - AI 서버가 꺼지거나 조사가 실패하면 기준표도 없었다. AI를 끈 고정 보고서는 권고가 늘 `NEEDS_CHECK`였다
  - 기준표 입력(결제 · FDS 근거 · 고객 30일 이력 · 같은 카드/기기/IP)은 모두 Spring Tool 값인데, FDS 규칙 등급표(R01~R08 → 고위험 · 주의)가 Python에 따로 있어 규칙이 바뀌면 어긋날 수 있었다
  - Spring은 권고가 허용된 3가지 값인지만 검사해, 근거와 다른 권고가 저장돼도 막지 못했다
  - #548 이후 AI 입력에 기준표가 들어가지 않아(결정 8), ai-server가 기준표를 계산할 이유도 없어졌다
- **결정:**
  - 기준표는 Spring `investigation/report`의 `DecisionBasisCalculator`가 계산한다. 계산 규칙은 결정 7 그대로 옮겼다(같은 시험지 사건 · 같은 기대값 테스트 `DecisionBasisCalculatorTests`). 조회 · 저장은 하지 않는 순수 계산이다
  - 새 Tool `GET /internal/ai/tools/get_decision_basis?caseId=` (`DecisionBasisToolResponse`): 결제별 `basis`(보고서 `paymentAnalyses[].basis`와 같은 키). 고객 이력은 늘 30일 기본 조회(#581), 고객 이력 조회가 실패하면 정상 사유 없이 계산한다(정상 사유만 빠져 매입 진행 쪽으로 올라가지 않는다). 연결 결제 조회가 실패하면 기준표를 주지 않는다 — "연결 징후 없음"으로 계산하면 고위험 징후(같은 카드 · 기기)가 빠져 승인 취소 검토가 내려가거나 매입 진행 검토까지 나온다(#618 Codex 리뷰). 고정 보고서도 같다(기준표 없이 추가 확인). 금액 · 요청 시각 · FDS 근거를 모르는 결제는 목록에 없다
  - ai-server는 기본 조회 맨 뒤(6번째, 앞 조회의 증거 번호가 바뀌지 않게)에 이 Tool을 부르고 받은 값을 그대로 싣는다. 조회가 실패하거나 결제가 빠져 있으면 그 결제는 `NEEDS_CHECK` + 한계 줄 "판정 기준표를 받지 못한 결제는 권고를 추가 확인으로 두었습니다." — 기준표 없이 승인 취소 · 매입 진행 쪽 권고를 만들지 않는다. AI 추가 조사 고르기 입력에는 넣지 않는다(AI가 판정을 보고 조사 방향을 정하지 않게)
  - Spring 저장 전 검사: 기준표가 있는 결제는 권고가 칸의 권고와 같아야 하고, 기준표가 없는 결제는 `NEEDS_CHECK`만 받는다. 종합 권고는 결제별 권고로 정한 값(결정 4)과 같아야 한다
  - AI를 끈 고정 보고서도 같은 계산기로 결제별 기준표 · 권고 · 이유 · 종합 권고를 채운다
  - 문구: 징후가 0개인 결제도 `ALL_EXPLAINED` 칸이라 "모든 징후에 정상 사유 있음"이 실제와 달랐다. 칸 값은 그대로 두고 문구만 "정상 사유 없는 징후 없음"으로 바꾼다(권고 요약 · 결론 한 줄 · 화면 기준표 4칸 · 판정 세 칸)
  - **주의 징후 무게는 넣지 않는다 (#614 기준선):** 시나리오 50건에서 규칙이 걸린 19건은 사기 · 정상 모두 `NEEDS_CHECK`였다. 무게 후보를 넣어 보면 — 주의 3개 이상 → 승인 취소 검토는 F2 계정 탈취(FDS 차단이라 사건이 열리지 않음)만 바꾸고 1014 해외 여행 정상 고객(새 기기 · 새 카드 · 해외)을 승인 취소 검토로 올린다. 고액 + 단시간 반복은 실제 사건 2건(F1)을 바꾸지만 단체 주문 분할 결제와 가를 자료(주문 정보)가 없다. 실제 사건을 가르는 데 필요한 것은 무게가 아니라 정상 사유 자료(주문 · 기기 로그인, T5 도구)라 그 뒤에 다시 본다
- **버린 대안:**
  - ai-server에 기준표 유지 — 위 상황 그대로(AI 꺼짐 = 기준표 없음, 등급표 이중 관리, 근거와 다른 권고를 Spring이 못 막음)

  - 배포 순서: Spring 먼저. ai-server만 먼저 나가면 기준표 조회가 404로 실패해 모든 결제가 추가 확인이 된다(조사 자체는 성공)

## 결정 12 — 주문 정보 Tool을 P5 공개 창구로, 기본 조회로 (#634)

- **상황:** 결정 1은 `get_order_context`를 "Spring이 CakeShop을 HTTP로 조회"로 두고 제공 범위를 §5.7 미결로 남겼다. 그 사이 CakeShop이 결제 준비 요청(ADR-0064 2절)에 주문번호 · 상품명 · 주문 시각과 주문자 · 픽업자 연락처(#602)를 보내게 됐고, 돈워리는 P5 `payment_sessions` · `payment_order_contacts`에 저장한다. 제공 범위는 CakeShop · P5와 합의했다 (11/07 사용자 확인). 구매자 로그인 기록은 이번 범위가 아니다(추후 논의)
- **결정:**
  - Spring `investigation/report`의 `OrderContextFinder`가 사건에 묶인 결제 ID만 P5 `payment.api.PaymentOrderReader.findOrders`에 넘겨 읽는다. CakeShop HTTP 호출은 없다. `investigation` → `payment :: api` 의존은 이미 허용돼 있다
  - 새 Tool `GET /internal/ai/tools/get_order_context?caseId=` (`OrderContextToolResponse`). 결제마다 `provided`(결제 준비 세션 있음) · `orderRef` · `orderName` · `orderGroup` · `orderToPaymentSeconds` · `ordererProvided` · `ordererPhoneGroup` · `pickupDiffers`
  - **주문자 이름 · 전화는 원문 · 가린 값 · 지문 어느 것도 P5 밖으로 내보내지 않는다** ([ADR-0082](0082-insider-access-security.md) 1절). 같은 전화인지는 P5가 저장된 지문(키 버전 + HMAC)으로 비교해 사건 안 묶음 번호(1, 2 …)로만 알린다. 같은 주문인지는 Spring이 주문번호로 묶음 번호를 매긴다. 픽업자는 원래 "주문자와 다름" 여부만 저장돼 있다
  - 값이 나가지 않으므로 직원 연락처 열람(`CustomerContactReader`, 결제 1건 · 접근 기록)과 달리 접근 기록을 남기지 않는다
  - **주문번호 · 상품명은 AI 입력에서 뺀다** — 가맹점이 쓴 글자라 지시문이 섞일 수 있다(프롬프트 주입). ai-server `tools.llm_content`가 빼고, 사실 목록(`facts.py` 주문 주제)도 이 둘을 쓰지 않는다. 보고서 `orderContext` 표에는 코드가 그대로 실어 직원만 본다
  - **기본 조회**(코드가 조사마다, 결정 9). 같은 사건엔 늘 같은 값이 있어야 나중에 기준표 정상 사유(한 주문을 나눠 낸 결제 등)에 쓸 수 있다. 참고 자료라 실패하면 `orderContext=null` + 한계 줄 "주문 정보를 조회하지 못했습니다."로 보고서는 만든다. 판정 기준표 · 권고는 이번에 바꾸지 않는다
  - 결제 준비 세션이 없는 결제(결제창을 거치지 않은 결제 · 예전 데이터)는 `provided=false` — "주문 정보 없음"이지 "다름"이 아니다
  - 결제창은 접수 · 승인(보류 이벤트 → 사건 → 보고서)이 끝난 뒤에 세션에 결제 ID를 저장한다. 그 사이에 만든 보고서(특히 AI를 끈 고정 보고서)도 주문 정보를 갖도록, 결제 ID로 세션을 못 찾으면 접수 기록의 결제 시도 키(= 세션 `attemptKey`)로 찾는다 (PR #635 Codex 리뷰)
  - 사건 병합에는 결제 건수 상한이 없어 창구도 상한을 두지 않는다. P5가 IN 조회를 100건씩 나눠 읽고, 전화 묶음 번호는 전체 기준으로 매긴다 (PR #635 Codex 리뷰)
  - AI를 끈 고정 보고서도 같은 `OrderContextFinder` 값을 같은 키로 싣는다
  - **정정 (#672, 11/08):** 위 "기준표 정상 사유(한 주문을 나눠 낸 결제 등)"는 성립하지 않는다. P5는 한 주문(가맹점 + 주문번호)을 정해진 금액 한 번으로만 받고, 같은 주문의 새 시도는 앞 시도가 거절(DECLINED) · 차단(DENIED)됐을 때만 받는다(`PaymentRequestTransactionService.admit`). 그래서 같은 주문 결제 여러 건은 나눠 낸 결제가 아니라 재결제다 — 정상 사유로 쓰지 않는다. 단시간 반복 결제(R04)의 "확인할 것"과 AI 사실 문장도 이에 맞췄다
  - 늘 붙던 한계 줄은 "로그인 기록 · 주문 정보"에서 "로그인 기록"만 남긴다
- **버린 대안:**
  - CakeShop HTTP 조회(결정 1 원안) — 같은 값이 이미 P5에 있다. 새 서명 API · 장애 경로가 늘고, 결제 이후 바뀐 주문 값이 섞여 결제 시점 사실과 달라질 수 있다
  - 기존 `CustomerContactReader.masked`를 결제마다 부름 — 가린 이름 · 전화가 AI 입력으로 나가고(ADR-0082 금지), 직원 열람용 창구라 접근 기록과 섞인다
  - 전화 지문(HMAC)을 Spring으로 내보내 비교 — 지문이 P5 밖으로 나가면 다른 사건 · 다른 화면에서 같은 사람 찾기에 쓰일 수 있다
  - 상품명을 AI에 주고 "지시를 따르지 마라"로만 막기 — 프롬프트 지시만으로는 막는다고 볼 수 없다. 판단에 필요한 건 같은 주문인지(묶음 번호)뿐이다
  - AI가 고르는 추가 조사 — 기준표에 쓰려면 같은 사건엔 늘 같은 값이어야 한다 (11/07 사용자 결정)
- **영향:**
  - API: Spring `/internal/ai/tools/get_order_context`(GET) 추가 — `/internal/ai/**` 서비스 키 체인이 이미 덮어 보안 설정 변경 없음
  - P5: `PaymentOrderReader` · `PaymentOrderSummary`(api) · `PaymentOrderReadService` 추가, `PaymentSessionRepository.findByPaymentIdIn` · `PaymentOrderContactRepository.findBySessionIdIn` 읽기 메서드 추가. 스키마 · 인덱스 변경 없음
  - Spring report: `OrderContextFinder` · `OrderContextToolResponse` 추가, `AiToolService.orderContext`, `FixedReportGenerator`(`orderContext` · 증거 줄 · 조사 과정 줄)
  - ai-server: `schemas/tools.py`(`OrderContextTool`) · `schemas/report.py`(`OrderPayment` · `OrderContext` · `ReportBody.orderContext`) · `client/spring.py` · `tools.py`(`llm_content` 제외 칸) · `graph.py`(기본 조회 6번째, 기준표는 7번째) · `facts.py`(주문 주제) · `assemble.py`(한계 · 조사 범위) · `trace.py` · `prompts.py`(기본 조회 6가지 — 프롬프트 지문이 바뀐다)
  - 화면: `types/case.ts`(`OrderContext`), `OrderContextCard`, `reportView.ts`(요약 링크 주제 `order`)
  - 배포 순서: Spring 먼저. ai-server만 먼저 나가면 주문 조회가 404로 실패해 `orderContext=null` + 한계 줄(조사 자체는 성공)

## 결정 13 — 판정 권고를 보고서에서 뺀다: 보고서는 자료와 확인할 것만 (#644)

- **상황:**
  - #614 기준선(정답이 있는 시나리오 결제 50건)에서 기준표 권고는 FDS 규칙 결과를 다시 말하는 수준이었다. 규칙이 하나라도 걸린 19건은 사기 · 정상 모두 `NEEDS_CHECK`, 걸리지 않은 결제는 대부분 `ACCEPT_REVIEW`였다. 사기 23건 중 `REJECT_REVIEW`는 0건이다 (결정 11)
  - 칸을 세게 만드는 방법(주의 징후 무게)은 정상 손님을 올렸다(1014 해외 여행). 정상 사유 자료(주문 · 로그인)를 더해도 "칸 하나가 판정을 대신하는" 모양은 같다
  - 권고는 참고용이라고 적어도 결론 맨 위 · 아래 판정 줄 · 사건 상세 요약 카드 · 가맹점 화면에 되풀이돼 판정처럼 읽혔다. 직원이 권고 쪽으로 끌릴 수 있고(자동화 편향), 근거가 약한 권고가 가맹점에도 나갔다
  - 보고서 화면에 같은 정보가 여러 곳 되풀이됐다 — 결제 2건 사건 기준 판정 권고 9곳 · 징후 6곳 · 정상 사유 4곳(화면 초안 비교, 11/07). 화면 전체가 "왜 이 판정인가"를 설명하는 순서로 짜여 있어서다
- **결정:** 보고서는 사람이 여러 화면에서 긁어 모으던 자료를 모으고, 징후마다 무엇을 확인하면 되는지 알려 준다. 판정 권고(승인 취소 검토 · 추가 확인 · 매입 진행 검토)는 만들지도 보여 주지도 않는다. 판정은 지금처럼 보안 직원이 한다
  - **남기는 것:** 징후(`signals` — 고위험 · 주의 등급, 같은 행동 묶기 `countedIn`) · 정상 근거(`normals` — 어떤 징후를 설명하는지) · 징후별 확인할 것(`checkBefore`) · FDS 점수 · 걸린 규칙 · ML 참고 위험도 · 근거 자료 카드 · 조사 범위. 징후 등급과 정상 사유 규칙은 결정 7 그대로다
  - **빼는 것:** 결제별 `recommendation` · `reason`, 기준표 칸 `basis.rule` · `basis.recommendation`, `verdict`(결론 한 줄 · 종합 권고), `recommendation.summary`(권고 요약). 결정 4의 종합 권고 계산, 결정 7의 기준표 4칸, 결정 11의 칸 ↔ 권고 저장 전 검사가 이 결정으로 끝난다
  - **"어디부터 볼지":** #501에서 권고를 없애지 않은 이유는 반대 판정 사유 규칙 · 사장님 화면이 권고를 쓰고, 직원이 볼 출발점이 사라진다는 것이었다(대안 표). 앞의 두 곳은 함께 없앤다(아래). 출발점은 징후 등급(고위험 먼저, 색)과 지난 사건 비교가 맡는다. 지난 사건 비교는 같은 규칙 조합으로 끝난 사건의 징후 · 정상 근거 · 직원 판정과 사유를 줄 단위로 놓는다. 직원이 실제로 내린 기록이라 칸 계산보다 근거가 분명하다. 다만 같은 규칙 조합만으로 고른 사건이라 "참고 자료"로 표시하고, 판정을 요약하는 해석 문장은 붙이지 않는다
  - **P3 판정 화면:** "권고와 반대로 판정하면 사유를 길게" 규칙(`caseDetailView.isOpposing` · `DecisionPanel`)과 판정 기록의 "권고 반대" 표시를 없앤다. 일반 판정 사유 필수는 그대로다. 서버는 원래 이 규칙을 검사하지 않았다
  - **가맹점 사건 상세:** `MerchantCaseDetailResponse.aiRecommendation`과 사장님 화면의 "AI 권고" 칸을 없앤다
  - **예전 보고서:** 권고 값이 든 보고서는 고치지 않는다(덮어쓰기 · 물리 삭제 금지). 화면과 가맹점 API가 그 값을 읽지 않는다
  - **화면 구조:** ① 무슨 일인가(사건 개요 · 가로 타임라인 · 결제 표 · AI 요약 3줄과 근거 링크) → ② 확인할 것(이상 징후 | 정상 근거 두 칸, 징후마다 사실 · 확인할 것) → ③ 지난 사건과 비교(미리보기, 전체는 기존 나란히 보기 페이지) → ④ 근거 자료 → ⑤ 조사 범위. 정보마다 자리를 하나만 둔다. 지난 사건 자료는 화면이 기존 사건 상세 조회(`getCase`, `CaseComparePage`와 같음)로 가져오고 보고서 본문에는 넣지 않는다
  - **나눠서 고친다 (각 PR 뒤에도 dev가 동작하게):** ① 권고 숨기기 — 모든 화면 · P3 판정 화면 규칙 · 가맹점 API와 화면 (이 개정과 같은 PR) ② 권고 만들지 않기 — ai-server와 Spring을 같은 PR에서 바꾼다. Spring 저장 전 검사가 지금 권고 · `verdict`를 필수로 보므로 ai-server만 먼저 바꾸면 AI 보고서 저장이 모두 실패한다 ③ 새 보고서 화면. ①에서는 결정 7 · 11의 계산 코드가 남아 있었고 ②에서 지웠다
  - **② 저장 전 검사와 배포 순서:** Spring은 권고 키를 필수로 보지 않고, 옛 ai-server가 보낸 권고 키도 거부하지 않는다(그대로 저장하되 화면 · 가맹점 API가 읽지 않음). 거부하면 배포 사이에 보고서 저장이 실패한다. 새 ai-server는 옛 Spring 검사(권고 · `verdict` 필수)에 걸리므로 **Spring을 먼저 또는 함께 배포한다**
  - **② 이름:** Tool `get_decision_basis` · `DecisionBasisCalculator` · `DecisionBasis` 이름은 그대로 둔다(바꾸면 ai-server · Spring · 증거 추적 기록 · 옛 보고서 이름이 함께 흔들림). 사람이 보는 글자(조사 범위 · 조사 과정 단계 이름)만 "징후 · 정상 근거"로 바꾼다
  - AI 실패 시 자동 판정 없음 · 판정은 직원 · 보고서 버전별 누적은 그대로다
- **버린 대안:**
  - 기준표를 고쳐 권고를 지킴(정상 사유 자료 · 무게 추가, #625 측정 도구로 전후 비교) — 기준이 나아져도 칸 하나가 판정을 대신하는 모양은 같다. 무게는 정상 손님을 올렸고(1014), 시나리오 50건에 맞춰 고치면 실제 결제에 맞지 않을 수 있다
  - 직원 화면에서만 권고를 숨기고 계산 · 저장은 둠 — 쓰지 않는 값이 계약 · 검사에 남아 다시 보이게 만들기 쉽고, 가맹점 화면은 따로 정리해야 한다
  - 이상 징후 vs 정상 근거 저울 · 가운데 게이지(화면 시안) — 게이지는 권고 그 자체다. 게이지를 빼도 기울기 표현은 카드 개수를 무게로 읽게 해, 주의 징후 3개뿐인 해외 여행 정상 손님(1014)이 사기처럼 보인다(결정 11에서 버린 "주의 3개 → 승인 취소 검토"와 같다). 좌우 두 칸은 두되 기울기는 없고, 등급 색이 개수보다 먼저 보이게 한다. 정상 근거가 없으면 칸을 채우지 않고 "찾지 못함 + 찾아본 것" 한 칸만 둔다
  - 보고서 결제 표에 허용 · 보류 · 취소 단추 — 판정 입력은 P3 판정 화면 몫이다. 자료(보고서)와 기록(판정)이 섞인다
  - 지난 사건 판정을 요약하는 문장("두 사건 모두 카드사 확인이 판정을 갈랐다") — 직원 사유를 다시 해석한 문장이라 권고처럼 읽힌다
  - 지난 사건 직원 사유를 보고서 본문에 저장 — P3 자료가 보고서에 복사돼 두 곳에 남는다. 화면이 기존 조회로 가져온다
- **영향:**
  - 화면: 권고 표시 전부(`ReportConclusion` · `ReportFull` 판정 줄 · `BasisCard` 기준표 · `ReportCard` · `CaseComparePage` · `reportView.ts` · `caseLabels`) → ③에서 새 구조
  - P3: `DecisionPanel` · `caseDetailView`(권고 반대 규칙), `MerchantCaseQueryService` · `MerchantCaseDetailResponse`(`aiRecommendation`) · 사장님 `MerchantCaseDetailPage` · `types/merchantCase.ts`. 판정 · 사건 데이터와 상태값은 그대로
  - ai-server: `schemas/report.py` · `assemble.py` · `verdict_text.py`(권고 문장)
  - Spring: `DecisionBasisCalculator`(칸 · 권고 · 종합 권고) · `DecisionBasisToolResponse` · `FixedReportGenerator` · `ReportBodyValidator`. Tool 경로 `get_decision_basis`는 그대로(징후 · 정상 근거 · 확인할 것)
  - DB: 없음 (`report_body` JSON 안 키만)
  - 테스트: 예전 보고서에 권고가 있어도 화면 · 가맹점 API에 나오지 않는지, 권고 없이도 짧은 사유로 판정을 저장할 수 있는지(①). 권고 없는 새 보고서를 Spring이 받는지 · 옛 ai-server의 권고 키도 받는지 · 고정 보고서 · Tool 응답 모양(②)

## 미정 — P3 ↔ P4 계약 (공통 페이지 §5.3)

정본 §5.3의 개발 전 결정 항목(조사 요청 방식 · 입력, 완료 · 실패 통지, 병합 중 중복 요청 · 구버전 처리, 판정 시 버전 검증 · 수동 판정 전달)은 **P3 담당과 합의 전이라 이 ADR에서 정하지 않는다.** 정해지면 이 절을 갱신한다.

이 ADR이 전제하는 것은 정본에 이미 있는 내용뿐이다.

- 둘 다 `investigation` 모듈 안이라 Modulith 의존 문제는 없다. 다만 테이블 소유가 달라(설계 3.9) P4는 `security_cases` · `case_payments`를, P3는 `ai_reports`를 직접 바꾸지 않는다
- 조사 요청 입력에는 최소 `caseId` · 증거 버전이 들어간다 (§5.3)
- 결정 3은 P3가 증거 버전을 커밋한 **뒤에** 조사를 요청한다고 전제한다. 요청 방식을 정할 때 이 순서를 함께 합의한다
- P4는 조사 완료 · 실패를 P3가 알 수 있게 해야 한다 (§5.3, 설계 3.7 "P3가 최신 보고서 확인 가능")

## Tool 조회 실패 처리 — 정본 원칙만 따르고 세부는 미정 (공통 페이지 §5.4)

**정본에 있는 원칙 (따른다)**

- 미확인 값을 임의로 채우지 않는다, 증거 없는 사실을 단정하지 않는다 (기획 2.7 작성 강제 규칙)
- 확인되지 않은 것은 "미확인 사항 · 판단의 한계"로 분리해 적는다 (기획 2.6 · 2.7, 04 예시 `limitations`)
- 조회 데이터의 품질과 한계를 고려한다 (업무분석 1.2 F)
- 부정거래 확률을 만들어내지 않는다 (기획 2.6)

**미정 (정본 §5.4 개발 전 결정 항목)**

- 데이터 누락 · 조회 실패 · 타임아웃 때 Tool이 돌려줄 응답 형식
- Tool 하나가 실패하면 보고서 생성 실패(재시도 횟수 차감)로 볼지, 미확인 사항으로 적고 계속 쓸지
- Tool별 타임아웃 · 반환 필드 · 필수/선택 데이터 — 각 제공 담당(P1 · P2 · P5 · CakeShop)과 합의

**1차 Tool 2종 응답 형식 (#254)** — 이미 공개된 조회(`PaymentInfoReader` = P5 + P2)만 쓰므로 P4가 정했다. 나머지 4종은 위 미정 항목을 따른다

- 경로: `GET /internal/ai/tools/get_case_payments?caseId=…`, `GET /internal/ai/tools/get_fds_evidence?caseId=…[&paymentIds=…]`
- 공통 필드: `caseId` · `evidenceVersion`(조회 시점 Case 증거 버전) · `source`(`P3·P5` / `P2`) · `retrievedAt` · `payments` · `missingPaymentIds`. ID는 문자열 (결정 4)
- `get_case_payments`의 결제: `paymentId` · `amount` · `paymentStatus` · `requestedAt`
- `get_fds_evidence`의 결제: `paymentId` · `riskScore` · `fdsResult` · `ruleHits`(`code` · `name` · `appliedScore` · `criterion` · `observed`). `paymentIds`를 비우면 Case 결제 전체
  - `criterion` · `observed`(#326): Spring이 P2 기준값 · 실제값 JSON에서 허용한 규칙의 숫자 키만 골라 만든 문장. R01 · R02 · R03 · R04 · R06 · R08만 만들고, 식별자가 든 R05 · R07과 모르는 규칙 · 깨진 JSON은 `null`. 원본 JSON은 응답에 넣지 않는다 (카드 토큰 · IP가 AI 입력에 들어가지 않게)
- 값을 못 찾은 결제는 추측하지 않고 `null`로 두고 `missingPaymentIds`에 넣는다 (`get_case_payments`는 금액, `get_fds_evidence`는 점수 기준). 응답은 성공(200)이다 — 보고서에 "미확인"으로 적을지는 AI 쪽에서 정한다
- 거부: 없는 Case `404 INV_001`, Case 소속이 아닌 결제 `400 INV_006`, `caseId` 누락 · 형식 오류 `400`
- 증거 버전과 결제 목록은 같은 읽기 트랜잭션에서 읽어 같은 시점 값이다
- 서비스 키가 맞아야 답한다 (보안 체인, [ADR-0041](0041-ai-server-internal-api-key-authentication.md)). ai-server를 켰을 때(`ai.server.enabled=true`)만 경로가 생긴다 — 2026-10-28 #266에서 별도 스위치 `ai.tools.enabled`를 합쳤다

보고서 JSON(`report_body`) 구조는 결정 4를 따른다 (기획 2.7 순서와 같다).

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| Spring이 증거를 전부 모아 요청에 담아 보냄 (Tool Calling 없음) | 구현은 단순하지만, 설계 2.6 · 3.6이 채택한 Tool Calling(AI가 필요한 증거를 골라 조회)과 다르다 |
| Tool API를 각 소유 모듈(payment, fds …)에 분산 | FastAPI가 여러 모듈 경로를 알아야 하고, Case 소속 · 가맹점 범위 검증이 여러 곳에 흩어진다 |
| FastAPI가 DB를 직접 읽음 | 설계 3.6이 금지한다 |
| 동기 HTTP 한 번으로 보고서를 받음 | 생성 시간이 길어 타임아웃 위험이 있다. 설계 3.7이 비동기 접수(202)를 정했다 |
| 결과 조회(polling)만 사용 | 완료가 늦게 반영되고 Spring에 주기 작업이 필요하다. 콜백 유실 복구용으로만 쓴다 |
| 별도 job ID · `attempt_count` · `error_message` 컬럼 추가 | 설계 3.9⑤가 8개 컬럼으로 확정했다. `report_id`와 `report_body.error`로 충분하다. 재시작 때 횟수 보존이 필요해지면 그때 3.9 변경을 제안한다 |
| `RUNNING`을 FastAPI 호출 전에 저장 | 콜백과의 순서 경합은 막지만, 호출이 실패해도 "진행 중"이 먼저 기록된다. `RUNNING` = "FastAPI가 접수함"이라는 뜻을 유지하고, 경합은 조건부 UPDATE로 막는다 |
| 시도 번호(1 · 2 · 3)로 콜백 구분 | 서버 재시작 후 번호가 다시 1부터 시작해 재시작 전 콜백과 겹친다. UUID 토큰은 겹치지 않고 컬럼도 필요 없다 |
| 이전 시도 취소 API(`DELETE /investigations/…`) | 현재 토큰만 받는 규칙으로 늦은 콜백이 이미 무시된다. 계약을 하나 더 늘릴 이유가 MVP에서는 작다 |
| 최신 요청 증거 버전을 따로 저장(watermark 컬럼) | 설계 3.9⑤ 8개 컬럼을 바꿔야 한다. 종료 커밋 후 비교 순서로 같은 효과를 낸다 |
| 버전 번호를 정할 때 `security_cases` 행을 잠금(`SELECT … FOR UPDATE`) | 동시 요청을 한 줄로 세울 수 있지만 P3 소유 테이블을 P4가 잠그게 된다. UNIQUE 위반 시 다시 읽어 합류하는 방식으로 충분하다 |
| 재시도마다 새 `report_version` 행 | 같은 증거를 다시 분석하는 것인데 버전이 늘어 "v1 · v2"의 뜻(증거가 바뀜)이 흐려진다 |
| 결론 카드에 AI가 매기는 위험도 점수(0~100)를 새로 둠 (#288) | FDS 점수와 숫자가 둘이 되어 헷갈리고, "FDS 점수는 확률이 아니다"는 원칙과 부딪힌다. 화면은 FDS 최고 점수를 그대로 쓴다 |
| 결정 6처럼 권고 기준 문장을 지시문에 계속 덧붙임 (#501) | 문장끼리 충돌한다. 1011번에서 "가족일 수도"가 "드문 정황이면 승인 취소 검토"를 이겼다. 같은 근거에도 실행마다 권고가 갈렸다 |
| 권고를 아예 없애고 근거만 보여 줌 (#501) | 반대 판정 사유 규칙(판정 패널)과 사장님 화면이 권고 값을 쓴다. 직원에게 "어디부터 볼지"의 출발점도 사라진다. **#644(결정 13)에서 채택** — 두 화면의 권고를 함께 없애고, 출발점은 징후 등급 · 지난 사건 비교가 맡는다 |
| 기준표를 고쳐 권고를 지킴 (#644) | 칸 하나가 판정을 대신하는 모양은 같고, 무게를 넣으면 정상 손님을 올린다(1014). 결정 13 |
| 이상 징후 vs 정상 근거 저울 · 게이지 화면 (#644) | 게이지는 권고다. 기울기는 카드 개수를 무게로 읽게 해 주의 징후뿐인 정상 손님이 사기처럼 보인다. 좌우 두 칸만 둔다 (결정 13) |
| AI 권고를 두고 기준과 다르면 "기준과 다름"만 표시 (#501) | 같은 사건에 다른 권고가 나오고, 직원이 어느 쪽을 믿을지 하나 더 고민하게 된다 |
| 종합 권고도 AI가 씀 (#288) | 결제별 권고와 어긋날 수 있다. 규칙이 단순해 코드가 계산하는 편이 항상 일치한다 |
| 근거 문장마다 출처를 AI가 붙임 (#288) | AI가 증거 ID를 지어낼 수 있다. 출처가 필요한 규칙 근거는 코드가 조회 기록에서 채운다 |
| 조사 과정을 별도 테이블 · 컬럼에 저장 (#294) | 보고서와 항상 함께 읽고 따로 검색하지 않는다. `report_body` 안에 두면 보고서 버전별로 함께 쌓이고 migration이 필요 없다 |
| Spring 저장 전 검사에서 `investigationTrace`를 필수로 요구 (#294) | 판정에 쓰지 않는 표시용인데, 필수로 두면 ai-server를 먼저 배포하지 않았을 때 보고서가 실패한다 (#288의 배포 순서 주의점과 같은 문제) |
| 비슷한 사건을 같은 카드 · 기기 · IP로도 찾음 (#296) | P2 공개 창구(`FdsPaymentEvidence`)에 `card_token` · `device_id`가 없고, 결제 데이터에는 IP 주소 없이 국가 코드만 있다. 카드 · 기기는 P2 합의(수치 근거 이슈와 함께) 후 추가한다 |
| (#637) 같은 IP 결제를 하루 중 시간대(새벽 · 낮 등)로 나눔 | "언제 결제했나"는 보여도 "몰렸나"는 보여 주지 못한다. 이 사건 결제 시각은 이미 보고서에 있다 |
| (#637) 구간을 여러 개(1시간 · 24시간 · 30일)로 나눔 | 숫자 줄이 늘어 직원 · AI가 읽기 어렵다. 몰림 · 흩어짐을 가르는 데는 짧은 구간 하나와 30일로 충분한지 먼저 본다 |
| (#637) 펼침에 다른 손님 결제 기록(시각 · 판정)을 한 줄씩 보여 줌 | "다른 고객 개별 결제는 집계만" 원칙(P2 합의)을 바꿔야 하고, 사건 하나로 무관한 손님 결제를 넓게 보게 된다(ADR-0082와 같은 이유). 읽는 법 설명으로 숫자를 이해하게 한다 |
| (#637) 읽는 법 설명을 LLM이 사건마다 씀 | 같은 숫자에도 설명이 달라지고 틀린 숫자 · 판단 문장이 섞일 수 있으며, AI가 꺼지면 사라진다. 숫자 비교로 고르는 고정 문장으로 충분하다 |
| (#637) 1시간 숫자를 바로 판정 기준표 징후 · 정상 사유에 씀 | 측정 없이 권고가 바뀐다. 기준표 개선 조각에서 T7b 측정과 함께 정한다 |
| 비슷한 사건의 결과를 사건 하나에 한 값("일부 승인 취소")으로 표시 (#296) | 결제가 2건인지 3건인지 구분되지 않는다. 판정은 원래 결제별로 저장되므로 건수를 그대로 보여 준다 |
| 비슷한 사건 조회 실패를 보고서 실패로 처리 (#296) | 참고 자료 때문에 판정에 필요한 보고서가 막히면 수동 판정이 늘어난다. 값만 비운다 |
| 진행 단계를 SSE · 웹소켓으로 밀어 줌 (#322) | 연결 관리 · 재연결이 새로 생기고, 열린 연결이 세션 무활동 만료(ADR-0014)를 막는다. 3초 간격이면 기존 자동 조회로 충분하다 |
| 진행 단계를 DB에 저장 (#322) | migration이 필요하고, 조사가 끝나면 `investigationTrace`와 중복된다. 생성 중에만 필요한 값이라 FastAPI 메모리로 충분하다 (FastAPI 재시작 시 사라져도 보고서에는 영향 없음) |
| P3 Case 상세 응답(`ReportGateway`)에 진행 단계를 실음 (#322) | P3 계약이 바뀌고, 상세 조회마다 FastAPI를 부르게 된다. P4 API로 따로 둔다 |
| 화면이 진행 조회용 타이머를 따로 둠 (#322) | 요청마다 세션이 연장돼 자리를 비워도 무활동 만료가 오지 않는다 (#238과 같은 문제) |
| 진행 조회 중 끝난 결과를 받으면 바로 반영 (#322) | 화면 조회가 상태를 바꾸면 결과 반영 경로가 둘이 되어 결정 2의 검증 · 멱등 규칙을 우회할 수 있다 |
| 프롬프트 · Tool 응답 원문을 그대로 저장 (#294) | 보고서가 커지고 결제 값이 본문과 중복 저장된다. 시연 · 확인에는 요약으로 충분하다 |
| Tool 응답에 P2 기준값 · 실제값 JSON 원본을 그대로 실음 (#326) | 차단 목록(R07) 실제값의 카드 토큰 · IP · 이메일이 AI 입력과 보고서에 남는다. 숫자 키만 골라 문장으로 만든다 |
| 기준 · 실제 문장을 ai-server나 화면에서 만듦 (#326) | 금액 단위 처리를 Python · TS에 따로 두게 되고, AI 서버를 끈 고정 보고서와 문장이 달라진다. Spring 한 곳에서 만든다 |
