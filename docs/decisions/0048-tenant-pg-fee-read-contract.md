# 0048. 가맹점별 PG 수수료율 공개 조회

- **상태:** 제안 — #356 P6 요청·P1 사용자 구현 승인, PR 리뷰 대상
- **날짜:** 2026-10-30
- **관련:** #356, [ADR-0020](0020-identity-public-read-contracts.md), [ADR-0038](0038-settlement-identity-dependency.md)
- **영향 받는 담당:** P1 주환 · P6 민정

## 배경

가맹점 생성·신청 승인에서 `merchants.pg_fee_rate`를 저장하지만 공개 조회에는 없다. P6가 가맹점별 PG 수수료율을 정산에 연결하기 위해 공개 조회를 요청했고 P1 사용자가 구현을 승인했다. ADR-0020에서 미뤘던 수수료율 공개를 이번 계약으로 확장한다. `settlement → identity :: api`는 ADR-0038에서 이미 허용되어 있다.

## 결정

- `TenantReader.findById(Long merchantId)`의 반환 `TenantSummary`에 `BigDecimal pgFeeRate`를 추가한다. 기존 ID·이름·상태와 함께 같은 가맹점 조회 결과로 제공한다.
- 단위는 백분율 숫자나 basis point가 아닌 **비율**이다. `0.020000`은 2%다. SQL `DECIMAL(9,6)` 값을 고정값 대체·반올림·백분율 변환 없이 반환한다. 0도 유효한 저장값이다.
- ACTIVE·INACTIVE 모두 반환하고 없는 가맹점만 `Optional.empty()`다. null·0 이하 ID는 `IllegalArgumentException`, DB 장애는 원래 예외를 전파한다. 조회 결과 자체는 인가가 아니다.
- 애플리케이션 캐시를 두지 않는다. 조회는 호출자의 트랜잭션과 JPA 영속성 문맥 규칙을 따르므로 동일 트랜잭션에서 외부 변경을 즉시 반영한다고 보장하지 않는다.
- P6는 공개 `TenantReader`를 사용한다. 없는 가맹점·조회 실패를 임의 기본 수수료율로 바꾸지 않는다. 계산 시점·기존 정산에 저장할 수수료율 스냅샷·원 단위 절사는 P6 연결 작업에서 처리한다.
- 이 작업은 PG 수수료율 **제공**까지다. P6 정산 계산 연결, 기존 정산 재계산은 포함하지 않는다. 카드 수수료 모의 정책 2%와 현재 계산기의 PG 임시값 1%는 이번 PR에서 변경하지 않는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 별도 수수료율 조회 포트 추가 | 기존 가맹점 조회가 이미 ID·이름·상태를 제공한다. 같은 행의 작은 필드 하나를 위해 조회 계약을 중복하지 않는다. |
| P6가 identity Entity·Repository 직접 조회 | 공개 api만 사용한다는 모듈 경계를 위반한다. |
| HTTP로 수수료율 조회 | 같은 앱 모듈 간 Java 호출 규칙에 어긋나며 불필요한 네트워크 경계가 생긴다. |
| 2 또는 bp 정수로 변환 | 저장 단위와 달라지고 정밀도 손실·단위 혼동 위험이 생긴다. |
| 조회 실패 시 PG 1% 기본값 반환 | 저장된 계약 수수료율과 다른 금액을 조용히 계산하게 된다. |

## 영향

- API: `TenantSummary`는 4필드 record이며 `@Builder`를 제공한다. 기존 3인자 생성자를 직접 사용하는 외부 작업 브랜치는 새 필드에 맞춰 수정해야 한다. 현재 저장소의 직접 생성 지점은 서비스 한 곳이다. 새 HTTP·이벤트는 없다.
- DB: 기존 `pg_fee_rate`를 읽는다. 스키마·migration 변경 없음.
- 화면: 변경 없음. 관리자 화면의 정산 미반영 안내는 P6 실제 연결 전까지 유지한다.
- 테스트: 기존 오류·없는 가맹점 계약을 유지하고 실제 MariaDB에서 두 상태의 수수료율, 가맹점별 0·소수 6자리·상한 근처 값, 새 영속성 문맥의 변경값 조회를 검사한다.
- 문서: identity README·P6 연결 계약·문서 대조 현황을 갱신한다. 이전 ADR의 당시 보류 기록은 보존한다.
