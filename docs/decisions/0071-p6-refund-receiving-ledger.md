# ADR-0071: 환불 성공 수신과 정산 적용을 분리한다

- 상태: 제안 (P6 로컬 구현 승인, 팀 채택과 운영 활성화는 별도)
- 관련: #478, [D+3 정책](../settlement/d3-policy-and-erd.md), [상세 ERD·계약](../settlement/refund-receiving.md)

## 배경

P5는 고객 전액 환불 성공을 통지하고 P6는 가맹점 정산에 반영한다. 원 매입은 유지해야 하며 수신 재전달이 중복 차감을 만들면 안 된다. 지급 전 제외와 지급 후 회수는 서로 다르고 수신 직후 지급 상태가 바뀔 수 있다.

## 결정 제안

기존 P6 공개 이벤트 여섯 필드를 원 매입·정산과 대조하고 별도 조정 원장에 PENDING으로 저장한다. 원 수수료·순정산액을 보존하며 현재 요율로 다시 계산하지 않는다. 수신 시 금융 반영 방향은 결정하지 않는다. 후속 적용 단계에서 가맹점 지급 잠금과 함께 확정한다.

원 정산 행 잠금과 READ_COMMITTED로 같은 결제 수신을 직렬화하고 취소·결제·정산 UNIQUE로 전액 중복을 막는다. 같은 취소의 내용 변경은 오류다. 예외를 정상 수신으로 숨기지 않는다. 원장과 원 매입·정산에는 P6 내부 FK만 추가하고 P5 테이블·서비스를 직접 참조하지 않는다.

수신 리스너는 기본 비활성이다. 서비스가 단독 새 트랜잭션을 소유하고 커밋 뒤 수신 완료 표시를 한다. 완료 표시 실패 재전달은 기존 원장으로 멱등 처리한다. 지급 제외·회수 구현과 P5 연동 검증 전에는 운영에서 켜지 않는다.

## 대안과 영향

원 매입을 취소 상태로 덮는 방식은 원 거래·환불 이력을 혼합하므로 택하지 않았다. 수신 즉시 지급 전/후로 분류하면 적용 시점의 지급 결과와 어긋날 수 있다. 수신 활성화와 P5 고객 환불 활성화를 묶으면 아직 금융 반영이 없는 상태에서 환불만 성공할 수 있다.

독립 원장·상태·플래그가 추가되지만 실패 전달을 조사하고 원본 금액을 보존할 수 있다. 이 단계만으로 정산 차감이 완성되지 않는다. 후속 PR은 지급 제외·경합 보호, 지급 후 회수·이월, 조회·현금흐름 갱신, 활성화 순서다.

## 검증 계획

일반 검사와 모듈 의존 검사, MariaDB 제약·동시 수신·재전달·DB 실패 복구를 실행한다. 실제 실행 결과는 PR에 남기며 구현 사실만으로 채택·운영 검증 완료로 바꾸지 않는다.
