# 0080. 사장님 403 원본 저장과 트랜잭션 이벤트 발행

- **상태:** 제안 — P1 사용자 저장 구조·보관 정책·구현 승인, PR 리뷰 대상
- **날짜:** 2026-11-04
- **관련:** #525, #515, [ADR-0079](0079-operator-security-contracts.md)

## 결정

P1 소유 `operator_access_denials`에 OPERATOR의 403 원본을 저장하고 같은 트랜잭션에서 `OperatorAccessDenied`를 발행한다.
원본 PK가 eventId다. 사용자·가맹점에만 P1 물리 FK를 두며 모듈 의존·HTTP API·화면은 추가하지 않는다.
Notion 선행 반영 대신 저장소 ERD·ADR 기준으로 구현하도록 사용자가 승인했으며 Notion 동기화는 후속이다.

기록 범위는 JsonAccessDeniedHandler까지 도달한 AccessDeniedException이다.
CSRF·비로그인·직원·비밀번호 강제 변경 403은 제외한다. MVC가 응답한 서비스 Guard 오류도 포함하지 않는다.
처리되지 않은 서비스 AccessDeniedException이 핸들러까지 도달하면 포함한다.
핸들러는 principal을 한 번 확보하고 기록 서비스를 호출한다. 서비스는 독립 트랜잭션에서 DB 계정의 역할·가맹점·loginId를 읽는다.
원본 저장·flush 후 발행하고 커밋한다. 실패는 핸들러에서 예외 종류와 사용자 ID만 기록하며 원래 403 AUTH_002 응답을 유지한다.
DB 오류 원문에는 경로·IP가 포함될 수 있으므로 예외 메시지·stack trace·쿼리·요청 본문은 로그에 남기지 않는다.

인가와 deniedType 분류는 OperatorAccessRoutes의 메서드·경로 목록을 공유한다. 기존 인가 조건·순서를 유지한다.
path는 servletPath에서 최대 512 Unicode 문자, 시각은 identityClock의 UTC 마이크로초를 원본과 이벤트가 공유한다.
httpMethod는 HTTP token의 앞 최대 10자를 원본·이벤트가 동일하게 기록한다. 요청·인가·거절 분류는 원문 메서드를 유지한다.
PR #527 리뷰에서 긴 메서드의 INSERT 실패를 재현해 저장 경계를 보완했다. 현재 기본 방화벽의 사용자 정의 메서드 400 차단은 유지한다.

## 보관 정책

사용자 결정(2026-11-04 개정): `client_ip`는 `occurred_at` 기준 1년 보관 후 NULL로 바꾼다.
행은 조사 근거이므로 IP 정리를 이유로 지우지 않으며, 행 보관 기간은 조사 기록 보관 정책으로 따로 정한다.
이 결정은 앞서 제안했던 일반 90일·조사 종료 후 90일 행 삭제 정책을 대체한다. 행의 무기한 보관을 확정한 것은 아니다.

근거로 참고한 규정:

- [개인정보의 안전성 확보조치 기준 제8조](https://www.law.go.kr/admRulInfoP.do?admRulSeq=2100000281400): 적용 대상 접속기록은 최소 1년 보관하며, 같은 조의 조건에 해당하면 최소 2년이다. 정보주체의 접속은 해당 의무에서 제외된다.
- [개인정보 보호법 제21조](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029334977): 보유기간 경과·목적 달성 등으로 불필요해진 개인정보는 파기하며, 다른 법령에 따른 보존 의무는 예외다.

1년은 이번에 정한 제품 정책이다. OPERATOR의 403 원본이 제8조의 법정 접속기록에 해당하는지와 운영 환경이 2년 보관 대상인지는 별도로 확인해야 한다.
2년 이상 보존 의무가 적용되는 기록에 1년 NULL 처리를 그대로 적용하지 않는다. 이 ADR만으로 법정 접속기록 요건을 충족했다고 표현하지 않는다.
IP만 NULL로 바꿔도 user_id 등 다른 개인정보가 모두 파기되는 것은 아니므로, 남는 행의 보관 목적·기간·처리는 조사 기록 정책에서 정한다.

#525는 수집·발행까지 구현했고, #528에서 원본 IP 정리 작업을 추가한다. 기동 후 및 매시간 UTC 현재 시각에서 달력상 1년을 뺀 경계와 같거나 오래된 행의 `client_ip`만 NULL로 바꾼다. NULL인 IP는 건너뛰며 1,000건씩 독립 커밋하고 한 실행의 배치 반복을 최대 5분으로 제한한다. 실패 시 실행을 종료하고 다음 주기에 재시도한다. 행과 다른 칸은 유지한다.
기존 `client_ip` 컬럼은 NULL 허용이므로 이번 문서 변경으로 migration을 추가하지 않는다.
#528은 원본의 1년 경계·재실행·장애 복구를 검증한다. P2 복사본은 #515 범위이며 이벤트 발행 기록·백업에 남는 IP의 실제 파기·복구 정책은 후속이다. 원본 IP 정리만으로 모든 복사본의 파기를 완료했다고 표현하지 않는다.
실행 근거·미검증은 [#528 구현 기록](../identity/528-access-record-retention.md)을 따른다.
정책 결정과 실제 파기 구현·운영 적용은 구분한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 필터에서 저장 없이 발행 | 트랜잭션이 없어 커밋 후 리스너·발행 기록에 전달되지 않음 |
| 세션 merchantId·loginId 저장·발행 | 오래됐거나 잘못된 세션 가맹점 값이 FK 위반·원본 누락을 만들 수 있음 |
| 저장 실패를 500으로 전파 | 기록 장애가 기존 접근 거절 응답을 바꾸면 안 됨 |
| 경로 목록을 분류기에 복제 | API 추가 때 인가와 탐지 분류가 어긋남 |
| 원본과 이벤트를 별도 트랜잭션으로 기록 | 원본 없는 이벤트 또는 커밋된 원본의 이벤트 누락을 만듦 |
| HTTP 메서드 컬럼만 확대 | 임의 길이 token은 다시 넘칠 수 있어 명시적인 기록 길이 제한이 필요함 |
| 90일 지난 원본 행 삭제 | IP 정리와 조사 근거 보존을 분리한다는 개정 사용자 결정과 다르고 논리 참조를 손상할 수 있음 |
| IP·행 모두 무기한 보관 | IP는 기간을 제한하고, 남는 행도 별도 조사 기록 보관 정책으로 정해야 함 |

## 영향과 검증

- DB: ERD에 명시한 P1 테이블·FK·인덱스·CHECK 추가. 기존 migration·다른 담당 테이블은 유지.
- API: 기존 공개 이벤트 모양 유지, 실제 발행 연결. 수신자가 없으면 원본만 남으며 과거 원본은 자동 재발행하지 않음.
- 화면·인가: 화면 변경 없음, 기존 역할·권한 조건 유지.
- 테스트: 경로 분류, 핸들러 대상 필터링·장애 시 응답, DB 저장·원본/이벤트·커밋·롤백·UTC·FK·경로 제한을 검증한다.
- 실행 근거·미검증: [#525 명세](../identity/525-operator-access-denials.md)에 실제 결과를 기록한다.
