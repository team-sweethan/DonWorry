# ADR-0073: 환불 회수 배분과 개별 잔여액으로 후속 지급을 차감한다

- 상태: 제안 (P6 5단계 구현 승인, 팀 채택·운영 활성화는 별도)
- 관련: #493, [상세 정책·ERD](../settlement/refund-recovery.md), [ADR-0072](0072-p6-unpaid-refund-exclusion.md)

## 배경

정산 이후에도 P5 전액 환불이 가능하다. 과거 완료 정산·지급을 덮지 않고 후속 지급에서 회수하며, 수입이 부족하면 잔액을 이월해야 한다. 원 고객 환불액과 가맹점 순정산 회수액은 다르다.

## 결정 제안

원 지급·상세를 검증한 환불을 APPLIED/RECOVERY로 등록한다. 원 수수료 전액 반환 가정에 따른 순정산액 스냅샷을 유지한다. 기존 조정 ID 순으로 이번 순정산 합계 이내에서 배분한다. 양수 배분을 payout_refund_allocations에 저장하고 remaining_amount를 줄인다. 지급 합계·차감·실제 지급액과 같은 금융 트랜잭션에 포함한다.

APPLIED는 회수 등록을 뜻하며 잔여액 0이 회수 완료다. 무수입이면 그대로 이월하고 음수 지급·과거 지급 재개방·자동 출금은 하지 않는다. 현금이 0인 상계 지급도 완료 이력으로 보존한다.

4단계 공통 가맹점 잠금·순차 트랜잭션을 유지한다. 같은 이벤트와 지급을 재실행해도 배분·잔액을 중복 반영하지 않는다. 배분·잔액·정산·지급 변경은 함께 롤백한다.

## 대안과 이유

- 과거 지급액을 수정하면 당시 지급 사실과 회수 이력이 사라진다.
- 환불 전액을 순정산액에 추가로 차감하면 이미 반환한 수수료까지 가맹점이 부담하므로 원 순정산액만 회수한다.
- 수입보다 큰 금액을 한 번에 차감해 음수 지급을 만들면 실제 지급·이월을 구분하기 어렵다.
- 초기 제안의 merchant_settlement_balances 캐시는 생성하지 않는다. 이미 공통 잠금이 있고 개별 조정 잔액이 정본이다. 중복 합계 불일치·파일/테이블 증가·총 채무 BIGINT 초과로 정상적인 개별 회수를 막는 문제를 피한다. 합계 조회는 DECIMAL로 수행한다.

배분 원장 한 테이블과 Entity/Repository를 추가하는 대신 회수별·지급별 추적과 원금=배분합+잔여액 대조가 가능해진다. 상태/이벤트 계약·다른 모듈 의존은 늘리지 않는다.

## 영향·검증

P6 서비스·원장 Entity·Repository·테스트, 신규 P6 SQL, 정책/ERD만 변경한다. P5·인증·공용 빌드·이벤트 필드는 변경하지 않는다. 과거 금융 데이터 backfill과 운영 활성화는 하지 않는다. 조회/현금흐름은 6단계에서 차감 후 지급액으로 전환한다.

실제 MariaDB에서 다회차 이월·FIFO·제약·최종 커밋 실패 롤백·총 채무 초과를 확인하고, 두 연결의 지급/재전달 경합과 전체 회귀·CI·Codex 리뷰 결과를 PR에 기록한다. 구현으로 ADR 상태를 채택으로 바꾸지 않는다.
