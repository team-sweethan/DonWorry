# 0060. 계정·신청 상태 이름과 데이터 보존 전환

- **상태:** 제안 — #131 PR A 사용자 구현 승인, PR 리뷰 대상
- **날짜:** 2026-11-01
- **관련:** [Issue #131](https://github.com/team-sweethan/DonWorry/issues/131) 최신 실행 계획·2차 재리뷰
- **영향 받는 담당:** P1 backend·frontend, 같은 DB를 쓰는 팀원과 배포 담당

## 배경

계정의 활성/정지를 ACTIVE/INACTIVE로 통일하고 신청 EMAIL_PENDING이 메일 발송 대기로 오해되지 않게 한다. 운영은 빈 DB로 시작할 예정이지만 팀원 로컬·공용 개발 DB의 데이터 보존 업그레이드를 지원해야 한다. 신청 진행 중 중복 방지는 상태 기반 생성 컬럼 3개와 UNIQUE가 담당하므로 enum만 바꾸면 예약이 풀리거나 기존 행을 읽지 못한다.

## 결정

계정 enum·입력·조회 필터·응답을 `ACTIVE / INACTIVE`, 신청 enum·조회·업무 조건을 `EMAIL_VERIFICATION_PENDING / REVIEW_PENDING / APPROVED / REJECTED`로 바꾼다. 구 API 이름은 400으로 거절한다. 브라우저의 이전 신청 목록 주소 `status=EMAIL_PENDING`은 첫 조회 전부터 새 상태로 해석하고 URL을 replace로 정규화하여 기존 필터·검색·페이지 의미를 유지한다. 서버에 구 상태 별칭을 추가하지 않는다. 활성/정지 의미, 기존 세션 종료·복구 후 새 로그인, 신청 이메일 확인·재발송·검토·메일 복구·보존 기간 정리 정책은 유지한다. 메일 `ApplicationMailStatus.PENDING`, 가맹점 상태와 HMAC 계약은 유지한다.

계정과 신청을 각각 독립적인 새 Flyway 파일로 전환한다. 계정은 DISABLED 행만 UPDATE한다. 신청은 한 파일 안에서 ① 기존 CHECK와 생성 컬럼 3개를 구/신 이름 양쪽을 포함하도록 함께 ALTER ② 기존 상태 UPDATE ③ CHECK와 생성 컬럼을 새 이름으로 제한한다. 기존 UNIQUE 인덱스는 제거하지 않는다. 두 파일 사이의 적용 순서에 기대지 않는다. 기존 병합 migration·시드는 보존한다.

새 수동 계정 정지 이력 유형은 `USER_INACTIVATED`(16자), 복구는 기존 `USER_ENABLED`다. 과거 `USER_DISABLED` 및 before/after JSON은 당시 사실이므로 변환하지 않는다. 이력 유형은 문자열이므로 과거 기록도 그대로 읽힌다. 운영 시작 전용 정지 유형·원자성은 PR B에서 별도로 정한다.

배포 전에 같은 DB의 모든 구버전 프로세스를 중단한다. HTTP뿐 아니라 예약 정리·메일 복구도 포함한다. 백업 후 DB 전환·신규 backend·frontend를 같은 점검 배포로 적용하며 기존 브라우저 탭은 새로고침한다. 구/신 이름을 동시에 쓰는 롤링 배포는 지원하지 않는다. MariaDB DDL은 자동 커밋되므로 실패 전체가 자동 롤백되지 않는다. DB 전환 뒤 구버전 앱만 재기동하지 않으며, 실패 시 [운영 안내](../identity/131-status-transition.md)에 따라 백업 전체 복원과 이전 앱 복구를 함께 수행한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| DB 초기화·기존 migration 수정 | 팀원 데이터 유실과 병합 migration 체크섬 위반 |
| enum만 변경 | 기존 데이터 역직렬화·CHECK·아이디 예약·JPQL/API/화면 불일치 |
| UNIQUE 제거 후 데이터 수정 | 전환 단계에서 중복 방지가 사라지고 복구 시 재생성 실패 위험 |
| 새 상태만 포함한 생성 컬럼으로 먼저 변경 | 기존 EMAIL_PENDING 행의 예약 해제가 발생 |
| 구/신 이름을 앱에서 동시에 지원하는 무중단 배포 | 현재 단일 서버 점검 배포 범위를 넘는 임시 계약·운영 복잡도 |
| 과거 이력까지 일괄 치환 | 감사 당시 기록을 왜곡하고 관계없는 이벤트 유형까지 변경할 위험 |

## 영향

- API: 관리자 계정 상태 PUT·GET 필터/응답, 신청 목록/상세 상태가 새 문자열을 쓴다. 경로·권한은 그대로다.
- DB: P1 두 테이블의 상태 데이터, 신청 CHECK·생성 컬럼 조건만 변경한다. 시드 ACTIVE·관계·감사 이력·금융 데이터는 보존한다.
- 화면: API 타입·계정 필터/정지 요청·신청 조건을 함께 맞춘다. ‘정지’, ‘이메일 미확인’ 문구는 유지한다.
- 테스트: 기존 인증·세션·신청/복구/정리 회귀, 새 문자열 API·구 이름 거절, 빈 DB 전체 적용과 기존 DB/중간 DDL 단계 예약 검사를 수행한다.
- 문서: identity 계약·ERD·운영 안내를 갱신한다. 과거 ADR은 보존하며 현재 이름은 이 ADR이 우선한다. 실제 Notion 대조·자동 구역 수정은 수행하지 않는다.

## 검증

실행 결과와 기준 커밋은 [운영 안내의 검증 기록](../identity/131-status-transition.md#검증-기록)과 PR에서 추적한다. PR A만으로 #131 전체 완료·운영 배포 완료를 뜻하지 않는다. 운영 시작 시 시연 계정 정지(PR B), 실제 HTTPS/프록시·브라우저·배포 비밀값 주입 검증은 별도다.
