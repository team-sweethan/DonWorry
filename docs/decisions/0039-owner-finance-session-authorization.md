# 0039. 사장님 정산·자금관리의 세션 인가

- **상태:** 채택 — 2026-10-27 P1 주환 결정 (P6 확인 전), P6 실제 통합 후속
- **날짜:** 2026-10-27
- **관련:** Issue #240 · #68 · #228 · #229 · #230 · #231 · #235 · #236, [ADR-0020](0020-identity-public-read-contracts.md), [ADR-0038](0038-settlement-identity-dependency.md)
- **영향 받는 담당:** P1 주환 · P6 민정

## 배경

P6의 정산 조회·현금흐름·잔액·지출 관리 로컬 구현은 실제 사장님 인증 연결을 기다리고 있다.
기준 `dev 7763518`에는 P6 업무 Controller가 없고, 일반 보안 체인의 나머지 경로는 `permitAll()`이다.
ADR-0038로 공개 API 의존은 허용됐지만 경로 인가와 가맹점 범위 검증이 구현됐다는 뜻은 아니다.

#240의 [P1 결정 댓글](https://github.com/team-sweethan/DonWorry/issues/240#issuecomment-6441716148)을 기준으로 공통 인가를 먼저 적용한다.
사용자가 이 범위의 구현을 승인했으며, P6의 정책 동의·로컬 코드 연결까지 확인된 것으로 기록하지 않는다.

## 결정

### 공통 경로 인가 (P1)

- `/api/v1/settlements`와 `/api/v1/settlements/**`는 기존 세션 보안 체인에서 모든 메서드를 보호한다. HEAD·OPTIONS와 아직 Controller가 없는 하위 경로도 포함한다.
- 사장님 정산·자금관리 API(#228 · #229 · #230 · #231)는 모두 `/api/v1/settlements/` 아래에 둔다. 이 밖의 경로는 아직 `permitAll()`이다. P6가 다른 경로를 원하면 합의한 경로를 보호 범위에 추가한다 (P1 결정, P6 확인 전).
- 인증된 `SessionUser`가 `OPERATOR`이고 `merchantId`가 있으며 `FINANCE_VIEW`를 보유해야 통과한다. 권한 목록이 null인 이전 세션도 거절한다.
- ADMIN·SECURITY_STAFF는 접근하지 못한다. ADMIN은 공개 조회 결과에서 `FINANCE_VIEW`를 받으므로 역할을 별도로 확인한다. ADMIN의 가맹점 선택 기능은 별도 설계다.
- 읽기·쓰기 모두 `FINANCE_VIEW`를 사용한다. 이름이 VIEW여도 이 경로의 쓰기를 포함하며, 새 권한은 추가하지 않는다.
- 기존 ProblemDetail 계약을 유지한다. 비로그인·만료 세션은 401 `AUTH_001`, 역할·권한·가맹점 누락은 403 `AUTH_002`다. 강제 비밀번호 변경은 기존 403 `AUTH_008`이 우선한다.
- CSRF 기본 비활성은 유지한다. 설정이 켜지면 변경 요청은 기존 CSRF 검사를 거치며, 실패 시 403 `CSRF_001`이 인가보다 먼저 반환될 수 있다. 정산 경로에 예외를 추가하지 않는다.

### 업무 가맹점 범위 (P6 통합 시)

- P6 내부 어댑터 한 곳에서 `CurrentStaff.findCurrent()`의 `StaffSummary`를 읽고 역할·권한·가맹점 조건을 확인한다. 요청에서 받은 가맹점 번호로 대체하지 않는다.
- 조회·생성은 세션 가맹점만 사용하고, 수정·삭제·반복 지출 중단은 자원 ID와 세션 가맹점을 함께 조건으로 사용한다. 타 가맹점 요청은 거절하고 데이터를 변경하지 않는다.
- 어댑터 미연결 시 차단을 유지한다. 로컬 어댑터 시그니처, `/report` 외 세부 경로·메서드, 기존 업무 오류 계약은 실제 P6 코드를 연결할 때 확인한다. 이번 P1 구현의 선행 조건은 아니다.
- 계정·권한·가맹점 정지의 기존 세션 무효화 흐름을 재사용한다. `CurrentStaff`는 DB를 다시 읽지 않는다. `TenantReader`의 INACTIVE 반환을 인증 성공으로 해석하지 않는다.
- CakeShop 픽업은 별도 HMAC 체인의 `CurrentMerchant`를 사용한다. 한 경로에서 세션과 HMAC 중 하나만 있으면 통과시키지 않는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| P6 코드가 병합될 때까지 P1 인가도 대기 | 정책과 공개 조회 계약은 이미 있어 공통 인가를 먼저 구현·검증할 수 있다 |
| `FINANCE_VIEW`만 검사 | ADMIN도 이 권한을 받아 사장님 전용 정책을 우회할 수 있다 |
| GET 경로만 보호 | 잔액·지출 쓰기가 `permitAll()`에 남고 새 경로마다 설정 누락이 생길 수 있다 |
| `FINANCE_EDIT` 신설 | 이번 정책은 읽기·쓰기 공통 권한이다. 새 권한은 계정·화면·관리 계약까지 바꾼다 |
| 요청의 merchantId나 SecurityContext를 P6가 직접 읽기 | 타 가맹점 접근 또는 identity 내부 구현 결합이 생긴다 |
| 매 요청마다 계정·가맹점 DB 재조회 | 세션 기반 공개 계약과 다른 최신성 정책이 생긴다. 기존 관리 API의 세션 무효화 흐름을 재사용한다 |

## 영향

- API: 정산 경로의 서버 인가를 활성화한다. 새 HTTP API·공개 Java 타입은 없다. P6 세부 업무 경로와 타 가맹점 오류 응답은 통합 단계에서 확인한다.
- DB·모듈: 스키마·의존 목록 변경 없음. ADR-0038의 `identity :: api`만 사용한다.
- 화면: 이번 변경 없음. #235·#236에서 기존 API 클라이언트의 쿠키·CSRF·401/403 처리를 사용한다. 관리자 `/admin/finance` 메뉴는 빈 화면이며 정산 API에 연결하지 않는다. 관리자용 자금 화면은 별도 설계다.
- 테스트: 역할·권한·가맹점·모든 메서드·경로 범위·CSRF·강제 변경을 검사한다. 실제 HTTP는 테스트 수신부에서 로그인 쿠키와 공개 조회, 권한 회수·계정/가맹점 정지·세션 종료를 검사한다.
- P6: 사용법과 오류 경계는 [#240 연결 계약](../identity/240-owner-finance-session.md)을 따른다. 실제 업무 데이터의 가맹점 격리는 P6 연결 후 검증한다.

## 검증 상태

실행 커밋·명령·결과는 PR에 기록한다. P1 공통 인가의 검증과 실제 P6 업무 API 통합을 구분하고, P1 작업만으로 #240을 종료하지 않는다.
