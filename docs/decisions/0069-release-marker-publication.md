# 0069. 릴리스 marker 사전 준비와 게시 직전 main 확인

- **상태:** 제안 — #461 발행 구간 축소, 엄밀한 최신성·실제 배포 차단은 미완료
- **날짜:** 2026-11-03
- **관련:** Issue #461, #435, #448
- **영향 받는 담당:** P1, Jenkins·VM 배포 담당

## 배경

기존 VM Images는 main HEAD를 확인한 뒤 marker를 빌드·업로드해 `prod`로 게시했다.
확인 이후 빌드 중 main이 바뀌어도 이전 실행의 확인 결과로 게시했다.
기존 테스트는 조회 결과만 검사하며 확인과 게시 사이의 변경은 검사하지 않았다.

## 결정

marker를 `sha-<SHA>`로 먼저 빌드·발행하고 반환된 digest를 고정한다.
그다음 같은 스크립트에서 main HEAD를 조회하고 일치할 때만 준비된 digest를
`prod`로 게시한다. 불일치는 게시 생략, 조회·게시 실패는 CI 실패로 처리한다.
기존 push workflow 직렬화와 수동 실행의 발행 금지는 유지한다.

`prod`는 검사를 통과해 발행된 릴리스 후보를 나타낸다. main HEAD와 항상 같다는
보장은 하지 않는다. main 변경과 GHCR 갱신은 같은 트랜잭션이 아니므로 최종 조회
이후에도 main이 바뀔 수 있다. 게시 후 재확인도 이미 노출된 marker를 되돌리지는 못한다.

실제 배포 전 승인 SHA·main HEAD·marker와 이미지 revision을 대조하고 digest를
고정하는 소비 측 차단은 #448의 필수 후속이다. 이 변경만으로 #461 원문의
"게시 시점의 main HEAD" 조건을 충족하거나 #448이 구현됐다고 판단하지 않는다.
완료 기준 조정은 이 ADR 리뷰에서 결정하며, 합의 전 #461을 해결 완료로 닫지 않는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 기존 확인 단계만 게시에 가깝게 이동 | marker 빌드·업로드 동안 확인 결과가 오래되는 문제를 남긴다 |
| concurrency 또는 실행 취소만 추가 | workflow 직렬화는 main 변경을 막지 못하며 실행 취소는 GHCR 쓰기를 되돌리지 못한다 |
| 게시 후 main 재확인·marker 삭제 | 조회 전 구 marker가 이미 소비될 수 있고, 삭제로 배포 가능한 직전 후보도 잃는다 |
| main 승격과 marker 게시에 공통 잠금 도입 | 엄밀한 게시 시점 최신성을 위해서는 모든 main 변경 경로 통제가 필요하다. 현재 PR 병합·발행 절차보다 영향이 크므로 이번 변경에서는 도입하지 않는다 |

## 영향

- API·DB·화면: 변경 없음.
- 이미지 계약: `prod` 경로와 revision label은 유지하며 준비용 marker SHA 태그를 추가한다.
- 테스트: 이전 확인 이후 main 변경 시 게시 생략, digest 고정, 조회·게시 실패를 검사한다.
- 문서: CI 릴리스 문서에 보장 범위와 #448 의존을 기록한다.

## 검증

검사 명령: `python3 -m unittest discover -s .github/scripts -p 'test_release_*.py' -v`.
실행 결과는 PR에 기록한다. 원격 Git·Docker 호출은 테스트 대역으로 검증한다.
실제 GHCR manifest 승격·revision 보존, GitHub Actions 실행, Jenkins·VM 소비 측 차단은 미검증이다.
