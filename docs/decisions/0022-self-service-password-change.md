# 0022. 본인 비밀번호 변경과 로그인 직렬화

- **상태:** 제안 — #128 구현 반영, PR 리뷰 대상
- **날짜:** 2026-10-24
- **관련:** #68, #125, #128, #129, ADR-0014, ADR-0021
- **영향 받는 담당:** P1 주환. 다른 모듈 공개 계약·DB 스키마 변경 없음.

## 배경

#68과 #128은 본인 비밀번호 변경 후 현재 세션을 유지하고 다른 세션을 종료하도록 정했다. #125의 세션 등록·종료 모니터만으로는, 옛 비밀번호 검증을 끝낸 로그인 요청이 변경 커밋과 세션 종료 뒤에 등록되는 문제를 막을 수 없다. #129도 동일한 새 비밀번호 정책과 변경 화면을 재사용해야 한다.

## 결정

### HTTP 계약

- `POST /api/auth/password`, 로그인한 모든 역할. 대상은 `SessionUser.userId`로 결정하며 요청에서 사용자 ID를 받지 않는다.
- JSON은 `currentPassword`, `newPassword`. 성공은 본문 없는 204이며 현재 세션 ID와 인증 정보는 유지한다.
- 비로그인·만료·존재하지 않거나 비활성화된 계정은 401 `AUTH_001`, 현재 비밀번호 불일치는 400 `AUTH_003`, 새 정책 위반은 400 `AUTH_006`이다. 기존 `AUTH_004`·`AUTH_005` 용도는 보존한다.
- 필수 입력 누락·잘못된 JSON은 입력값을 제외한 400 ProblemDetail, DB·트랜잭션 장애는 원인을 노출하지 않는 500 `AUTH_007`이다. 로그인 전용 `AUTH_005` 문구와 구분하며 원인은 error 로그에만 남긴다.
- `SecurityConfig`에서 이 경로만 추가로 인증을 요구한다. 전체 업무 인가·CSRF 활성화는 #68 5단계에 유지한다.

### 공통 정책과 비밀정보

- identity 내부 `PasswordPolicy.validate(loginId, password)`에 정책을 모은다. Unicode 코드 포인트 기준 8~64자, ASCII 영문·숫자를 각각 포함하며 DB에 저장된 로그인 아이디와 정확히 같은 값은 거절한다.
- 한글·특수문자·공백을 허용하고 trim·대소문자 변환을 하지 않는다. UTF-8 72바이트 이하를 요구해 BCrypt 입력 한도를 넘기지 않는다. 잘못된 단독 서로게이트는 UTF-8 변환 시 대체 문자가 되어 서로 다른 입력이 같은 해시가 되므로 거절한다.
- 72바이트 제한과 문자 정책은 구현 전 사용자 승인에 따라 #128과 상위 #68 결정 8번에 반영했다. Notion 동기화는 수행하지 않았다.
- 정책은 새 비밀번호에만 적용한다. 기존 시드의 `1234`도 현재 비밀번호 확인에는 사용할 수 있다. 같은 현재 비밀번호 재사용 금지 등 추가 정책은 넣지 않는다.
- 기존 `PasswordEncoder` BCrypt를 사용하고 `PlatformUser.changePasswordHash()`로 변경한다. 새 스키마나 다른 인코더를 도입하지 않는다.
- 변경 성공과 `AUTH_003`·`AUTH_006` 실패는 userId와 코드만 info 로그로 남겨 변경 시점을 추적한다.
- DTO의 문자열 표현은 비밀번호를 숨긴다. 비밀번호·해시·검증 예외의 입력값을 응답·로그·세션에 넣지 않는다.

### 로그인과 변경의 순서 보장

- 단일 서버에서 `AccountLockService`의 고정 256개 잠금으로 계정 작업을 직렬화한다. 없는 아이디 요청이 잠금 객체를 계속 늘리지 않게 한다. 같은 분할에 속한 다른 계정은 잠시 대기할 수 있다.
- 로그인은 먼저 입력 아이디를 정규화해 계정을 조회하고 DB의 실제 `loginId`를 잠금 키로 사용한다. `utf8mb4_unicode_ci`가 악센트가 다른 문자열도 같은 계정으로 찾을 수 있기 때문이다. 없는 계정은 정규화된 입력을 키로 사용하고 기존 인증 실패 흐름을 따른다.
- 첫 조회는 잠금 키만 정한다. 비밀번호 검증·계정 상태 확인은 잠금 안에서 `AuthenticationManager`가 DB를 다시 조회해 수행한다. 권한 조회·세션 등록까지 완료한 후 잠금을 해제한다. 기존 로그인 실패 응답은 유지한다.
- 변경은 세션에 저장된 실제 `loginId`로 같은 잠금을 획득한다. 대기 후 `SessionRegistry`에서 세션 ID·userId·만료 여부를 재확인한다. 만료된 세션은 복구하지 않고 401로 거절한다.
- 잠금 안에서 `TransactionTemplate(REQUIRES_NEW)`로 현재 비밀번호 확인·정책 검사·해시 변경·커밋을 수행한다. 반환된 후 `expireAllExcept(userId, currentSessionId)`를 호출하고 잠금을 해제한다. 실패·롤백·커밋 실패 시 세션 종료를 호출하지 않는다.
- 잠금 순서는 계정 잠금 → 기존 `UserSessionService` 모니터다. 기존 모니터는 세션 등록·종료의 짧은 메모리 작업만 보호한다. DB 작업은 기존 전역 세션 모니터 안에 넣지 않는다.
- 변경이 먼저면 옛 비밀번호 로그인은 커밋 후 실패한다. 다른 로그인이 먼저면 기존 세션의 변경은 거절된다. 변경 후 새 비밀번호로 로그인하면 기존 단일 세션 정책에 따라 이전 세션이 종료된다.
- 메모리 세션과 동일하게 단일 서버 범위다. 다중 서버, #129의 초기화·정지·권한 변경, #130의 가맹점 정지와 로그인 사이의 동시성까지 해결한 것으로 보지 않는다.

### 화면과 후속 연결

- `/account/password` 화면을 세 역할 공통 헤더에서 연다. 업무 기능 권한 없는 사장님도 접근하고, 기존 권한 없음 화면에도 진입 링크를 제공한다.
- 현재·새 비밀번호와 확인값을 입력한다. 서버가 최종 정책을 검사하며 화면은 확인값 일치·필수 입력을 검사하고 중복 제출을 막는다. 성공하면 폼을 지운다.
- 기존 API 클라이언트는 `/auth/*` 401을 전역 만료에서 제외한다. `/auth/password` 401은 예외적으로 만료 이벤트를 전달하되 이전 로그인에서 시작한 요청의 늦은 응답은 무시한다.
- #129는 정책과 화면을 재사용한다. 강제 변경 상태, 제한된 접근과 완료 후 `/me` 갱신은 #129에서 추가한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 커밋 후 세션 종료만 호출 | 옛 비밀번호로 인증을 끝낸 요청이 나중에 세션을 등록할 수 있다 |
| 입력 아이디 문자열로만 잠금 | DB collation이 같은 계정으로 보는 별칭이 서로 다른 잠금을 사용할 수 있다 |
| 전역 세션 모니터 안에서 BCrypt·DB 처리 | 모든 계정의 로그인·세션 종료가 한 계정의 DB 작업을 기다린다 |
| 계정마다 잠금을 무제한 생성 | 없는 아이디를 계속 보내면 메모리가 증가한다 |
| `@Transactional` 메서드 내부에서만 잠금 | 메서드 반환 후 프록시가 커밋하므로 커밋 전에 잠금이 풀릴 수 있다 |
| 비밀번호 버전 컬럼·Redis 도입 | 단일 서버 메모리 세션 요구에 불필요한 스키마·저장 방식 변경이다 |
| 비밀번호 pre-hash·인코더 교체 | 기존 BCrypt 로그인·해시 계약을 확장한다. 승인한 72바이트 제한으로 처리한다 |
| 프론트만 정책 검사 | API 직접 요청과 #129에서 우회하거나 규칙이 달라질 수 있다 |

## 영향과 검증

- API: 본인 변경 경로와 오류 코드 3개(400 `AUTH_003`·`AUTH_006`, 500 `AUTH_007`) 추가. 로그인 시 잠금 키 조회 1회 추가. 다른 모듈 API·인증 정책은 보존한다.
- DB: 기존 `password_hash` 값만 변경. migration·컬럼·공개 Java 계약 변경 없음.
- 화면: 공통 헤더·계정 경로·만료 처리 추가. 기존 역할별 첫 화면과 업무 권한은 보존한다.
- 테스트: 정책 문자·바이트 경계, 실제 MariaDB 저장과 HTTP 쿠키, 세 역할, 선택 종료·타 사용자 보호, 실패·커밋 순서, 로그인 경쟁 조건과 DB 별칭, 클라이언트 401·늦은 응답을 확인한다.
- 실행 기준·결과와 브라우저 미검증은 [identity README](../identity/README.md)의 #128 기록에 남긴다.
