# 0042. FDS 룰 활성화와 변경 승인 관리

- **상태:** 제안
- **날짜:** 2026-10-28
- **관련:** #283, ADR-0040
- **영향 받는 담당:** P1, P2, P5

## 배경

공통 결제 룰 R01~R08은 모든 가맹점에 동일하게 적용하되, 운영 중 일시 비활성화가 필요하다. 보안 직원의 비활성화는 탐지 공백을 만들므로 관리자 승인 절차가 필요하고, 관리자는 긴급 상황에서 직접 상태를 바꿀 수 있어야 한다.

## 결정

P2가 `fds_rule_policies`에 룰별 활성 상태와 마지막 변경자를 저장한다. 평가는 활성 정책만 적용한다. 보안 직원은 비활성화 사유를 담은 요청만 만들고, 꺼진 룰을 다시 활성화할 수 있다. 관리자는 요청을 승인·반려하거나 카탈로그에서 직접 상태를 변경한다. 직접 비활성화는 같은 룰의 대기 요청을 승인으로 종결하고, 직접 활성화는 반려로 종결한다.

P5는 실제 승인 성공·거절 결과를 P2 공개 `FdsAuthorizationResultRecorder`로 기록한다. P2는 이 스냅샷으로 R08 거절 후 재시도를 평가하며 P5 DB를 직접 조회하지 않는다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 보안 직원이 즉시 룰을 끔 | 탐지 공백에 대한 관리자 통제가 없다. |
| P2가 P5 결제 테이블을 직접 조회 | 모듈 소유 경계와 `payment → fds` 단방향 규칙을 위반한다. |
| 정책 변경 이력을 별도 테이블에 모두 저장 | 요청 이력과 정책의 마지막 변경자·시각으로 현재 범위의 추적 요구를 충족한다. |

## 영향

- API: 룰 정책 조회·활성화·비활성화 요청·승인 API 및 P5→P2 승인 결과 기록 계약.
- DB: P2 소유 정책·요청 테이블. 요청 사유와 요청·처리자 표시 이름 스냅샷을 보존한다.
- 화면: 보안 직원 카탈로그, 관리자 카탈로그·요청·대기 건수 배지.
- 테스트: 권한, 동시 처리, 상태 전이, R08 실제 승인 거절 결과 연결을 검증한다.
