# 0033. 로그인 이력의 독립 저장과 90일 조회

- **상태:** 제안 — #147 사용자 스키마·저장소 ERD 우선 구현 승인, 팀 리뷰 대상
- **날짜:** 2026-10-25
- **관련:** #147, #144, ADR-0014·0021·0029
- **영향 받는 담당:** P1 주환(identity + frontend)

## 배경

현재 로그인 성공·실패는 서버 로그만 남으며 본인·관리자의 계정별 접속 조회를 제공하지 않는다.
로그인은 메모리 세션과 DB 잠금 횟수 저장을 사용하므로 이력 테이블을 추가할 때 장애 경계를 구분해야 한다.

## 결정

[#147 상세 설계](../identity/147-login-history-design.md)의 별도 P1 login_histories를 사용한다.
기록은 REQUIRES_NEW로 저장하고 INSERT·커밋 실패를 격리한다.
기존 비밀번호 실패 횟수 저장·성공 초기화의 필수 처리 정책은 유지한다.

- 성공은 세션 인증 수립 완료 뒤 기록하며 이력 실패로 인증을 취소하지 않는다.
- 일반·전체 로그아웃은 세션 정리를 보장하고 동일 로그인 연결 ID와 이벤트 유형의 UNIQUE로 중복을 막는다.
- 성공·실패·로그아웃과 IP·User-Agent는 90일 보관 후 1,000건 배치를 반복해 삭제한다(한 실행 최대 5분). 조회도 항상 90일로 제한한다.
- 마지막 로그인은 보관 중인 가장 최근 성공이며 계정 테이블에 중복 저장하지 않는다.
- 사용자 입력 로그인 ID는 저장하지 않고 없는 계정 실패는 NULL 계정으로 유지한다.
- IP는 직접 연결 또는 설정된 관리 프록시만 신뢰하며 확인할 수 없으면 NULL로 남긴다.

## 고려한 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| admin_change_histories 재사용 | 관리자 변경과 인증 시도의 의미·보관 정책이 다르다 |
| platform_users에 마지막 로그인 추가 | 이력과 중복되고 90일 삭제 후 값이 남을 수 있다 |
| 인증 트랜잭션과 이력 저장 결합 | 이력 장애가 정상 로그인·로그아웃을 막고 실패 예외로 이력이 롤백될 수 있다 |
| 원본 세션 ID를 중복 방지 키로 저장 | 인증 비밀값 보관을 피해야 한다 |
| 메모리 플래그로만 로그아웃 중복 방지 | DB 저장 단계에서 중복을 보장하지 못한다 |
| 모든 전달 헤더 신뢰 | 요청자가 IP를 위조할 수 있다 |
| 보관 기간 밖 마지막 성공 별도 유지 | 이슈의 확정 90일 보관·표시 정책과 어긋난다 |
| IP·User-Agent·입력 ID 무제한 보관 | 범위에 필요하지 않으며 입력 크기·보관량을 제한할 수 없다 |

## 영향

- API: 본인 이력·최근 성공, ADMIN 계정별 이력 조회 추가. 익명·타 역할·강제 변경 인가 검사.
- DB: P1 신규 테이블·FK·인덱스·중복 방지·CHECK. 기존 테이블과 다른 담당 계약 변경 없음.
- 화면: 공통 계정 경로·헤더와 ADMIN 계정 상세 탭.
- 테스트: HTTP·DB 저장 장애·동시성·90일 경계·삭제 재실행 및 기존 인증 회귀.
- 문서: 합의 후 저장소 ERD·identity README·ADR 목록 갱신. 사용자 승인으로 저장소 문서 우선 반영, Notion은 후속 동기화.
- 설정: 원 접속 주소 보존을 위해 `server.forward-headers-strategy: none`을 명시하고 FRAMEWORK/NATIVE를 거절한다. 앱 전체 제약이므로 TLS 종료 프록시 뒤에서는 `request.isSecure()`가 false가 된다.
- #146: 직접 구현 의존 없음. 다만 위 설정 제약이 #146의 HTTPS 의존 쿠키(XSRF-TOKEN Secure 판정)에 닿으므로 배포 구조를 정할 때 함께 결정한다. dev 병합 후 운영 프로필과 통합 검증 필요.
