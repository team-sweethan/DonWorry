# 0017. 1차 MVP 매입 완료 이벤트 계약

- **상태:** 채택 — P5 수신 구현은 별도 작업
- **날짜:** 2026-10-23
- **관련:** [ADR-0012](0012-payment-settlement-dependency.md), [ADR-0016](0016-capture-request-event-contract.md)

## 배경

P5와 P6는 1차에 별도 접수 커밋 없이 매입 완료와 정산 예정금의 동시 저장으로 처리를 확인한다.
P5는 완료 결과로 CAPTURED를 반영하고 직원 ACCEPT 건의 P3 인계 완료를 이어서 처리한다.

## 결정

- `settlement.api.CaptureCompleted`를 Builder가 있는 record로 제공한다.
- 필드는 `paymentId(Long)`, `captureId(Long)`, `capturedAt(Instant)`이다.
- 기존 CaptureTransactionService에서 매입과 정산 예정금을 저장한 뒤 같은 트랜잭션에서 이벤트를 발행한다.
- P5는 `@ApplicationModuleListener`로 커밋 후 수신한다. 등록된 수신자에 대한 Modulith 발행 기록은 업무 데이터와 함께 커밋한다.
- 중복 요청으로 기존 매입을 반환할 때는 신규 완료 이벤트를 발행하지 않는다.
- 기본 입력 검증과 전체 롤백을 유지한다. 자동 재처리·거부 이벤트·최종 실패 판정은 이번 범위에 포함하지 않는다.

## 고려한 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 매입 접수 이벤트를 별도로 발행 | 1차에는 완료 커밋 자체로 접수를 확인하기로 했다 |
| 리스너에서 서비스 반환 후 완료 이벤트 발행 | 업무 데이터는 커밋됐는데 완료 발행 기록은 남지 않는 간격이 생긴다 |
| payment.api에 완료 타입 배치 | P6의 P5 의존이 생겨 ADR-0012 방향을 위반한다 |

## 영향

- API: P5가 위 완료 타입을 import해 수신한다. P5 업무 코드와 P3 통지는 P6에서 작성하지 않는다.
- DB: 컬럼과 migration 변경 없음. P5 수신 리스너가 등록돼야 해당 수신자의 발행 기록도 생성된다.
- 화면: 변경 없음.
- 테스트: 저장 이후 발행 순서·필드·중복 미발행·저장 실패 미발행, 커밋된 두 기록을 조회하는 테스트 수신자를 검증한다.
