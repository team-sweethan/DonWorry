# 0056. 고객 취소 요청 식별과 결과 조회 계약

- **상태:** 제안 — 재요청 키·정지 가맹점 정책과 2개 테이블 분리 방향은 사용자 확인, 저장 기반 구현·검증, HTTP·담당 확인은 후속
- **날짜:** 2026-10-31
- **관련:** #153, #381, [ADR-0054](0054-full-cancellation-policy.md), [ADR-0055](0055-inflight-cancellation-policy.md)
- **영향 받는 담당:** P5, P1/CakeShop, P3, P6

## 배경

진행 중 취소는 일시 거절하지만 같은 요청 키로 나중에 재요청할 수 있어야 한다. 키와 내용의 충돌을 막는 기록과 실제 금융 실행 접수를 구분해야 한다. 직원 조치는 decisionId 필수인 별도 계약이므로 고객 취소의 요청·결과 조회를 대신할 수 없다.

## 결정 제안

사용자가 확인한 정책은 가맹점 범위에서 최초 키·내용을 보존하면서 일시 거절 후 동일 요청의 재판단을 허용하고, 정지 가맹점도 유효한 인증으로 자기 결제 취소·조회를 허용하는 것이다. 키 폐기·신규 결제 차단은 유지한다.

이를 표현하기 위해 요청 키 기반 조회와 금융 작업 cancellationId를 구분하는 [HTTP 계약](../payment/381-cancellation-api-contract.md)을 제안한다. 진행 중 거절은 409, 실제 접수 후 처리/결과 미확정은 202, 성공·이미 취소 완료는 200으로 구분한다. GET은 읽기 전용이며 일시 거절 기록은 자동 실행 예약이 아니다.

저장은 [요청 기록과 금융 작업 2개 테이블](../payment/381-cancellation-storage.md)로 나누며 2026-10-31 사용자가 이 방향에 동의했다. 여러 요청 키를 보존하되 실제 작업은 결제당 하나만 허용한다. 작업은 최초 접수 요청을 참조하고 다른 요청은 동일 결제의 기존 작업에 연결한다. 금융 결과를 요청마다 복제하지 않는다. 직원 VOID는 기존 근거를 참조하며 고객 작업으로 백필하지 않는다. 설계 PR #385 병합 후 다음 단계 진행 요청에 따라 저장 명세를 migration·Entity·Repository로 구현한다. 최초 범위에는 삭제·키 만료를 두지 않으며 장기 보존·익명화는 후속이다. 운영 DB 적용·API 실행 연결은 별도다.

## 고려한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 일시 거절의 키를 저장하지 않음 | 같은 키로 내용 변경을 막는 사용자 정책을 보장할 수 없음 |
| 모든 키 응답을 영구 고정 | 진행 중 거절 뒤 같은 키 재요청을 계속 거절하게 됨 |
| 일시 거절도 202 접수로 반환 | 취소 실행을 예약하지 않는 정책과 충돌 |
| 모든 POST에 정지 가맹점 차단 적용 | 기존 고객의 취소·환불을 허용한다는 정책과 충돌 |
| 직원 payment_actions에 고객 취소를 그대로 저장 | decisionId 필수·결제당 직원 조치 하나·P3 결과 계약과 충돌 |
| 요청과 작업을 한 행에 합치고 결제당 UNIQUE 적용 | 일시 거절한 여러 키의 최초 내용을 보존하면서 실제 실행만 하나로 제한하기 어려움 |
| 요청 키마다 금융 작업 생성 | 서로 다른 키의 동일 결제 환불을 중복 실행할 수 있음 |

## 영향

- API: 새 POST·요청 키 GET, ProblemDetail 오류·재요청 안내를 제안한다. 기존 API 변경·활성화 없음.
- DB: P5 payment_cancellation_requests·payment_cancellations의 필드·제약·원자성 초안을 추가했다. 결제당 한 금융 작업, 가맹점별 키 고정, 접수 전 키 보존을 제안하며 저장소 ERD와 두 migration을 추가했다. Notion 동기화·장기 보존 정책은 후속이다.
- 화면: CakeShop은 DEFERRED를 취소 완료로 표시하지 않고 명시적 재요청을 제공한다. UI 구현 없음.
- 테스트: 키 충돌·동시 요청·기존 직원 취소·실패/미확정·정지 가맹점·조회 부작용을 후속 검증한다.
- 계약: P1 보안 경로, P3 직원 조치 연계, P6 성공 결과 전달 확인은 미완료다.

## 검증

기준 코드 `dev 7b0d4bb`의 Payment HTTP·가맹점 인증·직원 조치 구현을 참고했다. 설계 단계에서는 문서 링크·공백·예시 JSON만 검사했다. 이후 저장 기반 구현의 검사 결과와 미검증 범위는 [저장 명세 10절](../payment/381-cancellation-storage.md#10-저장-기반-구현-381-후속)을 따른다. 실제 API·금융 실행은 후속이다.
