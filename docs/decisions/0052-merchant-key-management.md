# 0052. 가맹점 HMAC 키의 암호화 저장과 사장님 직접 관리

- **상태:** 제안 — #354 PR B P1 사용자 설계·구현 승인, PR 리뷰 대상
- **날짜:** 2026-10-31
- **관련:** [Issue #354](https://github.com/team-sweethan/DonWorry/issues/354), [PR B 설계](../identity/354-pr-b-key-design.md), [ADR-0037](0037-merchant-hmac-authentication.md)
- **영향 받는 담당:** P1. P5·P6는 기존 HMAC 경계·서명 형식을 유지한다. 연동 전 신규 결제 차단은 PR C에서 P5에 공지한다.

## 배경

승인으로 만든 가맹점은 secret_reference가 없어 환경변수 방식으로 키를 직접 발급받을 수 없다. 연동 전에 키를 다시 볼 수 있어야 하므로 단방향 해시로는 요구를 충족하지 못한다. 기존 CAKESHOP 키는 같은 값으로 옮겨 쇼핑몰 서버 설정을 보존해야 한다.

이 ADR은 제안 상태 ADR-0037의 **키 보관 부분을 변경**한다. ADR-0037을 삭제하거나 대체됨으로 변경하지 않는다. 서명 형식·헤더·nonce·기존 조회/픽업 인가 계약은 유지한다.

## 결정

### 저장과 복구

`merchant_integrations`에 가맹점별 현재 키를 AES-256-GCM으로 암호화해 저장한다. 마스터 키는 표준 Base64 32바이트다. 운영(`prod`)에서는 `DONWORRY_HMAC_MASTER_KEY_<ID>` **실제 프로세스 환경변수만** 읽으며 Spring property·시스템 속성·로컬 YAML로 대신하지 않는다. 활성 ID는 `donworry.integration.active-master-key-id`(기본 V1)로 정한다. ID는 대문자·숫자·밑줄 1~40자다.

2026-10-31 PR C 사용자 승인으로 개발 환경에 한해 예외를 추가한다. `prod`가 활성화되지 않았고 해당 환경변수가 없을 때만 `donworry.integration.local-master-keys.<ID>`를 읽는다. Git 제외된 `backend/src/main/resources/application-local.yml`에 개발용 키를 한 번 생성해 저장하고 같은 DB를 사용하는 동안 유지한다. 환경변수가 있으면 그것이 우선이고, 형식이 잘못된 환경변수를 로컬 키로 대체하지 않는다. `prod`가 다른 프로필과 함께 켜져도 로컬 값은 무시한다. 기본 `application.yml`은 `!prod`에서만 로컬 파일을 import하며 복호화 코드도 독립적으로 prod를 검사한다.

이 설정 파일에는 키 원문이 있으므로 Git·배포 아티팩트에 포함하지 않는다. `build.gradle`의 기존 `tasks.withType(Jar)` 제외 규칙이 로컬 작업 트리의 `application-local.yml`도 jar/bootJar에 넣지 않는다. 배포는 `prod`로 실행하고 환경변수에 운영 키를 설정한다. 예제에는 설정 이름과 자리표시자만 둔다. 런타임 자동 키 생성은 하지 않는다. 버린 대안: 실행마다 환경변수에 새 키를 생성하면 기존 DB를 읽을 수 없고, 배포 직전 수동 삭제는 누락될 수 있다. 개발 편의는 로컬 파일·프로필 제한으로 제공하고 운영 키 경계는 유지한다. API·DB·화면 계약 변경은 없으며 프로필 차단·환경변수 우선순위·재시작 복호화 테스트를 같은 PR에 추가한다.

암호화마다 무작위 12바이트 IV와 128비트 태그를 사용한다. AAD는 `DONWORRY-KEY-V1`·merchant_id·key_version을 LF로 연결한다. 새 HMAC 키는 무작위 32바이트를 표준 Base64로 표시한다. 기존 32바이트 이상 키는 원래 바이트를 그대로 보존한다.

DB는 마스터 키 ID만 보관한다. 복호화는 저장된 ID를 따르며 새 발급은 활성 ID를 쓴다. 이전 ID의 마스터 키는 그 ID를 참조하는 DB·백업이 있는 동안 보존한다. 활성 ID 변경은 기존 행의 재암호화를 뜻하지 않는다. 재암호화 일괄 작업은 후속이다.

DB 백업과 별도로 접근 제한된 비밀 보관소에 마스터 키를 백업한다. 복원 환경에서는 DB와 그 DB가 참조하는 모든 마스터 키를 함께 복구하고, 기존 키로 서명한 읽기 요청이 인증되는지 검사한다. 마스터 키를 잃으면 암호문을 복구할 수 없다. 키가 없거나 잘못됐거나 암호문이 변조되면 503으로 차단하고 다른 키로 대체하지 않는다.

### 상태·이력·권한

상태는 `NO_KEY`·`PENDING_CONNECTION`·`CONNECTED`다. 행이 없으면 NO_KEY다. 계정 상태·가맹점 ACTIVE/INACTIVE와 분리한다. 현재 키 암호문은 재발급 시 교체하고 폐기 시 지운다. 발급·재발급·폐기·시스템 이전의 버전·시각·실행 계정·폐기 사유를 `merchant_key_histories`에 보존한다. 키 변경과 이력 저장은 원자적이다. 과거 키 원문·암호문은 이력에 저장하지 않는다.

ACTIVE OPERATOR가 자기 가맹점 키를 관리한다. FDS_VIEW·FINANCE_VIEW는 요구하지 않는다. 정지 계정·정지 가맹점·강제 비밀번호 변경 중에는 사장님 키 관리를 거절한다. 기존 복수 사장님 계정도 각자 같은 가맹점 키를 관리하되 실행 계정을 기록한다. 관리자는 원문을 볼 수 없고 정지 가맹점도 사고 대응을 위해 폐기할 수 있다.

발급·보기·재발급 요청마다 현재 비밀번호를 확인한다. 로그인과 같은 계정 잠금·실패 횟수 5회·15분 잠금을 공유한다. 실패는 작업 롤백과 무관하게 기록하고, 올바른 비밀번호 확인은 실패 횟수를 초기화한다. 관리자 폐기는 기존 관리자 세션 확인과 사유·키 버전 확인으로 처리한다.

연동 전만 키를 다시 볼 수 있다. CONNECTED는 보기 불가다. 재발급은 이전 키를 즉시 폐기하고 PENDING_CONNECTION으로 바꾼다. 폐기는 NO_KEY로 바꾸며 이전 환경변수로 fallback하지 않는다. 모든 키 응답은 Cache-Control: no-store다. 화면은 키를 메모리에만 보관하고 닫기·화면 이동·숨김·세션 만료 때 지운다. 복사 버튼은 사용자가 눌렀을 때만 클립보드에 쓴다.

### API와 동시성

B의 API는 [설계 5절](../identity/354-pr-b-key-design.md#5-api인가동시성-제안)을 따른다. 조회에는 원문을 포함하지 않는다. 키 작업·관리자 폐기는 전역 CSRF off에서도 CSRF를 검사한다. 사장님 요청은 세션에서 merchantId를 결정하고 대상 가맹점을 입력받지 않는다. 상태/이력은 20개씩 조회한다.

발급·보기·재발급·폐기에 expectedKeyVersion을 요구한다. 가맹점 행 잠금 후 버전을 재확인하며 중복·충돌은 409다. 서명을 검증한 키 버전도 nonce 소비 트랜잭션에서 같은 가맹점 잠금 후 다시 확인한다. 재발급·폐기가 먼저 커밋됐다면 옛 키 요청은 401이다. 이미 nonce 소비까지 마친 업무 요청을 소급 취소하지 않는다.

오류: INTEGRATION_001(409, 상태/버전 충돌), INTEGRATION_002(409, 보기 불가), INTEGRATION_003(429, 비밀번호 확인 잠금), INTEGRATION_004(400, 잘못된 입력), INTEGRATION_005(403, 정지 가맹점). 비밀번호 불일치는 기존 AUTH_003(400), 인증·역할·강제 변경은 AUTH_001/002/008을 쓴다. 암호화 설정 장애는 MERCHANT_AUTH_002(503)다.

### 기존 키 이전과 배포

1. **시연 이후** DB·현재 HMAC 키·마스터 키 백업을 준비한다. 현재 키를 새로 생성하거나 다른 환경 키로 대체하지 않는다. secret_reference가 있는 가맹점 목록을 확인한다.
2. 현재 `DONWORRY_MERCHANT_HMAC_*` 환경변수를 유지하고 새 마스터 키 환경변수를 추가한다. 키 값을 명령 인자·SQL·Git·로그에 넣지 않는다.
3. `donworry.integration.legacy-import-enabled=true`로 새 서버를 기동한다. Flyway/JPA 초기화 뒤, 웹서버가 요청을 받기 전 SmartInitializingSingleton에서 기존 참조를 가진 **모든 가맹점**을 원자적으로 이전한다. CAKESHOP은 같은 키로 CONNECTED가 된다. DEMOSHOP은 그대로 NO_KEY다.
4. 기존 integration 행이 있으면 상태와 관계없이 건너뛰어 재실행·폐기 후에도 옛 키가 되살아나지 않는다. 필수 환경변수·마스터 키·저장 오류는 이전 트랜잭션 롤백과 기동 실패로 처리한다.
5. 새 timestamp·nonce로 기존 키의 읽기 서명을 보내 인증 유지와 이력·CONNECTED 상태를 확인한다. 키·서명은 기록하지 않는다. 이후 이전 플래그를 끄고 더는 쓰지 않는 레거시 환경변수를 서비스에서 제거한다. CakeShop 서버의 키 값은 바꾸지 않는다.

이전 플래그 기본값은 false다. **이전하지 않은 레거시 가맹점의 HMAC 요청과 사장님 발급은 503**이므로 기존 환경은 3단계를 반드시 거친다. 신규 환경도 시드 CAKESHOP을 쓸 때는 같은 절차가 필요하다. 일반 신규 신청 가맹점에는 레거시 참조가 없어 직접 발급한다.

미이전 상태는 조회 응답·화면에 따로 표시하지 않는다(2026-10-31 결정). 이 상태는 3단계 이전 전에만 생기므로 응답 계약을 늘리지 않고 이전 절차로 해소한다. 그 사이 화면은 `NO_KEY`로 보이며 사장님 발급은 503이고, 관리자 화면 폐기 버튼은 꺼져 있다. 이전 전에 사고 대응 폐기가 필요하면 관리자 폐기 API(`expectedKeyVersion` 0)를 직접 호출한다. 버린 대안: 조회 응답에 이전 필요 표시를 추가하는 안은 일시 상태 때문에 API·화면 계약이 늘어나 채택하지 않았다.

롤백 시 새 버전에서 키 재발급·폐기를 했는지 먼저 확인한다. 옛 앱은 환경변수 키를 다시 받아들일 수 있으므로 키 변경 후에는 단순 구 버전 재기동으로 롤백하지 않는다. 이전 전 백업 복원·쇼핑몰 설정 정합성을 검토하고 서비스 재개를 결정한다.

### PR C 연결 확인과 신규 결제 차단

`POST /api/merchant-connections/check`는 빈 본문·기존 HMAC 헤더를 사용하고 성공하면 204를 반환한다. 직원 세션·CSRF로 대신 인증하지 않으며 로그인 세션을 만들지 않는다. 별도 연결 버튼으로 상태를 변경하지 않는다. 이 경로는 결제 API 활성화 여부와 무관하게 제공한다.

서명 확인 → 키 버전 재검사와 nonce 독립 커밋 → (POST만) 가맹점 행 잠금 → 현재 키 버전·키 존재·가맹점 상태 재검사 → 연결 확인 또는 신규 결제 허용 순서다. 조회·픽업 PUT은 nonce 소비 때의 잠금·버전 확인으로 끝내고 두 번째 잠금을 잡지 않아 같은 가맹점의 요청끼리 기다리지 않는다. HMAC 필터가 서비스 트랜잭션으로 연결 확인을 커밋한 뒤에만 Controller의 204에 도달한다. 중간에 재발급·폐기가 완료된 요청은 401이며 새 키 상태를 변경하지 않는다. 상태 검사 실패에도 nonce는 복구하지 않는다. 인증을 모두 끝낸 업무 요청을 나중의 재발급으로 소급 취소하지 않는다.

ACTIVE + PENDING_CONNECTION의 올바른 연결 확인만 CONNECTED·connected_at·updated_at을 변경한다. 이미 CONNECTED면 새 nonce의 재확인도 204이며 최초 연결 시각을 유지한다. key_version은 연결 확인으로 증가하지 않는다. 키 발급·폐기 이력에 CONNECT 작업을 섞지 않고 현재 행의 connected_at으로 확인을 기록한다. INACTIVE는 403 MERCHANT_AUTH_003, 빈 본문이 아니면 400 MERCHANT_AUTH_007이다. POST 경로는 위 연결 확인 경로와 `/api/payments`의 원문 표기를 사용하며 인코딩된 별칭으로 게이트를 우회하지 못하게 거절한다.

`POST /api/payments`는 CONNECTED + ACTIVE에서만 허용한다. 유효한 키가 있지만 PENDING_CONNECTION이면 403 MERCHANT_AUTH_006이다. NO_KEY는 검증할 키가 없어 401 MERCHANT_AUTH_001이며, 미이전 레거시는 기존 503을 유지한다. `GET /api/payments/{paymentId}`, `GET /api/payment-orders`, 기존 픽업 PUT·직원 업무 처리는 연동 상태로 막지 않는다. 폐기된 키로 기존 조회를 할 수 있다는 뜻은 아니다. 기존 키를 동일 값으로 이전한 CAKESHOP은 CONNECTED를 유지하므로 추가 연결 확인 없이 계속 인증된다.

사장님 계정 정지는 쇼핑몰 HMAC 인증에 추가 조건으로 쓰지 않는다. 첫 비밀번호 설정은 로그인·키 발급의 선행 단계라 PENDING_SETUP 계정 상태를 만들지 않는다. P5의 결제 업무 코드·공개 Java 계약·DB 스키마는 변경하지 않는다. P5에는 PR의 리뷰어 지정과 본문의 허용 조건·새 오류 코드로 공지한다.

버린 대안: 모든 POST를 미연동 차단하면 연결 확인 자체가 막힌다. Controller에서 키 버전 없이 CONNECTED로 바꾸면 재발급 직전 검증된 옛 요청이 새 키를 연결할 수 있다. nonce와 상태 변경을 한 트랜잭션에서 예외로 롤백하면 거절한 서명이 다시 살아난다. 별도 테이블·마이그레이션은 B의 현재 상태·시각 컬럼으로 충족되어 추가하지 않는다.

## 고려한 대안

### 사장님 홈과 로그인 첫 이동 (#354 후속)

2026-10-31 사용자 승인 배치로 `/owner` 홈을 추가한다. 홈·키 관리는 업무 권한 없이 접근하고 바로가기만 기존 업무 권한을 따른다. 일반 로그인과 인증된 루트 진입은 연동 상태와 무관하게 `/owner` 홈으로 이동하고, 미연동 안내는 홈 첫 카드가 맡는다. 강제 비밀번호 변경이 최우선이며 같은 사용자 세션 만료 복귀는 기존 `loginDestination`의 안전성·권한 검사로 유지한다. 홈의 상태 조회 실패를 키 없음으로 간주하지 않는다. 홈 직접 방문과 기존 업무 화면 접근은 연동 상태로 차단하지 않는다.

버린 대안: 인증 `/me` 계약 확대·새 홈 전용 API는 기존 조회로 충족할 수 있어 추가하지 않는다. 로그인 때 연동 조회로 미연동을 `/owner/integration`에 보내는 방식은 정지 가맹점(조회 403)과 통신 장애에서 로그인을 막아 버렸다. DB·HMAC·다른 모듈 계약 변경 없이 화면·라우팅·프론트 테스트를 함께 변경한다. 상세와 실행 증거·남은 로컬 키 이전은 [후속 기록](../identity/354-owner-home.md)을 따른다.

| 대안 | 버린 이유 |
| --- | --- |
| 환경변수에 가맹점 키 계속 보관 | 발급·재발급마다 서버 환경변수 변경이 필요하고 동적 관리가 어렵다 |
| 외부 비밀 저장소에 가맹점별 키 저장 | 현재 단일 앱 범위에서 별도 운영·권한·장애 경계 부담이 크다. 마스터 키 백업에는 비밀 보관소를 사용한다 |
| 키 단방향 해시 | 서명 검증과 원문 다시 보기에 필요한 키 바이트를 복원할 수 없다 |
| 발급 때 한 번만 표시 | 연동 설정 중 복사 오류마다 재발급해야 한다 |
| 이전 키 유예 기간 | 키 유출 시 즉시 차단과 이중 키 상태 관리가 복잡해진다 |
| 관리자가 키를 받아 전달 | 원문 전달 단계가 늘고 사장님 직접 연동 목표와 맞지 않는다 |
| 쇼핑몰 전용 연결 버튼 | 각 쇼핑몰마다 별도 버튼·리다이렉트 구현이 필요하다 |
| 계정 PENDING_SETUP 추가 | 로그인에 첫 설정이 이미 필요하며 계정·가맹점·연동 상태의 의미가 섞인다 |
| 관리자 이력 테이블에 모든 키 이력 저장 | 사장님과 시스템 이전을 포함한 별도 보존·조회 계약이 필요하다. 관리자 외 행위를 기존 관리 이력과 섞지 않는다 |

## 영향

- API: P1 내부 세션 키 관리 API 추가. identity.api와 다른 모듈의 공개 인터페이스는 유지한다.
- DB: P1 테이블 2개·같은 담당 FK·상태 CHECK·이력 인덱스. 기존 SQL·secret_reference 컬럼은 유지한다.
- 화면: 미리보기를 실제 키 관리로 전환, 관리자 상세 폐기 추가. 홈·로그인 첫 화면 변경은 C다.
- 테스트: 암호화·키 버전 경합·실패 잠금·인가·CSRF·HMAC·이전·Flyway/JPA·프론트 API.
- 문서: ERD·identity README·기존 HMAC·키 준비·승인 설계·검증 기록.
