# ADR-0072: 지급 전 환불 제외를 가맹점 공통 잠금으로 조율한다

- 상태: 제안 (P6 4단계 구현 승인, 팀 채택·운영 활성화 별도)
- 관련: #488, [ADR-0070](0070-p6-merchant-daily-payouts.md), [ADR-0071](0071-p6-refund-receiving-ledger.md), [계약·ERD](../settlement/unpaid-refund-exclusion.md)

## 배경

일정산은 가맹점·지급일 행을 잠그고 환불 수신은 원 정산 행을 잠근다. 두 경로를 따로 두면 수신과 지급 확정 사이에 상태가 바뀌고 서로 다른 잠금 순서가 생긴다. 이전 단계의 PENDING 수신도 지급 전에 반영해야 한다.

## 결정 제안

P6 전용 merchant_settlement_locks의 가맹점별 행을 짧은 독립 트랜잭션에서 먼저 준비하고 두 경로의 금융 트랜잭션이 최우선으로 잠근다. 동일 금융 트랜잭션의 커밋/롤백까지 보유하며 원장/정산 잠금보다 먼저 확보한다. 다른 모듈의 가맹점 행은 사용하지 않는다. TransactionTemplate으로 준비와 금융 트랜잭션을 순차 실행해 연결을 이중 점유하지 않는다. UPSERT의 인덱스 잠금을 금융 처리까지 보유하면 다른 가맹점의 최초 삽입도 지연되는 실제 재현 결과를 반영했다.

지급 대상은 ID 조회 후 해당 PK만 잠근다. 범위 FOR UPDATE가 전체 PK 스캔으로 다른 가맹점 정산을 기다리는 현상을 재현해 제거했다. 같은 가맹점 금융 상태는 공통 잠금으로 ID 조회와 잠금 사이에 바뀌지 않도록 한다.

환불 처리 시 미지급이면 원 금액을 보존한 채 정산 CANCELED와 조정 APPLIED/UNPAID_EXCLUSION/잔여 0을 원자적으로 반영한다. 지급 배치도 대상 선정 전에 이전 PENDING의 미지급 제외를 수행한다. 지급이 먼저 확정됐다면 완료 원장을 고치지 않고 조정을 PENDING으로 남겨 후속 회수 단계에 넘긴다.

이미 제외한 금액을 지급액에서 또 차감하지 않는다. 원 매입 COMPLETED·수수료·정산액·일정은 보존한다. 수신/자동 배치/P5 환불 활성화는 이번 범위에서 하지 않는다.

## 대안과 이유

- 상태를 조회한 뒤 잠금 없이 변경하면 조회와 실행 사이 경합이 남는다.
- 날짜별 지급 원장만 공통 잠금으로 쓰면 환불에 임의 지급일 행이 필요하고 날짜가 다른 실행을 직렬화하지 못한다.
- P1 merchants를 잠그면 타 담당의 저장소·테이블을 직접 참조하고 무관한 가맹점 관리까지 묶는다.
- DB 이름 잠금은 커넥션 반환·트랜잭션 종료와 생명주기가 달라 풀 환경에서 해제 누락 위험이 있다.

가맹점별 동시 쓰기를 제한하는 비용과 작은 잠금 테이블이 추가된다. 현재 규모에서는 금융 정합성을 우선하며 외부 HTTP를 잠금 중 호출하지 않는다. 지급 후 회수는 아직 없어 실제 환불 활성화는 후속 검증을 기다린다.

## 영향·검증

P6 Entity·Repository·서비스와 신규 SQL·테스트·문서만 변경한다. 다른 모듈/이벤트/HTTP/프론트 계약은 바꾸지 않는다. 두 DB 연결의 경합 양방향, 실패 롤백, 다른 가맹점 독립성, 이전 수신 보정과 페이지 경계, 기존 지급 회귀를 확인한다. 결과는 PR에 기록하며 구버전 금융 쓰기를 중지한 배포 전환이 필요하다.
