# 0029. 로그인 연속 실패의 고정 시간 잠금

- **상태:** 제안 — #127 정책 사용자 승인, 저장소 ERD 기준 구현 승인, PR 리뷰 대상
- **날짜:** 2026-10-25
- **관련:** #68, #125, #127, #128, #129, #130, ADR-0014·0021·0022·0024·0028
- **영향 받는 담당:** P1 주환. 다른 모듈의 공개 Java 계약·테이블은 변경하지 않는다.

## 배경

#68과 #127은 비밀번호 5회 연속 오류 후 15분간 로그인을 제한하도록 정했다. 현재 로그인은 BCrypt 인증·계정/가맹점 상태 검사·단일 세션 등록을 수행하지만 실패 횟수와 잠금 종료 시각은 저장하지 않는다.

## 결정

[#127 설계](../identity/127-login-attempt-design.md)의 고정 15분 잠금을 적용한다. P1 `platform_users`의 `login_failure_count`와 `login_locked_until`에 저장하고 계정 DISABLED·가맹점 INACTIVE와 분리한다.

- 잠금 중에도 BCrypt 비교를 수행하며 올바른 비밀번호도 거절한다. 재시도로 실패 횟수·종료 시각을 바꾸지 않는다.
- 종료 시각 이상이면 새 실패 묶음을 시작한다. 성공 시 0·NULL로 초기화한다.
- 비밀번호 변경·관리자 초기화·재활성화로 잠금을 풀지 않으며 기존 로그인 세션은 유지한다.
- 외부 응답은 기존 401 AUTH_004·동일 문구다. 화면에는 계정 상태와 무관한 공통 정책 안내만 표시한다.
- 실패 저장은 조건부 UPDATE 한 번과 독립 트랜잭션으로 처리한다. 커밋 뒤 401을 반환해 실패 예외가 횟수 저장을 롤백하지 않게 한다. 성공 초기화도 세션 등록 전에 커밋한다. 저장 오류는 로그인 장애 AUTH_005다.
- 기존 가맹점 → 계정 → 짧은 세션 모니터 잠금 순서를 유지한다. 새 세션을 만드는 성공 경로는 기존 단일 세션·CSRF 전략을 재사용한다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 메모리에만 실패 횟수 저장 | 재시작 시 제한이 사라지고 #68의 DB 저장 결정과 어긋난다 |
| 기존 계정 status를 잠금에 재사용 | 관리자 정지와 임시 제한을 구별하지 못해 만료 후 정지를 잘못 해제할 수 있다 |
| 잠금 중 재시도마다 15분 연장 | 제삼자가 계정을 무기한 잠글 수 있고 고정 15분 안내와 맞지 않는다 |
| 잠금 만료 뒤 실패 횟수 5 유지 | 다음 오답 한 번에 다시 잠겨 새로 시도할 기회를 주지 못한다 |
| 조회 후 Entity 횟수 +1 저장 | 동시 UPDATE에서 증가가 유실될 수 있고 #127의 단일 UPDATE 요구를 만족하지 않는다 |
| 로그인 전체 트랜잭션에서 실패 저장 후 예외 | 401 예외와 함께 증가가 롤백될 수 있다 |
| 잠금 상태를 비밀번호 검증 전에 반환 | 응답 속도로 상태를 추측할 수 있고 #127의 BCrypt 요구를 어긴다 |
| 별도 잠금 오류·남은 횟수 표시 | 계정 존재·상태를 외부에 노출한다 |
| Redis·IP 제한·CAPTCHA 도입 | 현재 단일 서버 범위에 추가 인프라가 필요하며 #127의 제외 범위다 |

## 영향

- API: 새 경로·응답 필드·코드 없이 기존 로그인에 제한을 적용한다. #68 5단계의 전체 업무 인가·CSRF 검사 활성화는 포함하지 않는다.
- DB: 새 migration 하나로 P1 계정 테이블에 두 컬럼을 추가한다. 기존 migration과 기존 계정·권한·비밀번호는 보존한다. 새 인덱스·FK는 필요 없다.
- 화면: 로그인 폼의 공통 정책 안내. 잠금 판정·횟수 계산은 서버에서만 한다.
- 테스트: 실제 MariaDB·HTTP의 실패 저장·동시성·만료 경계·세션 보존과 BCrypt·오류 처리·기존 인증 회귀를 검사한다.
- 문서: 저장소 ERD·identity README·상세 설계·ADR 목록을 갱신한다. 사용자는 이번 작업의 Notion 선행 반영을 저장소 ERD·ADR로 대체하도록 승인했다. Notion 동기화는 후속이다.
- 한계: 기존 단일 서버 잠금·메모리 세션 전제와 같은 가맹점 로그인 직렬화를 유지한다(ADR-0028). 다중 서버 전환 시 성공·실패·관리자 변경의 순서 보장을 별도로 설계해야 한다. 계정 단위 제한만으로 여러 계정을 대상으로 한 공격을 모두 막지는 않는다.
