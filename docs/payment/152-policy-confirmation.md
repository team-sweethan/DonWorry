# #152 담당자별 정책 확인 질문

- **상태: 전달용 초안 — 미발송·추가 회신 없음. 담당 수락 전.**
- 작성: 2026-10-26. [정책 초안](152-long-held-payment-policy.md), [ADR-0035](../decisions/0035-long-held-payment-policy.md), [Issue #152](https://github.com/team-sweethan/DonWorry/issues/152).
- 기존 #149 방향 확인과 #158 P3 회신은 해당 문서의 근거로 유지한다. 아래 새 질문에 동의한 것으로 확대하지 않는다.

## 이번 내부 대응 검토의 우선순위

CakeShop을 제외한 검토에는 [돈워리 내부 대응 기준](152-internal-response.md)을 사용한다. 아래 기존 질문 전체에 한 번에 답할 필요 없이 다음 항목부터 선택·합의한다. 정책 수락과 실제 구현·검증은 각각 기록한다.

| 대상 | 먼저 확인할 항목 | 결정 상태 |
| --- | --- | --- |
| P5 시은 | D1~D6: 분류·최초 확인·P5 기한·복구 중단 조건·조회 요구·해소 확인. 시간 수치·대체 담당도 선택 | 결정 후보 정리. 정책 확정 전 |
| P3 수민 | A1·A2·A6: 판정/금융 대기 시간·담당, 실제 결과 후 인계, VOID 실패 인계·충돌 처리 | 기존 #158 합의는 유지. 추가 운영 기준 수락 전. HELD 수신은 #170 병합, 금융 연결은 #161 후속 |
| P6 민정 | A3~A6: 매입 결과 확인 경계·담당, 원래 전달 복구, CAPTURE 확정 실패·충돌 처리 | 확인 수단·운영 절차·기한·도입 시점 합의 전 |
| P2 정후 | 평가 ERROR 원인 확인·대응 목표, 재평가를 별도 범위로 유지 | 추가 수락 전 |

P1/CakeShop 질문은 이후 연동 범위 협의용으로 보존한다. 이번 내부 정리가 예약 정책·외부 재시도나 고객 취소·환불 계약의 합의를 뜻하지 않는다.

## 공통 전달 문안

장기 보류 결제 정책(#152) 초안을 정리했습니다. **시간이 지나면 담당자가 확인하되, 실제 금융 결과 확인 전에는 실패·취소나 재고·쿠폰 해제를 확정하지 않는 방향**입니다. 최대 유지 시간과 담당별 대응 기한은 아직 미정입니다.

각 질문에 수락 가능/수정 필요/현재 지원 불가와 이유를 알려주세요. 시간은 시작 기준·기간·초과 시 담당까지, 기능은 현재 구현/추가 구현 필요와 검증 여부까지 구분해 주시면 좋겠습니다. 구현이 필요하면 담당자·선행 계약·후속 이슈도 함께 연결하려고 합니다.

## 1. P1 주환님 / CakeShop 담당 전달용

1. 결과 미확인·PENDING·HELD 동안 예약을 유지하고, 현재 시도의 최종 거절·취소가 확인된 뒤 해제하는 방향을 수락할 수 있을까요? 재고와 쿠폰 각각의 실제 예약 시작 시각, 최대 유지 가능 시간, 자동 해제 기능의 현재 동작을 알려주세요.
2. 예약을 더 유지할 수 없는데 금융 결과가 미확정인 경우 누구에게 인계할까요? 유지 가능한 주문만 접수하도록 제한할 수 있는지, 이미 예약이 풀린 뒤 늦게 CAPTURED가 오면 재확보·고객 안내·환불 협의를 누가 담당할지도 확인 부탁드립니다.
3. 화면 종료 후 CakeShop 서버가 GET 조회와 필요한 같은 키·같은 본문 POST 재시도를 맡을 수 있을까요? 각각의 간격·상한·중단 후 담당자 확인 방식, 401/403 등 인증 문제로 기존 결과를 조회하지 못할 때의 복구 주체를 제안해주세요. GET 자체는 처리를 재개하지 않습니다.
4. 주문·paymentId·attemptNo를 대조해 이전 시도의 늦은 거절로 현재 예약을 해제하지 않고, 중복 완료도 한 번만 반영할 수 있을까요? 결제 접수 전 통신 실패도 포함해 원래 키를 보존할 수 있는지 확인 부탁드립니다.
5. 최초 주문 +10분은 새 시도 기한으로 유지하고 기존 접수 건은 기한 이후에도 확인하는 방향이 맞을까요? 고객 취소를 직원 REJECT와 구분해 #153에서 계약하고, 그 전 고객 안내·서비스 활성화 제한을 어떤 범위로 둘지도 확인 부탁드립니다.

## 2. P3 수민님 전달용

1. HELD 판정 대기는 HELD 전이 시각, 직원 CAPTURE 대기는 P5 조치 requestedAt으로 구분하는 방향이 괜찮을까요? 각각 최초 경고·담당자 대응 기한과 부재 시 인계 담당을 제안해주세요. #158의 24시간 CAPTURE 경고는 자동 실패·Case 종료 기한으로 확대하지 않는 안입니다.
2. 조치 PENDING이면 REQUESTED/ACTION_PENDING을 유지하고 실제 성공 후 Case 종료에 반영한다는 기존 방침을 운영 Gateway·PaymentActionResult 수신(#161)에 어떻게 연결할 계획인가요? PaymentHeld 수신·Case 연결은 #170으로 dev 병합됐습니다. 남은 실제 구현·검증 범위와 운영 인계 절차를 확인 부탁드립니다.
3. 같은 조치 키로 결과를 다시 확인하되, 장기 대기만으로 새 키·반대 조치·자동 REJECT를 만들지 않는 방향을 수락할 수 있을까요? VOID 확정 실패 이후 현재 조치 변경 기능이 없는 건은 어떤 담당자에게 인계할까요?
4. 고객·주문 취소는 부정거래 REJECT로 기록하지 않는 방향입니다. 별도 취소가 Case·판정·인계에 미치는 영향과, 늦은 금융 완료·결과 중복/역순 수신에서 보존해야 할 이력을 알려주세요.

## 3. P5 시은 담당 검토용

1. RECEIVED/EVALUATED, NEEDS_REVIEW, 승인 후 자동 매입 대기, 직원 조치 대기를 구분해 발견·조회할 운영 수단은 무엇으로 제공할까요? 최초 경고·대응 기한, 담당자·인계 경로와 접근 권한을 정해야 합니다.
2. 같은 키 POST 재시도 간격·상한과 수동 복구 절차를 CakeShop과 어떻게 나눌까요? AUTHORIZED 이후에는 새 매입 이벤트를 만들지 않고 원래 전달 기록을 복구하는 담당·절차도 확인해주세요.
3. 미승인 PENDING을 종료할 조건과 필요한 계약은 무엇인가요? 진행 중 평가/승인과의 경합, 늦은 결과 차단 근거를 함께 정해야 합니다. 현재 기능이 없으므로 시간 초과 DENIED/EXPIRED로 대신하지 않는 방향을 검토해주세요.
4. 직원 CAPTURE 접수 뒤 VOID 전환 및 VOID 확정 실패 뒤 재조치가 현재 불가능합니다. 지원할 후속 범위, 영속 근거, P3·P6 합의와 #153 고객 취소 계약의 선행 관계를 어떻게 둘까요?
5. 자동 매입 발행 시점 추적·발행 기록 보존·미완료 전달 복구를 어떻게 보장할까요? 기존 기록을 운영자가 선택·확인할 수 있는 수단과 복구 전후 검증 기준을 정해주세요. 필요한 저장 변경은 별도 ERD 합의 대상으로 남깁니다.

## 4. P6 민정님 전달용

1. P5가 PENDING/HELD여도 P6에서는 매입·정산 예정금이 완료됐을 수 있습니다. 장기 대기 건의 실제 결과를 확인할 공개 계약 또는 운영 절차와 담당자를 어떻게 제공할까요? 현재 지원 범위와 추가 구현을 구분해주세요.
2. 요청 미수신·P6 롤백·매입 완료 후 통지 지연을 구분해 원래 요청/완료 전달을 복구하는 방향이 괜찮을까요? 기록 보존 기간, 재전달 권한·조건·상한, 복구 후 결과 대조 방법을 확인 부탁드립니다.
3. CAPTURE 확정 실패 기준·결과 전달·재처리는 #158에서 후속 협의로 남았습니다. 이번 활성화 전에 필요한 최소 범위가 있는지, 도입 시점과 담당 이슈를 어떻게 잡을지 의견 부탁드립니다. 기술 예외를 확정 실패로 보지는 않는 안입니다.
4. 향후 고객/자동 취소가 매입 요청 발행·처리 중과 겹칠 때, 조회 후 취소만으로는 경합을 막을 수 없습니다. 매입 시작을 막거나 이미 완료된 결과로 수렴할 통제 계약을 어떻게 정할까요? 매입 완료·정산 예정·정산 완료의 취소/환불 제약도 #153과 함께 확인 부탁드립니다.

## 5. P2 정후님 추가 확인용

1. NEEDS_REVIEW의 FDS ERROR는 같은 UUID·저장 입력의 반복 호출로 자동 재평가하지 않는 현재 동작을 유지하는 안입니다. 장기 미처리 시 원인 확인 담당·대응 기한과 P5 전달 정보는 어떻게 정할까요?
2. 재평가를 허용한다면 새 평가와 기존 결제의 연결, 기존 ERROR 보존, 늦은 기존 결과와의 경합·중복 승인 방지 계약이 필요합니다. 별도 합의·구현 이슈로 분리할 수 있을까요? 이번 #152로 재평가 승인이나 자동 ALLOW를 확정하지 않습니다.

## 6. 회신 기록과 합의 종료 조건

| 대상 | 이번 문안 전달 | 회신·근거 | 남은 결정 |
| --- | --- | --- | --- |
| P1/CakeShop | 미발송 | 없음 | 예약 한도·서버 조회/재시도·예외 주문·활성화 범위 |
| P3 | 미발송 | 없음. 기존 #158 근거는 ADR-0027에 보존 | 시간 기준·운영 연결·실패/취소 영향 |
| P5 | 검토용 작성 | 이번 초안 작성 요청. 정책 확정·구현 승인 아님 | 발견·복구·미승인 종료·조치 변경 |
| P6 | 미발송 | 없음 | 실제 결과 확인·전달 복구·확정 실패·경합 |
| P2 | 미발송 | 없음 | ERROR 확인·재평가 분리 |

회신에는 날짜, 원문 링크, 수락 범위, 수정 사항, 구현/검증 상태와 후속 이슈를 기록한다. 필요한 담당들의 기간·종료·예약·경합 합의와 검증 계획·구현 이슈 연결이 끝난 뒤 #152 완료 여부를 판단한다. 미응답이나 문서 검사 통과를 정책 수락으로 취급하지 않는다.
