# #152 담당별 회신과 조회 설계 합의 기록

- **상태: 내부 조회 설계의 P1·P2·P3·P5·P6 확인 완료. 운영 시간·담당 및 CakeShop 정책은 별도 미정.**
- 기록일: 2026-10-26. 관련: [#152](https://github.com/team-sweethan/DonWorry/issues/152), [조회 설계](152-payment-operations-design.md), [내부 대응 기준](152-internal-response.md), [ADR-0035](../decisions/0035-long-held-payment-policy.md).

## 1. 합의 근거와 기록 범위

사용자가 본 대화에 P3·P6·P2 회신을 전달했다. 추가 질문에 대한 답변 초안을 함께 검토한 뒤 사용자가 설계 확정 의사를 밝혔고 **"다른 담당자들도 다 확인했어"**라고 알렸다. 이 사용자 확인을 내부 조회 계약의 담당자 확인 근거로 삼는다. 예시 답변을 담당자가 직접 작성한 원문으로 인용하거나 별도의 Notion·메신저 확인을 수행한 것으로 기록하지 않는다.

기존 #158 회신은 ADR-0027에 유지한다. 이번 확인은 아래 내부 조회·오류 확인·P3 시각 보완·P6 공개 조회 범위에 한정한다. CakeShop 예약 정책·수동 재전달 수단·새 UUID 재평가 실행·시간 수치·운영 담당까지 확인됐다는 의미가 아니다.

## 2. P1 — 운영 조회 권한

- SECURITY_STAFF·ADMIN만 목록·상세를 조회하며 두 역할 모두 전체 가맹점을 볼 수 있다. OPERATOR는 기능 권한 보유와 무관하게 거절한다.
- 정지 가맹점 과거 기록도 조회한다. merchantId는 검색 조건이지 권한 근거가 아니다.
- P5가 정확한 목록·상세 GET 경로·메서드·권한표를 준비하고, P1이 SecurityConfig에 역할 검사를 연결한다. 이 경로의 권한 검사 전에는 공개하지 않는다.
- 상세의 요청 ID·평가 UUID·판정 ID·요청/조치 멱등키는 허용된 역할에 필요한 범위로 제공한다. 키 보유로 실행 권한을 부여하지 않는다.
- 승인 참조·customerRef 원문·인증 비밀값·전체 이벤트·원본 예외 메시지는 기본 응답에서 제외한다. 원문 조사 정보는 별도 접근 범위를 따른다.
- 실제 권한 구현·401/403/404 검증은 P5 [#188](https://github.com/team-sweethan/DonWorry/issues/188)에서 P1 [#68](https://github.com/team-sweethan/DonWorry/issues/68)과 연결한다.

## 3. P2 — 오류 조사 정보와 결과 복원

| 구분 | 정보·처리 |
| --- | --- |
| 우선 식별자 | evaluationRequestId·paymentId |
| 존재 시 제공 | evaluationId·저장 평가 결과/오류 코드·현재 결제 상태/요청 단계 |
| 입력 대조·재평가 준비 | 원래 customerRef·amount·paymentRequestedAt. 고객 원문은 일반 운영 응답에서 제외 |
| 조사 보조 | merchantId·requestId·멱등키·orderRef·오류 메시지/유형 |
| 미수집이면 생략 | 호출/응답/타임아웃 시각·상관 ID·시도 횟수. 추정값을 채우지 않음 |

- 평가 행·응답이 없으면 평가 ID·결과·오류 코드는 없음/미확인으로 구분한다.
- 응답 미수신이면 새 UUID를 즉시 만들지 않고 기존 UUID 결과부터 확인한다. 정상 결과는 복원, 저장 ERROR는 원인 확인 후 별도 재평가 절차, 결과 불명확은 기존 입력·UUID 유지 방향이다.
- 현재 P5 저장은 UUID·평가 결과가 고정돼 있다. 결과 확인·복원 경계와 새 UUID 재평가는 [#190](https://github.com/team-sweethan/DonWorry/issues/190)에서 별도 설계한다. 이 조회 작업에 재평가 실행을 넣지 않는다.
- 오류 연락 담당·대체 담당 지정은 사용자와 P2 회신에 따라 이번 범위에서 제외한다.
- 이번 오류 조사 합의 자체로 merchantId를 평가 DTO에 추가하지 않는다. 별도 [#176](https://github.com/team-sweethan/DonWorry/issues/176)·PR #181 가맹점 경계 변경은 계속 유효하며 병합 후 그 계약을 반영한다.

## 4. P3 — 완료 기반 인계와 완료 시각 보완

- 시간만으로 판정·인계·Case를 변경하지 않으며 기존 #158 합의를 유지한다.
- 기존 화면의 24시간 경고는 **Case 생성 시각** 기준이다. HELD 전이·조치 요청 시각과 동일시하지 않는다. 별도 메시지 알림·개인 배정은 2차이며 1차 보안 직원은 같은 목록을 처리한다.
- 실제 조치 호출·결과 수신·재확인·실패 표시·이력·공동 검증은 [#161](https://github.com/team-sweethan/DonWorry/issues/161) 범위다. dev의 현재 목업과 구분한다.
- 같은 키 재확인으로 성공을 먼저 반영한다. 실제 completedAt은 이벤트 전 미확인으로 유지하고 acceptedAt/재확인 시각으로 대체하지 않는다.
- 나중에 같은 결과 이벤트가 오면 멱등키·paymentId·decisionId·actionType·targetOperationId를 대조하고 완료 시각을 보완한다. 이미 성공한 건도 시각 보완을 건너뛰지 않는다.
- 상태·성공 이력·Case 종료는 중복 처리하지 않는다. 같은 완료 시각은 무시하고 다른 시각/식별자는 충돌로 확인한다.
- Case 종료는 전체 결제의 판정·인계 결과로 계산한다. VOID_DECLINED는 인계 FAILED·Case ACTION_FAILED로 유지하며 targetOperationId는 기존 P5 계약상 null이다.
- 계속 PENDING이면 caseId·paymentId·decisionId·actionType·멱등키·조치 요청/마지막 확인 시각을 P5 확인에 사용한다. 전달 위치와 해결이 어려운 건의 인계 담당은 미정이다.
- P3 업무 상태 반영과 원래 이벤트의 미완료 전달 기록 해소는 별도로 확인한다. 고객·주문 취소에 따른 Case 처리는 #153 후속이다.

## 5. P6 — 매입 상태 공개 조회

- 모의 매입·정산 예정금의 원자 저장·완료 이벤트 발행·중복 매입 방지는 기존 코드와 대조한 구현 사실이다. 회신의 추가 개발 제안과 구분한다.
- P6 추가 정정: 조회·재전달 운영 수단과 시간 기준은 기존 구현 완료가 아니다.
- 이번에는 settlement.api의 읽기 전용 Java 인터페이스·DTO로 paymentId 기반 매입 상태를 제공한다. 별도 HTTP나 내부 Entity·Repository 직접 참조를 사용하지 않는다.
- 결과는 paymentId·captureId·매입 상태/금액/완료 시각·정산 데이터 존재 여부/상태다. 매입 완료 전 시각은 비고, 정산 부재는 false/상태 없음으로 표현한다. SCHEDULED는 지급 완료가 아니다.
- 매입 없음은 명확한 빈 결과, DB 오류는 예외, null·0 이하 ID는 입력 오류로 구분한다. 행이 없다는 사실로 미전달·최종 실패를 단정하지 않는다.
- 구현·단위/MariaDB 검증은 [#189](https://github.com/team-sweethan/DonWorry/issues/189)로 분리한다. P5 자체 조회는 #189 완료를 기다릴 필요가 없다.
- 조회로 매입 실행·이벤트 발행·P5 상태 변경은 하지 않는다. 운영자용 실패 기록 선택·재전달은 [#191](https://github.com/team-sweethan/DonWorry/issues/191)의 후속 설계다.
- 1분 확인·최대 3회·1→3→5분 간격은 미확정 제안이다. 민정님이 P6 확인 담당 의사를 밝혔으나 개별 운영 분담·대체 담당 확정과 구분한다.

## 6. 미정 사항과 #152 전체 완료 조건

| 범위 | 상태·후속 |
| --- | --- |
| P5 목록/상세 제공 정보·권한 | 담당 확인 완료, 구현은 #188 |
| P6 공개 조회·P3 시각 보완 | 계약 방향 확인 완료, 구현은 #189·#161 |
| P2 UUID 결과 복원·재평가 실행 세부 | #190 별도 설계. 오류 연락 담당 지정은 범위 제외 |
| 운영 재전달 도구·개발/실행 담당·보존 | #191 후속. 현재 제공 기능으로 안내하지 않음 |
| T1~T6·R1~R4 | 미정 유지. 기존 모듈 담당표를 운영 배정으로 확대하지 않음 |
| CakeShop 예약·해제·예외 주문·서버 재조회/재시도 | 이번 내부 조회 확인 범위 밖. 추가 합의 필요 |
| 고객 취소·환불, 별도 외부 통지 | 기존 #153·#154 유지 |

합의·구현·검증 상태를 각각 기록한다. 내부 조회 계약이 확인됐다고 #152 전체나 ADR-0035 전체를 완료·채택으로 표시하지 않는다. Notion 정본 동기화는 이번 작업에서 수행하지 않았다.
