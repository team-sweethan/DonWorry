# 트랜잭션·동시성 설계

## 1. 우선 분석: P5–P6 계약 충돌

CONFIRMED(S4): 현재 5개 모듈 선언과 api NamedInterface만 있고 업무 의존은 없다. ModularityTests.verify()는 경계·순환을 검사한다. allowedDependencies는 미설정이다. 아래는 구현 상태가 아니라 설계 비교다.

CONFLICT: S6의 P5 → P6 `getCancellationEligibility`/`applyPaymentCancellation`과 P6 → P5 매입 대상·잠금 호출을 각 제공 모듈 api에 정의하면 `payment ↔ settlement` 컴파일 의존 순환이 된다. 인터페이스를 사용하는 것만으로 해결되지 않는다. 인터페이스 **소유 패키지**가 중요하다. ADR-0001은 P5에 환불 마감을 등록하고 이벤트로 알리는 대안을 제안하지만 아직 합의되지 않았다.

| 대안 | 정적 의존 | 기존 API-09/10 | 원자성·위험 | 평가 |
|---|---|---|---|---|
| 기존 양방향 직접 호출 | P5 ↔ P6 | 그대로 | 동일 DB 트랜잭션 가능해도 모듈 검사 실패 | 채택 불가: S1 규칙 위반 |
| P5 소유 취소 포트, P6 구현 | P6 → P5 | 메서드/응답 보존, 인터페이스 소유 위치 합의 필요 | 같은 TM·스레드·트랜잭션이면 원자성 가능 | S8 질문 1-A 사용자 선택 / 팀 합의 대기, ADR-0003 |
| 상위 오케스트레이터 | 상위 → P5/P6, P6 → P5 | 의미 보존, 호출자는 상위로 변경 | 상위가 트랜잭션 소유, 하위 MANDATORY | 새 모듈·진입 책임 증가; P5가 상위를 다시 호출하면 순환 |

단순 `ApplicationEventPublisher` 호출만으로 원자성을 보장하지 않는다. `@ApplicationModuleListener`의 비동기 별도 트랜잭션 처리와 동기 `@EventListener` 참여는 구분해야 한다. [Spring Modulith 이벤트 문서](https://docs.spring.io/spring-modulith/reference/events.html). 동기 이벤트도 listener 누락·비동기 executor·예외 흡수·다른 TM이면 필요한 처리가 함께 커밋되지 않는다.

이 문서의 T3/T4는 **Q01 합의 후 동일 트랜잭션 참여가 구현·검증된 경우의 실행 명세**다. 기존 API 삭제나 ADR-0001 확정으로 읽지 않는다.

## 2. 선택한 포트의 실행 조건 (사용자 선택 / 팀 합의 대기)

`payment.api.CancellationSettlementPort`에 기존 두 메서드를 정의하고 P6의 `settlement.service` 구현체가 이를 구현한다. 입력·출력 record도 payment.api에 있어 P5가 settlement 타입을 import하지 않는다. P6는 P5 공개 PaymentReader/SettlementGate를 사용할 수 있다. P5가 P6 구현 클래스나 Entity를 참조해서는 안 된다.

런타임으로 P5 취소 서비스 → P6 포트 구현 → P5 조회가 가능하더라도 빈 의존 순환을 만들지 않도록 PaymentReader/매입 잠금 구현을 취소 서비스와 분리한다. P6 포트는 P5 취소 서비스를 다시 호출하지 않는다. 하나의 포트 구현 필수, 누락/중복 시 시작 실패. 이 연결은 아직 미구현·미검증이다. 정적 의존을 단방향으로 만드는 것이 실행 시 양방향 호출까지 없애는 것은 아니다. AGENTS의 호출 방향 규칙에서 이 포트를 허용하는지는 팀 합의 대기이며, Modulith 검사 통과만으로 규칙 준수를 단정하지 않는다.

## 3. 트랜잭션 단위

| ID | 범위 | 시작·종료 | 참여·실패 |
|---|---|---|---|
| T0 | 세션 생성 | 인증 뒤 서비스 REQUIRED → payment/history/멱등 응답 커밋 | UNIQUE 충돌은 롤백 뒤 새 조회로 기존 결과 확인 |
| TF | P2 실제 시도 기록·평가 | P2 전용 별도 트랜잭션으로 시도 식별·집계·평가 결과 보존 | P5 롤백과 독립. 상세 시도 접수/실패 기록 경계는 P2 합의 대기 |
| T1 | P5 Mock 승인·상태 | payment 잠금 → 멱등 확인 → TF 호출 → 기한 재검사 → mock_card 잠금 → 원장·상태·이력·응답 커밋 | 기술 오류 시 P5만 롤백, 커밋된 TF는 유지. 업무 거절은 결과로 커밋 |
| T2 | P3 결정 저장 + HELD 유지 | P3 외부 서비스 REQUIRED 시작 → 결정 식별·저장 및 P5 실행 → 공동 COMMIT | P5 MANDATORY 참여. 어느 쪽 실패든 결정·상태·이력·응답 모두 롤백 |
| T3 | P3 결정 저장 + HELD 취소 | P3 REQUIRED 시작 → P5 payment 잠금·결정 키 확인 → P6 허용(조건부) → Mock 취소 → 상태·P6 반영 → 공동 COMMIT | P3 결정·P5·P6·응답 모두 같은 TM. 모든 참여 변경 전체 롤백 |
| T4 | APPROVED 취소 | payment 잠금 → P6 허용 → Mock 취소 → 상태 → P6 반영 → 응답 커밋 | P6 반영 실패 시 한도 복구·취소 원장도 롤백 |
| T5 | P6 매입 | P6 서비스 트랜잭션 시작 → P5 공개 API로 payment 잠금·APPROVED 검증 → P6 매입 커밋 | P5 메서드 종료 때 잠금이 풀리면 안 됨 |

**S8 질문 4-A 사용자 선택 / 팀 합의 대기:** TF는 실제 평가 시도를 남기며 T1과 분리한다. 첫 구현 초안은 P5가 payment 잠금을 유지하고 입력값을 전달한 뒤 P2 서비스의 독립 트랜잭션을 호출하는 방식이다. P2 경계의 REQUIRES_NEW는 구현 제안이며 P2는 P5 테이블을 조회·잠금하거나 역호출하지 않는다. 그렇지 않으면 중단된 P5 트랜잭션의 잠금을 P2가 기다릴 수 있다. 커넥션 풀에는 중첩 호출에 필요한 여유가 있어야 하며 부하·락 검증 전 안전하다고 단정하지 않는다.

동일 evaluationId는 동일한 논리 시도에만 사용한다. ID의 안정 생성, 정규화 입력과 동적 판단 재료의 원본 보존 위치, 재평가 유효기간은 Q05에서 P2 확인이 필요하다. 요청 실패마다 새 ID로 집계를 우회하지 않는다. 카드 변경·새 결제 시도 정의도 미결이다. P2가 실제 접수한 시도는 기술 실패여도 집계 대상으로 하되, 평가 트랜잭션 자체가 실패하면 기록이 사라질 수 있으므로 **시도 접수 내구성·실패 상태 저장의 세부 경계는 P2 구현 전 필수 합의**다. P2에 도달하지 못한 호출은 접수 여부 확인 없이 성공 집계로 간주하지 않는다. TF 완료 뒤 P5가 롤백되어도 원시도는 남고, 같은 시도의 기술 재전송은 추가 집계하지 않는다.

| ID | 추가 범위 | 경계 | 실패 처리 |
|---|---|---|---|
| TR | checkout 토큰 재발급 | 인증된 CakeShop 요청 → payment 잠금·멱등 확인 → 새 해시·응답 접수 결과 커밋 | 실패 시 기존 해시 유지, 최초 응답에만 원문 진입 정보 전달 |
| TE | 미승인 만료 | payment 잠금 → REQUESTED 및 기한 재검사 → EXPIRED·이력 커밋 | 원장·한도 변경 없음. 만료를 예외로 던져 상태 변경까지 롤백하지 않음 |

T1에서 TF 이후 기한이 지났다면 카드 승인 없이 EXPIRED로 종료하는 제안이다. 별도 만료 요청과 동일한 잠금·상태 검증을 사용한다. TE의 호출/배치 방식과 정확한 경계 시각은 팀 합의 대기다. HELD 자동 만료는 추가하지 않는다.

## 4. 잠금 순서와 경합

PROPOSED: P5·P6 결제 변경 경로는 payment 행을 먼저 `PESSIMISTIC_WRITE`로 잠근다. 작업 멱등 행은 payment 뒤, P6 관련 행은 그 뒤, mock_card는 마지막에 잠근다. 세션 T0는 payment가 없으므로 멱등 키 예약과 활성 주문 UNIQUE로 직렬화하고, 기존 payment를 추가로 잠그는 경로를 만들지 않는다.

P6 API-09는 단순 오래된 snapshot 조회가 아니라 payment 잠금 아래 현재 판정을 제공해야 한다. P6의 관련 captures/order_fulfillments/settlements 행을 정해진 순서로 잠그거나 최신 조회를 보장한다. 아직 행이 없는 매입 전에는 payment를 공통 직렬화 지점으로 삼는다. API-10도 같은 트랜잭션에서 같은 집합을 사용한다. P6의 정확한 행 접근 순서는 Q13에서 확정한다.

| 동시 실행 | 선행 커밋 | 후행 동작 |
|---|---|---|
| 취소 vs 매입 | 취소 | 매입이 payment 잠금 획득 후 CANCELED 확인, captures 생성 안 함 |
| 매입 vs 취소 | 매입 | 취소가 매입 상태 재조회, API-09 판단 후 허용 시 P6 CANCELED 반영 |
| 정산 확정 vs 취소 | 정산 확정 | 취소가 최신 settlementStatus·마감으로 거절 또는 계약상 처리 |
| HELD 유지 vs 취소 | 유지 | 다른 취소 결정은 HELD 전제 불충족; 별도 승인 결제 취소 계약으로만 수행 |
| 같은 카드의 승인 2건 | 첫 승인 | 두 번째는 mock_card 잠금 후 잔여 한도 재계산 |
| 동일 요청 2건 | 첫 완료 | 후행은 저장된 응답 재생, 한도·이력 중복 없음 |

P3 결정 경로는 P3 케이스/결정 직렬화 → payment → P5 멱등 행 → P6 관련 행 → mock_card 순서를 제안한다. P5/P6가 P3 행을 역으로 잠그지 않으며, P3의 모든 판정 경로에서 이 순서를 지켜야 한다. 구체 P3 행·유일 제약은 팀 합의 대기다.

P6 매입·정산 확정·픽업 정보/환불 마감 갱신도 payment 먼저 잠그는 규칙에 참여해야 한다. P6가 settlement를 먼저 잠그고 payment를 기다리면 취소와 데드락 위험이 생긴다. 여러 결제 배치는 결제별 짧은 트랜잭션을 권장하고, 묶음 처리가 필요하면 payment_id 정렬 후 잠근다. 공용 정산 행을 여러 결제가 공유하는 경우의 잠금·트랜잭션 범위는 Q13 확인 전 확정하지 않는다.

## 5. 전파·롤백

P5 외부 요청 진입과 P6 배치, P3 직원 결정 진입 서비스는 REQUIRED, 같은 커밋을 요구하는 P5 ReviewExecutor·Mock·P6 포트·P5 매입 잠금은 MANDATORY 제안. MANDATORY는 호출자가 트랜잭션 없이 사용하면 실패하게 한다. P3/P5/P6 원자적 실행 범위는 같은 DataSource·PlatformTransactionManager·스레드를 사용해야 하며 `REQUIRES_NEW`, 비동기 실행, 자기 호출로 프록시 우회를 허용하지 않는다. 별도 보존하도록 선택한 P2 TF와 인증 nonce 소비는 이 범위 밖이다. [Spring 전파 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).

기술 실패는 RuntimeException 또는 명시적 rollbackFor 대상으로 통일한다. checked exception이 기본 롤백 대상일 것이라고 가정하지 않는다. P6 오류를 catch 후 성공 응답으로 바꾸지 않는다. inner rollback-only는 outer에서도 실패로 취급한다. UNIQUE 위반 이후 같은 오염된 트랜잭션에서 조회·계속 쓰기 하지 않고 종료 후 재시도한다.

FDS REJECT·Mock 한도 거절은 정상적인 업무 결과로 DECLINED 커밋. FDS 타임아웃은 P5 T1을 롤백하지만 이미 커밋된 P2 TF는 유지한다. DB 락 타임아웃·취소 기술 실패는 해당 P3/P5/P6 공동 업무 트랜잭션 전체를 롤백한다. COMMIT 응답 유실은 실패 단정 대신 동일 키 재요청으로 커밋 결과를 확인한다.

## 6. 멱등성의 범위와 한계

- 외부 nonce: 요청 재전송 공격 방지. 같은 업무를 재시도할 때 새 nonce, 동일 멱등 키를 사용한다. 인증 성공 뒤 nonce를 짧은 별도 트랜잭션으로 소비하는 안(PROPOSED Q11)은 업무 금액 변경을 포함하지 않는다. 업무 롤백 뒤 nonce 재사용은 거부한다.
- idempotency_record: `(tenant_id, idempotency_key)`로 결과 재생. request_type과 정규화 request_hash가 같아야 한다. 내부 키는 `p3:decision:{decisionId}`처럼 예약 namespace를 사용하고 외부 키가 이를 점유하지 못하게 한다(Q03).
- P3 유지도 idempotency_record에 저장한다. card_approval만 사용하면 카드 작업 없는 유지 결정의 원응답·중복 판단을 보장할 수 없다.
- 카드 request_id UNIQUE는 두 번째 방어다. 다른 requestId의 같은 결제 취소는 payment 상태와 성공 원장으로 차단한다.
- P6 API-10 재생은 cancellationId 및 동일 본문 비교가 필요하다. P6 저장 위치·보존기간은 OPEN. P5의 로컬 멱등만으로 독립 P6 재호출까지 증명하지 않는다.
- P5 기술 롤백 시 P5 idempotency_record의 IN_PROGRESS 행도 함께 롤백하는 안이다. P2 실제 시도 기록은 별도이므로 남는다. 따라서 평상시 영구 IN_PROGRESS가 남지 않는다. 별도 선점 커밋/lease를 도입한다면 복구 정책을 다시 설계한다.
- P3 결정 키는 성공 응답 보존기간 동안 유지해야 한다. 삭제 후 현재 상태만 보고 과거 동일 결정을 판별하지 않는다. 최소 보존기간은 Q10.

## 7. HELD의 P6 호출 생략 조건

CONFIRMED(S6): HELD 매입 금지. 그러나 생략은 OPEN(Q06)이다. 기본 비교 흐름은 API-09/10을 호출한다. 생략하려면 모든 경로에서 HELD 무매입이 보장되고, 기존 잘못된 매입 데이터가 없으며, API-10에 매입 외 필수 부수효과가 없고, P6가 생략에 동의해야 한다. 예외 데이터가 발견되면 무조건 생략하지 않고 정합성 오류로 중단한다. P5에서 P6 테이블을 직접 조회해 이 조건을 판정하지 않는다.

## 8. 데드락·재시도·복구 수용 조건

시간 제한·최대 재시도 수·backoff 값은 OPEN(Q10). 기술 재시도는 반드시 새 트랜잭션에서 동일 업무 키로 제한적으로 수행한다. 무한 재시도·새 UUID 발급으로 중복 회피 금지. 락 오류 후 응답은 재시도 가능 기술 오류이며 CANCELED/DECLINED로 바꾸지 않는다.

미실행 테스트 계획: MariaDB 11.8 실제 락으로 두 스레드 barrier 경합, P6 API-10 실패 주입 후 P5/P6 모두 원상태, 동일 카드 한도 경합, 중복 결정·다른 payload 충돌, commit 응답 유실 후 결과 재생, 정산 확정·마감 갱신 경합, 모듈 verify(), 포트 구현 빈 순환 검사. H2 테스트만으로 MariaDB 락·생성 컬럼을 검증했다고 쓰지 않는다.

## 10. 선택한 판정·매입 경계

**질문 5-A 사용자 선택 / 팀 합의 대기:** P3 결정이 커밋됐는데 P5 실행은 실패한 상태를 정상 처리 모델로 두지 않는다. P3 응답은 공동 COMMIT 이후 성공을 반환한다. P3 저장 실패도 P5 변경을 롤백해야 한다. 재시도는 같은 decisionId를 사용하며 P3 자체 중복 결정도 막아야 한다. 롤백 뒤 같은 ID를 다시 전달하는 주체·저장 방식은 Q03 미결 세부사항이다.

**질문 7-A 사용자 선택 / 팀 합의 대기:** P6는 매 실행마다 APPROVED 후보 조회를 시작점부터 수행하고 기매입 paymentId를 자신의 데이터로 제외한다. 페이지 cursor는 한 실행 안에서만 사용하며 다음 실행에 승인 시각 watermark를 넘기지 않는다. HELD 해제 시 approved_at을 변경하지 않는다. 실행 도중 커서 앞에 들어온 거래는 다음 실행에서 회수한다. P6는 매입 직전 P5 잠금·상태 검증과 자체 중복 매입 방어를 모두 수행한다.

**질문 6·8은 OPEN:** P6의 정산 단위·정산 상태 의미·중복 취소 저장 위치 및 P3 케이스 생성 기준·이벤트 책임은 선택하지 않았다. T3/T4는 정산 세부 검증이 끝난 계약 아래의 조건부 설계이며, 이벤트 표도 확정된 생성 규칙이 아니다.

추가 수용 테스트(미실행): P3 결정 저장 실패 시 P5 상태·한도 롤백, TF 커밋 후 P5 실패에도 평가 시도 보존, 같은 평가 재전송 1회 집계, REQUESTED 만료와 승인 경합, 성공 confirm 재생 시 REQUESTED 재검사로 거부하지 않음, 토큰 재발급 후 이전 토큰 거부·동일 키 재생 시 추가 회전 없음, 오래된 approved_at의 HELD 해제 거래가 다음 매입 실행에 포함됨.
