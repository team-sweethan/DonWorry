# #152 미처리 결제 조회·확인 설계

- **상태: P1·P2·P3·P5·P6 설계 방향 확인 완료 — 구현·운영 활성화 전.**
- 작성: 2026-10-26. 코드 대조 기준: `dev 66c8ff1`. 이번 작업은 별도 `feature/152-payment-operations-design` 브랜치에서 문서만 변경한다.
- 관련: [#152](https://github.com/team-sweethan/DonWorry/issues/152), [내부 대응 기준](152-internal-response.md), [합의 기록](152-policy-confirmation.md), [ADR-0035](../decisions/0035-long-held-payment-policy.md).

## 1. 합의 근거와 적용 범위

사용자는 본 대화에서 목록·상세 제공 정보와 조회 권한을 수락했고, 담당별 확인 문안을 제시한 뒤 **"다른 담당자들도 다 확인했어"**라고 알렸다. 이를 해당 조회 설계의 담당자 확인 근거로 기록한다. 별도의 GitHub 회신 링크·Notion 확인을 수행한 것으로 표시하지 않는다.

이번 범위는 **P5 저장 데이터의 읽기 전용 목록·상세, 처리 구분·확인 근거·인계용 식별자 제공**이다. P6는 별도의 공개 Java 매입 상태 조회를 제공한다. API 구현, 프론트 화면, 운영 복구가 이미 제공된다는 의미가 아니다.

다음은 제외한다.

- 담당 배정·메모·해결 여부를 저장하는 추적 시스템과 신규 업무 테이블
- 재평가 실행, 실패 이벤트 선택·재전달, 자동 취소, 금융·조사 상태 강제 변경
- CakeShop 인증·주문·재고·쿠폰·외부 통지와 고객 취소·환불 계약
- P3·P6 데이터 또는 공통 이벤트 저장소를 P5 Repository에서 직접 조회하는 구현

조회 결과는 외부 작업 기록에 결제별 확인을 이어가기 위한 정보다. 기록 위치·접근 대상·시간 수치·개별 운영 담당자는 미정이다. 조회만으로 운영자용 복구 기능이 생기지 않는다.

## 2. 조회 권한

| 역할 | 목록·상세 | 가맹점 범위 |
| --- | --- | --- |
| SECURITY_STAFF | 허용 | 전체 가맹점 |
| ADMIN | 허용 | 전체 가맹점 |
| OPERATOR | 불허 | FDS_VIEW·FINANCE_VIEW 보유 여부와 무관 |
| 비로그인 | 불허 | 없음 |

- 정지 가맹점의 과거 결제도 조회한다. merchantId 필터는 허용된 범위를 좁히는 조건이며 권한을 부여하지 않는다.
- 목록·상세·ID 직접 접근에 동일한 서버 검사를 적용한다. 개발 담당자라는 이유로 운영 권한을 부여하지 않는다.
- P1이 SecurityConfig의 기존 permitAll보다 앞에 정확한 GET 경로의 역할 검사를 연결한다. P5는 조회 데이터와 필터를 처리한다.
- 비로그인 401, OPERATOR 등 역할 불허 403, 허용된 사용자의 없는 결제 단건 404를 검증한다.
- 이 조회 경로는 P1 검사와 함께 공개한다. 다른 업무 API의 일괄 인가·CSRF 활성화까지 이번에 변경하지 않는다. P1 연계는 [#68](https://github.com/team-sweethan/DonWorry/issues/68)과 구분해 이 경로의 조건으로 검증한다.

정확한 URL·페이지 크기·정렬/커서·파라미터 검증·오류 코드 이름은 후속 구현 설계에서 확정한다. 이번 합의는 역할·가맹점 범위·응답 의미를 확정한 것이다.

## 3. 목록 조회

기본 후보는 PENDING·HELD 결제 또는 PENDING·FAILED 직원 조치가 있는 결제다. 단순히 목록에 있다는 이유로 장애로 판단하지 않는다. 원래 결제를 기준으로 요청·조치를 선택적으로 연결하며, 요청 행이 없는 기존 내부 서비스 경로도 누락하지 않는다.

| 제공 정보 | 근거·의미 |
| --- | --- |
| paymentId | payments의 결제 식별자 |
| merchantId, orderRef | 가맹점·주문 참조. 가맹점 이름은 이번 필수 정보가 아님 |
| amount, paymentStatus | 원 단위 금액·현재 저장 상태 |
| 처리 구분·분류 근거 | §5의 P5 관측 분류. 실제 오류 원인이나 P6 상태를 단정하지 않음 |
| 직원 조치 종류·상태 | 존재하는 조치만 제공 |
| 최초 결제 시각 | payments.createdAt |
| 대기 기준·시각·경과 시간 | §6의 의미를 함께 제공. 기준 없으면 미확인 |
| 조회 시각 | 이번 관측 시각. 모든 모듈의 동시 스냅샷 보장은 아님 |

검색·필터는 결제 ID, 가맹점 ID, 주문 참조, 결제 상태, 처리 구분, 최초 결제 기간을 지원한다. 페이지 단위로 조회하고, 시간 기준이 미정인 동안 기한 초과 판정·자동 알림을 하지 않는다. 조회 횟수·재시도 상한을 이유로 후보를 제외하지 않는다.

기본 목록에서 빠지는 완료 결제도 ID 상세 조회로 결과를 확인할 수 있어야 한다. P3 반영 지연은 P5 완료 상태만으로 검출할 수 없으며 별도 P3 확인 대상이다.

## 4. 상세 조회

| 영역 | 제공 정보 | 저장 근거 |
| --- | --- | --- |
| 결제 | 결제 ID·가맹점 ID·주문 참조·금액·상태·최초 결제/상태 변경 시각·승인 참조 존재 여부·거절 코드 | payments |
| 요청 | requestId·attemptNo·요청 멱등키·processingStage | payment_requests. 없는 경우 명시 |
| 평가 | evaluationRequestId·evaluationId·저장 결과/점수/오류 코드·evaluatedAt | P5가 저장한 평가 스냅샷. P2 원장 최신 결과가 아님 |
| 직원 조치 | actionId·decisionId·조치 종류·조치 멱등키·상태/실패 코드·요청/완료 시각·저장된 captureId | payment_actions |
| 확인 정보 | 처리 구분·관측 근거·확인 불가/미수집 항목·조회 시각 | 조회 시 계산. 지속 추적 상태가 아님 |

- 요청 멱등키와 직원 조치 멱등키는 필드 이름을 구분한다. 키 보유 자체는 실행·상태 변경 권한이 아니다.
- 승인 참조 원문·customerRef 원문·인증 토큰·비밀값·전체 이벤트 본문·원본 예외 메시지는 기본 응답에서 제외한다.
- 자동 매입 경로는 P5 직원 조치의 captureId가 없을 수 있다. 이를 매입 없음으로 판단하지 않는다.
- 기존 [PaymentReader](../decisions/0026-payment-read-api.md)의 4필드 공개 계약은 이번 운영 상세 응답으로 교체하거나 무인가 HTTP로 노출하지 않는다.

## 5. 처리 구분과 확인 한계

아래는 업무 상태를 바꾸지 않는 관측 분류다. 모순이 발견되면 정상 분류보다 원인 미확인·불일치 근거를 먼저 표시한다. 예외 전체 조합의 우선순위는 후속 구현의 규칙·테스트로 명시한다.

| 처리 구분 | 대표 관측 조건 |
| --- | --- |
| 평가·미승인 처리 확인 필요 | 승인 참조 없는 PENDING + RECEIVED/EVALUATED. 평가 또는 승인 확정 전 구간임을 함께 표시 |
| 평가 ERROR 확인 필요 | NEEDS_REVIEW와 저장 ERROR. 오류 원인은 P2 확인 필요 |
| 자동 매입 대기 | 승인된 PENDING·직원 조치 없음. P6 실행 전/후 여부는 모름 |
| 직원 판정 대기 | HELD·직원 조치 없음. Case 연결 여부는 별도 P3 확인 |
| 직원 매입 대기 | HELD·CAPTURE 조치 PENDING |
| 승인 취소 실패 | HELD·VOID 조치 FAILED/VOID_DECLINED |
| 원인 미확인 | 요청 없는 기존 경로의 근거 부족, 상태·조치 모순 등. 누락값을 추정하지 않음 |
| 금융 처리 완료 | 상세 조회의 CAPTURED/VOIDED 및 해당 조치 결과. P3 인계 완료를 뜻하지 않음 |

`기록 없음`, `미수집`, `조회 실패`를 구분한다. null 하나로 뭉개지 않고 해당 영역의 상태·사유를 표현하는 방식으로 후속 DTO를 설계한다. DB 오류를 데이터 없음이나 정상 응답으로 바꾸지 않는다.

## 6. 시간 기준

| 관측값 | 기준 |
| --- | --- |
| 전체 경과 | 최초 payments.createdAt. 재조회로 초기화하지 않음 |
| HELD 판정 대기 | HELD 전이 statusChangedAt. 과거 null을 추정하지 않음 |
| 직원 매입 대기 | 조치 requestedAt |
| 자동 매입 대기 | 원래 매입 발행 시각을 확보하지 못하면 미확인. 최초 결제 시각을 승인/매입 요청 시각으로 대체하지 않음 |

P3의 기존 화면 경고는 Case 생성 후 24시간 기준이다. HELD 시각·조치 요청 시각과 동일시하지 않으며 새 P5 경고 임계값으로 사용하지 않는다. P6의 1분 확인·최대 3회·1→3→5분 간격은 제안으로 보존하고 채택하지 않는다.

## 7. 담당별 합의 계약

### P2 오류 조사·재평가 분리

- 우선 식별자는 evaluationRequestId·paymentId다. evaluationId·저장 결과/오류 코드·현재 상태/단계는 있을 때 전달한다.
- 원래 customerRef·amount·paymentRequestedAt은 입력 대조/재평가 준비 정보다. customerRef 원문은 일반 조회 응답에 넣지 않고 별도 조사 경로의 권한·필요 범위를 따른다.
- merchantId·requestId·멱등키·orderRef·오류 메시지/유형은 보조 정보다. 호출/응답/타임아웃 시각·상관 ID·시도 횟수는 미수집이면 생략 가능하며 자동으로 추정하지 않는다.
- 응답 미수신 시 새 UUID를 바로 만들지 않고 기존 UUID 결과를 먼저 확인하는 방향이다. 정상 결과 복원 수단과 새 UUID 재평가 실행은 별도 계약·설계다.
- 기존 ERROR 보존, 늦은 응답·중복 승인 방지, 실행 조건과 처리 재개를 맞춘 뒤 재평가를 도입한다. P2 오류 연락 담당·대체 담당 지정은 이번 범위에서 제외한다.
- 이번 합의만으로 기존 FdsEvaluationRequest에 merchantId를 추가하지 않는다. 별도 진행 중인 [#176](https://github.com/team-sweethan/DonWorry/issues/176)·PR #181은 가맹점 경계 변경 작업이다. 병합 시 해당 계약을 우선 반영하며 이번 문서로 취소·되돌리지 않는다.

### P3 성공 선반영·완료 시각 보완

- [#161](https://github.com/team-sweethan/DonWorry/issues/161)에서 같은 키 재확인으로 성공을 먼저 반영할 수 있다. completedAt은 이벤트 수신 전 미확인으로 유지하며 재확인 시각으로 대신하지 않는다.
- 나중에 같은 결과 이벤트가 오면 멱등키·paymentId·decisionId·actionType·targetOperationId를 대조하고 실제 완료 시각을 보완한다. 이미 성공했다는 이유로 보완을 건너뛰지 않는다.
- 성공 이력·상태 변경·Case 종료를 중복 처리하지 않는다. 같은 완료 시각은 무시하고 다른 시각/식별자는 덮어쓰지 않고 충돌로 확인한다.
- Case 종료는 전체 결제의 판정·인계 결과로 계산한다. VOID_DECLINED의 targetOperationId는 기존 P5 계약상 null이다.
- 이벤트가 오지 않으면 실제 완료 시각은 계속 미확인이다. 업무 상태 반영과 미완료 전달 기록 해소는 각각 검증한다.

### P6 읽기 전용 공개 조회

- 같은 Spring 앱에서 paymentId로 호출할 인터페이스·DTO를 settlement.api에 두고 구현은 P6 service에 둔다. 기존 payment → settlement.api 의존 방향을 유지한다.
- 반환 의미: paymentId, captureId, 매입 상태/금액/완료 시각, 정산 데이터 존재 여부/상태. 이름·DTO 타입·메서드명은 P6 구현 계약에서 확정한다.
- 완료 전 capturedAt은 비어 있다. 매입은 있으나 정산이 없으면 존재 여부 false·상태 없음으로 구분한다. SCHEDULED는 지급 완료가 아니다.
- 매입 없음은 Optional.empty() 등 명확한 빈 결과, DB 실패는 예외, null·0 이하 ID는 입력 오류로 구분한다. 매입 행 부재는 미전달·최종 실패의 증거가 아니다.
- 조회로 매입·이벤트 발행·P5 상태 변경을 수행하지 않는다. 여러 모듈 데이터가 같은 시점의 스냅샷이라고 보장하지 않는다.
- P5 운영 목록의 각 행마다 P6를 호출하거나 P3·P6 정보를 합친 API를 P5에 만들지 않는다. 합쳐 보는 화면/HTTP가 필요하면 ADR-0012에 따라 상위 모듈 또는 분리 조회로 별도 설계한다.

## 8. 구현 순서와 검증 계획

| 작업 | 담당 범위·이슈 | 선행 관계 |
| --- | --- | --- |
| P5 목록·상세 | P5·P1 [#188](https://github.com/team-sweethan/DonWorry/issues/188) | 정확한 GET 경로·SecurityConfig 동시 연결. P6 없이 P5 데이터 조회 진행 가능 |
| P6 공개 조회 | P6 [#189](https://github.com/team-sweethan/DonWorry/issues/189) | 인터페이스·DTO 구체화 후 공개 호출 검증 |
| P3 완료 시각 | P3 기존 [#161](https://github.com/team-sweethan/DonWorry/issues/161) | 성공 선반영 뒤 지연 이벤트 보완·중복/충돌 검증 |
| 평가 결과 복원·재평가 | P2·P5 [#190](https://github.com/team-sweethan/DonWorry/issues/190) | 별도 설계. #176 계약 변화 반영, 조회 개발을 막지 않음 |
| 운영자 이벤트 복구 | 설계 정리 P5, 실제 개발·실행 담당 미정 [#191](https://github.com/team-sweethan/DonWorry/issues/191) | 후속 설계 백로그. 조회 제공과 별개로 복구 수단 미제공 제한 유지 |

1. P5 단건·목록의 정확한 HTTP 경로·페이지 규격·필터 검증을 정하고 P1과 SecurityConfig 규칙을 함께 연결한다.
2. P5 소유 데이터 조회·분류·누락 표현을 구현한다. 상태·평가·조치·이벤트를 변경하지 않는지 검사한다.
3. P6 공개 조회 구현·검증 후 필요한 내부 확인에 연결한다. P3 #161의 시각 보완은 P3 소유 범위에서 검증한다.
4. ERROR 조회·응답 미수신 확인과 재평가 실행을 구분하고, 실행 기능은 별도 이슈에서 설계한다.

| 검증 영역 | 후속 구현에서 확인할 결과 |

| 권한 | 익명 401, OPERATOR 403(기능 권한 보유 포함), STAFF/ADMIN 전체 범위, 정지 가맹점, ID 직접 접근 |
| 후보·상세 | 정상 HELD 포함, 요청 없는 경로 누락 없음, 완료 단건 조회, null 시각·없는 조치 표현 |

구현 시 backend spotlessApply·check·mariaDbTest를 실행하고 해당 커밋의 결과를 기록한다. 문서만 변경하는 이번 단계에서는 backend·MariaDB를 실행하지 않는다.

## 9. 미정·운영 제한과 #152 종료 범위

- 미정: 정확한 HTTP 경로·DTO/페이지 세부, T1~T6·R1~R4, 운영 기록 위치·권한, 복구 실행 담당·재시도 수치·보존.
- 별도 후속: P2 기존 UUID 결과 확인·재평가 설계, 운영자 이벤트 선택·재전달 수단, 자동 종료·조치 변경.
- 내부 조회 계약 확인은 완료했으나 CakeShop 예약·해제·예외 주문과 운영 기한·담당은 남아 있다. #152 전체나 ADR-0035 전체를 완료·채택으로 바꾸지 않는다.
- 합의·이슈 연결·문서 검사 통과를 기능 구현·통합 검증·운영 활성화로 표시하지 않는다.
