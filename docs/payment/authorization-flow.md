# #118 상태 전이·트랜잭션 설계

2026-10-23 · 기준 `4a41a3f` · 3번 단계 설계 및 4·5번 단계 구현. Entity 전이·모의 승인·잠금 조회·승인 처리 서비스를 구현했다. createAndAuthorize로 최초 저장·평가·승인을 연결했다. 6번 단계에서 MariaDB 커밋·롤백·동시성 통합 테스트 9건이 통과했다. 실행 기준과 한계는 [검증 기록](verification.md)에 남긴다. DB 스키마는 변경하지 않았다.
#122에서 추가할 매입 요청·완료 연결은 [이벤트 설계](capture-events.md)를 따른다. 아래 발행하지 않는다는 설명은 #118 구현 범위의 기록이다.

#136의 4번 단계에서 NOTIFY_HELD 분기에 [PaymentHeld 계약](../decisions/0023-payment-held-event-contract.md)을 연결했다. HELD·승인 참조 저장과 같은 트랜잭션에서 저장 결제 값·REVIEW 평가 ID·전환 시각을 발행한다. NOTIFY_HELD 반환을 받은 호출자가 다시 발행하지 않는다. P3 리스너 등록·실제 전달은 별도 검증 대상이다.

승인기 입력·출력과 부작용 제한은 [모의 승인 계약](mock-authorization.md)을 따른다.

## 서비스 경계와 평가 연결

기존 `PaymentEvaluationFlowService.createAndEvaluate()`는 평가·분기 판단만 반환하는 계약으로 유지한다. 기존 테스트의 평가 후 PENDING 유지 조건을 삭제하거나 새 승인 동작의 증거로 사용하지 않는다.
같은 서비스에 별도 `createAndAuthorize(input)` 진입 메서드를 추가했다. 두 진입 메서드는 저장·평가를 수행하는 private helper를 재사용한다. 두 메서드 모두 Spring 프록시로 호출하며 NOT_SUPPORTED를 적용한다. private helper의 어노테이션이나 같은 객체 내부 호출에 트랜잭션 적용을 기대하지 않는다.

helper는 한 호출 안에서 다음 정보를 묶어 내부 평가 문맥을 만든다.

- 최초 저장 서비스가 반환한 PaymentCreationSnapshot: paymentId·customerRef·amount·createdAt·최초 상태·승인 참조
- 이 결제에 대해 생성한 evaluationRequestId
- 해당 요청에 대한 PaymentEvaluationResult

평가 문맥은 P5 service 내부에서 생성·전달한다. HTTP·다른 모듈·일반 호출자가 임의의 paymentId와 판정 enum을 조합해 승인시키는 공개 API로 노출하지 않는다. 별도 문맥 타입을 두면 생성 경로·가시성도 이 원칙에 맞춘다.
P2 응답에는 paymentId·amount가 없으므로 응답만으로 결제 일치를 증명할 수 없다. 같은 스냅샷에서 요청을 만들고 응답의 요청 UUID를 대조한 기존 흐름을 보존한다. 상태 반영 서비스도 문맥의 요청 UUID와 응답 UUID 일치를 확인한다. P2 내부 Entity·Repository를 조회하지 않는다.

승인 전용 경로는 helper의 문맥을 별도 Bean인 `PaymentAuthorizationService`에 전달한다. 이 서비스는 새 트랜잭션으로 저장된 결제를 잠금 조회하고 스냅샷의 ID·고객·금액·생성 시각이 같은지 대조한다. 승인 입력의 ID·금액은 잠금으로 다시 읽은 Entity에서 구성한다.
문맥의 기존 Decision을 그대로 저장하지 않고 잠금 이후의 현재 State와 원래 평가 응답으로 PaymentRules를 적용한다. 다른 평가를 나중에 선택하는 복구 기능은 이번 범위에 없다.

## 트랜잭션 순서

| 단계 | 경계 | 완료·실패 의미 |
| --- | --- | --- |
| 전체 진입 | NOT_SUPPORTED | 호출자 트랜잭션 중단. 전체 흐름을 하나의 쓰기 트랜잭션으로 묶지 않음 |
| 최초 결제 생성 | 기존 PaymentCreationService REQUIRES_NEW | PENDING을 먼저 커밋. 이후 실패에도 이 기록은 남음 |
| P2 평가 | 기존 FdsEvaluator의 트랜잭션 | 결제 잠금 없이 호출. 예외·null·UUID 불일치면 승인 단계 진입 금지 |
| 결과 반영·모의 승인 | 별도 PaymentAuthorizationService REQUIRES_NEW | 결제 잠금 → 문맥·상태 검증 → 분기·모의 승인 → 상태·참조 반영 → 커밋 |

모의 승인기는 외부 HTTP·별도 저장소·독립적인 금융 효과가 없으므로 짧은 결제 트랜잭션 안에서 호출한다. 실제 외부 승인으로 교체할 때 이 설계를 그대로 사용하지 않는다.
상태 반영 서비스가 반환할 값은 Entity가 아닌 불변 결과다. Spring 프록시 호출이 반환되어 커밋을 확인한 뒤 전체 진입 메서드가 성공을 반환한다. 내부 flush만으로 커밋 완료를 주장하지 않는다.

## 상태와 저장

처리 진입은 **PENDING이며 authorization_ref가 null인 결제**만 허용한다. 모든 분기에서 먼저 이 조건을 검사한다. PENDING+승인 참조 있음, HELD·DENIED·DECLINED·CAPTURED·VOIDED·EXPIRED는 IllegalStateException으로 거절하고 모의 승인기를 호출하지 않는다. 없는 결제·문맥 불일치도 성공으로 처리하지 않는다.

| 평가·승인 결과 | 저장 상태 | authorization_ref | 다음 단계 판단 |
| --- | --- | --- | --- |
| DENY | DENIED | null | NONE |
| ERROR | 기존 PENDING 유지 | null | RECORD_FDS_ERROR (실제 오류 이력 저장 아님) |
| ALLOW + 성공 | PENDING | 승인기가 반환한 유효 참조 | REQUEST_CAPTURE (이번에는 발행 안 함) |
| REVIEW + 성공 | HELD | 승인기가 반환한 유효 참조 | NOTIFY_HELD (이번에는 발행 안 함) |
| ALLOW/REVIEW + 업무 거절 | DECLINED | null | NONE |
| 승인기 예외·null/부적합 결과 | 결과 반영 트랜잭션 롤백 | 기존 값 보존 | 예외 전달, 성공 결과 반환 없음 |

Entity에는 예를 들어 `deny()`, `recordAuthorizationSuccess(reference, hold)`, `declineAuthorization()`처럼 의도가 드러나는 메서드를 둔다. 구현 시 이름은 조정할 수 있지만 임의 setter나 service 타입을 받는 Entity 메서드는 만들지 않는다. Entity는 자신의 상태·참조 조합을 검사하고, FDS 분기 판단은 service의 PaymentRules가 담당한다.
성공 참조는 공백 불가·100자 이하를 검사한다. 상태와 참조는 같은 Entity·트랜잭션에서 변경한다. 신규 컬럼·@Version 컬럼·보조 테이블을 추가하지 않는다.

새 승인 경로의 반환값에는 paymentId, 원래 평가 결과, 최종 결제 상태, 승인 참조, 다음 단계 판단, 업무 거절 코드가 필요하다. 필드가 많은 record는 @Builder를 사용한다. 기존 PaymentEvaluationFlowResult를 승인 완료 결과로 의미 변경하지 않고 별도 내부 결과 타입을 사용한다. 거절 코드·오류 사유는 현재 DB에 영속 저장되지 않음을 명시한다.

## 중복·동시 처리

PaymentRepository에 PESSIMISTIC_WRITE를 사용하는 명시적 `findByIdForUpdate(paymentId)` 조회를 추가한다. 현재 P3의 동일 잠금 패턴을 참고하되 P3 코드를 호출하지 않는다. 상태 반영 트랜잭션 안에서 조회하고 커밋/롤백까지 잠금을 유지한다.

1. 같은 paymentId로 두 처리가 들어오면 첫 처리가 잠금 아래 승인 가능 조건을 확인한다.
2. 첫 처리가 성공 또는 거절을 커밋하면, 기다린 처리는 최신 상태·참조를 다시 보고 충돌 예외로 종료한다. 모의 승인기는 다시 호출하지 않는다.
3. 첫 처리가 롤백하면 후속 처리는 최초 PENDING을 볼 수 있다. 부작용 없는 모의라는 전제 아래 유효한 동일 평가 문맥으로 다시 처리할 수 있다.

같은 요청의 결과를 그대로 재생하는 범용 멱등 API는 제공하지 않는다. 현재 DB에 채택 평가·거절 코드 등 원 응답을 모두 복원할 데이터가 없으므로 이미 처리된 요청은 일관되게 충돌 예외로 거절한다. 다른 요청을 같은 성공으로 오인하는 것보다 명시적 거절을 택한다.
잠금 대기 실패·교착 예외는 호출자에게 전달하고 자동 반복하지 않는다. 다른 상태 변경 경로가 추가되면 같은 잠금·조건을 따라야 하며, 이번 설계가 향후 P6/VOID 경합까지 해결한 것은 아니다.

## 실패·재호출 범위

- P2 예외·응답 검증 실패: 상태 반영 서비스에 들어가지 않는다. 최초 PENDING과 이미 커밋된 P2 기록은 보존한다.
- 모의 승인 기술 실패: unchecked 예외로 상태 반영을 롤백한다. 기존 TECHNICAL_FAILURE → UNKNOWN 규칙으로 변환하거나 DECLINED를 저장하지 않는다. 외부 효과가 없다는 계약에 한정한다.
- DB flush/commit 실패: 성공 응답을 반환하지 않는다. P2 평가·최초 저장을 함께 되돌리지 않는다. 상태 반영 트랜잭션이 확실히 롤백됐는지와 응답만 유실됐는지를 구분한다.
- 성공 후 응답 유실: 같은 결제를 재처리해도 잠금 조회로 이미 반영된 상태·참조를 확인하고 승인 없이 충돌로 종료한다. 상태 조회와 작업 복구를 혼동하지 않는다.
- 확실한 롤백: 호출 중 보존한 동일한 평가 문맥을 가진 내부 호출자만 명시적 재처리를 할 수 있다. 서비스가 스스로 재시도하지 않는다. 프로세스 재시작 후 문맥 복원은 이번 범위 밖이다.
- `createAndAuthorize(input)`을 재호출하면 새 결제를 생성한다. 최초 생성 진입점은 재시도 API가 아니며, 주문 단위 중복 접수 방지를 제공한다고 설명하지 않는다.

현재 API에서 기술 실패를 받은 외부 호출자에게 자동 복구를 제공하는 단계가 아니다. 외부 API 노출 전 결제 식별·조회·중복 접수·복구 계약을 별도로 갖춰야 한다.

## 대안·영향·검증 계획

- 전체 흐름에 쓰기 트랜잭션: PENDING 선커밋과 P2 트랜잭션 분리를 깨므로 제외한다.
- 잠금 없이 상태 확인 후 승인: 동시 호출 둘 다 미승인으로 판단할 수 있어 제외한다.
- 낙관적 잠금: 현재 버전 컬럼이 없고 충돌 확인 전에 모의 호출이 중복될 수 있어 이번에는 행 잠금을 선택한다.
- 메모리 중복 처리 표: 여러 인스턴스·재시작·DB 롤백과 일관성을 보장하지 못해 제외한다.

현재 모듈 의존·SQL·외부 계약을 유지하는 내부 처리다. 4번 단계에서 독립 승인 처리 서비스를 구현했고 5번 단계에서 createAndAuthorize를 연결했다. 필요한 원자성·동시성이 기존 스키마로 구현되지 않으면 임의 컬럼을 추가하지 않고 담당 합의·ADR 절차로 돌아간다.

후속 테스트는 실제 MariaDB에서 커밋 후 재조회, 승인 참조와 상태의 동시 반영, 실패 후 최초 PENDING 보존, 두 트랜잭션의 동시 진입과 승인기 호출 횟수, 첫 처리 롤백 이후 재처리, 이미 처리된 결제·문맥 불일치 차단을 확인한다. latch 등으로 실행 순서를 통제하며 단순 순차 호출만으로 동시성 검증을 대체하지 않는다. 기존 평가 전용 테스트도 유지한다.
