## 1. 검증 수준과 공통 데이터

| 수준 | 증명할 수 있는 범위 | 필요한 준비 |
|---|---|---|
| U: P5 단위 검증 | 통제된 FDS·Mock·포트 결과에 대한 분기, 호출 여부, 입력 검증 | P5 구현과 테스트 대역. 실제 DB 원자성은 증명하지 못함 |
| D: P5 DB 검증 | 실제 P5 저장·롤백·유니크·동시 한도 갱신 | 스키마 Q08 확인, 실제 MariaDB와 독립 트랜잭션. 외부 모듈은 대역 가능 |
| X: 모듈 연동 검증 | P2·P3·P6와 실제 공동 커밋·기록·배치·외부 계약 | 해당 Q번호 합의, 실제 참여 모듈과 환경 |

독립 검증은 U 또는 D에서 P5만의 결과를 관찰한다는 뜻이다. 지금 구현 승인을 받았거나 DB 설계가 확정되었다는 뜻이 아니다.

예시 금액은 계산용이다. 통화·소수 자릿수·운영 한도 정책을 정하지 않는다.

- 기본 카드: 총한도 100,000, 기존 사용액 20,000. 기존 사용액은 다른 결제의 정상 승인으로 준비한다.
- 신규 결제 금액: 30,000. 승인 후 사용액 50,000, 해당 결제 전액 취소 후 20,000.
- 결제·카드·요청 키·결정 ID는 서로 구분되는 테스트 식별자로 준비한다.
- 성공 승인/취소 원장 수는 해당 결제를 기준으로 센다. 상태 이력은 테스트 직전 건수 대비 증가량을 센다.
- FDS 경계 점수는 P2 결과 입력 예시다. P5가 P2 점수 계산 로직을 재구현하는 테스트가 아니다.
- 시각은 통제된 기준 시각으로 고정한다. 미정인 만료 기간·유예 시간은 임의로 넣지 않는다.

## 4. 실패·동시성 검증에서 남길 증거

- D/X 테스트는 실제 MariaDB에서 별도 연결·트랜잭션으로 실행한다. 대역 호출 횟수만으로 DB 원자성을 증명하지 않는다.
- 경합은 barrier/latch 등으로 순서를 제어한다. 단순 대기 시간으로 동시 실행을 가정하지 않는다.
- 검증 조회는 작업이 커밋·롤백된 후 새 트랜잭션에서 한다. 같은 영속성 컨텍스트의 메모리 값만 확인하지 않는다.
- 상태·이력·원장·한도·멱등 결과를 함께 비교한다. 초기 원장이 없는 사용액을 만들어 원장 합계와 모순시키지 않는다.
- 승인과 취소의 성공 건수, 각 요청의 결과, 최종 사용액, 실제 DB 제약 오류·잠금 오류를 기록한다.
- 장애 주입은 저장 호출뿐 아니라 flush/commit 실패도 포함한다. 어떤 모듈의 기록이 남아야 하는지는 P5와 P2/P3/P6를 구분한다.

실행 후에만 다음 기록을 작성한다.

| 기록 항목 | 작성 내용 |
|---|---|
| 대상 | 불변식 ID·시나리오 ID·적용한 Q번호 합의 버전 |
| 코드 기준 | 실행 커밋 SHA 및 미커밋 변경 유무 |
| 환경 | Java·DB 버전, 스키마 버전, 실제 모듈과 테스트 대역 목록 |
| 실행 | 명령, 입력, 실패 주입 위치, 동시 실행 순서 |
| 결과 | 실제 관찰값, 예상값과 차이, 로그·보고서 위치 |
| 한계 | 미실행 사례, 대역으로 대체한 부분, 정본 미동기화·미합의 사항 |
