## 1. P1·CakeShop 전달용

주환님, 합의한 방향으로 결제 요청·조회 API 설계를 정리했습니다. 서버 간 호출, 동일 요청 재전송, 거절 후 조건부 재결제, 처리 중 주문 만료 보류는 기존 합의대로 유지합니다.

구현 연결을 위해 아래 추가 항목을 확인 부탁드립니다. 각 항목에 **동의 / 변경할 내용 / 미정**으로 답해주시면 됩니다.

### A. 인증 담당과 전달 방식

- DonWorry의 API Key 발급·검증·폐기와 가맹점 연결은 P1 identity에서 맡을 수 있을까요?
- CakeShop은 서버에서만 키를 보관하고, `X-API-Key` 헤더로 보내는 안을 제안합니다. 기존에 정한 헤더가 있으면 맞추겠습니다.
- P5는 키를 직접 검사하거나 요청 본문의 가맹점 번호를 믿지 않고, **P1이 인증한 가맹점 번호**를 받아 사용하겠습니다.
- 로그인한 직원 정보를 알려주는 기존 CurrentStaff와 별도로, 서버 인증 가맹점을 알려주는 공개 Java 인터페이스가 필요합니다. P1에서 제공할 인터페이스 이름·반환 형식을 알려주세요. 상세 예시는 문서 4절에 적었습니다.

키 누락·잘못된 키·폐기된 키는 요청과 조회 모두 차단하는 안입니다. 정지 가맹점은 새 결제를 막되, **아직 유효한 키로 자기 기존 결제 결과를 읽는 것은 허용**하면 결과 확인이 끊기지 않을 것 같습니다. 이 정책도 가능한지 확인 부탁드립니다. 정지 상태의 POST 재전송은 처리를 재개할 수 있으므로 차단하고 GET으로 확인하도록 제안합니다.

### B. 주문 시각과 같은 주문의 내용

기존 주문번호·고객 식별값·최종 금액에 **최초 주문 생성 시각(orderCreatedAt)**을 추가로 받을 수 있을까요? UTC 시각으로 받고 P5도 그 시각 +10분을 새 결제 시도 접수 기한으로 쓰려 합니다. 기존 CakeShop 만료 기준이 같은 생성 시각 기준인지도 확인 부탁드립니다.

같은 주문의 재결제에서는 고객·금액·최초 생성 시각을 그대로 유지하는 안입니다. 쿠폰 변경 등으로 금액이 달라지면 새 주문번호를 만드는 방식이 가능한지도 확인 부탁드립니다. 이는 기존에 합의된 내용이 아니라 이번 추가 제안입니다.

### C. 요청·조회 주소와 결과

- 결제 요청: `POST /api/payments`
- 특정 결제 조회: `GET /api/payments/{paymentId}`
- 주문별 결제 시도 조회: `GET /api/payment-orders?orderRef=주문번호`
- 결제 시도 식별값: `Idempotency-Key` 헤더에 UUID. 같은 시도 재전송이면 같은 값입니다.

요청 본문은 orderRef(주문번호), customerRef(회원 번호의 문자열), amount(원 단위 금액), orderCreatedAt(최초 주문 시각)입니다. 가맹점 번호는 인증 정보에서 얻으므로 본문에는 넣지 않습니다.

단건 결과는 **결제 ID·주문번호·시도 번호·금액·현재 상태·최초 요청 시각·상태 변경 시각·거절 사유 코드**를 제공합니다. 주문 조회는 최신 시도와 이전 시도 목록을 구분합니다. 목록은 기본 20건이며 이전 시도 번호로 다음 페이지를 조회하는 안입니다.

- 상태 변경 시각은 P5가 해당 결제 상태로 바꾼 시각입니다. 중복 조회·이벤트로 갱신하지 않습니다.
- 거절 코드는 우선 `FDS_REJECTED`(평가 거절), `AUTHORIZATION_DECLINED`(승인 거절)로 구분하고, 구체 탐지 규칙·내부 오류는 제공하지 않는 안입니다.
- 과거 데이터의 시각·사유를 알 수 없으면 null일 수 있습니다.
- POST 응답은 처리 중/보류이면 HTTP 202, 최종 결과이면 200입니다. 조회 성공은 항상 200이고 **결제 성공 여부는 paymentStatus로 확인**합니다.
- 형식 오류 400, 인증 실패 401, 신규 요청 금지 403, 없는 결제/다른 가맹점 결제 404, 요청 내용 충돌·새 시도 불가·접수 기한 경과 409, 처리 장애 500/503으로 구분합니다. 오류에는 code와 설명을 함께 제공합니다. 최종 코드 이름은 구현 전에 맞추겠습니다.

위 주소·필드·응답 방식으로 연동 가능한지 확인 부탁드립니다. 세부 JSON과 페이지 필드는 상세 설계 문서에 있습니다.

### D. 재고·쿠폰 예약과 결과 확인

앞서 전달한 **결제 전 재고 예약 → 처리 중 재고·쿠폰 유지 → 완료 시 확정 / 최종 거절·취소 확인 시 해제 → 재결제 전 재확보** 방식과 담당 범위를 수락할 수 있는지 확인 부탁드립니다.

화면을 닫은 후에도 CakeShop 서버가 결과를 조회하는 기존 제안대로 연결하되, 아래 둘을 구분하면 좋겠습니다.

- 응답을 못 받거나 500/503이면 같은 키·같은 본문으로 POST를 재전송합니다. 새 키를 만들지 않습니다. 이를 CakeShop 서버 작업에서도 수행할 수 있을까요?
- 정상 응답을 받으면 GET으로 결과를 조회합니다. GET은 조회만 하므로 중간에 멈춘 처리를 다시 실행하지 않습니다.

자동 POST 재시도 횟수·간격과 장기 GET 조회 간격은 아직 정하지 않았습니다. 재시도를 다 했는데도 해결되지 않은 건은 실패로 확정하거나 예약을 풀지 않고 담당자 확인 대상으로 남겨야 합니다. 401/403은 키·가맹점 상태 확인, 409는 충돌 내용 확인이 필요합니다.

최대 보류 시간은 P5가 종료·승인 취소 정책과 함께 제안하겠습니다. CakeShop에서 재고·쿠폰을 유지할 수 있는 최대 시간 또는 업무상 제한을 알려주세요. 시간이 지났다고 자동 실패로 처리하는 기능은 이번 API만으로 제공되지 않습니다.

## 2. P2 전달용

정후님, CakeShop 결제 요청·조회 API(#149)를 설계 중입니다. 두 가지 확인 부탁드립니다.

1. CakeShop은 고객 식별값으로 회원 번호를 보냅니다. 가맹점마다 같은 회원 번호가 있을 수 있어, P5 내부에서는 `가맹점번호:회원번호`(예: `7:42`)를 customerRef로 만들어 P2 평가와 P3 HELD 이벤트에 동일하게 전달하려고 합니다. **서로 다른 가맹점의 회원을 별도 고객으로 취급하는 기준**으로 괜찮을까요? 현재 반복 결제 집계·기존 데이터와 영향이 있는지도 확인 부탁드립니다. 실제 같은 사람을 가맹점 간 연결하는 기능은 이 방식으로 제공하지 않습니다.
2. 응답 유실·중단 후에는 저장해 둔 **같은 evaluationRequestId와 완전히 같은 입력**으로 evaluate를 다시 호출해 기존 결과를 받으려 합니다. 현재 코드의 기존 UUID 결과 반환을 이 복구 계약으로 사용해도 될까요? 동시에 두 번 호출돼도 한 결과로 수렴해야 합니다. P5는 입력과 UUID를 고정하고 임의로 새 UUID를 만들지 않겠습니다.

ERROR가 저장된 경우 같은 UUID 재호출로 새 평가가 되었다고 보지 않고, P5 결제는 PENDING으로 유지합니다. ERROR를 다시 평가하는 정책은 별도 합의하며 자동 ALLOW나 최종 거절로 바꾸지 않겠습니다. 위 기준 확인 부탁드립니다.

## 3. P3 전달용

수민님, CakeShop 연동에서 고객 식별값을 정리하려고 합니다.

CakeShop 회원 번호만 사용하면 다른 가맹점의 같은 번호와 겹칠 수 있어, P5가 내부 customerRef를 **`가맹점번호:회원번호`(예: `7:42`)**로 구성하고 PaymentHeld에도 그 값을 그대로 보내는 안입니다.

P3에서 이 값을 고객의 표시 이름이나 숫자 ID로 해석하지 않고, **Case 연결에 사용하는 문자열 식별값**으로 받을 수 있을까요? 기존 Case 병합·조회·보고서 연결에 영향이 있는지 확인 부탁드립니다.

기존 데이터의 customerRef는 자동으로 바꾸지 않는 안이어서, 이전 Case와 새 참조의 Case가 바로 병합되지 않을 수 있습니다. 기존 데모 데이터 유지/이관 기준도 확인 부탁드립니다. 이 변경으로 HELD 필드 수나 P3 수신 시각 기준의 30분 병합 정책을 바꾸지는 않습니다.

## 4. P1 개발 연결용 보충안

다음 이름은 **구현된 타입이 아니라 협의용 예시**다. P1 내부 principal·Entity·Repository를 P5가 import하지 않는다.

```java
// identity.api 내부에 P1이 제공하는 안
public interface CurrentMerchant {
    Optional<MerchantIdentity> findCurrent();
}
public record MerchantIdentity(Long merchantId) {}
```

- P1 인증 필터가 키를 검증하고 요청 범위에 가맹점 신원을 설정한다. P5는 공개 API로만 조회한다. 세션 로그인은 API Key 인증을 대체하지 않는다.
- 인증 없으면 empty, 잘못된 인증 컨텍스트는 내부 오류. P5 HTTP 서비스도 신원 없으면 거절한다. 운영 fallback으로 고정 merchantId를 제공하지 않는다.
- P1이 키 유효성/폐기를, P5가 TenantReader를 통한 신규 접수 가능 여부와 조회 가맹점 조건을 담당하는 안이다. 키 변경 후에도 같은 가맹점이면 멱등 키 범위는 유지된다.
- API Key 검사는 GET 포함 3절의 외부 API 전부에 적용한다. P1은 기존 직원 세션 API 보안 정책과 구분한다. CSRF 예외는 합의된 서버 간 경로/메서드에 한정하고 `/api/**` 전체를 풀지 않는다.
- 정지 가맹점은 POST 전부 금지/유효 키 GET 허용 제안이며, 폐기된 키는 GET도 금지한다. 담당자 확인 없이 이 정책을 확정하지 않는다.
- 오류 본문 형식은 ProblemDetail + code를 맞춘다. 인증 코드 이름·P5 코드 번호는 함께 확정하며 공통 예외 클래스를 독자적으로 추가하지 않는다.
- 키·비밀값·원문 요청 헤더는 로그/DB 업무 행에 저장하지 않는다. TLS·키 배포/교체·운영 설정은 P1/CakeShop 범위와 함께 검증한다.

- P1 세션용 CurrentStaff를 CakeShop 서버 인증으로 대체하지 않는다. 가맹점 ID를 body/header에서 직접 받아 신뢰하거나 고정 가맹점 fallback을 만들지 않는다. P1 identity·SecurityConfig도 이번 범위에서 수정하지 않는다.

### P1에게 전달할 짧은 문안 (미발송)

주환님, P5 결제 접수·평가/승인·결과 조회 구현까지 끝났고 이제 HTTP를 연결하려고 합니다.

최신 dev에는 가맹점 API Key 인증이 아직 없어서 아래 세 가지만 연결 부탁드립니다.

1. CakeShop이 `X-API-Key`로 호출하면 P1에서 키를 검증하고, P5가 **인증된 가맹점 번호**를 읽을 수 있는 공개 인터페이스를 제공해주세요. 예전에 제안한 CurrentMerchant는 예시라 실제 이름·반환 형식을 알려주시면 맞추겠습니다.
2. 적용할 주소는 `POST /api/payments`, `GET /api/payments/{paymentId}`, `GET /api/payment-orders`입니다. 키가 없거나 잘못됐거나 폐기됐으면 모두 차단하고, 직원 로그인 세션으로 대신 통과하지 않게 연결해주세요. 기존 직원 API의 보안·CSRF 설정은 유지하고 이 서버 간 경로에 필요한 처리를 구분해주세요.
3. 정지 가맹점은 POST 금지, 아직 유효한 키로 자기 결제 GET은 허용하는 안으로 진행 가능한지 확인해주세요. 다른 정책이면 알려주세요.

이미 구현 중이면 **이슈/PR 또는 브랜치와 공개 인터페이스 이름**만 알려주셔도 됩니다. P5에서는 그 경계를 연결한 뒤 인증 실패·다른 가맹점 접근·정지 상태를 포함해 HTTP 테스트하겠습니다.

이번 단계는 원격 코드·이슈 확인과 전달안 정리다. 담당자에게 메시지를 보내지 않았다. Java/SQL 변경은 없어서 backend 검사를 다시 실행하지 않았으며, 이전 `c7c5268` 구현 작업 트리의 일반 385개·MariaDB 212개 통과 기록을 유지한다. 실제 HTTP·API Key·CakeShop 통합은 미검증이다.


## 8. 인증 대기 중 구현 범위 변경 (사용자 승인)

사용자가 HTTP 구현·테스트를 먼저 진행하고 실제 인증 전 운영 비활성을 유지하도록 승인했다. POST/GET Controller와 P5 내부 PaymentMerchantIdentity 연결 지점을 구현하며, 테스트 소스에만 인증 대역을 둔다. 운영 기본값은 Controller 미등록, 명시적으로 활성화해도 실제 어댑터 없이는 503 차단이다. 위 7절의 “HTTP 컨트롤러는 아직 없다”는 당시 확인 기록이며 현재 구현 범위는 #149 상세 설계의 후속 기록을 따른다. P1 API Key 공개 계약/운영 구현 완료나 담당자 발송으로 표시하지 않는다.
