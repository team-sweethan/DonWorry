# #152 돈워리 내부 장기 미처리 대응 기준

- **상태: P5 D1~D6 대응 방향 확정 — 시간 수치·운영 담당자 미정, 타 담당 합의·운영 구현 전.**
- 작성: 2026-10-26. 관련: [#152](https://github.com/team-sweethan/DonWorry/issues/152), [전체 정책 초안](152-long-held-payment-policy.md), [ADR-0035](../decisions/0035-long-held-payment-policy.md).
- 범위: P5 결제 처리 중단, P3 판정·인계 대기, P6 매입·완료 전달 지연. CakeShop 인증·요청·조회, 주문·재고·쿠폰, 고객 취소·환불 계약은 별도 범위다.

## 2. P5 D1~D6 확정 범위

2026-10-26 사용자가 **"시간이랑 담당자는 미정으로 두고, 나머지 D1~D6은 추천안대로 확정해서 문서에 반영해줘"**라고 승인했다. 이에 따라 아래 분류·추적·시간 관리 방식·복구 조건·조회 요구·완료 기준을 P5 확정 방향으로 기록한다. 시간 수치·지원 시간대·개별 운영 담당자는 §2.7의 미정 상태를 유지한다. 이 결정은 구현 착수·운영 활성화 승인이나 P3·P6 합의를 뜻하지 않는다.

| ID | P5 결정 항목 | 확정 방향과 범위 |
| --- | --- | --- |
| D1 | P5 내부 미처리 분류 | 처리 구간과 확인 사유를 함께 기록한다. 미승인 처리 중단·평가 ERROR·자동 매입·HELD 판정·직원 금융 조치 대기·VOID 실패·금융 완료·원인 미확인을 구분한다. 새 결제 상태값이 아니다 |
| D2 | 최초 확인 담당·추적 방식 | P5 소유 중단은 P5가 최초 접수하고 결제별 추적 항목 하나를 유지한다. 인계 요청·수락·해소 근거를 기록하며 요청 발송만으로 추적을 종료하지 않는다. 개인 담당자는 미정 |
| D3 | P5 측 확인 기한 | 정기 확인·경고·최초 응답·미해소 재확인을 따로 관리한다. **시간 수치·지원 시간·운영 담당자는 미정**. P3 판정·P6 매입 완료의 보장 기한으로 사용하지 않는다 |
| D4 | 복구 전 확인·중단 조건 | §4의 식별자·상태·전달 대조를 먼저 수행한다. 시간 초과를 실패·EXPIRED로 바꾸거나 DB 상태를 직접 고쳐 해소하지 않는다. 식별자 충돌·상충 결과는 반복 실행을 멈추고 소유 담당과 확인한다 |
| D5 | P5 운영 조회의 최소 요구 | 결제·요청 단계·평가 참조·승인 유무·직원 조치·시각을 P5 소유 범위에서 조회할 요구사항을 정한다. 우선 읽기 전용으로 설계하고, P3·P6 내부 Repository를 참조하지 않는다. 실제 운영 도구·권한 연결은 별도 구현·검증 대상이다 |
| D6 | P5 작업 범위·복구 완료 기준 | 먼저 발견·분류·조회와 수동 확인 절차를 구체화하고, 자동 종료·새 평가·반대 조치 변경은 별도 설계로 둔다. P5 처리 복구와 P3 인계 복구를 각각 확인한다. 공동 사고 종료는 관련 담당의 반영 확인을 받아 기록한다 |

현재 계약에서 허용되지 않는 미승인 PENDING 종료, CAPTURE 후 VOID 전환, FAILED 조치 초기화는 이번 확정 범위에 포함하지 않는다. 이 기능을 추가하려면 계약·경합·저장 근거를 별도로 설계해야 한다.

### 2.1. D1 확정 — 금융 처리와 전달 문제를 구분해 추적

결제 한 건마다 **처리 구간과 확인 사유를 함께 기록**한다. 직원 CAPTURE 대기와 완료 전달 실패는 함께 나타날 수 있으므로 하나의 원인 코드로 덮어쓰지 않는다.

| 처리 구간 | 분류 근거 | 확인 사유·우선 처리 |
| --- | --- | --- |
| 미승인 처리 중단 | PENDING·승인 없음 + RECEIVED/EVALUATED | 단순 진행 중인지 예외 후 중단인지 구분. 경과 시간만으로 오류 확정하지 않음 |
| 평가 ERROR | NEEDS_REVIEW + 저장 ERROR | P5 저장 근거 확인 후 P2 원인 확인 요청 |
| 자동 매입 대기 | 승인된 PENDING·직원 조치 없음 | P6 미완료와 완료 전달 지연을 A3의 확인으로 구분 |
| HELD 판정 대기 | HELD·직원 조치 없음 | P3 Case 연결 확인과 정상 판정 대기를 구분 |
| 직원 금융 조치 대기 | HELD·CAPTURE 조치 PENDING | P6 결과 확인과 P3 대기 상태를 구분해 추적 |
| VOID 확정 실패 | VOID 조치 FAILED·VOID_DECLINED | 시간 경고를 기다리지 않고 확인 대상으로 등록. 취소 완료로 표시하지 않음 |
| 금융 처리 완료 | CAPTURED 또는 VOIDED와 해당 조치 결과 | 관련 전달이 남으면 전달 장애 추적을 계속함 |
| 원인 미확인 | 근거 부족·기존 내부 경로·관측값 모순 | 없는 값은 미확인으로 기록. 요청 행 부재를 미승인 증거로 사용하지 않음 |

확인 사유는 `경과 시간 초과`, `처리 예외`, `미완료 전달`, `식별자/결과 충돌`, `담당자 확인 요청`으로 기록한다. 충돌·확정 실패·명시적 처리 예외는 시간 임계값을 기다리지 않고 확인 대상으로 등록한다. 정상 HELD 자체를 장애로 분류하지 않는다. 이 분류는 작업 기록 기준이며 새 Enum·DB 컬럼 설계가 아니다.

### 2.2. D2 확정 — 결제별 추적 항목 하나와 명시적 인계

결제별 추적 항목 하나에 원인 변경·재확인·타 담당 회신을 이어 기록한다. P5 소유 중단의 최초 접수·진행 확인은 P5 범위로 두되 **실제 접수자·대체자·조율 담당은 미정**이다. 타 모듈 조사·복구 실행은 소유 담당과 합의한다.

- 최초 기록: paymentId, 처리 구간·확인 사유, 최초 발견 시각, 현재 확인 담당, 관측 근거, 다음 확인 시각. 아직 배정되지 않은 값은 미정으로 표시한다.
- 추가 대조: 존재하는 requestId·평가 UUID/ID·actionId·decisionId·조치 키·관련 발행 식별자. 승인 유무만 기록하고 승인 참조 원문·고객 정보·비밀값·이벤트 본문 전체는 복사하지 않는다.
- 인계 기록: 요청 상대·시각·질문·수락 여부·다음 확인 담당·시각. **요청 발송만으로 P5 추적을 종료하지 않는다.** 수락 전에는 P5 범위에서 진행 확인을 유지한다.
- 작업 진행 표시는 `확인 중`, `타 담당 회신 대기`, `복구 조건 미충족`, `반영 검증 중`, `해소 확인`으로 구분한다. 금융 상태를 대신하지 않는다.

회신 기한 초과·담당 부재 시 대체·조율 담당에게 인계하는 방식으로 한다. 기한·담당 확정 전에는 자동 인계나 응답 보장을 안내하지 않는다. 기록 매체는 접근 제한 작업 기록으로 선택하며 구체 위치·접근 대상은 미정이다. 새 업무 테이블은 이번 범위에 포함하지 않는다.

### 2.3. D3 확정 — 발견·응답·재확인 시간을 따로 관리

**정기 확인 주기, 경과 시간 경고, 최초 응답 목표, 미해소 재확인 주기**를 따로 관리한다. 최초 응답은 근거를 확인하고 다음 조치를 기록한 때이며 금융 복구 완료를 뜻하지 않는다.

1. 최초 적용은 개발·시연 중 합의할 지원 시간의 수동 확인으로 시작한다. 자동 경고가 구현된 것으로 가정하지 않는다.
2. 경과 시간은 §5의 원래 시작 시각을 사용하고 최초 발견·최초 응답·마지막 확인 시각은 따로 기록한다. 시작 근거가 없으면 경과 시간을 추정하지 않는다.
3. 예외·충돌·VOID 확정 실패는 발견 시 확인 대상으로 등록한다. 응답 목표는 최초 발견부터 측정하고 지원 시간 밖 계산 방식은 미정으로 남긴다.
4. 확인할 때마다 다음 확인 담당·시각을 기록한다. 지원 시간 밖의 건도 보존하며 야간 대응은 담당·시간 확정 후에만 약속한다.

시간 수치·지원 시간대·운영 담당은 §2.7에서 모두 미정으로 유지한다. 이 상태로 SLA가 활성화되거나 P3·P6의 완료 기한이 확정된 것으로 보지 않는다.

### 2.4. D4 확정 — 근거를 확인한 한 건만 복구

복구 전 다음 조건을 모두 확인한다.

1. 원래 결제·평가·직원 조치·대상 발행 식별자가 맞고 현재 결과와 충돌하지 않는다.
2. 중단 구간·실패 수신자가 특정됐고 P6 실제 매입 여부 등 필요한 소유 담당 확인이 있다.
3. 같은 요청·같은 키 또는 원래 미완료 발행을 사용하는 기존 경로이며 실행 권한·대상 선택·멱등성·운영 수단이 검증돼 있다.
4. 복구 후 대조할 결과·확인 담당이 정해져 있다. 확인 뒤에도 상태가 바뀔 수 있으므로 실행 경로의 잠금·멱등 검사를 유지한다.

식별자 충돌, 상충 성공, 상태/조치 모순, 원래 전달 기록 부재, 필요한 확인·권한·운영 수단 부재이면 실행을 보류하고 관측 근거를 남긴다. **재전달 횟수·간격·실행 담당은 A4 공동 합의 전 미정**이다. 이 절은 복구 요구사항이며 현재 운영 명령을 제공하는 것이 아니다.

실행 시 대상 식별자·실행자·시각·전후 결과를 기록한다. 새 키·임의 이벤트 생성·DB 상태 수정·조치 삭제/초기화로 실패를 우회하지 않는다.

### 2.5. D5 확정 — 결제 식별자 조회와 미처리 목록부터

첫 구현 범위는 P5 소유 데이터의 **읽기 전용 단건 조회 + 미처리 목록**으로 정한다.

| 구분 | 최소 요구사항 |
| --- | --- |
| 단건 조회 | paymentId로 상태·생성/상태 변경 시각·승인 유무 확인. 존재할 때만 요청 단계·평가 참조/결과/오류 코드·직원 조치 종류/결과/요청·완료 시각 표시 |
| 목록 | 처리 구간·확인 사유 후보·원래 시작 시각/경과 시간으로 확인 대상을 찾고 페이지 단위 조회. 미해소 항목을 조회 횟수 초과로 제외하지 않음 |
| 근거 부족 | 없는 요청·시각·승인/조치 근거는 미확인으로 표시. 데이터 없음과 조회 실패를 구분 |
| 타 모듈·이벤트 | P3 Case·P6 결과는 각 소유 담당 확인 또는 합의된 공개 조회 사용. 발행 조회·접근·보존은 A4 확인 후 연결하고 공통 테이블을 P5 업무 정본으로 취급하지 않음 |
| 접근 | 개발 담당과 운영 조회 권한을 동일시하지 않음. 역할·접근 범위는 P1과 확인하고 승인 참조 원문·전체 이벤트 payload는 기본 출력에서 제외 |

재실행·강제 상태 변경 버튼, P3·P6 내부 데이터 직접 조회, 자동 종료는 첫 조회 구현에 포함하지 않는다. HTTP 경로·DTO·화면·저장 구조는 후속 설계 대상이다.

### 2.6. D6 확정 — 조회·추적을 먼저 만들고 복구 실행은 합의 후

먼저 D1 분류 근거를 조회하고 D2 확인 기록을 남긴다. 이후 A3·A4 합의와 운영 수단 검증을 마친 경로부터 복구 대상으로 삼는다. 자동 종료·재평가·반대 조치 변경·새 CAPTURE 실패 계약은 별도 설계로 유지한다.

| 확인 단계 | 해소로 기록할 근거 | 추적을 계속할 조건 |
| --- | --- | --- |
| P5 처리 중단 | 기존 결제에서 처리 단계·결과가 커밋되고 원래 요청과 일치 | HELD 판정·매입 대기가 남으면 같은 추적 항목의 처리 구간 갱신 |
| 금융 사실 반영 | 매입은 P6 매입·정산 예정금과 P5 CAPTURED, 직원 경로는 조치 SUCCEEDED까지 확인. VOID는 VOIDED·조치 SUCCEEDED 확인 | 기술 오류·저장 실패·상충 결과·VOID_DECLINED는 금융 해소로 처리하지 않음 |
| P3 전달·인계 | HELD는 Case 연결, 직원 결과는 원래 판정·조치에 맞는 인계 반영을 P3가 확인 | 수신 실패·미설치 리스너·목업 응답만 있으면 실제 연동 완료로 처리하지 않음 |
| 추적 항목 종료 | 확인 대상 장애 해소, 남은 정상 업무 인수, 금융 미확정·미반영 장애가 남지 않았다는 관련 담당 확인 기록 | 요청 발송·재시도 상한·장기 대기·후속 이슈 생성만으로 종료하지 않음 |

HELD 전달 장애가 복구돼 P3가 정상 판정 대기를 인수하면 전달 장애 해소를 기록할 수 있다. 결제는 HELD를 유지하고 장기 판정 경고는 P3 합의 기준으로 계속 추적한다. ALLOW 자동 매입에는 P3 직원 인계 완료를 요구하지 않는다. 타 담당의 확인·인수 책임은 §3 합의 후 구체화한다.

### 2.7. 미정으로 유지할 시간 수치·담당자

사용자 결정에 따라 다음 값은 **모두 미정**으로 유지한다. 이번 방향 확정으로 감시·경고·복구의 실행 담당이나 운영 SLA를 활성화하지 않는다.

| 구분 | 남은 값 | 적용 기준 |
| --- | --- | --- |
| 시간 T1 | 지원 요일·시간대: **미정** | 개발·시연 지원 시간과 야간 대응 여부 |
| 시간 T2 | 정기 미처리 확인 주기: **미정** | T1 안에서 수행할 확인 주기 |
| 시간 T3 | 미승인 처리 중단 최초 경고 시간: **미정** | payments.createdAt 기준. 명시적 오류는 경고를 기다리지 않음 |
| 시간 T4 | 최초 응답 목표: **미정** | 최초 발견부터 근거 확인·다음 조치 기록까지. 지원 시간 밖 계산 방식 포함 |
| 시간 T5 | 미해소 재확인 주기: **미정** | 마지막 확인부터 다음 확인까지 |
| 시간 T6 | 인계 미수락 시 재문의·조율 요청 시간: **미정** | P5 재문의 목표이며 상대 완료 기한은 공동 합의 |
| 담당 R1 | 최초 접수·진행 확인 담당: **미정** | P5 소유 중단 추적. 특정 개인에게 배정하지 않음 |
| 담당 R2 | 부재 시 대체 담당: **미정** | 실제 확인 가능한 사람의 수락 필요 |
| 담당 R3 | 미응답·책임 불명·소유 간 충돌 조율 담당: **미정** | 팀 수락 필요. 금융 결과 임의 판정 권한은 아님 |
| 담당 R4 | 기록 위치·접근 대상: **미정** | 접근 제한 팀 작업 기록 선택. 개인 담당·운영 권한은 미배정 |

HELD 판정·직원 CAPTURE·자동 매입 대기 기한, P2 ERROR 확인 기한, 재전달 횟수·간격·보존 기간·실행자·타 모듈 대체 담당은 공동 합의 대상으로 유지한다. 담당표의 시은·수민·민정은 모듈 소유·협의 상대이며 이번 운영 책임 수락으로 확대하지 않는다. 기존 P3 24시간 경고를 새 P5 기한의 기본값으로 복사하지 않는다.

## 3. P3·P6 합의가 필요한 부분

| ID | 상대 | 합의할 내용 | P5 제안 / 현재 제한 |

## 4. 원인별 내부 대응안

각 행의 담당은 **분담 제안**이다. A1~A6 수락 전 타 담당의 운영 책임이 확정된 것으로 안내하지 않는다. 아래 분류가 맞지 않거나 필수 근거가 없으면 원인 미확인으로 P5가 확인을 이어간다.

| 관측 조건 | 최초 확인·분담 제안 | 대응안 | 해소 확인 근거 |
| --- | --- | --- | --- |
| 미승인 PENDING + 요청 단계 RECEIVED/EVALUATED | P5. 평가 장애는 P2 협의 | 저장 입력·고정 평가 UUID·현재 단계·실패 원인 확인. 기존 요청 흐름은 중단 단계 재개가 가능하지만, 운영 재개 수단·실행 조건은 별도 확보. 새 결제를 만들거나 시간만으로 종료하지 않음 | 기존 paymentId에서 처리 단계와 결과가 커밋됨. 이어서 매입/HELD 대기가 남으면 해당 분류로 계속 추적 |
| 미승인 PENDING + NEEDS_REVIEW | P5 → P2 | 저장 ERROR·평가 ID·오류 코드 확인. 같은 요청 재확인만으로 재평가되지 않음. P2 원인 확인 후 별도 복구 방침 결정 | 원인·다음 담당·조치가 기록됨은 인계일 뿐 금융 해소가 아님. 실제 처리 또는 합의된 종료 근거가 생길 때까지 미해소 |
| 승인된 PENDING, 직원 조치 없음 | P5 ↔ P6 | 자동 매입 요청·P6 결과·완료 전달을 순서대로 대조. AUTHORIZED 단계 재호출로 매입이 새로 발행되지 않음. PENDING만 보고 취소하지 않음 | P6 매입·정산 예정금 완료 확인과 P5 CAPTURED 반영. ALLOW 경로에는 P3 직원 결과를 요구하지 않음 |
| HELD, 직원 조치 없음 | P5는 HELD 발행·전달, P3는 Case·판정 | Case 미연결/전달 실패와 실제 판정 대기를 구분. P5가 P3 저장소를 읽지 않고 P3가 연결 여부 확인. 정상 판정 지연을 재승인·자동 REJECT로 처리하지 않음 | 전달 장애는 P3의 Case 연결 확인으로 해소. 판정 대기는 이후 허용된 직원 조치와 실제 금융 결과까지 별도로 추적 |
| HELD + 직원 CAPTURE PENDING | P5 ↔ P6, P3 인계 유지 | 같은 조치 키는 저장 결과 재확인. 요청 전달 실패·P6 처리 실패·완료 반영 실패를 구분. 반대 VOID와 새 매입 발행으로 우회하지 않음 | P6 완료, P5 CAPTURED·조치 SUCCEEDED, P3 인계 반영을 각각 확인. #161 실제 연결 전에는 P3 완료를 주장하지 않음 |
| HELD + VOID 조치 FAILED(VOID_DECLINED) | P5 ↔ P3 | 저장 실패·HELD 보존. 같은 키는 같은 거절 결과. 자동 재시도·조치 삭제·새 키 우회 없이 예외 대응 인계 | 실패 결과 전달 확인과 금융 해소를 구분. 취소 성공 근거가 없으면 미해소로 유지하며 후속 방침 합의 필요 |
| P5 금융 완료, P3 인계는 미완료 | P5는 저장 결과·발행 확인, P3는 인계 대조 | 원래 미완료 결과 전달 복구 또는 #161 동일 키 결과 재확인. 리스너 설치 전 발행으로 기록이 없는 경우 자동 소급 전달을 가정하지 않음 | P3가 동일 paymentId·decisionId·actionType·멱등키와 결과 ID를 대조해 인계·Case에 반영. 금융 실행을 반복하지 않음 |
| 식별자 불일치·서로 다른 성공 결과·상태와 조치 모순 | P5 + 해당 사실 소유 P3/P6 | 증거 보존, 반복 복구 중단, 소유 담당 대조. 하나의 상태를 골라 강제 덮어쓰지 않음 | 충돌 원인, 수락한 실제 결과, 각 모듈의 반영 근거와 담당 확인 기록 |

`payment_requests`가 없는 기존 내부 서비스 경로는 요청 단계·고정 UUID 복원 절차를 그대로 적용하지 않는다. 생성 경로와 남은 승인·이벤트 근거를 확인하며, 요청 행이 없다는 사실만으로 신규 결제나 미승인으로 판단하지 않는다.

## 5. 확인 순서와 시간 기준

1. paymentId와 가맹점·주문 참조를 대조하고 관측 시각을 남긴다. 요청이 있으면 requestId·처리 단계·평가 UUID/ID, 직원 조치가 있으면 actionId·decisionId·actionType·멱등키를 함께 확인한다. 입력 전체나 비밀값을 작업 기록에 복사하지 않는다.
2. P5의 현재 결제·승인 유무·조치 결과와 원래 발행의 이벤트 타입·발행 식별자·수신자·완료 여부를 대조한다. 미완료 기록만으로 P6 금융 미완료를 단정하지 않는다.
3. P6 매입 사실과 P3 Case·인계 사실은 각 소유 담당의 확인을 받는다. 읽기 확인은 담당자 조사를 위한 근거이며, 여러 모듈을 한 시점에 잠근 실행 보장이 아니다.
4. 원인·대상·실행 조건·복구 담당이 확인된 경로만 재개한다. 현재 운영 수단이 없거나 원래 전달 기록이 없으면 임의 이벤트를 만들어 보내지 않고 후속 설계로 넘긴다. 복구 수단 확보 전에는 실행 가능한 운영 절차로 안내하지 않는다.
5. 복구 후 결제·조치·매입·인계 결과를 해당 범위에서 다시 대조하고, 미해소 대상과 다음 확인 담당·시점을 남긴다. 재시도 상한에 도달해도 금융 미확정 건을 추적에서 제거하지 않는다.

| 측정 대상 | 시작 기준 제안 | 확정할 사람 / 남은 값 |
| --- | --- | --- |
| 전체 미처리 경과 | payments.createdAt(공개 조회의 requestedAt) | P5가 내부 경고·응답 목표·확인 주기 선택. 수치 미정 |
| HELD 판정 대기 | HELD 전이 statusChangedAt | P3와 A1 합의. CAPTURE 대기와 분리하며 과거 null은 추정하지 않음 |
| 직원 CAPTURE 대기 | payment_actions.requestedAt | P3·P6와 대응 목표·인계 합의. 기존 P3 24시간 경고를 자동 종료로 확대하지 않음 |
| 자동 매입 전달·처리 대기 | 원래 CaptureRequested 발행 근거의 시각 | P5·P6가 추적 근거·보존과 기한 합의. 승인 후 PENDING 유지에서는 statusChangedAt이 승인 시각으로 갱신되지 않음 |

재조회·재전달로 위 시작 시각을 초기화하지 않는다. 최초 발견 시각·마지막 확인 시각은 별도 운영 기록으로 구분한다. 발견·필터링 수단, 시간 수치, 재전달 횟수·간격은 아직 구현·합의되지 않았다.

미승인 PENDING 종료, 재평가, 조치 교체, CAPTURE 확정 실패는 필요한 기능·도입 시점을 합의한 뒤 별도 이슈로 분리한다. 내부 기준 정리만으로 CakeShop 범위까지 포함하는 #152 전체 완료를 표시하지 않는다.

## 7. 이번 변경의 검증 범위

- `python3 .github/scripts/check_md_links.py` — 통과. 저장소 Markdown 상대 경로 검사이며 제목 앵커·외부 URL 검사는 포함하지 않는다.
- `git diff --check` — 통과. 신규 파일이던 최초 초안의 공백 검사와 이번 확정 문서 검사를 구분한다.
- backend·MariaDB 검사는 문서만 변경한 이번 단계에서 실행하지 않았다. 위 운영 기준·복구 수단·공동 흐름은 미구현 또는 미검증으로 남긴다. Notion 최신 내용과 담당자 수락 여부는 추정하지 않는다.
