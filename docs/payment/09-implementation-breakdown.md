## 1. 작업을 나누는 기준

| 구분 | 진행할 수 있는 범위 | 완료의 의미 |
|---|---|---|
| A: 먼저 진행 가능 | 기존 요청의 정책을 P5 내부 규칙으로 표현하고, 통제된 입력·테스트 대역으로 단위 검증 | 해당 내부 규칙만 구현·검증됨. API·DB·모듈 연동 완료를 의미하지 않음 |
| B: 팀 합의 후 진행 | 물리 저장, 인증·외부 계약, 다른 모듈과의 트랜잭션·이벤트·배치 연결 | 필요한 답변이 정본/ADR에 기록되고 실제 DB 또는 실제 모듈 검증까지 통과 |

여기서 “먼저 진행 가능”은 **향후 구현 착수를 요청받았을 때의 순서**다. 이번 작업에서는 문서만 작성한다.
PROPOSED 정책을 확정으로 바꾸지 않으며, 기존 HELD 정책과의 충돌도 유지한다.
A 작업은 초안 정책의 내부 구현 범위로 제한하고, 공유 API·DB 상태값·배포에 반영하기 전에 관련 합의를 확인한다.

독립 테스트가 가능한 항목도 저장 구현은 B로 나뉜다. 특히 L11·L12는 실제 DB 검증이므로 A 완료 조건으로 사용하지 않는다.
단위 테스트 대역을 실제 P2·P3·P6의 확정된 인터페이스로 간주하지 않는다.

이하 불변식은 전체 ID로 표기하고, L/E 번호의 상세 입력·예상 결과는 테스트 시나리오 문서를 따른다.

## 2. 먼저 진행할 수 있는 작업

담당은 모두 **P5 시은**이다. 선행 작업은 해당 범위의 검증까지 끝난 상태를 뜻한다.

### A01. 내부 상태 전이와 매입 허용 규칙

- 산출물: P5 내부 상태 전이 판단과 실제 전이 여부 판정, HELD 매입 금지 규칙.
- 선행 조건: 없음. 기존 요청의 승인 후 HELD 기준을 사용한다.
- 연결 불변식: INV-P5-04·05·10·12.
- 연결 시나리오: L06·L07·L16의 U 범위, L18.
- 완료 조건: KEEP은 재승인 없이 APPROVED가 되고, HELD는 매입 허용 대상에서 제외된다. 금지 전이는 실패하고 전이 효과가 없다. 전이 이력 생성 필요 여부를 구분한다.
- 경계: 이력의 실제 저장·잠금은 B03, P3 공개 API는 B05, P6 조회 API는 B07이다. EXPIRED와 HELD 자동 만료는 포함하지 않는다.

### A02. FDS 결과에 따른 승인 처리 분기

- 산출물: 통제된 FDS 결과를 받아 Mock 승인 여부와 성공·업무 거절·기술 실패를 구분하는 내부 처리.
- 선행 작업: A01.
- 연결 불변식: INV-P5-01·02·03·04·08.
- 연결 시나리오: L01~L05의 U 범위.
- 완료 조건: ALLOW/HOLD는 Mock 성공 후 각각 APPROVED/HELD, REJECT는 승인 호출 없이 DECLINED다. Mock 업무 거절도 DECLINED다. FDS 기술 실패에는 승인 호출이 없고, Mock 기술 실패를 성공으로 처리하지 않는다.
- 경계: P2 점수 계산·실제 호출·시도 저장은 구현하지 않는다. L04의 DB 롤백은 B03, P2 기록 보존은 B04에서 검증한다.

### A03. 한도 계산과 전액 취소 내부 규칙

- 산출물: 승인 가능 한도 계산, 승인·전액 취소의 한도 변화 계산, 취소 성공 이후 상태 전이 규칙.
- 선행 작업: A01.
- 연결 불변식: INV-P5-06·07·08.
- 연결 시나리오: L08~L10의 U 범위.
- 완료 조건: 예시 한도 경계 80,000은 허용하고 80,001은 거절한다. 승인 30,000 이후 해당 금액만 취소하여 다른 결제의 사용액 20,000을 보존한다. 취소 거절·예외에는 CANCELED 전이와 한도 해제 효과가 없다.
- 경계: 예시 수치의 계산 검증만 우선한다. 운영 금액 타입·통화·부분 취소·카드 상태 규칙은 Q17·Q16 합의 후 B01·B06·B11에 반영한다. DB 동시 한도 갱신은 B03이다.

### A04. 완료 요청의 재생·충돌 판단

- 산출물: “동일 주체·동일 키의 완료 기록”이 주어졌을 때 재생 또는 본문 충돌을 판정하는 내부 규칙.
- 선행 작업: A01. 승인·취소 흐름에 연결할 때 A02·A03을 사용한다.
- 연결 불변식: INV-P5-09·10.
- 연결 시나리오: L13~L15의 U 범위, L05의 거절 결과 재생.
- 완료 조건: 동일 본문 재생은 승인·취소·전이 효과를 반복하지 않는다. 다른 본문은 충돌이다. 완료 요청은 현재 상태가 REQUESTED가 아니라는 이유로 새 승인 검사를 받지 않는다. 취소 식별자는 완료 기록의 값을 유지한다.
- 경계: 키 범위·본문 정규화·저장 형식·보존 기간·실패 후 재시도는 B02에서 확정한다. 인증을 먼저 수행하는 실제 요청 경로는 B08이다. 토큰 응답은 일반 업무 결과와 별도로 B08에서 다룬다.

### A05. 신뢰된 금액·주체를 사용하는 내부 입력 경계

- 산출물: 저장된 주문 정보와 인증된 주체를 입력받는 내부 처리 경계 및 변조 입력 시나리오.
- 선행 작업: A02·A04.
- 연결 불변식: INV-P5-11·09.
- 연결 시나리오: L17의 U 범위.
- 완료 조건: 클라이언트가 제시한 금액으로 저장된 승인 금액을 덮어쓰지 않는다. 인증 실패·주체 불일치 입력에서는 신규 실행과 완료 결과 재생 모두 허용하지 않는다.
- 경계: 테스트에서는 인증 결과를 통제한다. 실제 인증·가맹점 조회·권한 데이터 공급·HTTP 노출은 B08이다. 이 작업만으로 보안 연동이 검증됐다고 기록하지 않는다.

### A06. 내부 규칙 통합과 모듈 경계 검사

- 산출물: A01~A05를 연결한 P5 내부 처리와 단위 회귀 테스트, 경계 검토 결과.
- 선행 작업: A01~A05.
- 연결 불변식: INV-P5-01~12 중 U 검증 범위, 특히 INV-P5-12.
- 연결 시나리오: L01~L10·L13~L17의 U 범위, L18. L11·L12 제외.
- 완료 조건: 앞선 작업의 단위 시나리오와 저장소 계층·모듈 검사가 통과한다. 타 모듈 내부 접근이나 직접 테이블 변경이 없다. 대역 사용 범위와 DB·연동 미검증 항목을 기록한다.
- 경계: 공개 포트의 의존 방향을 이 단계에서 확정하지 않는다. 전용 테스트 도구·새 라이브러리 도입은 별도 기술 선택이 필요하면 ADR로 다룬다.

## 3. 팀 합의 후 진행할 작업

모든 작업의 P5 구현 담당은 **P5 시은**이다. 아래 협업 담당은 답변 및 해당 모듈 구현 담당이며,
P5가 그 모듈의 Entity·Repository·업무 코드를 대신 소유한다는 뜻이 아니다.
선행 Q번호는 해당 작업 범위에 필요한 답변을 뜻한다. 모든 질문이 한꺼번에 해결될 때까지 기다릴 필요는 없다.

### B01. 저장 스키마와 P5 영속 모델

- 협업·선행 답변: P1 주환·DB 담당, 금액 관련 P6 민정·CakeShop 담당 / Q08·Q17. 주문·멱등 제약 관련 부분은 Q10·Q12도 필요.
- 선행 작업: A01·A03의 규칙 정리.
- 산출물: 합의된 ERD에 맞는 P5 Entity·Repository·DB 제약·스키마 변경.
- 연결 불변식: INV-P5-07·08·10·12, INV-TEAM-09.
- 연결 시나리오: E09의 DB 제약 범위, L10·L16의 D 범위, L18.
- 완료 조건: 타입·키·금액·시간·관계·제약이 정본과 일치한다. 타 모듈 FK 및 내부 참조가 없다. 실제 MariaDB에서 저장·조회·제약을 확인한다.
- 경계: Flyway 전환 시점도 확인한다. 확정 후 새 마이그레이션을 사용하고 번호는 병합 직전 정한다. 이번 계획에서 Flyway를 켜거나 기존 마이그레이션을 수정하지 않는다.

### B02. 세션 생성과 멱등 결과 저장

- 협업·선행 답변: P1·CakeShop·재시도 관련 P2/P3/P6 / Q08·Q10·Q11·Q12·Q15·Q17.
- 선행 작업: B01·A04·A05.
- 산출물: 주문별 세션 생성·중복 방지, 요청 식별과 완료 결과 저장·재생. 인증된 주체를 입력받는 서비스 범위로 먼저 구현.
- 연결 불변식: INV-P5-09·10·11, INV-TEAM-09.
- 연결 시나리오: L13~L15의 저장·재생 범위, E09. 승인·취소 결과를 통한 전체 검증은 B03에서도 수행.
- 완료 조건: 같은 가맹점·주문의 동시 세션 생성이 합의한 정책대로 제어된다. 같은 키의 다른 본문은 충돌하고, 재생 시 원장·이력이 늘지 않는다. 보존·복구 정책이 문서와 일치한다.
- 경계: 토큰 발급·재발급과 외부 인증 연결은 B08. 미합의 상태에서 성공 키 삭제 작업을 만들지 않는다.

### B03. P5 승인·취소 트랜잭션과 동시성

- 협업·선행 답변: DB 담당 및 관련 정책 담당 / Q08·Q10·Q16·Q17의 적용 정책.
- 선행 작업: B01·B02·A02·A03·A06.
- 산출물: P5 상태·이력·Mock 원장·한도·멱등 결과의 공동 저장, 카드 경합 제어, 장애 주입 DB 테스트.
- 연결 불변식: INV-P5-01~10.
- 연결 시나리오: L01~L16의 D 범위, 특히 L11·L12.
- 완료 조건: 실패 시 P5 변경 전체가 새 트랜잭션 조회에서 원복된다. 동시 70,000/60,000 승인으로 한도를 초과하지 않는다. 응답 유실·동시 같은 키 요청에서 업무 효과가 중복되지 않는다.
- 경계: FDS·취소 자격·직원 결정은 대역으로 통제할 수 있다. 실제 P2 기록, P3/P6 공동 커밋 완료는 각각 B04~B06으로 구분한다.

### B04. 실제 P2 FDS 연결

- 협업·선행 답변: P2 정후 / Q05·Q10·Q15.
- 선행 작업: A02·B03.
- 산출물: P2 공개 API 호출과 합의된 평가 식별자·입력·재시도 처리.
- 연결 불변식: INV-P5-01·02·03, INV-TEAM-04.
- 연결 시나리오: L01~L05 실제 연동, E04.
- 완료 조건: FDS 결과 후 P5가 실패해도 합의한 시도 기록이 남는다. 같은 논리 요청 재전송은 중복 집계하지 않는다. 타임아웃·P2 기록 실패 때도 승인 금지 및 합의된 복구 규칙을 지킨다.
- 경계: 시도 저장·점수 계산 구현은 P2 소유다. 별도 트랜잭션 방식은 팀 승인된 계약을 적용한다.

### B05. P3 KEEP/CANCEL 실행 계약

- 협업·선행 답변: P3 수민 / Q03·Q10·Q15; CANCEL 경로는 B06의 P6 합의도 필요.
- 선행 작업: A01·B03. KEEP 검증부터 진행 가능하며 전체 CANCEL 검증은 B06 이후.
- 산출물: P3가 사용하는 P5 공개 실행 API, 결정 식별자 재생·충돌 처리, 공동 커밋 연동.
- 연결 불변식: INV-P5-05·06·09·10, INV-TEAM-03.
- 연결 시나리오: L07·L14·L15, E03.
- 완료 조건: P3 저장 실패와 P5 실행 실패를 각각 주입해 양쪽 롤백을 확인한다. KEEP은 재승인하지 않고, 같은 결정은 반복 실행되지 않는다. 롤백 후 같은 결정 ID 재전달도 계약대로 작동한다.
- 경계: P3 결정 저장 구현은 P3 소유다. KEEP 부분 완료와 CANCEL 포함 전체 완료를 따로 기록한다.

### B06. P6 취소 포트와 공동 커밋

- 협업·선행 답변: P6 민정·팀 / Q01·Q04·Q06·Q13·Q15·Q17. **질문 6은 미결 유지.**
- 선행 작업: B03. P3 경유 취소의 전체 검증은 B05와 연결.
- 산출물: 합의된 P5 소유 포트, P6 구현과 연결되는 취소 자격 확인·취소 반영 흐름.
- 연결 불변식: INV-P5-06·08·09·12, INV-TEAM-01·02.
- 연결 시나리오: L08·L09·L12·L14, E01·E02.
- 완료 조건: 매입 전후·마감 경계에서 합의된 자격 판단을 적용한다. P5 또는 P6 실패 시 양쪽 원복, 성공 재시도 시 동일 취소 식별자와 중복 없는 반영을 확인한다. 모듈 의존·실행 방향도 승인된 규칙과 일치한다.
- 경계: 정산 단위·상태 의미·취소 저장 위치를 추측하지 않는다. HELD라는 이유로 P6 호출을 생략하지 않는다. P6 구현은 P6 담당이다.

### B07. 매입 후보 조회와 매입·취소 경합

- 협업·선행 답변: P6 민정 / Q01·Q06·Q13·Q15·Q19.
- 선행 작업: A01·B03·B06.
- 산출물: P5 APPROVED 후보 조회·상태 잠금 API, P6 배치와의 경합 검증.
- 연결 불변식: INV-P5-04·08·12, INV-TEAM-08.
- 연결 시나리오: L06, E08.
- 완료 조건: HELD는 매입되지 않는다. 오래된 승인 시각의 HELD가 KEEP 후 APPROVED가 되어도 다음 실행에서 누락되지 않는다. 취소 선행·매입 선행 양쪽 경합에서 중복 매입이나 잘못된 취소 반영이 없다.
- 경계: 실행별 재조회·기매입 제외·매입 저장은 P6와 공동 검증한다. P5는 P6 테이블을 직접 조회하지 않는다.

### B08. 인증·checkout 토큰·HTTP 입력 경계

- 협업·선행 답변: P1 주환·CakeShop 담당 / Q11·Q15, 주문 기한은 Q12, 키 정책은 Q10.
- 선행 작업: A05·B02. 승인까지 연결한 검증은 B03·B04 이후.
- 산출물: 실제 인증·권한·nonce 검증, 토큰 발급·검증·재발급, 세션·승인 요청 HTTP 연결.
- 연결 불변식: INV-P5-09·11·12, INV-TEAM-07.
- 연결 시나리오: L17, L13·L15의 인증 선행 검증, E07.
- 완료 조건: 실제 무권한·주체 불일치·금액 변조 요청을 차단한다. 인증된 서버만 재발급하고 이전 토큰은 무효화된다. 주문 기한은 늘지 않으며 응답 유실·동시 재발급·승인 경합이 합의된 계약대로 처리된다.
- 경계: 토큰 없는 완료 응답 재생을 일반적인 “응답 전체 동일” 규칙으로 덮어쓰지 않는다.

### B09. 미승인 만료 처리

- 협업·선행 답변: P1·CakeShop 담당·HELD 정책 관련 P3/P6 / Q12·Q02.
- 선행 작업: A01·B01·B02·B03. HTTP 응답 연결은 B08.
- 산출물: 합의된 만료 상태·기한 판정·실행 방식·활성 주문 해제 처리.
- 연결 불변식: INV-P5-10, INV-TEAM-06·09.
- 연결 시나리오: E06, E09의 만료 후 재주문 범위.
- 완료 조건: 기한 직전·정각·직후와 승인/만료 경합에서 최종 상태가 일관된다. 미승인 만료가 카드 취소 원장을 만들지 않는다. HELD를 REQUESTED 만료 경로로 처리하지 않는다.
- 경계: HELD 자동 취소는 별도 정책과 작업이 필요하다. Q02 미결을 임의의 30분·24시간 정책으로 채우지 않는다.

### B10. 케이스·이벤트 연결

- 협업·선행 답변: P2 정후·P3 수민 / Q07·Q10. **질문 8은 미결 유지.**
- 선행 작업: B03·B04. 합의된 생성 조건이 P3 결정에 의존하면 B05도 선행.
- 산출물: 합의된 책임 범위 내 P5 이벤트 또는 호출 연결, 재전달·중복 방지 연동.
- 연결 불변식: INV-P5-12, INV-TEAM-05.
- 연결 시나리오: E05.
- 완료 조건: 합의된 생성 조건별로 케이스 수와 연결 대상이 맞고, 실패·재전달 시 누락·중복·롤백된 결제의 유령 케이스 여부를 검증한다.
- 경계: 생성 주체·이벤트 종류·전달 저장 방식을 현재 확정하지 않는다. P5 역할이 없다고 합의되면 구현 작업 대신 계약 확인·연동 검증으로 범위를 변경한다.

### B11. 카드 정책과 외부 결과 조회·표시 계약

- 협업·선행 답변: Q16은 P3 수민·P5, 결과 계약은 P1·CakeShop·P3·필요 시 P6 / Q09·Q15·Q16·Q17.
- 선행 작업: B03·B08. 최종 상태 전체 검증은 B05·B06·B09도 필요.
- 산출물: 합의된 Mock 카드 상태별 승인·취소 규칙, 결제 결과 조회와 외부 DTO·오류 매핑.
- 연결 불변식: INV-P5-03·06·11·12, INV-TEAM-10.
- 연결 시나리오: L05·L08·L09·L17, E10.
- 완료 조건: 카드 상태별 결과와 실제 저장값이 일치한다. HELD의 승인 사실·매입 보류가 합의된 조회 응답에 반영된다. 타 주체 조회를 차단하고 합의된 오류 형식으로 응답한다.
- 경계: CakeShop 화면은 해당 저장소 담당이 구현한다. 웹훅 여부는 합의에 따라 범위를 정하며, 조회만으로 웹훅까지 완료했다고 기록하지 않는다.

## 4. 권장 진행 순서

1. **내부 규칙:** A01 → A02·A03 → A04·A05 → A06. A04의 재생 판정 자체는 A01 이후 먼저 준비할 수 있다.
2. **저장 기반:** 필요한 스키마·금액·키·주문 정책 합의 후 B01 → B02 → B03. 여기서 처음 실제 DB 원자성과 동시성을 검증한다.
3. **연동:** 답변이 온 영역부터 B04(P2), B05의 KEEP(P3), B06(P6), B08(인증)을 진행한다. 각 작업에 적힌 선행 조건을 따르며 전체 답변을 기다릴 필요는 없다.
4. **경합·완성:** B06 이후 B05의 CANCEL·B07을 연결한다. 만료 B09·이벤트 B10·결과 계약 B11은 각각의 답변과 선행 작업이 준비되는 대로 진행한다.
5. **출시 범위 검증:** 아래 공통 완료 기준으로 실제 포함할 기능의 U/D/X 시나리오를 확인한다. 미합의 기능을 대역으로 남긴 상태를 전체 결제 모듈 완료로 표시하지 않는다.

질문 6의 답변은 B06·B07 및 B05 CANCEL의 실제 연동을 막는다.
질문 8의 답변은 B10을 막는다. 둘 다 A 작업을 막지는 않는다.
Q08은 DB 작업의 선행 조건이므로, 독립 검증 항목이라고 해서 Entity·마이그레이션을 먼저 확정하지 않는다.

## 5. 공통 완료 조건과 추적 방식

각 작업을 Issue로 옮길 때 다음 내용을 유지한다.

| 필드 | 기록할 내용 |
|---|---|
| 작업 ID·담당 | A/B 번호, P5 담당, 협업 담당 |
| 선행 조건 | 선행 작업, Q번호, 합의자·날짜·정본/ADR 링크 |
| 범위 | 구현 산출물과 이번 작업에 포함하지 않은 연동 |
| 검증 연결 | 불변식 ID, L/E 시나리오 ID, U/D/X 중 실제 실행 범위 |
| 완료 증거 | 코드 커밋, 실행 명령·환경·결과, 테스트 보고서 |
| 미검증 | 대역으로 대체한 모듈, 미실행 시나리오, 남은 정책 충돌 |

업무 구현 후 변경 영역에 맞는 테스트와 `backend`의 `./gradlew check`를 실행한다.
DB·연동 테스트가 해당 명령에 포함되지 않으면 별도 실행 명령과 결과를 남긴다.
현재 커밋에서 실행한 증거만 사용하고, 상태를 결정됨·구현됨·검증됨으로 구분한다.
API·DB·화면·테스트 영향이 있는 설계 변경은 관련 정본과 ADR에 반영한다.

이 계획은 L01~L18과 E01~E10을 작업에 연결하지만, 중복 참조된 시나리오의 통과를 서로 다른 검증 수준으로 확대 해석하지 않는다.
예를 들어 A02의 L04 단위 테스트는 B03의 롤백이나 B04의 FDS 기록 보존을 대신하지 않는다.

현재 기록: 작업 분해 문서만 작성했다. Issue 생성·구현·테스트 코드 작성·DB 변경·Gradle 실행·commit/push/PR은 수행하지 않았다.
