# 02. 왜 Spring Modulith를 채택했나

[← Modulith 문서 목차](README.md)

## 1. 우리 프로젝트의 조건

| 조건 | 설계에 주는 영향 |
| --- | --- |
| 6명이 **동시에** 각자 모듈 개발 | 서로의 코드를 건드리지 않게 경계가 필요 |
| 약 **4주** (1차 MVP) | 서버 여러 대를 띄우고 운영할 시간이 없음 |
| 금융 업무 (결제 · 매입 · 취소) | 트랜잭션 · 데이터 정합성이 중요 |
| 담당자별 데이터 소유권이 정해져 있음 (Notion 설계 3.2) | "남의 테이블은 직접 고치지 않는다"를 지킬 장치가 필요 |

## 2. 다른 방식을 고르지 않은 이유

### MSA (서버 여러 개)

```text
payment 서버 ──HTTP──▶ fds 서버
   │  네트워크 장애·타임아웃 처리, 서버마다 DB·배포·로그, 분산 트랜잭션
   ▼
4주 안에 업무 기능보다 인프라 작업이 더 커짐
```

- 서버 간 호출마다 실패 · 재시도 · 타임아웃을 설계해야 합니다
- 결제 저장과 FDS 평가 저장을 한 트랜잭션으로 묶을 수 없습니다
- 우리 팀 규모(6명)에서 서버를 나눠 얻는 이점(독립 배포 · 독립 확장)이 크지 않습니다

### 경계 없는 모놀리스

```text
1주차  investigation이 payment.entity.Payment를 직접 수정 (빠르니까)
2주차  P5가 Payment 필드 이름 변경 → investigation 컴파일 에러
3주차  누가 어떤 테이블을 바꾸는지 아무도 모름 → "데이터 소유권" 규칙이 말로만 남음
```

- 경계가 문서에만 있고 코드로 검사되지 않아, 마감이 급하면 쉽게 무너집니다

## 3. 모듈러 모놀리스로 얻는 것

| 얻는 것 | 어떻게 |
| --- | --- |
| 6명 병렬 개발 | 각자 자기 모듈 내부는 마음대로 바꾸고, 공개 `api/`만 약속으로 지킨다 |
| 경계가 무너지지 않음 | `ModularityTests`가 다른 모듈 내부 접근 · 순환을 CI에서 막는다 |
| 운영이 단순 | 앱 하나, DB 하나, 배포 한 번 |
| 이벤트 유실 대비 | 모듈 간 이벤트를 DB(`EVENT_PUBLICATION`)에 기록해 실패 시 다시 보낼 수 있다 |
| 나중에 분리 가능 | 경계가 지켜져 있으면 특정 모듈(예: `settlement`)만 별도 서버로 떼어내기 쉽다 |

## 4. 대가 (감수하는 것)

- 의존 방향을 미리 정하고 지켜야 합니다. 두 모듈이 서로를 부르고 싶어지면 한쪽은 이벤트로 바꿔야 합니다 ([04](04-dependency-and-events.md))
- 이벤트를 쓰는 곳은 비동기라서, "같은 이벤트가 두 번 와도 한 번만 반영"(멱등)을 받는 쪽이 책임져야 합니다
- 모든 모듈이 같은 DB를 쓰므로, 남의 테이블을 SQL로 직접 조회하는 것을 **규칙으로** 막아야 합니다 (Modulith는 Java 코드만 검사)
