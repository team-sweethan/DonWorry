# #127 로그인 시도 제한 설계

관련: [상위 #68](https://github.com/team-sweethan/DonWorry/issues/68), [#127](https://github.com/team-sweethan/DonWorry/issues/127), #125·#128·#129·#130.

## 확정한 정책

2026-10-25 사용자가 아래 정책과 컬럼 이름을 승인했다. 구현·검증 완료를 뜻하지 않는다.

- 같은 계정의 비밀번호 오류 5회 연속이면 다섯 번째 실패부터 15분간 새 로그인을 막는다.
- 잠금 중에는 BCrypt 비교를 수행하되 실패 횟수·종료 시각은 바꾸지 않는다. 올바른 비밀번호도 거절한다.
- 종료 시각과 같거나 늦으면 다시 시도할 수 있다. 만료 후 첫 오답은 새로운 1회이며, 성공 시 횟수 0·종료 시각 NULL이다.
- 계정 DISABLED·가맹점 INACTIVE와 별도로 관리한다. 잠금 만료가 계정·가맹점 정지를 해제하지 않는다.
- 본인 비밀번호 변경·관리자 초기화·계정/가맹점 재활성화로 로그인 잠금을 해제하지 않는다.
- 실패·잠금은 이미 로그인한 세션을 종료하지 않는다. 성공한 새 로그인에는 기존 #125 단일 세션 정책을 적용한다.
- 없는 계정·비밀번호 오류·계정 정지·가맹점 정지·잠금은 같은 401 AUTH_004와 기존 문구를 사용한다. 횟수·잠금 여부·해제 시각은 응답하지 않는다.
- 입력 검증 400·계정/가맹점 정지 자체·DB 장애는 비밀번호 오류 횟수로 세지 않는다. 비밀번호를 실제로 틀렸으면 ACTIVE 계정에 대해서만 센다.
- 로그인 과정의 조회·횟수 저장·커밋 오류는 500 AUTH_005다. 실패를 저장하지 못했는데 정상적인 인증 실패로 숨기지 않는다.

## 스키마 계약

P1 소유 `platform_users`만 변경한다. 기존 migration은 수정하지 않고 `./gradlew newMigration -Pdesc=add_login_attempt_lock`으로 생성한 새 파일에 하나의 ALTER TABLE을 쓴다.

| 컬럼 | 타입 | 기본값 | 의미 |
| --- | --- | --- | --- |
| `login_failure_count` | INT NOT NULL | 0 | 연속 비밀번호 오류 횟수. 앱은 0~5만 저장 |
| `login_locked_until` | DATETIME(6) NULL | NULL | UTC 잠금 종료 시각 |

기존 계정은 0·NULL로 보존한다. FK·인덱스·다른 담당 테이블 변경은 없다. 시간 비교에는 주입 가능한 UTC Clock을 사용하고 DATETIME(6) 정밀도에 맞춘다. 잠금 해제를 위한 예약 작업은 두지 않고 다음 로그인 때 만료를 판단한다.

Notion P1 ERD 선행 반영이 원칙이다(AGENTS.md 4절). 현재 Notion 연결 도구가 없고 Chrome 접근이 자동 승인 검토에서 거부되어 최신 ERD를 확인·수정하지 못했다. 사용자는 2026-10-25 이번 작업에 한해 저장소 ERD·ADR을 기준으로 구현하고 Notion은 후속 반영하도록 승인했다. Notion 동기화는 미수행이다.

## 인증·저장 순서

1. 기존 아이디 정규화·DB 실제 loginId 확인 후 가맹점 잠금 → 계정 잠금 순서로 진입한다. DB collation이 같은 별칭도 같은 계정 잠금을 사용한다. 최초 조회 뒤 새 계정이 생겨 확보한 잠금 키와 실제 loginId가 달라지면 횟수 초기화·세션 등록을 거절한다. 다음 요청은 실제 계정 잠금을 얻는다.
2. BCrypt 비교를 먼저 수행한다. 비밀번호가 맞아도 잠금·계정 정지면 거절하며, 사장님은 기존 가맹점 ACTIVE 검사를 통과해야 한다. 인증 결과에 사용한 잠금 상태는 응답·세션에 저장하지 않는다.
3. 비밀번호 오류는 독립 트랜잭션의 조건부 UPDATE 한 번으로 저장한다. 아직 잠금 중인 행은 갱신하지 않는다. 만료된 행은 1회로 시작하고, 나머지는 기존 횟수 +1과 다섯 번째의 종료 시각을 함께 갱신한다.
4. 실패 횟수 저장 트랜잭션의 커밋이 끝난 뒤 401 예외를 던진다. 로그인 실패 때문에 저장이 롤백되지 않는다.
5. 계정·잠금·가맹점·권한 검사가 끝난 성공 경로에서는 DB의 횟수·종료 시각 초기화를 커밋한 다음 기존 세션 등록 전략을 실행한다. 초기화 오류 시 새 인증을 등록하지 않는다.
6. 위 DB 커밋과 세션 등록까지 기존 계정 잠금을 유지한다. BCrypt·DB 작업은 전역 세션 모니터 안에 넣지 않는다. 다중 서버·세션 저장소 변경은 범위 밖이다.

조건부 UPDATE는 JPQL로 Entity의 `LOCAL_DATE_TIME` 매핑을 사용한다. native query에 LocalDateTime을 직접 바인딩하면 JVM 시간대와 Hibernate UTC 설정에 따라 DATETIME 값이 이동할 수 있다. 종료 시각 식을 횟수 식보다 먼저 배치해 MariaDB의 순차 SET 평가에서도 두 식이 변경 전 횟수를 사용하게 한다. 실제 MariaDB로 UTC 마이크로초 저장·다섯 번째 전환·만료 후 재시작을 검증한다. 비밀번호 변경·관리자 갱신이 오래된 Entity로 새 횟수를 덮지 않도록 기존 계정 잠금 규약을 유지한다.

## 화면·기존 계약

`LoginPage`에 항상 보이는 “비밀번호를 5번 연속 틀리면 15분 동안 로그인할 수 없습니다.” 안내만 추가한다. 기존 실패 문구·공통 API 클라이언트·CSRF 준비·로그인/로그아웃 세션 정책은 유지한다. 남은 횟수·카운트다운·관리자 해제 UI·새 API는 만들지 않는다.

## 검증 계획

- 실제 MariaDB·HTTP로 네 번 실패 후 성공 시 초기화, 다섯 번째 잠금·정답 거절·기존 세션 보존, 잠금 중 재시도로 종료 시각 유지.
- 주입한 시각으로 만료 직전·정확히 만료·만료 이후를 검사한다. 실제 15분 대기는 하지 않는다.
- 만료 후 첫 오답 1회, 다시 다섯 번 실패 시 새 15분, 다른 계정·없는 계정·정규화·악센트 별칭 분리/공유.
- 잠김·DISABLED·없는 계정·일반 오류의 HTTP 상태·code·detail 동일, BCrypt 호출과 세션/권한 조회 미수행.
- 실패 UPDATE/성공 초기화/커밋 오류는 AUTH_005, 실패 응답 이후 DB에 횟수가 남는지 확인.
- 동시 오답의 누락 없는 증가·다섯 번째 잠금과 로그인↔비밀번호 변경/관리자 정지/가맹점 정지 회귀 검사.
- `cd backend && ./gradlew spotlessApply check mariaDbTest`.
- `cd frontend && npm run lint && npm run format:check && npm run test && npm run build`.
- Markdown 상대 링크·`git diff --check`. 실제 브라우저 검증이 차단되면 미검증으로 별도 기록한다.
