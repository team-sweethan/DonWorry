# #354 후속 — 사장님 홈과 로그인 첫 이동

[Issue #354](https://github.com/team-sweethan/DonWorry/issues/354) · [연동 안내](354-merchant-integration.md) · [ADR-0052](../decisions/0052-merchant-key-management.md)

## 합의와 범위

2026-10-31 사용자가 연동 상태 카드와 권한별 메뉴 바로가기 배치를 승인하고 실제 구현의 UI/UX 개선을 요청했다. 배포 환경은 없으며 모두 로컬이다. 기존 키 이전도 로컬 CAKESHOP을 대상으로 한다.

`dev 93f865b`에서 `feature/354-owner-home`을 만들었다. 새 API·DB·권한 코드는 추가하지 않고 기존 자기 가맹점 조회 API를 재사용한다. P5·P6 업무 코드와 외부 HMAC 계약은 변경하지 않는다.

## 화면과 이동

- `/owner`는 업무 권한 없이 들어가는 실제 홈이다. 사이드바 첫 메뉴와 헤더 로고도 홈으로 연결한다. 홈 메뉴는 하위 업무 화면에서 함께 활성화되지 않는다.
- 상단은 연동 상태, 다음 행동, 가맹점 코드, 연결 확인 시각(한국 시간) 순서다. 키 없음이면 발급, 연동 전이면 연동 방법, 완료면 키 관리로 안내한다. 버튼은 `/owner/integration`으로 연결하며 홈에서 키 원문을 요청하지 않는다.
- 연동 전의 단계 표시는 다음 행동 안내다. 키 발급 이후 쇼핑몰 서버 설정 여부는 추측하지 않는다. 연동 완료를 신규 결제의 실제 승인·매입 성공으로 표현하지 않는다.
- 업무 바로가기는 사이드바와 같은 권한 필터 결과를 쓴다. 업무 권한이 없으면 이유와 문의 안내를 보여주며 홈·키 관리는 계속 사용할 수 있다.
- 처음 진입·새로고침·탭 복귀 때 상태를 조회한다. 재조회 중에는 마지막 상태를 유지해 깜빡이지 않게 하고, 실패하면 낡은 상태 대신 오류와 재시도를 보여준다. 오류일 때는 헤더 새로고침을 숨기고 카드의 다시 시도만 둔다. 정지 가맹점은 통신 장애와 구분한다. 계정 변경·화면 종료·이전 요청의 늦은 응답을 버린다.
- 모바일에서는 헤더를 줄바꿈하고 사이드바를 가로 메뉴로 바꾸며 카드·주요 버튼은 한 열로 배치한다. 로딩 자리, 상태별 색과 문구, 키보드 포커스를 제공한다.

| 진입 조건 | 이동 |
| --- | --- |
| 강제 비밀번호 변경 필요 | `/account/password`가 우선 |
| 사장님 일반 로그인 또는 인증된 `/` 진입 | 연동 상태와 무관하게 `/owner` 홈. 미연동이면 홈 첫 카드가 키 발급·연동 방법으로 안내 |
| 세션 만료 뒤 같은 계정 재로그인, 또는 로그인 전 연 주소 | 기존 `loginDestination`의 경로 안전성·현재 권한 검사를 통과한 복귀 경로, 실패하면 `/owner` |
| 연동 상태 조회 실패·가맹점 정지 | 로그인 이동을 막지 않는다. 홈 카드가 오류(정지는 별도 문구)와 재시도를 보여주고 권한 있는 업무 메뉴는 그대로 쓴다 |
| 관리자·보안 직원 | 기존 이동 유지 |

`/owner` 직접 방문은 상태에 관계없이 홈을 보여준다. 연동 상태로 업무 메뉴 접근을 차단하지 않는다. 실제 결제 인가는 기존 서버 HMAC 게이트가 담당한다. 버린 대안: `/me`에 연동 상태를 넣으면 기존 인증 계약이 늘고 상태가 낡을 수 있어 기존 조회 API를 사용한다. 로그인·공개 루트에서 연동 상태를 먼저 조회해 미연동이면 `/owner/integration`으로 보내는 방식(PR #378 첫 커밋)은 버렸다. 조회 API가 정지 가맹점에 `403 INTEGRATION_005`를 주므로 정지 가맹점 사장님은 로그인 후 어떤 업무 화면에도 들어갈 수 없었고, 통신 장애에도 로그인이 막혔다. 또 미연동 사장님은 로그인마다 키 화면으로 끌려가고 세션 만료 복귀도 끊겼으며, 홈 첫 카드와 같은 안내를 한 번 더 하는 셈이었다.

### 실제 로컬 HTTP·SMTP·Python 스크립트

Spring 8081, MariaDB 3307, Mailpit SMTP 1025/API 8025, Vite 15354에서 수행했다. Spring은 `payment.http.enabled=true`, `donworry.scheduling.enabled=false`, 신청 링크 origin `http://localhost:15354`로 실행했다. 이 검증은 브라우저 클릭 검증과 구분한다. 메일·FDS는 실제 로컬 구현을 사용했다.

- 신규 신청(201) → 실제 Mailpit 확인 메일 수신 → 이메일 확인(200) → 관리자 승인(200) → 실제 승인 메일 수신 → 첫 비밀번호 설정(204) → 업무 권한 없는 사장님 로그인(200).
- 발급 전 `NO_KEY`, 발급 후 `PENDING_CONNECTION` 확인. 실제 `merchant_connect.py --payment-only`는 403 `MERCHANT_AUTH_006`, `--payment`는 연결 확인 204·결제 202 `PENDING`. 이후 DB에서 결제 ID 3의 `CAPTURED`를 확인했다. 접수와 최종 결과를 구분했다.
- 상태 `CONNECTED`와 연결 확인 시각, 연결 후 키 다시 보기 409를 확인했다. 관리자 상태 응답에는 발급한 키 원문이 없었다.
- 관리자 폐기 204 → `NO_KEY` → 옛 키로 연결 확인 401 `MERCHANT_AUTH_001`을 확인했다. 키·비밀번호·토큰은 검증 출력에 남기지 않았다.
- 테스트 신청 ID 5, 가맹점 `HOME3547CCB446368`, 로그인 ID `home3547ccb446368`은 로컬에 보존했다. 첫 스크립트의 신청 목록 검색 오류 후 같은 신청을 이어서 검증했으며, 중복 신청은 기존 정책대로 409였다. 금융·조사 기록은 삭제하지 않았다.

## 미검증과 이슈 종료 전 남은 일

1. **브라우저**: Chrome 제어가 승인되지 않아 실제 로그인 첫 이동·홈/키/관리자 화면 클릭·모바일·키보드·시각 배치를 확인하지 못했다. 자동 테스트와 HTTP 결과로 대체 완료 처리하지 않는다.
2. **기존 로컬 CAKESHOP 키 이전**: 로컬 DB에는 `secret_reference`만 있고 integration 행은 없다. 현재 실행 셸에 예전 키가 없어 이전하지 않았다. 사용자에게 기존 키 설정 위치를 확인 중이다. 키를 새로 만들어 기존 값인 것처럼 처리하지 않는다. [이전 절차](../decisions/0052-merchant-key-management.md#기존-키-이전과-배포)에 따라 같은 값으로 이전 후 `CONNECTED`·`MIGRATE` 이력·기존 서명 인증을 확인해야 한다.
3. **누출 확인**: 관리자 HTTP 응답·테스트 이력·검증 출력의 원문 미포함은 검사했다. 실제 브라우저 관리자 화면·실행 로그/메일 전체에서 발급 키 원문이 없는지 종합 점검은 미수행이다.
4. 실제 CakeShop 발신 코드(#242), 운영 배포·HTTPS·운영 키 백업 복원은 이번 범위 밖이다. 배포 환경이 없다는 확인은 기존 로컬 키 이전 검증 완료를 뜻하지 않는다.

PR에는 `Refs #354`를 쓰고 위 미검증을 해소하기 전 이슈를 자동으로 닫지 않는다. 사용자에게 추가 업무 정책 결정을 받을 항목은 없으며, 기존 키의 보관 위치와 브라우저 실행 결과가 필요하다.
